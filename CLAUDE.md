# CLAUDE.md — постоянный контекст проекта repracer

## Что строим

Мультитенантный SaaS, который для продавца:

1. **Синхронизирует остатки** из внешнего источника между каналами продаж. Мы **не владелец остатка**:
   общий пул + буфер на канал.
2. **Автоматически меняет цены** по стратегиям, не опускаясь ниже обязательного абсолютного `min_price`.
3. **Ведёт историю наших цен по каждому каналу** для Omnibus и §11 PAngV.

## Для кого

Профессиональные продавцы (SMB и mid-market) на нескольких маркетплейсах. Пользователь может состоять в
нескольких тенантах, например агентство.

Вне скоупа: создание листингов, выполнение заказов, бухгалтерия, хранение PII.

## Жёсткие ограничения

### Amazon
- `getCompetitiveSummary`: **0.033 req/sec, burst 1** → поллинг конкурентов невозможен, только нотификации.
- **Запись остатка меняет остаток SKU во всех маркетплейсах EU сразу** [Р-1], даже если мы работаем только с DE.
- DPP: не-PII из SP-API — **≤ 18 месяцев**; логи — **≥ 12 месяцев**; PII не храним [Р-4].
- AUP: не агрегировать данные разных продавцов; строгая изоляция тенантов; модели на данных SP-API не обучаем [Р-10].
- **Не пишем никогда** [Р-111, Р-114]: `automated_pricing_merchandising_rule_plan` (включает репрайсер Amazon), `minimum_seller_allowed_price` и `maximum_seller_allowed_price` (второй набор границ: цена вне них — отказ Amazon; наши границы — единственные). Поле порта отклоняет БД (0077), тело запроса — контрактный стенд.
- **Чужой репрайсер** [Р-115, Р-120]: при обнаружении оффера (`searchListingsItems` с атрибутами), перед записью и при обратном чтении; привязка к правилу — единица BLOCKED, стратегию не назначит база (0082). **База цены** [Р-116, Р-118]: цена покупателя ≠ отправленной ровно на ставку НДС — недоверие каналу, все цены витрины, снятие только человеком со вторым фактором (0082).
- **Уведомления** `ANY_OFFER_CHANGED` и `PRICING_HEALTH` — только очередь SQS (стандартная: без порядка, с повторами, без подписи); приёмник `packages/amazon-notifications` — дедупликация по `NotificationId`, порядок по `EventTime`, потеря уведомления обнаруживается только сверкой по кругу [Р-121] (риск 21). Автоматического снятия остановки выборкой нет [Р-119].
- `patchListingsItem` — 5 rps на пару «продавец × приложение» и 500 rps на приложение, срабатывает первый порог: ограничитель на двух уровнях (AMZ_C01). Запись асинхронна: ACCEPTED ≠ применено, подтверждение — обратное чтение. Неподтверждённое — AMZ_C01…C10 (channel-capabilities §11).

### eBay
- **Адаптер заблокирован до снимка спецификации** [Р-112]: документация отвечает 403, снимок требует ключей разработчика (E-01).
- Низкие дефолтные лимиты до Application Growth Check; часть лимитов — на приложение, общая для всех тенантов.
- **Миграция листинга необратима** (Revise/Relist/Verify перестают работать; потеря Best Offer, требований к
  покупателям, благотворительности, шаблона). Аукционы не мигрируются. Только после предполётной проверки и
  согласия `OWNER` — [docs/onboarding-ebay-migration.md](docs/onboarding-ebay-migration.md).
- **250 правок листинга в календарный день** — бюджет на листинг, резерв под остаток.

### Kaufland
- **`minimum_price` не пишем никогда** — запись включает Smart Pricing Kaufland [Р-12]. Исключение — явный режим тенанта Smart Pricing на единице записи: наш движок для неё выключен, пишется только `minimum_price` не ниже нашего `min_price`.
- **Smart Pricing до ответа поддержки не включается ни у кого [Р-41]**; `minimum_price` > 0 у unit — CRITICAL-алерт.
- Единица записи цены — аккаунт + витрина + unit; остатка — аккаунт + `id_offer`, общий для витрин [Р-35]. Конкуренты — `buy_box_changed` + `GET /buybox`, `competitors-comparer` — сверка [Р-36].
- Лимит — 111 запросов в секунду на продавца на все эндпоинты; `units/bulk` — до 150 unit одной витрины.
- `buy_box_changed` — ранний доступ [Р-45]; до выдачи конкуренты — опрос `/buybox` по ярусам волатильности [Р-47]; уведомления с данными и без [Р-46]; потерянная подписка — восстановление и догон опросом [Р-48].
- Вебхук: один адрес на аккаунт с токеном в пути; подпись проверяется всегда [Р-40]. Всё неподтверждённое документацией — консервативное правило с кодом и вопросом K-nn (channel-capabilities §7–8).

### Otto Market
- ~10 req/sec; OAuth2 client credentials, токен 60 минут → централизованное обновление.

### ЕС
- История цен по каждому каналу/маркетплейсу (Omnibus / §11 PAngV).
- Цены витрин брутто, НДС внутри цены — режим `VAT_INCLUDED` [Р-58].

### США
- Цены витрин нетто, sales tax добавляется при покупке — режим `SALES_TAX_EXCLUDED` [Р-58]; валюта USD [Р-57].
- Граница суток витрин США не задана: amazon.com и EBAY_US — (проверить) по отдельности; до подтверждения записи с бюджетом правок не создаются, дни не закрываются, сырьё цен не удаляется [Р-65]; себестоимость в EUR переводится по курсу ЕЦБ [Р-61]; данные тенанта — в базе региона клиента, не витрины [Р-60].

## Архитектурные инварианты (кратко; полностью — [docs/domain-model.md §4](docs/domain-model.md))

1. **Граница тенанта.** Один запрос — один тенант, выбранный через `Membership`. `tenant_id` — из контекста сессии.
2. **Обе границы вне движка стратегий** [Р-43, Р-44]: Price Gate, БД при вставке решения, БД при создании записи и перед КАЖДОЙ отправкой — пол (min_price и пол маржи) вычисляется заново по текущим себестоимости, комиссии, курсу и НДС [Р-83]; выход за границу — отказ, не округление. **Входы проверяются до движка** [Р-42]: испорченный снимок — REJECT, массовый сдвиг — остановка витрины до снятия человеком.
3. **Единица записи — `WriteScope` на поле**, а не оффер ([ADR-0002](docs/adr/0002-write-scope-per-field.md)).
   Версии, идемпотентность, схлопывание, упорядочивание, наблюдение и история цен — по `write_scope_id`.
4. **Наши цены:** сырьё `price_history` — 90 дней в PostgreSQL, затем архив; **суточная свёртка `price_daily` — вечно** [Р-21]. Прочитанное из каналов — ClickHouse, ≤ 18 мес.
5. **«Отправили» ≠ «видим»:** `ObservedChannelState` отдельно; реакция — только через `DivergencePolicy`.
   Уменьшение опубликованного остатка никогда не блокируется.
6. **Fail-closed.** Неподтверждённые лимиты каналов → консервативная политика Dispatcher.
7. **Деньги** — целые minor units + валюта + база; валюта, база и налоговый режим — атрибуты единицы записи, сверяются со справочником витрины; EUR и USD наравне, конвертации нет [Р-57, Р-58].
8. **Изоляция в БД** — общая схема, `tenant_id` везде, RLS `ENABLE`+`FORCE`, составные FK `(tenant_id, …)`, без `BYPASSRLS` ([ADR-0003](docs/adr/0003-tenant-isolation.md)).
9. **Три слоя хранения** ([ADR-0004](docs/adr/0004-storage-tiering.md), [docs/data-retention.md](docs/data-retention.md)): данные каналов ≤ 18 мес в любом слое и не попадают в архив; данные тенанта удаляются из PostgreSQL по времени только после подтверждённого экспорта.
10. **Решение о цене читает только PostgreSQL** [Р-22]: всё нужное ему — горячие проекции (`competitor_state`, `observed_price_daily`, `observed_channel_state`).
11. **Шина:** ключ `write_scope_id`, retry-топиков для `scope.*` нет, ошибка блокирует единицу записи ([ADR-0005](docs/adr/0005-message-broker.md)).
12. **Запись не теряется** [Р-64]: одна запись в полёте на единицу; ждущую запись отправляет диспетчер, событие о ней ставится в той же транзакции; завершение без отправки — только с причиной в БД ([ADR-0009](docs/adr/0009-write-dispatcher-and-broker.md)).
13. **Три остановки** [Р-69, Р-70, Р-118]: остановка человеком (`price_stop`) — все цены, тенант — объект без аккаунта; системная (`pricing_halt`) — только цены из данных конкурентов, снятие выборкой там, где канал её даёт [Р-52, Р-119]; недоверие каналу (`channel_distrust`) — все цены и порог цены канала, ставит система, снимает только человек со вторым фактором; права — роли в БД.
14. **Объяснение без данных канала** [Р-68, Р-72, Р-74, Р-75]: слепок — у CHANGED и REJECTED_BY_GATE (у NO_OP — код причины); ключи параметров класса `CHANNEL` в нём отклоняет БД; суммы — с валютой [Р-71]; повторяющиеся части — ссылками на неизменяемый справочник и версию стратегии; столбцы строки в слепке не повторяются [Р-80]; архив ядра несёт справочники и объясняет себя без базы [Р-79]; производные от цены конкурента, в том числе подрез стратегии, в вечное ядро не попадают, проверка ключей слепка — fail-closed [Р-85, Р-91].
15. **Вход не наш, аудит наш** [Р-78, Р-76]: паролей и сессий в системе нет — пользователь по токену поставщика и `(issuer, subject)`, роль — из `Membership` при каждом запросе; автор остановки и снятия — пользователь сессии (сверяет БД); остановка цен без события `audit_event` не записывается; привязка identity — только приёмом приглашения, снятие остановки тенанта, ручное снятие системной остановки и смена роли — со вторым фактором [Р-88]; роли подключения разделены: путь решения не пишет аудит, членства, тенантов и остановки человеком, пользователь сессии и второй фактор принимаются только у административного сервиса, который база заявить за себя не мешает [Р-90, ADR-0016].
16. **Тест не пропускается, не выпадает из сборки и проверяет причину** [Р-84, Р-89, Р-94, Р-95]: тест без базы или брокера падает; сборка с пропущенным тестом или с файлом теста вне скрипта сборки — красная (`scripts/test-all.mjs`, `scripts/check-test-inclusion.mjs`, CI).

## Правила работы в репозитории

- Существенное решение → ADR в `docs/adr/NNNN-kebab-case.md`; решение владельца продукта → `docs/decisions.md`.
- Новая таблица → миграция в `migrations/`: `tenant_id`, `security.register_table(...)`, строка в `maintenance.retention_policy`, `security.grant_retention(...)`; последняя проверка схемы (сейчас `0107`) должна проходить; правило проверки — поведение, не имена [Р-93], тест защиты проверяет причину отказа [Р-94], новая защита — строка в каталоге мутационной проверки при создании, иначе красная сборка [Р-95, Р-108]; тесты — `scripts/db/prepare.sh` и `node scripts/test-all.mjs`, пропуск теста и файл теста вне скрипта сборки — красная сборка [Р-84, Р-89]. Правила — [migrations/README.md](migrations/README.md).
- Индекс — только под конкретный запрос, с комментарием над индексом.
- Таблица ClickHouse: `tenant_id` первым в ключе сортировки, TTL ≤ 18 мес, политика строк `tenant_isolation`; `099_verify.sql` должен возвращать 0 строк.
- Никаких запросов к ClickHouse или архиву из пути решения о цене; никаких выгрузок, объединяющих тенантов.
- Адаптер канала реализует `ChannelAdapter` ([ADR-0006](docs/adr/0006-channel-port.md)): описывает канал данными, классифицирует ошибки, проверяет тенанта; не хранит версии и не решает о повторах.
- Факты об API канала — только из снимка спецификации в `vendor/` и страниц документации со ссылкой; неясное — вопрос в поддержку (`channel-capabilities.md` §7).
- Сгенерированный код (`src/generated/`) не редактируется; перегенерация — из конкретного снимка с проверкой SHA-256.
- Инвариант, который можно выразить ограничением или триггером, закрепляется в БД, а не только в приложении.
- **Цифры лимитов и поведение API не выдумывать.** Неподтверждённое — «(проверить)» с планом проверки в `channel-capabilities.md`.
- Никаких реальных данных продавцов в тестах, фикстурах, логах отладки и внешних инструментах (включая LLM).
- Поведение адаптера меняется вместе со сценарием в `tests/contract/fixtures/`. Фикстуры — синтетические по документации или записанные рекордером, обезличенные и прошедшие рецензию (`provenance.reviewedBy`); запись с реального аккаунта хранится вне репозитория до рецензии.
- Никакой логики, отчётов или метрик, объединяющих бизнес-данные нескольких тенантов (в том числе детекторов сдвига рынка: окно Р-42 — внутри тенанта).
- Новая причина решения или правило проверки входов — код и схема параметров в `packages/pricing-model/src/reasons.ts` (вид, класс источника; сумма — с валютой [Р-71]); тексты — в словаре `packages/console-model/src/i18n` на немецком и английском [Р-72]; новый ключ класса `CHANNEL` — и в `security.channel_param_keys()`. Изменение порогов Р-42 — только с оценкой ложных срабатываний.
- Нет кода, мигрирующего листинги eBay без `MigrationConsent`.
- Никогда не логировать секреты, токены, данные покупателей.
- Документация — на русском; идентификаторы — на английском.
- Неизвестное — в [docs/open-questions.md](docs/open-questions.md).
