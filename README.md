# repracer

Мультитенантный SaaS, который для продавца на маркетплейсах делает три вещи: **синхронизирует остатки** между каналами,
**автоматически меняет цены** по стратегиям, не опускаясь ниже обязательного пола, и **ведёт историю своих цен** по
каждому каналу для Omnibus и §11 PAngV.

Каналы Release 1.0 — **Kaufland**, **Amazon (SP-API)**, **eBay**; Otto Market и Walmart — после первых клиентов. Amazon и
eBay — ЕС и США, Kaufland — Германия и Австрия; EUR и USD, НДС и sales tax.

> **Статус: в разработке, к живым каналам не подключён.** Всё, что ниже, работает на контрактном стенде, симуляторах
> каналов и синтетических данных: реальных аккаунтов продавцов нет ни у одного канала (нет регистрации технологического
> партнёра Kaufland, ключей разработчика eBay, живой очереди уведомлений Amazon). Данных реальных продавцов нет ни в
> тестах, ни в фикстурах, ни в логах — это правило проекта, а не следствие обстоятельств.

**Репозиторий публичный, но не open source** — см. [LICENSE](LICENSE). Сторонние материалы — [NOTICE.md](NOTICE.md).

## Чем этот репозиторий может быть интересен

Проект строится длинными шагами, и почти всё в нём подчинено одному вопросу: **чем подтверждается, что заявленное
действительно работает.** Несколько приёмов, которые здесь доведены до рабочего состояния:

- **Инвариант живёт в базе, а не в приложении.** 114 миграций PostgreSQL: RLS с `FORCE`, составные внешние ключи с
  `tenant_id`, append-only таблицы, права по столбцам, списки разрешённого в обе стороны. Приложению не доверяют.
- **Мутационная проверка схемы.** Защиты снимаются по одной, и каждая обязана уронить СВОЮ проверку с СВОЕЙ причиной —
  падение соседней не засчитывается. Сейчас: 78 строк каталога, **385 мутаций, ни одной непойманной**. Эта проверка
  регулярно находит дыры, которые прошли ревью: например, что выполняющаяся выгрузка отчёта открывала изменение пола
  маржи у всех предложений тенанта.
- **Живой прогон вместо вызова функций.** То, к чему прикасается продавец, проверяется через настоящий HTTP-сервер на
  каталоге в 10 000 предложений, с утверждением времени и размера каждого ответа. Это ловит то, чего не видит юнит-тест:
  запрос в 381 КБ, ответ в 10 МБ, операцию на 122 секунды, скачивание файла, которое не работает, потому что браузер по
  ссылке не шлёт заголовок авторизации.
- **Находка закрывается правилом, а не только исправлением.** Ревьюер и мутация ловят случайно; правило ловит всегда.
  Примеры действующих правил: «ни один экран не ведёт ссылкой на адрес API», «файл собирается ровно в одном месте»,
  «вид задания, которому не нужен второй фактор, не может стоять в списке стража».
- **Отрицательный результат записывается наравне с положительным.** [docs/open-questions.md](docs/open-questions.md)
  ведёт список того, что неизвестно или недоступно, а [docs/accepted-risks.md](docs/accepted-risks.md) — того, что
  решено НЕ закрывать. Числа лимитов каналов не выдумываются: неподтверждённое помечается «(проверить)» с планом
  проверки.

## Ключевые принципы

1. Ни один запрос не пересекает границу тенанта — это обеспечивает сама БД, а не код.
2. Обе границы цены обязательны и проверяются вне движка стратегий: в Gate и в БД — при решении, при создании записи и
   заново перед КАЖДОЙ отправкой, по текущим себестоимости, комиссии, курсу и налогу.
3. Каждая запись в канал идемпотентна и версионирована по единице записи конкретного поля, а не по офферу.
4. Свои цены хранятся бессрочно; прочитанное из каналов — с ограниченным сроком и никогда не попадает в архив.
5. «Отправили» и «видим в канале» — разные состояния; расхождение обрабатывается политикой, а не молча.
6. Необратимое (миграция листингов eBay) — только с явным информированным согласием владельца со вторым фактором.
7. Тест не пропускается, не выпадает из сборки и проверяет ПРИЧИНУ отказа, а не факт.

## Разработка

Node ≥ 22, PostgreSQL 16. Зависимостей времени выполнения четыре; остальное — стандартная библиотека.

```sh
npm install                      # только dev-зависимости
npm run typecheck                # типы всех рабочих областей
node scripts/test-all.mjs --scope=fast    # тесты; пропуск теста — красная сборка

# тесты на базе: PostgreSQL должен быть поднят
PGHOST=127.0.0.1 PGPORT=5432 PGUSER=postgres \
  REPRACER_PG_ADMIN_URL=postgres://postgres@127.0.0.1:5432/postgres \
  REPRACER_PG_URL=postgres://svc_app@127.0.0.1:5432/repracer_eu \
  REPRACER_PG_TEMPLATE=repracer_template scripts/db/prepare.sh repracer_eu

node scripts/db/mutation-check.mjs --jobs 3   # мутационная проверка схемы (~25 минут)

npm run stand -w @repracer/console   # сервер стенда: http://127.0.0.1:4318
npm run dev -w @repracer/console     # консоль: http://127.0.0.1:5173
```

Сборка делится на быстрый прогон (каждый коммит: типы, юнит-тесты, PostgreSQL) и полный (слияние в main и по запросу:
мутации, брокер, ClickHouse, запуск развёртываний). Что отложено в полный прогон — названо поимённо с причиной в
`scripts/test-scopes.mjs`.
