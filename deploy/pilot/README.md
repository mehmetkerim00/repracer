# Пилот: первый прод на отдельном сервере

Шаг 124, решения владельца по аудиту авторизации Amazon (Р-245…Р-248). Что получится: `https://app.<домен>` — промышленная консоль продавца
(вход у ZITADEL, подключение Amazon кнопкой «Connect Amazon»). Аккаунт продавца живёт в тени: решения считаются, записи в каналы не уходят.
Панель оператора — только через SSH-туннель.

**Сервера у пилота пока нет.** Он покупается с одобрения Мердана при запуске; здесь — развёртывание как код. Параметры сервера в репозитории
не зашиты: адрес — аргумент команд, имя консоли и база — `pilot.env`. Без сервера проверено:
- разбор `compose.yaml` с примером настроек и файлами `secrets.sh`;
- загрузка конфигурации каждого процесса (`scripts/test/pilot-deploy.test.ts`);
- генератор секретов, первая сборка базы, выкладка поверх живой базы и страж (`scripts/test/pilot-db.test.ts`);
- журнал миграций (`scripts/test/db-migrate.test.ts`);
- копии базы (шаг 126): отказ выкладки без копий, вынос в R2 и на машину оператора, вердикт смоука (`scripts/test/pilot-backup.test.ts`),
  восстановление копии пилота со стражем и журналом миграций (`scripts/test/pilot-db.test.ts`).

`deploy.sh`, `smoke.sh`, `backup-key.sh`, `restore-check.sh` (контейнерами) и туннель впервые пройдут на сервере.

Состав (`compose.yaml`):

| Сервис | Что |
|---|---|
| `postgres` | живая база: пароли ролей, выкладка применяет только новые миграции (`scripts/db/migrate.sh`); страж боевых записей с первого дня [Р-247] |
| `clickhouse` | история снимков конкурентов [Р-122]; выгрузка обязательна, журнальная логика прежняя [Р-246] |
| `console` | `deploy/console` через `extends`, промышленный профиль, без публичного демо |
| `scheduler` | `deploy/scheduler`: обнаружение отчётом, опрос сводки [Р-240], проверка авторизаций |
| `bulk-worker` | импорты себестоимости и границ, выгрузки, включение набора |
| `operator` | `deploy/operator`: только loopback, ссылка приглашения — оператору один раз [Р-245] |
| `cloudflared` | туннель `app.<домен>` → `http://console:4319` |
| `backup` | суточная копия PostgreSQL: `pg_dump` → `gpg` открытым ключом владельца, 7 суток (`deploy/production/backup-loop.sh`) — §8 |
| `backup-offsite` | только при `REPRACER_BACKUP_OFFSITE=r2`: вынос копий в Cloudflare R2 — §8 |
| `tools` | разовые работы выкладки (DDL ClickHouse, логины выгрузки) |

**Брокера и диспетчера записей нет:** пилот в тени. Бой невозможен дважды: его держит страж базы, а подтверждение принятой записи ведёт
только диспетчер (`deploy/worker`, брокер). Перевод в бой — отдельное решение со своей выкладкой (§6).

## 1. Внешние шаги — с Керимом при развёртывании

**ZITADEL** (облачный, бесплатный тариф) — вход продавца и оператора [Р-180, Р-183]:
- [ ] Инстанс и проект. ID проекта — `REPRACER_CONSOLE_OIDC_AUDIENCE` и `REPRACER_OPERATOR_OIDC_AUDIENCE`.
- [ ] Приложение консоли — тип «User Agent» (PKCE, без секрета):
  - адрес возврата `https://app.<домен>/auth/callback`;
  - тип токена доступа — **JWT**: opaque не проверится, и вход откажет всем (vendor/zitadel/SOURCE.md).
- [ ] Приложение панели — «User Agent»: адрес возврата `http://127.0.0.1:4327/auth/callback`. Допускает ли ZITADEL http-адрес на петле вне
  режима разработки — проверить на месте.
- [ ] Второй фактор (OTP) включён для организации. Без него импорт границ и себестоимости откажет [Р-135], и каждое действие панели тоже
  [Р-165].
- [ ] Учётная запись оператора — строка `platform.platform_operator` (издатель и subject оператора). Заводит суперпользователь базы: у
  панели такого действия нет [Р-166].

**Кабинет разработчика Amazon** (Developer Central / Solution Provider Portal), приложение TMPrice:
- [ ] **OAuth Redirect URI** — `https://app.<домен>/connect/callback`, **первым в списке**. Адрес согласия не передаёт `redirect_uri`, и
  Amazon берёт первый зарегистрированный.
- [ ] **OAuth Login URI** — `https://app.<домен>/connect/amazon/login`. По документации обязателен: после согласия Amazon ведёт продавца на
  него (шаги 5–8 потока с сайта, [vendor/amazon/lwa-authorization/2026-11-14](../../vendor/amazon/lwa-authorization/2026-11-14/SOURCE.md)),
  консоль сверяет его со своим «Connect» и возвращает на Amazon (шаг 125). Подключение начинается только с Channels → «Connect Amazon» в
  консоли; приход из Appstore без этого консоль не продолжает (до публикации приложения его нет).
- [ ] Роли: Product Listing (листинги и запись цены) и Pricing или Inventory and Order Tracking (отчёт листингов, A-40) —
  [docs/channels/amazon.md](../../docs/channels/amazon.md), «Роли разработчика».
- [ ] Флаг `REPRACER_AMAZON_APP_DRAFT` в `pilot.env` — по фактическому состоянию приложения:
  - `on` — Draft, согласие идёт с `version=beta`;
  - `off` — приложение опубликовано в Appstore.

  После публикации флаг меняется и процессы перезапускаются (`deploy/pilot/compose.sh up -d`).

**Cloudflare** — туннель и DNS (§3).

## 2. Сервер

Подготовка хоста — как у QA-A ([deploy/qa/README.md](../qa/README.md), §1–4):
- вход только по ключу;
- случайный пароль root;
- пользователь `deploy` без sudo;
- межсетевой экран — снаружи только SSH;
- Docker из источника deb822;
- `git clone` в `/srv/repracer`.

Отличия пилота:

- **uid пользователя `deploy` — 1000.** От этого uid работают контейнеры процессов: файлы секретов `600` должны принадлежать ему.
- **Каталог секретов** `/srv/repracer-pilot/secrets` (700, владелец `deploy`) — его создаёт `push-secrets.sh`.
- **Размер сервера** — решение при покупке. ClickHouse держит память сам; сколько займёт стек пилота, первая выкладка покажет числом,
  как у QA-A.

## 3. Cloudflare: туннель и DNS

Как у QA-A (§5), через API с токеном из `$HOME/.config/repracer/secrets/cloudflare.env`. Значения не печатаются.

1. Туннель `repracer-pilot` с конфигурацией у Cloudflare: ingress `app.<домен>` → `http://console:4319`, остальное — `http_status:404`.
2. CNAME `app` → `<id туннеля>.cfargotunnel.com`, проксируемый.
3. Токен установки туннеля — в `$HOME/.config/repracer/secrets/pilot/tunnel.env` (образец — [tunnel.env.example](tunnel.env.example)), права 600.

Cloudflare Access перед консолью не нужен: вход закрывает ZITADEL со вторым фактором. Список адресов Access можно добавить отдельным решением,
и тогда продавцу понадобится и он.

## 4. Секреты

На машине владельца:

```sh
deploy/pilot/secrets.sh                          # создаёт недостающее в $HOME/.config/repracer/secrets/pilot; значения не печатает
deploy/pilot/push-secrets.sh deploy@<сервер>     # копирует каталог на сервер (700/600); нужен tunnel.env из §3
```

Что делает `secrets.sh`:
- **генерирует** пароли ролей подключения и суперпользователя базы, логины и пароли ClickHouse, кольцо ключей токенов каналов;
- **собирает** строки подключения процессов;
- **берёт** секрет клиента LWA и идентификаторы приложения из `amazon-production.env`.

Повторный запуск ничего не меняет. Пароль меняется удалением файла и повторной выкладкой: `db.sh` задаёт пароли ролей каждый раз.

На сервере — настройки:

```sh
cp deploy/pilot/pilot.env.example deploy/pilot/pilot.env   # заполнить: имя консоли, ZITADEL, Draft, копии базы (§8)
mkdir -p /srv/repracer-pilot/backups && chmod 700 /srv/repracer-pilot/backups
```

Ключ копий и цель их выноса — §8: без них выкладка откажет первой же строкой.

## 5. Выкладка

```sh
deploy/pilot/deploy.sh <тег или SHA main> --first-time   # первая: база заново, страж ставится
deploy/pilot/deploy.sh <тег или SHA main>                # дальше: только новые миграции, база живая
```

Что делает выкладка, по порядку:
1. Код нужной версии.
2. Сборка интерфейса в контейнере Node.
3. Версия сборки.
4. PostgreSQL и ClickHouse.
5. База: `deploy/pilot/db.sh` внутри контейнера базы.
6. DDL ClickHouse и логины выгрузки (`tools`).
7. Процессы.
8. Проверка (`smoke.sh`), снаружи — `https://app.<домен>/healthz`.

Первая выкладка вдобавок ставит страж, кладёт роли входа и строки возможностей каналов.

До всего выкладка спрашивает готовность копий (`backup-state.sh --ready`, §8). Первая выкладка кончается красной строкой смоука про копии:
копия уже снята, но ещё не вынесена (при `pull`) и не проверена восстановлением. Это ожидаемо — шаги §8, затем `deploy/pilot/smoke.sh`.

**Никогда не запускать на пилоте `scripts/db/prepare.sh`** — он пересоздаёт базу: стёр бы подключённый аккаунт продавца, его каталог и
неделю тени (Р-204 требует 7 суток подряд). Миграции живой базы — только журналом (`scripts/db/migrate.sh`): изменённая задним числом
миграция — отказ выкладки.

Обрыв SSH во время выкладки не прерывает работу, если запускать её в фоне под журналом:

```sh
QA_STATE_DIR=deploy/pilot/state deploy/qa/detach.sh deploy deploy/pilot/deploy.sh <тег>
```

## 6. Страж боевых записей [Р-247]

База пилота закрыта с первой выкладки: `ALTER DATABASE <база> SET repracer.live_writes = 'forbidden'` (P0-09, [ADR-0073](../../docs/adr/0073-qa-live-writes-guard.md)).
Пока он стоит, у клиентского тенанта:
- аккаунт не переводится в бой;
- ни одна запись не уходит в канал — проверка перед каждой отправкой.

Тень работает целиком. Выкладка стража не ставит заново и не снимает; `smoke.sh` называет его состояние.

**Снятие — только явным решением Мердана и владельца.** Это не настройка выкладки, а решение о первой боевой записи живого продавца.
Порядок:

1. Записать решение: кто решил, когда, для какого аккаунта и витрины. Строка — в `docs/decisions.md` или в доказательствах шага боевого
   запуска. Предусловия — чеклист «День перевода в бой» ([docs/live-first-account-checklist.md](../../docs/live-first-account-checklist.md)):
   неделя тени, граница суток amazon.com принята оператором [Р-204], брокер и диспетчер подняты (`deploy/worker`).
2. Снять стража явным значением, а не `RESET`. Без значения выкладка откажет, потому что не отличит решение от ошибки:

   ```sh
   set -a; . deploy/pilot/pilot.env; set +a   # имя базы — REPRACER_PILOT_DB
   deploy/pilot/compose.sh exec -T -u postgres postgres psql -X -c "ALTER DATABASE ${REPRACER_PILOT_DB} SET repracer.live_writes = 'allowed'"
   ```

3. Перевод аккаунта в бой делает владелец тенанта в консоли: второй фактор и набранное имя аккаунта [Р-170].
4. Вернуть стража — одной командой, в любой момент. Новые записи не уйдут, уже ушедшие не отзываются:

   ```sh
   deploy/pilot/compose.sh exec -T -u postgres postgres psql -X -c "ALTER DATABASE ${REPRACER_PILOT_DB} SET repracer.live_writes = 'forbidden'"
   ```

## 7. Путь пилота

1. Оператор открывает панель туннелем: `ssh -L 4327:127.0.0.1:4327 deploy@<сервер>`, затем `http://127.0.0.1:4327`.
2. В панели «New pilot» создаёт тенант (регион US, язык en), затем «Invite the owner».
3. Панель показывает ссылку приглашения **один раз** (Р-245, [ADR-0075](../../docs/adr/0075-invite-link-reveal.md)). Оператор передаёт её
   владельцу не открытым каналом.
4. Владелец входит у ZITADEL, проходит онбординг и нажимает «Connect Amazon»: аккаунт рождается в тени.
5. Каталог приходит отчётом листингов. Если отчёт не готов за заход, продолжение идёт через 5–40 минут, а не через час (шаг 122).
6. Себестоимость с комиссией, границы, стратегия, включение — решения тени.

## 8. Копии базы (шаг 126)

Решение владельца: копии — в составе пилота до запуска, пилот без них не стартует; копия без проверенного восстановления копией не
считается; ничего не покупаем. Три части, и смоук требует все три (`backup-state.sh`):

1. **Копия.** Сервис `backup` раз в сутки снимает `pg_dump` базы пилота и роли кластера и сразу шифрует их открытым ключом владельца
   (`deploy/production/backup-loop.sh`, тот же скрипт, что у промышленного профиля). На сервере — только шифротекст и только 7 суток (данные
   каналов не переживают свой срок в копиях, [docs/data-retention.md](../../docs/data-retention.md)). Провал — отметка `BACKUP_FAILED`.
2. **Вынос с сервера** — `REPRACER_BACKUP_OFFSITE` в `pilot.env`. **Пилот — `pull`** (решение владельца 2026-11-14): R2 не включаем —
   при включении Cloudflare может попросить способ оплаты, а любые возможные списания — только с одобрения Мердана; пересмотр — при go-live.
   - `r2` — сейчас не используется. Cloudflare R2, бесплатный уровень (10 GB-month, снимок [vendor/cloudflare/r2/2026-11-14](../../vendor/cloudflare/r2/2026-11-14/SOURCE.md)).
     Бакет, токен «Object Read & Write» только на него; ключи — файлами `backup_r2_access_key_id` и `backup_r2_secret_access_key` в
     каталоге секретов (на машине владельца, затем `push-secrets.sh`); `REPRACER_BACKUP_R2_BUCKET_URL=https://<бакет>.<ACCOUNT_ID>.r2.cloudflarestorage.com`.
     Сервис `backup-offsite` выносит каждую готовую копию, сверяет длину в бакете и только тогда ставит отметку `.offsite`; в бакете копии
     тоже живут 7 суток. Попросит ли Cloudflare способ оплаты для включения R2 — проверить при включении; любые возможные списания — с
     одобрения Мердана.
   - `pull` (выбор пилота) — машина оператора забирает копии сама, раз в сутки:

     ```sh
     deploy/pilot/pull-backups.sh deploy@<сервер>           # в $HOME/.config/repracer/backups/pilot, SHA-256 каждой копии, 7 суток
     ```

     Ежедневно — `launchd` (macOS) или `cron`; машина спала — следующий запуск заберёт всё пропущенное.

     **Когда смоук краснеет из-за выноса.** Смоук требует на сервере отметку `OFFSITE_PULLED`, в которой последняя вынесенная копия не старше
     26 часов. Значит, смоук красный, если машина оператора не забрала копию дольше суток, — в том числе если она выключена, спит или без сети.
     Выключена дольше 7 суток — хуже: копии старше 7 суток сервер удаляет раньше, чем их заберут, и вне сервера их уже не будет. Смоук идёт при
     выкладке (`deploy.sh`) и вручную; между выкладками за выносом по расписанию никто не следит.
3. **Проверка восстановления** — на сервере, в одноразовом контейнере без сети: закрытый ключ — со стандартного ввода, копия
   восстанавливается во временный PostgreSQL тем же `deploy/production/restore.sh`, что при настоящей беде; проверяются регион, страж
   боевых записей [Р-247] (копия, потерявшая его, подняла бы базу с разрешённой записью), журнал миграций и числа:

   ```sh
   ssh deploy@<сервер> 'cd /srv/repracer && deploy/pilot/restore-check.sh' < "$HOME/.config/repracer/secrets/pilot-backup-private.asc"
   ```

   Смоук требует отметку проверки у одной из хранимых копий, то есть **не реже раза в 7 суток** — и после каждой смены ключа.

**Ключ копий** создаётся один раз. Закрытый ключ — только у владельца, вне каталога секретов пилота (`push-secrets.sh` откажет, найдя его
там; выкладка откажет, найдя его на сервере). Если на машине владельца есть GnuPG — команды [deploy/production/README.md](../production/README.md)
(«Шифрование копии»), открытый ключ — в `$HOME/.config/repracer/secrets/pilot/backup_public_key.asc`. Если нет — пара рождается в памяти
одноразового контейнера на сервере, открытый ключ ложится в каталог секретов сервера, закрытый уходит по SSH владельцу:

```sh
ssh deploy@<сервер> 'cd /srv/repracer && deploy/pilot/backup-key.sh' > "$HOME/.config/repracer/secrets/pilot-backup-private.asc"
chmod 600 "$HOME/.config/repracer/secrets/pilot-backup-private.asc"     # и вторую копию — в сейф владельца
```

Новый сервер со старым ключом — `deploy/pilot/backup-key.sh --public` с закрытым ключом на стандартном вводе.

**Настоящая беда** (сервер потерян): новый сервер по §2–5, затем восстановление копии — [docs/runbook-disaster.md](../../docs/runbook-disaster.md)
и `deploy/production/restore.sh` с закрытым ключом; копия берётся из R2 или с машины оператора. Теряется всё после последней копии
(до суток): восстановления на момент времени нет.

**ClickHouse в пилоте не копируется** (решение владельца). Гибель его тома уносит выгруженную историю — наблюдения, снимки конкурентов
[Р-122] и завершённые записи [Р-20] — с подключения по день гибели. Цены от этого не страдают: решение о цене ClickHouse не читает [Р-22],
суточная свёртка наших цен [Р-21] живёт в PostgreSQL и в копии.

## 9. Чего здесь нет

- **Почты.** Письма собираются и не уходят, в базе отметка `DRY_RUN` (OQ-224); приглашение — ссылкой в панели.
- **Внешнего контроля** (OQ-188): отметки выключены явно.
- **Приёмника уведомлений Amazon** — часть Б заблокирована снаружи; пилот — на опросе [Р-240].
