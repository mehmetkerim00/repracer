# Пилот: первый прод на отдельном сервере

Шаг 124, решения владельца по аудиту авторизации Amazon (Р-245…Р-248). Что получится: `https://app.<домен>` — промышленная консоль продавца
(вход у ZITADEL, подключение Amazon кнопкой «Connect Amazon»). Аккаунт продавца живёт в тени: решения считаются, записи в каналы не уходят.
Панель оператора — только через SSH-туннель.

**Сервера у пилота пока нет.** Он покупается с одобрения Мердана при запуске; здесь — развёртывание как код. Параметры сервера в репозитории
не зашиты: адрес — аргумент команд, имя консоли и база — `pilot.env`. Без сервера проверено:
- разбор `compose.yaml` с примером настроек и файлами `secrets.sh`;
- загрузка конфигурации каждого процесса (`scripts/test/pilot-deploy.test.ts`);
- генератор секретов, первая сборка базы, выкладка поверх живой базы и страж (`scripts/test/pilot-db.test.ts`);
- журнал миграций (`scripts/test/db-migrate.test.ts`);
- копии базы (шаг 126): отказ выкладки без копий, вынос в R2 и на машину оператора, вердикт смоука (`scripts/test/pilot-backup.test.ts`),
  восстановление копии пилота со стражем и журналом миграций (`scripts/test/pilot-db.test.ts`);
- внешний контроль (шаг 129): отказ выкладки без отметок, отметки копий и выноса, заведение проверок на модели API
  (`scripts/test/pilot-monitoring.test.ts`);
- архив журналов (шаг 130): выгрузка проекта пилота тем же скриптом, отметка захода, строка crontab, вердикт смоука; вынос журналов на
  машину оператора (шаг 133) (`scripts/test/pilot-logs.test.ts`);
- откат (шаг 131): план миграций и отказ «база новее кода» (`scripts/test/db-migrate.test.ts`), копия перед выкладкой и порядок шагов
  (`scripts/test/pilot-rollback.test.ts`), учение «N → N+1 с миграцией → откат» (`scripts/test/pilot-db.test.ts`);
- сброс QA-B (шаг 132): только база с отметкой `qa-b` при настройках `qa-b`, новая база со стражем, повтор после обрыва
  (`scripts/test/pilot-db.test.ts`), отказ `reset.sh` на пилоте до любой команды Docker (`scripts/test/pilot-rollback.test.ts`);
- путь записи, память ClickHouse и шлюз SSH QA-B (шаг 141): брокер и процесс пути решения — только под профилем `live`, процесс принимает
  окружение и файлы `secrets.sh`, обёртка включает профиль только значением `on`, внешний контроль процесса, потолок памяти ClickHouse, три
  команды шлюза (`scripts/test/pilot-write-path.test.ts`).

`deploy.sh`, `smoke.sh`, `backup-key.sh`, `restore-check.sh` и `rollback.sh` (контейнерами), выгрузка журналов настоящим `docker compose logs`
и туннель впервые пройдут на сервере. Брокер и процесс пути решения контейнерами впервые поднимутся в день перевода в бой — или раньше,
репетицией на QA-B: страж там стоит, и ничего не уходит.

Состав (`compose.yaml`):

| Сервис | Что |
|---|---|
| `postgres` | живая база: пароли ролей, выкладка применяет только новые миграции (`scripts/db/migrate.sh`); страж боевых записей с первого дня [Р-247] |
| `clickhouse` | история снимков конкурентов [Р-122]; выгрузка обязательна, журнальная логика прежняя [Р-246] |
| `console` | `deploy/console` через `extends`, промышленный профиль, без публичного демо |
| `scheduler` | `deploy/scheduler`: обнаружение отчётом, опрос сводки [Р-240], проверка авторизаций |
| `bulk-worker` | импорты себестоимости и границ, выгрузки, включение набора |
| `operator` | `deploy/operator`: только loopback, ссылка приглашения — оператору один раз [Р-245] |
| `cloudflared` | туннель `app.<домен>` → `http://console:4319` |
| `backup` | суточная копия PostgreSQL: `pg_dump` → `gpg` открытым ключом владельца, 7 суток (`deploy/production/backup-loop.sh`) — §8 |
| `backup-heartbeat` | отметка во внешнем сервисе после каждой готовой копии, «сбой» — при `BACKUP_FAILED`; каталог копий только читает — §9 |
| `backup-offsite` | только при `REPRACER_BACKUP_OFFSITE=r2`: вынос копий в Cloudflare R2 — §8 |
| `tools` | разовые работы выкладки (DDL ClickHouse, логины выгрузки) |
| `redpanda` | только профиль `live`: брокер пути записи [Р-24], как в CI и `infra/local` — §6 |
| `worker` | только профиль `live`: `deploy/worker` через `extends` — диспетчер записей [Р-64] и ретранслятор outbox [Р-34] — §6 |

**Путь записи — к дню перевода в бой** (шаг 141, решение владельца 2026-11-16): брокер и процесс пути решения — как в промышленном профиле,
без отдельной схемы «диспетчер без брокера». Обычная выкладка их не поднимает (`REPRACER_PILOT_WRITE_PATH=off`): пилот в тени, записи рождаются
удержанными, отправлять нечего. Бой невозможен дважды: его держит страж базы, а подтверждение принятой записи, записи количества, повторы и
сверку ведёт только этот процесс. Включение — §6.

## 1. Внешние шаги — с Керимом при развёртывании

**ZITADEL** (облачный, бесплатный тариф) — вход продавца и оператора [Р-180, Р-183]:
- [ ] Инстанс и проект. ID проекта — `REPRACER_CONSOLE_OIDC_AUDIENCE` и `REPRACER_OPERATOR_OIDC_AUDIENCE`.
- [ ] Приложение консоли — тип «User Agent» (PKCE, без секрета):
  - адрес возврата `https://app.<домен>/auth/callback`;
  - тип токена доступа — **JWT**: opaque не проверится, и вход откажет всем (vendor/zitadel/SOURCE.md).
- [ ] Приложение панели — «User Agent»: адрес возврата `http://127.0.0.1:4327/auth/callback`. Допускает ли ZITADEL http-адрес на петле вне
  режима разработки — проверить на месте.
- [ ] Второй фактор (OTP) включён для организации. Без него импорт границ и себестоимости откажет [Р-135], и каждое действие панели тоже
  [Р-165].
- [ ] Учётная запись оператора — строка `platform.platform_operator` (издатель и subject оператора). Заводит суперпользователь базы: у
  панели такого действия нет [Р-166].

**Кабинет разработчика Amazon** (Developer Central / Solution Provider Portal), приложение TMPrice:
- [ ] **OAuth Redirect URI** — `https://app.<домен>/connect/callback`, **первым в списке**. Адрес согласия не передаёт `redirect_uri`, и
  Amazon берёт первый зарегистрированный.
- [ ] **OAuth Login URI** — `https://app.<домен>/connect/amazon/login`. По документации обязателен: после согласия Amazon ведёт продавца на
  него (шаги 5–8 потока с сайта, [vendor/amazon/lwa-authorization/2026-11-14](../../vendor/amazon/lwa-authorization/2026-11-14/SOURCE.md)),
  консоль сверяет его со своим «Connect» и возвращает на Amazon (шаг 125). Подключение начинается только с Channels → «Connect Amazon» в
  консоли; приход из Appstore без этого консоль не продолжает (до публикации приложения его нет).
- [ ] Роли: Product Listing (листинги и запись цены) и Pricing или Inventory and Order Tracking (отчёт листингов, A-40) —
  [docs/channels/amazon.md](../../docs/channels/amazon.md), «Роли разработчика».
- [ ] Флаг `REPRACER_AMAZON_APP_DRAFT` в `pilot.env` — по фактическому состоянию приложения:
  - `on` — Draft, согласие идёт с `version=beta`;
  - `off` — приложение опубликовано в Appstore.

  После публикации флаг меняется и процессы перезапускаются (`deploy/pilot/compose.sh up -d`).

**Cloudflare** — туннель и DNS (§3).

## 2. Сервер

Подготовка хоста — как у QA-A ([deploy/qa/README.md](../qa/README.md), §1–4):
- вход только по ключу;
- случайный пароль root;
- пользователь `deploy` без sudo;
- межсетевой экран — снаружи только SSH;
- Docker из источника deb822;
- `git clone` в `/srv/repracer`.

Отличия пилота:

- **uid пользователя `deploy` — 1000.** От этого uid работают контейнеры процессов: файлы секретов `600` должны принадлежать ему.
- **Каталог секретов** `/srv/repracer-pilot/secrets` (700, владелец `deploy`) — его создаёт `push-secrets.sh`.
- **Размер сервера.** QA-B — 4 vCPU / 8 GB RAM / 80 GB SSD (решение владельца 2026-11-16). Пилот — решение при покупке, ориентир тот же. QA-A
  на 3 vCPU / 3,9 GB работает впритык, а в нём нет ClickHouse и четырёх процессов Node. Сборка интерфейса при выкладке на пике берёт ещё 1,5–2 GB.
- **Память ClickHouse** — потолок контейнера `REPRACER_CLICKHOUSE_MEM_LIMIT` (по умолчанию 2 GiB). Сервер берёт 0,9 от памяти контейнера, а не
  машины (снимок [vendor/clickhouse/server-config/26.8.4.11-lts](../../vendor/clickhouse/server-config/26.8.4.11-lts/SOURCE.md)). Хватает ли,
  покажет первая неделя QA-B (`docker stats`). Брокер в день перевода в бой берёт ещё 1 GiB.

## 3. Cloudflare: туннель и DNS

Как у QA-A (§5), через API с токеном из `$HOME/.config/repracer/secrets/cloudflare.env`. Значения не печатаются.

1. Туннель `repracer-pilot` с конфигурацией у Cloudflare: ingress `app.<домен>` → `http://console:4319`, остальное — `http_status:404`.
2. CNAME `app` → `<id туннеля>.cfargotunnel.com`, проксируемый.
3. Токен установки туннеля — в `$HOME/.config/repracer/secrets/pilot/tunnel.env` (образец — [tunnel.env.example](tunnel.env.example)), права 600.

Cloudflare Access перед консолью не нужен: вход закрывает ZITADEL со вторым фактором. Список адресов Access можно добавить отдельным решением,
и тогда продавцу понадобится и он.

## 4. Секреты

На машине владельца:

```sh
deploy/pilot/secrets.sh                          # создаёт недостающее в $HOME/.config/repracer/secrets/pilot; значения не печатает
deploy/pilot/push-secrets.sh deploy@<сервер>     # копирует каталог на сервер (700/600); нужен tunnel.env из §3
```

Что делает `secrets.sh`:
- **генерирует** пароли ролей подключения и суперпользователя базы, логины и пароли ClickHouse, кольцо ключей токенов каналов;
- **собирает** строки подключения процессов;
- **берёт** секрет клиента LWA и идентификаторы приложения из `amazon-production.env`.

Повторный запуск ничего не меняет. Пароль меняется удалением файла и повторной выкладкой: `db.sh` задаёт пароли ролей каждый раз.

На сервере — настройки:

```sh
cp deploy/pilot/pilot.env.example deploy/pilot/pilot.env   # заполнить: имя консоли, ZITADEL, Draft, копии базы (§8)
mkdir -p /srv/repracer-pilot/backups && chmod 700 /srv/repracer-pilot/backups
```

Ключ копий и цель их выноса — §8: без них выкладка откажет первой же строкой.

## 5. Выкладка

```sh
deploy/pilot/deploy.sh <тег или SHA main> --first-time   # первая: база заново, страж ставится
deploy/pilot/deploy.sh <тег или SHA main>                # дальше: только новые миграции, база живая
```

Что делает выкладка, по порядку:
1. Готовность копий (§8) и внешнего контроля (§9).
2. План миграций выкладываемой версии к живой базе (`scripts/db/migrate.sh --check`, шаг 131) — пока рабочая копия и процессы ещё на
   прежней версии. Версия старше базы — отказ здесь же, ничего не менялось (§11).
3. Код нужной версии.
4. Сборка интерфейса в контейнере Node.
5. Версия сборки.
6. PostgreSQL и ClickHouse.
7. Если у версии есть миграции — копия базы до них с отметкой выкладки (`pre-release-copy.sh`); провал копии — стоп до миграций (§11).
8. База: `deploy/pilot/db.sh` внутри контейнера базы.
9. DDL ClickHouse и логины выгрузки (`tools`).
10. Процессы; строка в журнале выкладок `deploy/pilot/state/releases.log` (с какой версии на какую).
11. Журналы: выгрузка по сей момент и ежедневный запуск (§10). Журналы контейнеров, которые выкладка пересоздаст, выгружаются раньше — до шага 6.
12. Проверка (`smoke.sh`), снаружи — `https://app.<домен>/healthz`.

Первая выкладка вдобавок ставит страж, кладёт роли входа и строки возможностей каналов. После неё, когда `https://app.<домен>/healthz`
отвечает, заводится монитор UptimeRobot (§9, п. 4). Раньше его не заводят: он слал бы письма о «падении» адреса, которого ещё нет.

До всего выкладка спрашивает готовность копий (`backup-state.sh --ready`, §8). Первая выкладка кончается красными строками смоука про копии
и журналы. Копия уже снята, но ещё не вынесена (при `pull`) и не проверена восстановлением, а журналы не вынесены (§10). Это ожидаемо:
шаги §8, затем `deploy/pilot/smoke.sh`.

**Никогда не запускать на пилоте `scripts/db/prepare.sh`** — он пересоздаёт базу: стёр бы подключённый аккаунт продавца, его каталог и
неделю тени (Р-204 требует 7 суток подряд). Миграции живой базы — только журналом (`scripts/db/migrate.sh`): изменённая задним числом
миграция — отказ выкладки; версия старше базы — отказ своей причиной до переключения рабочей копии (§11).

Обрыв SSH во время выкладки не прерывает работу, если запускать её в фоне под журналом:

```sh
QA_STATE_DIR=deploy/pilot/state deploy/qa/detach.sh deploy deploy/pilot/deploy.sh <тег>
```

## 6. Страж боевых записей [Р-247]

База пилота закрыта с первой выкладки: `ALTER DATABASE <база> SET repracer.live_writes = 'forbidden'` (P0-09, [ADR-0073](../../docs/adr/0073-qa-live-writes-guard.md)).
Пока он стоит, у клиентского тенанта:
- аккаунт не переводится в бой;
- ни одна запись не уходит в канал — проверка перед каждой отправкой.

Тень работает целиком. Выкладка стража не ставит заново и не снимает; `smoke.sh` называет его состояние.

**Снятие — только явным решением Мердана и владельца.** Это не настройка выкладки, а решение о первой боевой записи живого продавца.
Порядок:

1. Записать решение: кто решил, когда, для какого аккаунта и витрины. Строка — в `docs/decisions.md` или в доказательствах шага боевого
   запуска. Предусловия — чеклист «День перевода в бой» ([docs/live-first-account-checklist.md](../../docs/live-first-account-checklist.md)):
   неделя тени, граница суток amazon.com принята оператором [Р-204].
2. **Путь записи** (шаг 141) — брокер и процесс пути решения. Страж ещё стоит, поэтому ничего не уходит:
   - на машине владельца — проверка процесса во внешнем сервисе и её адрес на сервер:

     ```sh
     HC_API_KEY="$(cat "$HOME/.config/repracer/secrets/healthchecks-api-key")" node scripts/setup-heartbeats.mjs --stand pilot --write-path   # ключ — файлом, как в §9
     deploy/pilot/push-secrets.sh deploy@<сервер>
     ```
   - на сервере — `REPRACER_PILOT_WRITE_PATH=on` в `pilot.env`, затем `deploy/pilot/compose.sh up -d --wait` и `deploy/pilot/smoke.sh`. Смоук
     зелёный со строкой «путь записи: брокер и процесс пути решения работают». Без адреса отметки процесса выкладка и смоук откажут
     (`heartbeat-state.sh`).
3. Снять стража явным значением, а не `RESET`. Без значения выкладка откажет, потому что не отличит решение от ошибки:

   ```sh
   set -a; . deploy/pilot/pilot.env; set +a   # имя базы — REPRACER_PILOT_DB
   deploy/pilot/compose.sh exec -T -u postgres postgres psql -X -c "ALTER DATABASE ${REPRACER_PILOT_DB} SET repracer.live_writes = 'allowed'"
   ```

4. Перевод аккаунта в бой делает владелец тенанта в консоли: второй фактор и набранное имя аккаунта [Р-170].
5. Вернуть стража — одной командой, в любой момент. Новые записи не уйдут, уже ушедшие не отзываются:

   ```sh
   deploy/pilot/compose.sh exec -T -u postgres postgres psql -X -c "ALTER DATABASE ${REPRACER_PILOT_DB} SET repracer.live_writes = 'forbidden'"
   ```

   Путь записи после этого можно оставить: при стоящем страже процесс ничего не отправляет. Выключить —
   `deploy/pilot/compose.sh --profile live stop worker redpanda`, затем `REPRACER_PILOT_WRITE_PATH=off` в `pilot.env`.

## 7. Путь пилота

1. Оператор открывает панель туннелем: `ssh -L 4327:127.0.0.1:4327 deploy@<сервер>`, затем `http://127.0.0.1:4327`.
2. В панели «New pilot» создаёт тенант (регион US, язык en), затем «Invite the owner».
3. Панель показывает ссылку приглашения **один раз** (Р-245, [ADR-0075](../../docs/adr/0075-invite-link-reveal.md)). Оператор передаёт её
   владельцу не открытым каналом.
4. Владелец входит у ZITADEL, проходит онбординг и нажимает «Connect Amazon»: аккаунт рождается в тени.
5. Каталог приходит отчётом листингов. Если отчёт не готов за заход, продолжение идёт через 5–40 минут, а не через час (шаг 122).
6. Себестоимость с комиссией, границы, стратегия, включение — решения тени.

## 8. Копии базы (шаг 126)

Решение владельца: копии — в составе пилота до запуска, пилот без них не стартует; копия без проверенного восстановления копией не
считается; ничего не покупаем. Три части, и смоук требует все три (`backup-state.sh`):

1. **Копия.** Сервис `backup` раз в сутки снимает `pg_dump` базы пилота и роли кластера и сразу шифрует их открытым ключом владельца
   (`deploy/production/backup-loop.sh`, тот же скрипт, что у промышленного профиля). На сервере — только шифротекст и только 7 суток (данные
   каналов не переживают свой срок в копиях, [docs/data-retention.md](../../docs/data-retention.md)). Провал — отметка `BACKUP_FAILED`.
2. **Вынос с сервера** — `REPRACER_BACKUP_OFFSITE` в `pilot.env`. **Пилот — `pull`** (решение владельца 2026-11-14): R2 не включаем —
   при включении Cloudflare может попросить способ оплаты, а любые возможные списания — только с одобрения Мердана; пересмотр — при go-live.
   - `r2` — сейчас не используется. Cloudflare R2, бесплатный уровень (10 GB-month, снимок [vendor/cloudflare/r2/2026-11-14](../../vendor/cloudflare/r2/2026-11-14/SOURCE.md)).
     Бакет, токен «Object Read & Write» только на него; ключи — файлами `backup_r2_access_key_id` и `backup_r2_secret_access_key` в
     каталоге секретов (на машине владельца, затем `push-secrets.sh`); `REPRACER_BACKUP_R2_BUCKET_URL=https://<бакет>.<ACCOUNT_ID>.r2.cloudflarestorage.com`.
     Сервис `backup-offsite` выносит каждую готовую копию, сверяет длину в бакете и только тогда ставит отметку `.offsite`; в бакете копии
     тоже живут 7 суток. Попросит ли Cloudflare способ оплаты для включения R2 — проверить при включении; любые возможные списания — с
     одобрения Мердана.
   - `pull` (выбор пилота) — машина оператора забирает копии сама, раз в сутки:

     ```sh
     deploy/pilot/pull-backups.sh deploy@<сервер>           # в $HOME/.config/repracer/backups/pilot, SHA-256 каждой копии, 7 суток
     ```

     Ежедневно — `launchd` (macOS) или `cron`; машина спала — следующий запуск заберёт всё пропущенное. Тем же проходом выносятся журналы
     в `…/backups/pilot/logs` (§10, шаг 133).

     **Когда смоук краснеет из-за выноса.** Смоук требует на сервере отметку `OFFSITE_PULLED`, в которой последняя вынесенная копия не старше
     26 часов. Значит, смоук красный, если машина оператора не забрала копию дольше суток, — в том числе если она выключена, спит или без сети.
     Выключена дольше 7 суток — хуже: копии старше 7 суток сервер удаляет раньше, чем их заберут, и вне сервера их уже не будет. Смоук идёт при
     выкладке (`deploy.sh`) и вручную. Между выкладками пропуск выноса замечает внешняя проверка: `pull-backups.sh` отмечается после
     каждого прохода, а молчание 26 часов даёт письмо (§9). Отметка `OFFSITE_PULLED` записывает, был ли вынос под этим контролем, и
     смоук без него красный.
3. **Проверка восстановления** — на сервере, в одноразовом контейнере без сети: закрытый ключ — со стандартного ввода, копия
   восстанавливается во временный PostgreSQL тем же `deploy/production/restore.sh`, что при настоящей беде; проверяются регион, страж
   боевых записей [Р-247] (копия, потерявшая его, подняла бы базу с разрешённой записью), журнал миграций и числа:

   ```sh
   ssh deploy@<сервер> 'cd /srv/repracer && deploy/pilot/restore-check.sh' < "$HOME/.config/repracer/secrets/pilot-backup-private.asc"
   ```

   Смоук требует отметку проверки у одной из хранимых копий, то есть **не реже раза в 7 суток** — и после каждой смены ключа.

**Ключ копий** создаётся один раз. Закрытый ключ — только у владельца, вне каталога секретов пилота (`push-secrets.sh` откажет, найдя его
там; выкладка откажет, найдя его на сервере). Если на машине владельца есть GnuPG — команды [deploy/production/README.md](../production/README.md)
(«Шифрование копии»), открытый ключ — в `$HOME/.config/repracer/secrets/pilot/backup_public_key.asc`. Если нет — пара рождается в памяти
одноразового контейнера на сервере, открытый ключ ложится в каталог секретов сервера, закрытый уходит по SSH владельцу:

```sh
ssh deploy@<сервер> 'cd /srv/repracer && deploy/pilot/backup-key.sh' > "$HOME/.config/repracer/secrets/pilot-backup-private.asc"
chmod 600 "$HOME/.config/repracer/secrets/pilot-backup-private.asc"     # и вторую копию — в сейф владельца
```

Новый сервер со старым ключом — `deploy/pilot/backup-key.sh --public` с закрытым ключом на стандартном вводе.

**Настоящая беда** (сервер потерян): новый сервер по §2–5, затем восстановление копии — [docs/runbook-disaster.md](../../docs/runbook-disaster.md)
и `deploy/production/restore.sh` с закрытым ключом; копия берётся из R2 или с машины оператора. Теряется всё после последней копии
(до суток): восстановления на момент времени нет.

**ClickHouse в пилоте не копируется** (решение владельца). Гибель его тома уносит выгруженную историю — наблюдения, снимки конкурентов
[Р-122] и завершённые записи [Р-20] — с подключения по день гибели. Цены от этого не страдают: решение о цене ClickHouse не читает [Р-22],
суточная свёртка наших цен [Р-21] живёт в PostgreSQL и в копии.

## 9. Внешний контроль (шаг 129)

Решение владельца 2026-11-15: процесс, который остановился, о себе не сообщит [Р-127], поэтому пилот контролируется снаружи. Письмо
шлют сами внешние сервисы на адрес своего аккаунта, наша почта для этого не нужна. Пилот без отметок не выкладывается:
`deploy.sh` и `smoke.sh` спрашивают `heartbeat-state.sh`, а строка `REPRACER_*_HEARTBEAT=off` в `pilot.env` — отказ.

| Проверка | Кто отмечается | Период / допуск | Письмо значит |
|---|---|---|---|
| `repracer-pilot-scheduler` | планировщик, раз в минуту; «сбой» при проваленном такте | 2 мин / 3 мин | процесс стоит, такты проваливаются (например, нет базы), сервер или его сеть недоступны |
| `repracer-pilot-console` | консоль, раз в минуту | 2 мин / 3 мин | процесс консоли стоит |
| `repracer-pilot-operator` | панель, раз в минуту | 2 мин / 3 мин | панель стоит |
| `repracer-pilot-bulk-worker` | исполнитель заданий, раз в минуту | 2 мин / 3 мин | импорты и выгрузки не идут |
| `repracer-pilot-backup` | `backup-heartbeat` — после каждой готовой копии; «сбой» — при `BACKUP_FAILED` | 1 сут / 2 ч | копия не снята 26 часов или проваливается |
| `repracer-pilot-logs` | `deploy/pilot/logs-archive.sh` — после каждого захода архива журналов; «сбой» — при провале (§10) | 1 сут / 2 ч | журналы не выгружались 26 часов или выгрузка проваливается |
| `repracer-pilot-pull` | `pull-backups.sh` на машине оператора — после каждого прохода (копии и журналы, §10); «сбой» — при красном | 1 сут / 2 ч | копии или журналы не выносились 26 часов: машина оператора выключена, спит, без сети или вынос красный |
| `repracer-pilot-worker` | процесс пути решения — только с путём записи (§6, `setup-heartbeats.mjs --write-path`), раз в минуту | 2 мин / 3 мин | диспетчер записей стоит: записи не уходят и не подтверждаются |
| UptimeRobot: `https://app.<домен>/healthz` | внешний монитор сам ходит по адресу раз в 5 минут, ищет `"status":"ok"` | — | консоль недоступна снаружи: туннель, DNS, Cloudflare, сервер |

Отметки процессов не видят, доступна ли консоль снаружи. Монитор не видит процессов за туннелем. Поэтому нужны оба сервиса.
Факты сервисов — [vendor/healthchecks](../../vendor/healthchecks/2026-09-17/SOURCE.md), [vendor/uptimerobot](../../vendor/uptimerobot/2026-11-14/SOURCE.md).

**Что сделать Кериму** (оба аккаунта бесплатные; любые платные уровни — только через Мердана):

1. **healthchecks.io** — аккаунт на бесплатном плане Hobbyist (20 проверок; пилот берёт 7, с путём записи — 8, QA-B — ещё 7). В проекте:
   - Settings → API Access → ключ API с правом записи;
   - **интеграция Email добавляется в проект руками**: Integrations → Email → адрес получателя (если сервис попросит — подтвердить по
     ссылке из письма). Сама она не появляется: в проекте пилота 2026-11-15 интеграций не было ни одной. Проверки получают все
     интеграции проекта, а без интеграций — ни одного получателя. Поэтому `setup-heartbeats.mjs` без интеграций отказывает и ничего не
     заводит, а после заведения сверяет, что получатель есть у каждой проверки (шаг 134).
   - Второй получатель — ещё одна интеграция Email в проекте и повторный запуск п. 2: он обновит те же проверки.
2. На машине владельца — проверки и адреса. Ключ API не вставляется в команду (он остался бы в истории оболочки) и не пересылается в чат:
   он кладётся в файл, который после запуска удаляется.

   ```sh
   umask 077; pbpaste > "$HOME/.config/repracer/secrets/healthchecks-api-key"   # ключ скопирован из Settings → API Access
   HC_API_KEY="$(cat "$HOME/.config/repracer/secrets/healthchecks-api-key")" node scripts/setup-heartbeats.mjs --stand pilot   # 7 проверок; адреса — файлами 600, в вывод не попадают
   rm "$HOME/.config/repracer/secrets/healthchecks-api-key"
   deploy/pilot/push-secrets.sh deploy@<сервер>                         # шесть адресов — на сервер
   ```

   Адрес выноса ложится в `$HOME/.config/repracer/secrets/pilot-pull-heartbeat-url`, его читает `pull-backups.sh`. Если копии выносит не
   эта машина, файл переносится на машину оператора. После запуска ключ не нужен.
3. **UptimeRobot** — сейчас только аккаунт на бесплатном плане (50 мониторов, интервал 5 минут, коммерческое использование разрешено).
   Монитор — при первой выкладке, п. 4.
4. Выкладка (§5). Когда `https://app.<домен>/healthz` отвечает — монитор UptimeRobot (решение владельца 2026-11-15: раньше он слал бы
   письма о «падении» адреса, которого ещё нет). New monitor:
   - тип **Keyword**;
   - адрес `https://app.<домен>/healthz`;
   - ключевое слово `"status":"ok"`, тревога — **Keyword not exists**;
   - интервал 5 минут;
   - получатель — адрес аккаунта.
5. Проверка живьём, один раз:
   - остановить процесс (`deploy/pilot/compose.sh stop scheduler`) — письмо healthchecks.io примерно через 5 минут, затем `start`;
   - остановить `cloudflared` — письмо UptimeRobot за 5–10 минут.

   Время до письма — в доказательства первой выкладки.

**Чего этот контроль не видит:**
- **Алерты из базы** (CRITICAL продавца, отставание выгрузки и прочие из `tenant_data.alert`) по-прежнему не доходят ни до кого: почты нет,
  в базе отметка `DRY_RUN` (OQ-224). Их видно только в панели оператора. Почта отложена до выбора провайдера.
- **ClickHouse** — только через планировщик: такт, который не может выгрузить сутки, поднимает алерт в базе, а не «сбой» отметки.
- **Проверка восстановления** (не реже раза в 7 суток, §8) — только смоуком при выкладке.

## 10. Журналы ≥ 12 месяцев (шаг 130)

Требование Amazon DPP, решение владельца 2026-11-15: обязательно до подключения продавца. Пилот берёт тот же скрипт, что промышленный
профиль ([deploy/production/logs-archive.sh](../production/logs-archive.sh), README промышленного профиля, «3в»). Обёртка
[logs-archive.sh](logs-archive.sh) называет проект `repracer-pilot` и каталоги из `pilot.env`.

- **Горячий хвост.** Журналы всех контейнеров пилота (`docker compose -p repracer-pilot logs`) идут сутками в
  `REPRACER_LOGS_HOT_DIR/repracer-pilot/<день>.log.gz`, хвост — от 30 до 61 суток. Пропущенные сутки догоняются от отметки «выгружено по».
- **Месячные архивы.** Месяц, вышедший из окна, становится одним файлом `REPRACER_ARCHIVE_DIR/platform=logs/repracer-pilot/<ГГГГ-ММ>.log.gz` с
  суммой SHA-256 и хранится 13 месяцев, то есть не меньше 12.
- **Каждый день.** Строка crontab пользователя `deploy` в 00:20 по часам сервера (`logs-cron.sh`). sudo у него нет, поэтому не таймер
  systemd. Вывод захода — в системный журнал: `journalctl -t repracer-pilot-logs-archive`.
- **Выкладка.** Журнал контейнера уходит вместе с контейнером, а `up` пересоздаёт контейнеры с изменённой настройкой. Поэтому `deploy.sh`
  выгружает журналы по сей момент ДО первого `up`, а провал выгрузки останавливает выкладку. После подъёма — ещё раз, и ставит строку crontab.
- **Вынос с сервера** (шаг 133, решение владельца 2026-11-15: требование DPP «12 месяцев» не должно умирать вместе с сервером). Тот же
  `pull-backups.sh` на машине оператора, тем же ежедневным проходом, что копии (§8), кладёт журналы в `…/backups/pilot/logs`:
  - месячные архивы с их суммой SHA-256, 13 месяцев, как на сервере;
  - законченные сутки горячего хвоста: сутки раньше отметки «выгружено по», их файл больше не меняется. Сумма считается на сервере.

  Каждый файл сверяется до того, как его примут. Сутки месяца, который пришёл архивом, удаляются: архив содержит их целиком. После прохода
  на сервере остаётся отметка `LOGS_PULLED`. Гибель сервера теперь уносит только журналы с последнего прохода и текущих суток.
- **Контроль.** Каждый заход отмечается во внешнем сервисе (`repracer-pilot-logs`, §9), вынос — отметкой `repracer-pilot-pull`. Смоук
  (`logs-state.sh`) требует:
  - строку crontab;
  - отсутствие отметки `LOGS_ARCHIVE_FAILED`;
  - выгрузку не старше 26 часов;
  - вынос не старше 26 часов и под внешним контролем (`LOGS_PULLED`).

Чего здесь нет:
- **Записи без ротации контейнера.** Журнал каждого контейнера — 50 МБ × 5 файлов. Если контейнер напишет больше 250 МБ за сутки, выгрузка
  застанет его не целиком. Сколько пишут процессы пилота, покажет первая неделя.
- Секретов и данных покупателей в журналах нет: токены и тела запросов процессы не пишут [Р-177], PII не храним [Р-4].

## 11. Откат (шаг 131)

Решение владельца 2026-11-15, п. 3.3. Откат — к прежней версии кода, одной командой с машины владельца:

```sh
ssh deploy@<сервер> 'cd /srv/repracer && deploy/pilot/rollback.sh [<SHA прежней версии>]' < "$HOME/.config/repracer/secrets/pilot-backup-private.asc"
```

Без SHA — к версии, с которой ушла последняя выкладка (`deploy/pilot/state/releases.log`). Повторный откат без SHA отменяет предыдущий.

Миграцию назад не откатить: в репозитории миграции только вперёд, а код прежней версии к базе после миграции не подходит. Поэтому у отката
два пути, и скрипт выбирает сам по плану миграций (`migrate.sh --check`):

1. **Между версиями нет миграций.** Откат — обычная выкладка прежней версии (`deploy.sh <SHA>`). База не трогается, ничего не теряется.
2. **Выкладка применила миграции.** База новее прежней версии: `deploy.sh <SHA>` сам откажет до переключения рабочей копии.
   `rollback.sh` делает так:
   - останавливает процессы, кроме базы. Внешний контроль пришлёт письма о молчании — это ожидаемо;
   - восстанавливает на место живой базы копию, снятую перед миграциями этой выкладки. Её находит отметка
     `repracer-<время>.pre-release` («ушли с версии X»). Работает одноразовый контейнер сервиса `backup` тем же `deploy/production/restore.sh`,
     что при беде (`rollback-inner.sh`);
   - выкладывает прежнюю версию.

   До того как тронуть живую базу, проверяются суммы копии и ключ: чужой ключ или испорченная копия — отказ, база как была. Живая база не
   удаляется, а откладывается под именем `<база>_rb_<время копии>`. Провал восстановления возвращает её на место.

**Что теряется во втором случае:** всё, что записано после копии перед выкладкой. Это решения тени, импорты и правки продавца, подключения
каналов. Записанное не пропадает молча: оно остаётся в отложенной базе, и его можно найти запросом. Отложенная база занимает место на диске.
После проверки её удаляет владелец:

```sh
deploy/pilot/compose.sh exec -T -u postgres postgres psql -X -c 'DROP DATABASE <база>_rb_<время копии>'
```

Копии перед выкладкой живут 7 суток, как суточные. Откат через миграцию позже — только суточной копией, по имени
(`rollback-inner.sh` принимает `repracer-<время>`); потери — до её времени.

**Проверено** учением «N → N+1 с миграцией → откат» в сборке (`scripts/test/pilot-db.test.ts`, теми же скриптами на настоящем
PostgreSQL). Выкладка N+1 даёт план с одной миграцией, затем копию до неё, миграцию и данные после выкладки. Код N отказывает «база новее
кода». После отката:
- база снова на журнале N, схема N+1 исчезла;
- записанное до выкладки на месте, записанное после — в отложенной базе;
- страж боевых записей вернулся;
- выкладка N поверх не применяет ничего.

Остановку процессов и одноразовый контейнер на сервере (`rollback.sh`) пройдёт первая репетиция на QA-B.

## 12. QA-B (шаг 132)

Решения владельца 2026-11-15:
- QA-B — этот же `deploy/pilot` на временной машине, и он же первая генеральная репетиция выкладки пилота;
- перед QA-B стоит Cloudflare Access: внутренний стенд с настоящими токенами. Пилот остаётся без Access;
- копии проходятся целиком, как репетиция, без исключений для QA;
- аккаунт продавца Amazon для QA-B — владелец с Мерданом. Машину покупают с одобрения Мердана.

Код QA-B — код пилота. Отличаются настройки, секреты и внешние шаги:

| Что | Пилот | QA-B |
|---|---|---|
| `REPRACER_PILOT_STAND` в `pilot.env` | `pilot` | `qa-b` — первая сборка отмечает им базу, сброс работает только на ней |
| `REPRACER_PILOT_HOST` | `app.<домен>` | `qa-b.<домен>` |
| Секреты на машине владельца | `$HOME/.config/repracer/secrets/pilot` | `REPRACER_PILOT_LOCAL_SECRETS=$HOME/.config/repracer/secrets/qa-b` у `secrets.sh` и `push-secrets.sh` |
| Ключ копий | `pilot-backup-private.asc` | свой: `backup-key.sh` на машине QA-B → `qa-b-backup-private.asc` |
| Внешний контроль (§9) | `setup-heartbeats.mjs --stand pilot` | `--stand qa-b`: свои 7 проверок; адрес выноса — `$HOME/.config/repracer/secrets/qa-b-pull-heartbeat-url` |
| Вынос копий и журналов (§8, §10) | `pull-backups.sh deploy@<пилот>` | `REPRACER_PILOT_BACKUP_PULL_DIR=$HOME/.config/repracer/backups/qa-b REPRACER_PILOT_PULL_HEARTBEAT_URL_FILE=$HOME/.config/repracer/secrets/qa-b-pull-heartbeat-url deploy/pilot/pull-backups.sh deploy@<QA-B>`; журналы — в `backups/qa-b/logs` |
| Монитор `/healthz` снаружи | UptimeRobot | не заводится (решение владельца 2026-11-15): за Access монитор видит только страницу входа, а обход Access ослабил бы защиту внутреннего стенда ради временной витрины. QA-B хватает отметок процессов |
| Cloudflare Access | нет | да, как у QA-A ([deploy/qa/README.md](../qa/README.md)): приложение на `qa-b.<домен>`, политика — адреса тестировщиков, One-time PIN, проверка Access на туннеле (`originRequest.access`); Access — раньше DNS |
| Сброс базы | нет и не бывает | `deploy/pilot/reset.sh` |

**Внешние шаги в день одобрения:**
1. **Машина** — подготовка хоста по §2.
2. **Cloudflare** — туннель `repracer-qa-b` (`qa-b.<домен>` → `http://console:4319`), приложение Access и CNAME. Порядок и API — как у
   QA-A.
3. **ZITADEL** — приложения консоли и панели QA-B: адрес возврата консоли `https://qa-b.<домен>/auth/callback`, остальное — по §1.
4. **Amazon** — у приложения TMPrice добавить Redirect URI `https://qa-b.<домен>/connect/callback` и Login URI `https://qa-b.<домен>/connect/amazon/login`.
   Адрес согласия не передаёт `redirect_uri`: Amazon берёт первый зарегистрированный (§1). Пока у приложения один Login URI (проверить), QA-B
   и пилот подключают продавца по очереди: перед подключением на QA-B его адреса ставятся первыми, перед пилотом — адреса пилота.
5. **Секреты, контроль, выкладка** — §4, §9 с `qa-b`, затем `deploy/pilot/deploy.sh <SHA> --first-time`. Первая выкладка кончается красной
   строкой копий, как у пилота (§5, §8).
6. **ZITADEL на месте** (решение владельца 2026-11-16: проверка — в день развёртывания): вход в панель туннелем (§7, п. 1). Если ZITADEL не
   принимает адрес возврата `http://127.0.0.1:4327/auth/callback` вне режима разработки — записать ответ и доложить владельцу: панель без входа
   не заведёт тенанта.
7. **Шлюз SSH тестировщика** — как у QA-A ([deploy/qa/README.md](../qa/README.md)): ровно три команды без оболочки (`deploy/pilot/ssh-gate.sh`).
   Открытый ключ Мердана — одной строкой в `~deploy/.ssh/authorized_keys` машины QA-B:

   ```
   command="/srv/repracer/deploy/pilot/ssh-gate.sh",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA… merdan
   ```

   - `ssh deploy@<машина QA-B> logs` — последние 500 строк консоли, планировщика, исполнителя заданий и панели и итог последнего сброса;
   - `ssh deploy@<машина QA-B> reset` — сброс базы QA-B (ниже). Идёт в фоне под журналом и переживает обрыв SSH; повтор во время работы
     показывает её журнал. Шлюз отказывает в сбросе, если `pilot.env` говорит не `qa-b`;
   - `ssh deploy@<машина QA-B> version` — какая сборка работает.

   На пилоте шлюз не ставится.

**Сброс базы QA-B** — одной командой на машине QA-B:

```sh
deploy/pilot/reset.sh
```

Порядок:
1. журналы по сей момент;
2. остановка процессов, кроме базы;
3. копия перед сбросом — ошибочный сброс восстанавливается, как беда;
4. новая база (`db.sh --reset-qa-b`).

Новая база собирается под именем `<база>_next` со стражем, прежняя целая до замены. Повтор после обрыва между удалением и переименованием
доводит замену. Сброс отказывает, если `pilot.env` или сама база говорят не `qa-b`. На пилоте он отказывает первой строкой, до любой команды
Docker. ClickHouse не сбрасывается: выгруженная история прежних тенантов живёт свой срок, консоль и решение о цене её не читают [Р-22].
После сброса онбординг — заново: тенант и приглашение из панели (§7).

**Когда QA-B больше не нужен:**
- машина удаляется;
- туннель, DNS и приложение Access `qa-b` удаляются;
- проверки `repracer-qa-b-*` в healthchecks.io удаляются;
- Redirect URI и Login URI QA-B у приложения Amazon и приложения QA-B в ZITADEL удаляются;
- на машине владельца удаляются каталоги `secrets/qa-b`, `backups/qa-b` и ключ `qa-b-backup-private.asc`.
