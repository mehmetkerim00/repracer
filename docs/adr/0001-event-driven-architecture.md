# ADR-0001: Событийная архитектура ядра

- **Статус:** Proposed · брокер выбран в [ADR-0005](0005-message-broker.md), слои хранения — [ADR-0004](0004-storage-tiering.md)
- **Дата:** 2026-09-14
- **Связанные документы:** [domain-model.md](../domain-model.md), [open-questions.md](../open-questions.md)

## Контекст

Продукт реагирует на изменения во внешних системах (цены конкурентов, заказы, остатки) и пишет изменения
обратно в четыре канала. Определяющий фактор архитектуры — **лимиты API**, а не нагрузка на наши серверы.

### Известные лимиты

| Канал / операция | Лимит | Источник |
|---|---|---|
| Amazon `getCompetitiveSummary` | 0.033 req/sec, burst 1 | Требования проекта |
| Amazon — единица лимитирования | Пара «продавец × приложение» на операцию | Документация SP-API (проверить для каждой операции) |
| Amazon `ANY_OFFER_CHANGED` | Push через SQS | Документация SP-API |
| Amazon Listings Items / Feeds / Product Fees | Отдельные лимиты, в т.ч. асинхронная обработка фидов | Проверить |
| Otto Market API | ~10 req/sec; токен OAuth2 client credentials на 60 мин | Требования проекта |
| eBay | Низкие дефолтные лимиты до Application Growth Check; часть лимитов — на приложение, т.е. общие для всех тенантов | Требования проекта; числа проверить через Developer Analytics API |
| Kaufland | Неизвестно | Открытый вопрос |

### Расчёт: почему поллинг конкурентов на Amazon невозможен

- 0.033 req/sec ≈ **1 запрос в 30 секунд ≈ 2 880 запросов в сутки** на пару продавец × приложение.
- Пример: продавец с 10 000 SKU на 5 маркетплейсах EU = 50 000 пар (ASIN, маркетплейс).
  - По одному элементу на запрос: полный цикл ≈ **17 суток**.
  - Даже при пакете до 20 элементов на запрос (проверить): ≈ **0,9 суток** на цикл.
- Цены конкурентов в Buy Box меняются в пределах минут. Данные с задержкой в сутки бесполезны
  и опасны для репрайсинга.
- Лимит привязан к продавцу, а не к нашему серверу: **горизонтальное масштабирование не помогает.**

Вывод: изменения у конкурентов можно получать только через **нотификации**, а pull-запросы оставить
на редкие точечные случаи.

### Другие свойства среды

- **Всплески:** популярный ASIN порождает серии `ANY_OFFER_CHANGED` за секунды; импорт каталога или
  распродажа порождает десятки тысяч событий у одного тенанта.
- **Асинхронные записи:** часть каналов обрабатывает изменения фидами/задачами, подтверждение приходит позже
  и не обязательно в порядке отправки.
- **Общие квоты:** лимиты eBay уровня приложения делятся между всеми тенантами, и один тенант может исчерпать квоту для всех.
- **Токены с коротким сроком жизни** (Otto — 60 мин) требуют централизованного обновления.
- **Доставка нотификаций не гарантирована во всех случаях** (подписка может слететь, сообщения — дублироваться).
- **Omnibus / §11 PAngV** требует точной истории цен по каналу, т.е. хронологии фактов изменения.

## Решение

Ядро системы строится как **событийный конвейер** с долговременным хранением сообщений.

1. **Push по умолчанию.** Изменения у конкурентов на Amazon поступают только из нотификаций. Pull-запросы
   (`getCompetitiveSummary` и аналоги) допускаются только для первичного заполнения при подключении и
   точечной сверки, в пределах явного бюджета токенов на аккаунт.

2. **Этапы — независимые потребители событий:**
   `Ingest → Normalize → Strategy → Price Gate → Dispatch → Confirm`, а для остатков
   `Ingest → Reservation/Stock → Allocation → Dispatch → Confirm`.
   Каждый этап читает событие, изменяет своё состояние и публикует следующее событие.

3. **Семантика доставки: at-least-once + идемпотентные потребители.** Exactly-once не предполагается.
   Идемпотентность — через `source_event_id`, `idempotency_key` и версии (INV-03).

4. **Единственная точка выхода в каналы — Dispatcher.** Никакой другой компонент не вызывает API каналов на запись.
   Dispatcher:
   - держит token bucket на `(channel_account, operation)` и отдельно на квоты уровня приложения;
   - схлопывает очередь по `(offer, field)`: отправляется только последняя версия
     *(уточнено [ADR-0002](0002-write-scope-per-field.md): по `write_scope_id`)*;
   - учитывает дневные бюджеты правок объекта канала (eBay: 250 правок листинга в день) *(добавлено после Р-2)*;
   - объединяет записи в пакеты/фиды, где канал это поддерживает;
   - выполняет финальную проверку floor непосредственно перед сетевым вызовом (INV-02);
   - соблюдает правило «одна in-flight запись на `(offer, field)`».

5. **Ключ упорядочивания:** `(tenant_id, channel_account_id, offer)` для событий цены и остатка
   *(уточнено [ADR-0002](0002-write-scope-per-field.md): `(tenant_id, write_scope_id)`)*. Порядок
   сохраняется в пределах оффера, обработка разных офферов — параллельна.

6. **Справедливость между тенантами.** Очереди и квоты учитывают тенанта (взвешенная справедливая очередь).
   Всплеск одного тенанта не задерживает остальных; общая квота уровня приложения делится по тенантам.

7. **Схлопывание входящих всплесков.** Серия событий по одному офферу в коротком окне приводит к одному
   расчёту стратегии по последнему снимку. Размер окна — параметр (открытый вопрос о целевой задержке).

8. **Transactional outbox.** Изменение состояния и публикация события — атомарны.

9. **Сверка как обязательная часть конвейера.** Периодические отчёты каналов (дешёвые по квоте) выявляют
   пропущенные нотификации и изменения, сделанные вне системы.

10. **Конверт события:** `tenant_id`, `event_id`, `event_type`, `schema_version`, `occurred_at`,
    `correlation_id`, `causation_id`. Полезная нагрузка без PII и секретов. Потребитель проверяет `tenant_id`.

11. **Event sourcing — только там, где история и есть предметная область:** PriceHistory, жизненный цикл
    `ChannelWrite`, AuditEvent. Остальные сущности — обычное хранение состояния + outbox.

### Что не решается этим ADR

- Выбор брокера/очередей и хранилищ.
- Топология развёртывания. Событийная архитектура **не означает** микросервисы; модульный монолит с
  долговременной очередью совместим с этим решением.
- Механизм изоляции тенантов в хранилище.

## Рассмотренные альтернативы

### A. Периодический поллинг + синхронные вызовы по расписанию
Отклонено. Для Amazon математически невозможно (расчёт выше). Для eBay общая квота приложения исчерпывается
ростом числа тенантов. Нет буфера при всплесках, нет естественного места для схлопывания и приоритезации.

### B. Синхронные запросы между компонентами с ретраями
Отклонено. Rate limit канала превращается в каскад таймаутов; ретраи усиливают нагрузку на уже
лимитированный API; при падении компонента теряются необработанные изменения.

### C. Полный event sourcing всех агрегатов
Не принято. Усложняет модель, миграции схем и удаление данных по срокам DPP (удаление событий из журнала
противоречит самой идее). Применяем точечно (п. 11).

## Последствия

### Положительные
- Расход квот каналов контролируется в одной точке; всплески поглощаются очередью.
- Защита цены (floor) и версионирование сосредоточены в исходящем конвейере и не зависят от стратегий.
- Естественная хронология для PriceHistory и аудита.
- Изоляция сбоев: недоступность одного канала не останавливает остальные.
- Повторная обработка (replay) возможна без повторной отправки в канал благодаря версиям и идемпотентности.

### Отрицательные
- **Eventual consistency:** цена в канале отражает изменение у конкурента через секунды–минуты, не мгновенно.
  Нужен явный SLA.
- Сложнее отладка → обязательны `correlation_id`, трассировка, метрики лагов по тенанту и каналу, DLQ.
- Эволюция схем событий требует версионирования и контрактных тестов.
- Тестирование требует симуляторов каналов с реалистичными лимитами и асинхронностью.
- Хранение в брокере подпадает под сроки DPP: retention топиков ограничен, полезная нагрузка без PII.
- Больше операционных компонентов, чем у CRUD-приложения.
