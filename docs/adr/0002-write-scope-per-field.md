# ADR-0002: Единица записи определяется для каждого поля (WriteScope)

- **Статус:** Accepted (следует из решений Р-1, Р-2)
- **Дата:** 2026-09-14
- **Уточняет:** [ADR-0001](0001-event-driven-architecture.md), п. 4–5 (ключи схлопывания и упорядочивания)
- **Связанные документы:** [decisions.md](../decisions.md), [domain-model.md](../domain-model.md), [channel-capabilities.md](../channel-capabilities.md)

## Контекст

В модели v0.1 `OfferMapping` (оффер на маркетплейсе) был единицей всего: версии записи, ключа идемпотентности,
схлопывания очереди, водяных знаков и истории цен. Неявное допущение — **одно поле оффера живёт там же, где сам оффер**.

Принятые решения показывают, что это неверно:

| Канал | Цена живёт на… | Остаток живёт на… | Лимит правок считается на… |
|---|---|---|---|
| Amazon EU | SKU **в маркетплейсе** [Р-1] | SKU **в регионе**, одно значение на все маркетплейсы, last write wins [Р-1] | — |
| eBay (Inventory API) | оффере в маркетплейсе (проверить) | товаре инвентаря или оффере (проверить) | **листинге**, 250 правок в день [Р-2] |
| Kaufland | unit на витрине (проверить) | unit на витрине (проверить) | ? |
| Otto | SKU | SKU | ? |

Kaufland и Otto — вырожденный случай, где единицы совпадают. Amazon и eBay — нет.

### Что ломается при общей единице

**Вариант «единица = оффер в маркетплейсе» (как в v0.1), Amazon, SKU на .de и .fr:**
1. Остаток SKU — одно физическое значение, но у него появляются две независимые последовательности версий.
2. Оффер .fr пересчитан по старым данным (версия 7 своей последовательности), оффер .de — по свежим (версия 3 своей).
   Обе записи проходят проверку «версия не устарела», потому что сравниваются в разных последовательностях.
3. Last write wins на стороне Amazon: побеждает та, что пришла позже, — возможно, устаревшая. **INV-03 нарушен молча.**
4. Схлопывание не срабатывает (разные ключи): два вызова вместо одного, двойной расход квоты.
5. Наблюдение остатка с .de «расходится» с отправкой для .fr — ложные расхождения и `REASSERT`-войны сами с собой.
6. Буфер канала применяется дважды или неоднозначно.

**Вариант «единица = SKU в аккаунте/регионе» для всех полей:**
1. Цена Amazon задаётся по маркетплейсу; одна цена на регион невозможна по смыслу.
2. История цен по маркетплейсу (Omnibus / §11 PAngV — «по каждому каналу») становится невозможной.
3. Floor и стратегия не могут различать маркетплейсы.

**eBay — третья, независимая единица:** бюджет 250 правок считается на листинг и делится между ценой, остатком и
(вероятно) всеми вариациями. Единица бюджета не совпадает ни с единицей цены, ни с единицей остатка. Её нельзя
«пришить» ни к офферу, ни к полю.

**Вывод:** любая общая единица либо нарушает инвариант версий, либо теряет обязательную гранулярность цены.
Единица записи — свойство пары **(канал, поле)**, а не оффера.

## Решение

1. Вводится `WriteScope` — единица записи **одного поля** в канал. `OfferMapping` остаётся только сопоставлением
   «оффер канала ↔ товар» и ссылается на свой `WriteScope` для каждого поля.

2. Правило построения ключа — **данные** в `ChannelCapability` (`write_scope_kind`, `write_scope_key_template`),
   а не условия в коде адаптеров. Ядро не знает имён каналов при вычислении ключей.

3. Из `write_scope_id` выводятся:

   | Ключ | Было (v0.1) | Стало |
   |---|---|---|
   | Последовательность версий | `(offer_mapping, field)` | `write_scope_id` |
   | Идемпотентность | `hash(tenant, account, marketplace, offer_key, field, version)` | `hash(tenant, account, field, scope_key, version)` |
   | Схлопывание / in-flight | `(offer, field)` | `write_scope_id` |
   | Упорядочивание событий | `(tenant, account, offer)` | `(tenant, write_scope_id)` |
   | Водяные знаки | `OfferSyncState(offer, field)` | `WriteScopeSyncState(write_scope_id)` |
   | Наблюдаемое состояние | — | `ObservedChannelState(write_scope_id)` |
   | История наших цен | `(account, marketplace, offer_key)` | `WriteScope(PRICE)` + цепочка `supersedes_id` |
   | Бюджет правок | — | `budget_scope_key` + день канала (отдельно от write scope) |

4. **Бюджет — отдельное измерение.** `WriteScope.budget_scope_key` указывает на `EditBudget`; несколько scope
   разных полей и SKU могут делить один бюджет.

5. **Инвариант согласованности:** все офферы одного scope ссылаются на один `Product`; иначе scope в `CONFLICT`,
   запись блокируется.

6. **Побочные эффекты scope видимы:** если scope шире того, что пользователь считает «своим оффером»
   (остаток Amazon на весь EU), это показывается и подтверждается до включения синхронизации.

7. **Требование к PRICE-scope:** на маркетплейсах ЕС шаблон ключа цены обязан содержать маркетплейс/витрину.

8. **Смена правила = перевыпуск ключей.** Новая версия capability с другим `write_scope_kind` активируется только
   вместе с процедурой: старые scope → `RETIRED`, новые — со ссылкой `supersedes_id`; история продолжается по цепочке.

## Рассмотренные альтернативы

### A. Оставить `OfferMapping` единицей, особые случаи — в адаптерах каналов
Отклонено. Версионирование и схлопывание — инварианты ядра. Их пришлось бы переизобретать в каждом адаптере, и
нарушение INV-03 (сценарий выше) стало бы ошибкой адаптера, невидимой ядру и тестам ядра.

### B. Всегда самая крупная единица (SKU в аккаунте)
Отклонено: теряется цена по маркетплейсу и история Omnibus.

### C. Всегда самая мелкая единица (оффер × маркетплейс) + «сборщик» для остатка Amazon
Отклонено. Сборщик должен координировать несколько офферов за одно значение — это и есть неявный `WriteScope`,
только без явного ключа, версий и наблюдения.

### D. Правила в коде (switch по каналу), без справочника
Отклонено. Правило должно быть проверяемым (`verification`), версионируемым, аудируемым и переопределяемым по аккаунту;
изменение поведения канала не должно требовать релиза ядра.

## Последствия

### Положительные
- INV-03 выполняется для Amazon EU: одно физическое значение — одна последовательность версий.
- Одна модель для четырёх каналов; Kaufland/Otto — частный случай, где scope цены и остатка совпадают по ключу.
- Бюджеты eBay выражаются без специальных случаев в ядре.
- Наблюдение и расхождения сравниваются в той же единице, в которой пишем.

### Отрицательные
- Больше сущностей: `WriteScope`, `WriteScopeSyncState`, `EditBudget`.
- UI обязан объяснять побочные эффекты («остаток на amazon.de — это остаток на всех маркетплейсах EU»).
- Остаток Amazon рассчитывается по SKU в регионе: при работе только с DE мы влияем на маркетплейсы вне скоупа
  (OQ-50).
- Ошибка в справочнике capability меняет семантику записи для всех тенантов — справочник требует ревью и тестов.
- Перевыпуск ключей — сложная миграция данных; её нужно проектировать до первой смены правила.
- Гонка last write wins с собственным уменьшением остатка Amazon при заказе этим ADR **не решается**; она
  смягчается буфером и порядком обработки событий.

## Дополнение (Р-37): область записи остатка шире области записи цены

Дата: 2026-09-14 (шаг 6). Статус: Accepted.

### Правило

**У всех известных каналов остаток живёт на объекте, который охватывает больше офферов, чем объект цены.** Цена — свойство
предложения на конкретной витрине или маркетплейсе. Остаток — свойство физического товара у продавца, и канал связывает его
между витринами своим способом.

| Канал | Единица записи цены | Единица записи остатка | Чем связаны офферы остатка | Решение |
|---|---|---|---|---|
| Amazon EU | аккаунт + маркетплейс + SKU | аккаунт + регион + SKU | Единый SKU в регионе | Р-1 |
| Kaufland | аккаунт + витрина + unit | **аккаунт + `id_offer`** | Одинаковый `id_offer` на витринах: общие количество и склад (документация 2.44.0) | Р-35 |
| eBay | аккаунт + маркетплейс + offer | аккаунт + inventory SKU | Товар инвентаря общий для офферов разных маркетплейсов (проверить, OQ-47) | Р-2 |
| Otto | аккаунт + SKU | аккаунт + SKU | Один маркетплейс — области совпадают (частный случай) | — |

Kaufland показал, что правило легко пропустить. Р-14 зафиксировал одну единицу для обоих полей, и ошибку нашла только
разведка документации на шаге 5.

### Обязательная проверка при подключении нового канала — первым делом

1. **На каком объекте канала живёт количество?** Ищем в документации слова «shared», «synced», «connected», «inventory item»,
   «warehouse», а также поля, связывающие офферы (SKU, `id_offer`, inventory item, parent).
2. **Сколько офферов и маркетплейсов меняет одна запись количества?** Если больше одного — единица записи остатка шире цены,
   и в `channel_capability` для QUANTITY нужен свой шаблон ключа без атрибута витрины или маркетплейса.
3. **Есть ли порядок применения между витринами?** Kaufland прямо пишет, что для файлов импорта порядок между витринами
   не гарантирован. Если порядок не гарантирован, запись в одну единицу из двух мест запрещена.
4. **Нужно ли подтверждение побочных эффектов?** Если одна запись меняет витрины, которыми продавец не управляет через нас —
   `requires_side_effects_ack` (INV-11).
5. **Результат проверки** записывается в `channel-capabilities.md` и в описание адаптера (`FieldCapability.writeScope`,
   `SideEffect SHARED_ACROSS_MARKETPLACES`) **до** первой строки кода адаптера.

Если документация молчит, остаток по умолчанию считается **общим** для всех витрин аккаунта с одинаковым идентификатором товара,
а синхронизация остатка не включается до подтверждения.
