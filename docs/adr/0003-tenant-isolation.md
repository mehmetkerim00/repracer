# ADR-0003: Изоляция тенантов — общая схема + RLS

- **Статус:** Accepted (решение Р-16) · область действия — PostgreSQL; ClickHouse, архив и брокер — [tenant-isolation-analytics.md](../tenant-isolation-analytics.md) (Р-23)
- **Дата:** 2026-09-14
- **Реализация:** [migrations/](../../migrations/) (0001 — основа, 0014 — проверка)
- **Связанные документы:** [data-retention.md](../data-retention.md), [domain-model.md](../domain-model.md)

## Контекст

Требования, влияющие на выбор:

- Amazon AUP: данные тенантов строго изолированы; данные разных продавцов не агрегируются.
- «Ни один запрос не может пересечь границу тенанта» (INV-01).
- Данные каналов удаляются через 18 месяцев, данные тенанта хранятся бессрочно — массовые операции по времени через всех тенантов.
- История цен и наблюдения — самые большие таблицы; их объём растёт с числом офферов и частотой репрайсинга.
- ЕС и США — раздельные юрисдикции.
- Ожидается от сотен до тысяч тенантов разного размера.

## Рассмотренные варианты

| Критерий | A. Общая схема + RLS | B. Схема на тенанта | C. База на тенанта |
|---|---|---|---|
| Защита от ошибки в запросе (забытый `WHERE tenant_id`) | Да — политика на уровне БД | Частично — ошибка в `search_path` даёт чужую схему | Да — нет пути к чужим данным |
| Защита от скомпрометированного приложения | Нет (роль может выставить любой контекст) | Нет | Частично (разные учётные данные) |
| Миграции | Один раз | N раз; расхождение версий схем между тенантами | N раз, N баз |
| Размер каталога | ~45 таблиц + партиции | ~45 таблиц × N + партиции × N (десятки тысяч объектов) | Отдельные каталоги |
| Пул соединений (режим транзакций) | `SET LOCAL` в транзакции — совместимо | `search_path` на сессию — плохо совместимо | Пул на базу — N пулов |
| Удаление по сроку через всех тенантов | Одна операция на партицию месяца | N операций | N операций |
| Удаление тенанта | DELETE по `tenant_id` (процедура) | DROP SCHEMA | DROP DATABASE |
| Резервная копия/восстановление одного тенанта | Нет (логический экспорт) | Возможно (pg_dump схемы) | Да |
| «Шумный сосед» | Общие ресурсы | Общие ресурсы | Изолированы |
| Стоимость эксплуатации | Низкая | Средняя | Высокая |

## Решение

**Вариант A: одна общая схема на регион, `tenant_id` в каждой таблице, RLS на всех таблицах, партиционирование
по тенанту на больших таблицах. Отдельные базы — только EU и US.**

1. **`tenant_id` в каждой таблице**, включая глобальные: строки пользователей и справочника каналов принадлежат
   платформенному тенанту `00000000-0000-0000-0000-000000000000`.
2. **RLS `ENABLE` + `FORCE`** на всех таблицах и на каждой партиции. Политика `tenant_isolation` для `repracer_app`:
   `tenant_id = security.current_tenant_id()`. Нет контекста — ноль строк.
3. **Контекст — `SET LOCAL app.tenant_id` в каждой транзакции**, из аутентифицированной сессии, никогда из тела запроса.
4. **Составные внешние ключи `(tenant_id, …_id)`**: строка не может сослаться на сущность другого тенанта даже при ошибке приложения.
5. **Никакой роли с `BYPASSRLS`.** Исключения доступа — узкие роли с политиками:
   - `repracer_resolver` — функции резолва тенанта для входящих событий, ключей Inbound API и входа; читает только нужные столбцы;
   - `repracer_retention` — удаление по сроку и закрытие тенанта; только SELECT и DELETE, только внутри своих функций для append-only таблиц.
6. **Прямого доступа к партициям у приложения нет** — только через родительскую таблицу, где действует политика.
7. **Партиционирование:**
   - бессрочные большие таблицы (`price_history`, `channel_write`) — `HASH (tenant_id)`, 64 партиции;
   - большие таблицы данных каналов — `RANGE` по месяцу → `HASH (tenant_id)`, 16 подпартиций;
     удаление по сроку = `DROP` месячной партиции для всех тенантов сразу;
   - малые таблицы — без партиций.
8. **Региональные базы:** `repracer_eu`, `repracer_us`; тенант создаётся только в базе своего региона (`repracer.region`).
9. **Проверка при миграции** (`0014`): таблица без `tenant_id`, без RLS, без регистрации, с доступной партицией,
   с FK из данных тенанта в данные каналов или с `SECURITY DEFINER` без фиксированного `search_path` — миграция падает.

## Модель угроз

| Угроза | Защищает ли решение |
|---|---|
| Ошибка разработчика: запрос без фильтра по тенанту, неверный JOIN | **Да** — RLS и составные FK |
| Ошибка в ORM/аналитическом запросе, объединяющем тенантов | **Да** — RLS режет результат до текущего тенанта |
| Новая таблица без изоляции | **Да** — `0014` не даёт применить миграцию |
| Скомпрометированный процесс с ролью `repracer_app` выставляет чужой `app.tenant_id` | **Нет.** Смягчение — подписанный контекст (OQ-60) |
| Суперпользователь / владелец схемы | Нет — эти роли не используются в рантайме |
| Побочный канал через уникальные индексы (ошибка «аккаунт уже подключён» раскрывает факт подключения в другом тенанте) | Принимается: это требуемое поведение для глобальной уникальности аккаунтов каналов |
| Утечка через резервные копии / реплики | Вне RLS — шифрование и доступ к копиям (OQ-61) |

## Последствия

### Положительные
- Одна схема, одна последовательность миграций на регион.
- Удаление данных каналов по сроку — дешёвые `DROP PARTITION` для всех тенантов.
- Совместимость с пулом соединений в режиме транзакций.
- Инварианты целостности (версии, `min_price`, режимы цены) выражаются обычными ограничениями и триггерами в одной схеме.

### Отрицательные
- **RLS не защищает от скомпрометированного приложения** — только от ошибок. Нужен подписанный контекст или отдельный слой авторизации (OQ-60).
- **Крупный тенант в HASH-партиции** делит её с другими; если один тенант станет доминировать по объёму,
  потребуется перепартиционирование (переход на LIST для крупных тенантов) — отдельная миграция данных.
- **Восстановление одного тенанта из копии** — только логическим экспортом по `tenant_id`.
- **Шумный сосед:** общие ресурсы базы региона; нужны лимиты на уровне приложения и мониторинг по тенантам.
- **Тысячи партиций** (месяцы × подпартиции): планирование запросов опирается на отсечение партиций — каждый запрос
  к большим таблицам обязан содержать `tenant_id` и диапазон времени.
- **Тенант с рынками ЕС и США** должен выбрать один регион данных — OQ-59.
- Триггеры исполняются от имени вызывающей роли: приложению выданы права, которые ограничены триггерами
  (`security.only_from_trigger`, `security.restrict_update`) — эту дисциплину нужно соблюдать в каждой новой таблице.
