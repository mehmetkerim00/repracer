# ADR-0004: Трёхслойное хранение — PostgreSQL / ClickHouse / архив Parquet

- **Статус:** Accepted (решения Р-20, Р-21, Р-22, Р-23)
- **Дата:** 2026-09-14
- **Заменяет в части хранения:** раскладку шага 3 ([ADR-0003](0003-tenant-isolation.md) остаётся в силе для PostgreSQL)
- **Реализация:** [migrations/0015–0023](../../migrations/), [schemas/clickhouse/](../../schemas/clickhouse/)
- **Связанные документы:** [data-retention.md](../data-retention.md), [tenant-isolation-analytics.md](../tenant-isolation-analytics.md), [ADR-0005](0005-message-broker.md)

## Контекст

### Причина

Схема шага 3 хранит аналитический временной ряд в транзакционной базе. Для базового сценария (10 000 SKU × 4 канала):

| Показатель | Значение |
|---|---|
| Объём на клиента в устойчивом режиме | **~200 ГБ** (наблюдения ~92 ГБ + снимки конкурентов ~126 ГБ) |
| Вечный прирост на клиента | **~89 ГБ в год** (`price_history` ~34 ГБ + `channel_write` ~55 ГБ) |
| 100 клиентов | **~20 ТБ** и **~9 ТБ прироста ежегодно** |
| Диск на клиента | **~24 € в месяц** при подписке 100–150 € |

Объёмы шага 3 не включали `price_intent` и `price_decision` (18 месяцев в PostgreSQL). По грубой оценке — ещё ~250 ГБ на клиента.
Предположения: intent = 2 × запись цены, около 1 КБ на пару intent + decision с индексами; строки не замерялись.

Вторая проблема — не объём, а смешение нагрузок. Бэктест и симулятор по месяцам истории читают ту же базу, где Price Gate
держит блокировки и проверяет инварианты в пределах 60 секунд p95 (Р-8).

### Что нужно текущему решению о цене

| Нужно Price Gate и стратегии | Не нужно синхронно |
|---|---|
| Последнее конкурентное состояние | Вся история снимков конкурентов |
| Последнее наблюдаемое значение и расхождение | Все наблюдения |
| Минимальная цена за 30 дней (Omnibus) | Сырьё цен старше 90 дней |
| Незавершённые записи, версии, бюджеты | Завершённые записи |
| Решение, из которого создаётся запись (минуты) | Решения за месяцы |

## Решение

### 1. Три слоя

| Слой | Назначение | Что лежит |
|---|---|---|
| **PostgreSQL** (горячий) | Текущее решение и инварианты [Р-22] | Конфигурация, единицы записи, `min_price`, резервации; незавершённые `channel_write`; проекции `competitor_state`, `observed_channel_state`, `observed_price_daily`; `price_history` за 90 дней; **`price_daily` — вечно**; буферы `price_intent`/`price_decision` на 3 дня, `channel_write_history` и `outbox_event` до экспорта |
| **ClickHouse** (аналитика) | Аналитика, симулятор, бэктест; только чтение через шлюз [Р-22, Р-23] | `channel_observation`, `competitor_snapshot`, `channel_write_completed`, `channel_write_response`, `price_intent`, `price_decision`, `fee_actual`; TTL 18 месяцев |
| **Архив** (Parquet в объектном хранилище) | Вечное хранение данных тенанта | Сырьё `price_history` старше 90 дней, завершённые записи (id, статус, время); префикс и ключ шифрования на тенанта |

### 2. Потоки

```
Адаптер ── брокер ──┬─> потребитель ─> PostgreSQL: observed_channel_state, observed_price_daily, competitor_state
                    └─> ClickHouse: channel_observation, competitor_snapshot, channel_write_response, fee_actual

PostgreSQL ── outbox_event ── брокер (порядок по write_scope_id, ADR-0005)

PostgreSQL дневные партиции ── экспортёр ──┬─> ClickHouse: price_intent, price_decision, channel_write_completed
                                           └─> архив: channel_write
PostgreSQL месячные партиции price_history ── экспортёр ─> архив: price_history

PostgreSQL удаляет партицию только после записи в maintenance.partition_export с совпадающим числом строк
```

### 3. Правила

1. **Решение о цене никогда не читает ClickHouse и архив синхронно** [Р-22]. Всё, что ему нужно, имеет горячую
   проекцию в PostgreSQL.
2. **Данные каналов живут не дольше 18 месяцев в любом слое и не попадают в архив.**
3. **Данные тенанта удаляются из PostgreSQL по времени только после подтверждённого экспорта** с тем же числом строк
   (`maintenance.drop_expired_partitions`, проверка 0023). Принудительное удаление без экспорта (`force_drop_after`)
   разрешено только буферам данных каналов (`price_intent`, `price_decision` — 14 дней).
4. **Суточная свёртка `price_daily` — вечное юридическое доказательство Omnibus** [Р-21]. Ведётся триггером в той же
   транзакции, что и сырьё. Закрытый день неизменяем, свёртка только расширяется.
5. **Минимальная цена за 30 дней для решения** = минимум по `price_daily` (наши цены) и `observed_price_daily`
   (цены, наблюдённые в канале, 60 дней) + последняя цена перед окном.
6. Изоляция тенантов в ClickHouse и архиве описана отдельно [Р-23].

### 4. Партиционирование PostgreSQL после выноса аналитики

| Таблица | Разбиение | Подпартиции | Живых партиций в устойчивом режиме |
|---|---|---|---|
| `price_history` | месяц (`accepted_at`) | **HASH(tenant_id) × 8** | ~7 месяцев × 9 = ~63 |
| `price_intent`, `price_decision` | день | нет | ~8 + ~8 |
| `channel_write_history` | день | нет | ~6 |
| `outbox_event` | день | нет | ~7 |
| `audit_event` | месяц | нет | ~22 |
| **Итого** | | | **~114** (при миграции создаётся 61) |

**Нужны ли ещё 16 подпартиций — нет.**

- Таблицы с 16 подпартициями (наблюдения, снимки конкурентов, ответы каналов, комиссии) ушли в ClickHouse.
- У `price_history` за 90 дней при 100 клиентах ~1 ТБ на ~4 месяца, это ~30 ГБ на подпартицию при 8 — достаточно.
- Число подпартиций задаётся политикой для каждого нового месяца: при росте его можно увеличить без миграции данных.
- У транзитных дневных таблиц подпартиции бессмысленны: удаление — DROP целого дня, доступ тенанта — по индексу с `tenant_id`.
- В ClickHouse тенант — первый столбец ключа сортировки, партиция — месяц.

Шаг 3: ~2 400 партиций в устойчивом режиме, 4 405 в тесте.

## Объём на клиента: до и после (базовый сценарий)

Замерено на PostgreSQL 16 (1 млн синтетических строк, те же индексы):

| Таблица | Байт на строку |
|---|---|
| `price_history` | 399 |
| `channel_observation` | 370 |
| `competitor_snapshot` | 1 217 |
| `price_daily` | 267 |
| `channel_write_history` | 338 |

**Не замерялось:** сжатие ClickHouse и Parquet — ClickHouse в этом шаге не устанавливался. Ниже — диапазоны по
предположению о 5–15-кратном сжатии столбцовых форматов относительно строки PostgreSQL с индексами. Проверить на
реальном кластере (OQ-67).

Строк на клиента: цены — 230 тыс. записей в сутки, остаток — 120 тыс. записей в сутки, наблюдения — 175 млн в год,
снимки конкурентов — 73 млн в год. Intent и decision — по 460 тыс. в сутки (предположение).

### PostgreSQL

| Таблица | До | После |
|---|---|---|
| `channel_observation` | ~92 ГБ | — (ClickHouse); проекции < 1 ГБ |
| `competitor_snapshot` | ~126 ГБ | — (ClickHouse); `competitor_state` < 0,1 ГБ |
| `price_intent` + `price_decision` | не учитывались (~250 ГБ оценка) | ~1,5 ГБ (3 дня) |
| `price_history` | +34 ГБ/год вечно | **~10 ГБ** (90–120 дней), дальше архив |
| `price_daily` | — | **+3,9 ГБ/год вечно** |
| `channel_write` | +55 ГБ/год вечно | < 0,1 ГБ (незавершённые) + ~0,4 ГБ транзит |
| `outbox_event`, прочее | — | ~1–1,5 ГБ |
| **Итого** | **~200 ГБ + 89 ГБ/год** | **~13 ГБ + 3,9 ГБ/год** |

### ClickHouse (TTL 18 месяцев, прироста нет)

| Таблица | Строк в окне | Сжатый объём (оценка) |
|---|---|---|
| `channel_observation` | ~255 млн | 6–13 ГБ |
| `competitor_snapshot` | ~106 млн | 8–16 ГБ |
| `channel_write_completed` | ~186 млн | 5–11 ГБ |
| `channel_write_response` | ~190 млн | 8–15 ГБ |
| `price_intent` + `price_decision` | ~490 млн | 22–44 ГБ |
| `fee_actual` | мало | < 1 ГБ |
| **Итого** | | **~50–100 ГБ** |

### Архив (вечно)

| Набор | Прирост в год (оценка) |
|---|---|
| `price_history` | 2–3,5 ГБ |
| `channel_write` (id, статус, время) | 2,5–4,5 ГБ |
| **Итого** | **~5–8 ГБ/год** |

### Сводка

| | До | После |
|---|---|---|
| Год 1, всего на клиента | ~200 ГБ (PostgreSQL) | ~13 ГБ PostgreSQL + ~50–100 ГБ ClickHouse + ~6 ГБ архив |
| Вечный прирост в год | ~89 ГБ (PostgreSQL) | ~3,9 ГБ PostgreSQL + ~5–8 ГБ архив |
| Год 5 на клиента | ~645 ГБ PostgreSQL | ~33 ГБ PostgreSQL + ~75 ГБ ClickHouse + ~30 ГБ архив |
| 100 клиентов, год 1 | ~20 ТБ + 9 ТБ/год | ~1,3 ТБ PG + 5–10 ТБ ClickHouse + ~0,6 ТБ/год архив |

**Деньги.** Из ваших цифр ставка горячего диска ≈ 24 € / 200 ГБ ≈ 0,12 € за ГБ в месяц.
- PostgreSQL: ~1,6 € в месяц на клиента в первый год против ~24 € раньше.
- ClickHouse по той же ставке SSD: 6–12 € в месяц. Это теперь главная статья, и в основном она состоит из `price_intent`/`price_decision`.
- Архив: копейки при любой разумной цене объектного хранилища.

Цены ClickHouse и объектного хранилища зависят от поставщика (OQ-67). Резерв экономии в ClickHouse — перенос частей старше
1–3 месяцев на объектное хранилище (TTL MOVE) и более короткий срок для intent/decision (OQ-70).

## Что теряем

1. **Точность доказательства Omnibus после 90 дней.** В PostgreSQL остаются только минимум, максимум, первая и последняя цена
   за день. Каждое изменение с точным временем лежит в архиве, не онлайн. Юридическая достаточность — OQ-68.
2. **Гарантии БД вне PostgreSQL.** Append-only, составные FK и RLS с FORCE есть только в горячем слое. ClickHouse и архив
   держатся на правах, политиках строк, манифестах и контрольных суммах.
3. **Синхронная согласованность.** ClickHouse отстаёт: секунды для потоков из брокера, до суток для intent, decision и
   завершённых записей. «Почему такая цена» старше 3 дней объясняется только через ClickHouse.
4. **Мягкие ссылки.** `price_history.channel_write_id`, `price_intent.competitor_snapshot_id`,
   `migration_consent_item.listing_migration_check_id`, `write_submission.channel_write_id` больше не FK.
5. **Исправления `price_history` запрещены** — правило исправления вечной свёртки не определено (OQ-66).
6. **Удаление тенанта неатомарно по слоям.** Прогресс фиксирует `maintenance.tenant_purge_status`.
7. **Эксплуатация.** На регион теперь PostgreSQL, ClickHouse, объектное хранилище, брокер, ретранслятор outbox и экспортёр.
   Остановка экспортёра **растит горячий слой**: данные тенанта без экспорта не удаляются, нужны алерты на отставание.
8. **Проверка экспорта — по числу строк, записанному экспортёром.** БД не видит содержимое ClickHouse и архива.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
|---|---|
| Всё в PostgreSQL + сжатие временных рядов расширением | Доступность расширений у управляемых PostgreSQL не подтверждена (OQ-61). Бэктест продолжает нагружать базу Price Gate. Индексы и обновления сжатых данных ограничены |
| Только архив + движок запросов поверх Parquet | Нет потоковой загрузки и быстрого симулятора; изоляцию тенантов пришлось бы строить в движке |
| Облачное хранилище-сервис | Привязка к поставщику, стоимость за запросы, выгрузка данных между сервисами; изоляция возможна, но выигрыша над ClickHouse нет |

## Последствия

- Горячий слой почти перестаёт расти: вечный прирост ~4 ГБ в год на клиента вместо ~89 ГБ.
- Адаптеры (шаг 5) пишут сырые данные в брокер, а в PostgreSQL — только команды записи и их статусы.
- Новые обязательные компоненты: ретранслятор outbox с порядком по `scope_seq`, приёмник ClickHouse, экспортёр партиций,
  задания закрытия тенанта в ClickHouse и архиве (OQ-65, OQ-67).
- DDL ClickHouse нужно прогнать и замерить сжатие на выбранной версии до выводов о стоимости.
