# ADR-0005: Брокер сообщений — Kafka-совместимый, ключ `write_scope_id`

- **Статус:** Accepted (решение Р-24)
- **Дата:** 2026-09-14
- **Уточняет:** [ADR-0001](0001-event-driven-architecture.md) (п. 3–5, 8), закрывает брокерную часть OQ-41
- **Связанные документы:** [ADR-0002](0002-write-scope-per-field.md), [ADR-0004](0004-storage-tiering.md), [tenant-isolation-analytics.md](../tenant-isolation-analytics.md)

## Контекст

Шина обслуживает три потока:

| Поток | Производитель | Потребители | Требование к порядку |
|---|---|---|---|
| События единицы записи (`scope.*`): наблюдение, запрос оценки, запись создана/завершена | Адаптеры каналов, outbox PostgreSQL | Стратегия, Price Gate, Dispatcher, проекции PostgreSQL, приёмник ClickHouse | **Строгий порядок внутри единицы записи** (INV-03) |
| Сырые данные для аналитики: снимки конкурентов, ответы каналов, комиссии | Адаптеры | Приёмник ClickHouse, проекция `competitor_state` | Порядок внутри товара канала; дубли допустимы |
| События тенанта: алерты (истечение резервации), подключение аккаунта | outbox PostgreSQL | Уведомления, аудит | Порядок внутри тенанта желателен |

Объём (базовый сценарий ADR-0004, 10 000 SKU × 4 канала): ~1,5 млн событий в сутки на клиента; при 100 клиентах —
~150 млн в сутки, ~1 700 в секунду в среднем, пики кратно выше (распродажи, всплески `ANY_OFFER_CHANGED`).

Почему порядок критичен именно для единицы записи. База данных уже отвергает устаревшую версию: запись с меньшей
версией не отправится. Но шина, перепутавшая события, приведёт к отказу от **свежего** значения. Для остатка Amazon EU
это одно физическое значение на все маркетплейсы (Р-1).

## Критерии

| Критерий | Kafka-совместимый | NATS JetStream | Redis Streams |
|---|---|---|---|
| Порядок по ключу при параллельной обработке | Да: ключ → партиция, порядок внутри партиции, группы потребителей | Через разбиение subject по N разделам и потребителя на раздел; менее идиоматично | Нет привязки ключа к потребителю в группе; порядок — только поток на ключ или ручной шардинг |
| Долговременный журнал и повторное чтение (дни) | Да, retention по времени | Да (streams с limits) | Ограничено памятью; не рассчитан на дни при нашем объёме |
| Потоковая загрузка в ClickHouse | Готовые механизмы (движок Kafka в ClickHouse, коннекторы) | Нужен свой потребитель/коннектор | Нужен свой потребитель |
| Идемпотентный продюсер, транзакции | Да | Дедупликация по msg-id в окне | Нет |
| Управляемые сервисы в ЕС и США | Много вариантов (Kafka-совместимые) | Меньше | Много, но как кэш |
| Операционная сложность | Выше | Ниже | Низкая |
| Изменение числа разделов | Ломает соответствие ключ → партиция | Аналогично при смене разбиения | — |

## Решение

1. **Брокер — Kafka-совместимый** (Apache Kafka или совместимая реализация, управляемая или своя; выбор поставщика — OQ-67).
   Отдельный кластер на регион EU/US [Р-16].
2. **Топики `scope.*` имеют ключ `write_scope_id`.** Все события одной единицы записи попадают в одну партицию.
3. **Топики сырых данных** (`raw.competitor-snapshot.*`, `raw.write-response.*`, `raw.fee-actual.*`) имеют ключ предмета источника:
   снимки — `channel_account_id|marketplace|channel_product_ref`, ответы — `write_scope_id`, комиссии — `channel_account_id`.
   Снимок конкурентов относится к товару канала, а не к единице записи; расщепление на единицы записи
   (`scope.evaluate.*` с ключом `write_scope_id`) выполняет потребитель. *(Толкование Р-24: ключ `write_scope_id`
   обязателен для событий единицы записи; для событий без единицы — ключ их предмета.)*
4. **Топики тенанта** (`alert.*`, `tenant.*`) имеют ключ `tenant_id`.

## Почему ключ именно `write_scope_id`

| Кандидат | Что ломается |
|---|---|
| `tenant_id` | Крупный тенант (десятки тысяч единиц) занимает одну партицию: нет параллелизма; одна зависшая единица блокирует весь тенант |
| `channel_account_id` | То же в пределах аккаунта |
| `offer_mapping_id` | Остаток Amazon EU — одна единица записи на несколько офферов (Р-1): события одного физического значения расходятся по партициям и переупорядочиваются — ровно ошибка из ADR-0002 |
| `product_id` | Смешивает несвязанные единицы (разные каналы и поля), горячие ключи у популярных товаров, порядок нужен не на товар |
| Без ключа | Порядка нет |
| **`write_scope_id`** | Единица порядка = единица версий (ADR-0002). Максимальный параллелизм без нарушения INV-03 |

Бюджет правок eBay охватывает несколько единиц записи одного листинга. Порядок между ними не нужен: счётчики
атомарны в PostgreSQL (Р-19).

## Обязательства, которые следуют из решения

1. **Число партиций топиков `scope.*` фиксируется при создании и не увеличивается.** Рост — новый топик
   `scope.<name>.v<N+1>` и переключение по границе `scope_seq` для каждой единицы (процедура — при первой необходимости).
   Начальное число партиций рассчитывается на 3 года по нагрузке (OQ-67).
2. **Продюсер** — идемпотентный, подтверждение всеми репликами. Настройки, гарантирующие порядок при повторах, проверяются
   на выбранной реализации.
3. **Outbox → брокер в порядке коммитов.** `tenant_data.outbox_event.scope_seq` выдаётся под блокировкой строки
   `write_scope_sync_state` и монотонен в порядке коммитов внутри единицы (миграция 0015). Ретранслятор публикует
   события единицы строго по возрастанию `scope_seq`; обнаружив пропуск, ждёт (транзакция ещё не закоммичена) —
   либо читает outbox логическим декодированием (порядок WAL). Выбор реализации ретранслятора — шаг 5.
4. **Потребитель** обрабатывает партицию последовательно или параллельно по ключам с последовательной обработкой внутри
   ключа. Смещение фиксируется после обработки. Идемпотентность — по `(write_scope_id, scope_seq)` и версии записи.
5. **Нет retry-топиков для `scope.*`**: повтор в отдельном топике переупорядочивает события. Ошибка обработки ⇒
   единица записи переводится в `BLOCKED` в PostgreSQL (INV-14), событие паркуется вместе со всеми последующими
   событиями этой единицы до разбора.
6. **Retention топиков — не больше 7 дней.** Полезная нагрузка без PII и секретов. Данные закрытого тенанта исчезают из
   брокера не позже чем через 7 дней; это фиксируется в процедуре закрытия.
7. **Изоляция тенантов:** общие топики, `tenant_id` в конверте и заголовке. Доступ к топикам — только сервисам по ACL,
   не тенантам. Потребитель сверяет `tenant_id` события с владельцем единицы записи в PostgreSQL. Топики на тенанта
   не заводятся (тысячи топиков).
8. **Справедливость:** крупный тенант делит партиции с другими. Смягчение — достаточное число партиций, лимиты на
   тенанта в Dispatcher (ADR-0001 п. 6) и мониторинг лага по тенанту.

## Рассмотренные альтернативы

- **NATS JetStream** — проще в эксплуатации, но упорядоченная параллельная обработка по ключу и загрузка в ClickHouse
  требуют своих механизмов. Отклонено по совокупности, не по невозможности.
- **Redis Streams** — нет привязки ключа к потребителю в группе, журнал на дни при нашем объёме упирается в память.
  Отклонено как основная шина; допустим для внутренних очередей без требований к порядку.
- **Только PostgreSQL (LISTEN/NOTIFY, очередь в таблице)** — противоречит Р-20: горячий слой перестанет быть «только
  данными для текущего решения», нет потоковой загрузки в ClickHouse.

## Последствия

- **Плюсы:** порядок INV-03 гарантирован шиной; параллелизм — по числу единиц записи; прямая загрузка сырых данных в ClickHouse мимо PostgreSQL.
- **Минусы:** фиксированное число партиций; обязательный порядок в ретрансляторе outbox; блокировка единицы при ошибке
  вместо простого retry; ещё одна распределённая система на регион.
