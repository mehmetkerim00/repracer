# ADR-0009: Диспетчер записей и путь решения за брокером

- **Статус:** Accepted
- **Дата:** 2026-09-14
- **Решения:** Р-64 (диспетчер записей), Р-24 (ключ `write_scope_id`), Р-34 (ретранслятор outbox с advisory lock), Р-59 (≤ 3 транзакций на оценку)
- **Уточняет:** [ADR-0005](0005-message-broker.md) (реализация обязательств 2–5), [ADR-0008](0008-price-decision-path.md) §7
- **Реализация:** [packages/write-dispatcher](../../packages/write-dispatcher/), [packages/broker](../../packages/broker/), [services/pricing-worker](../../services/pricing-worker/); миграции 0036, 0038; [infra/local](../../infra/local/)

## Контекст

В шаге 9 путь решения сам отправлял только запись, которую захватил в транзакции решения. Запись, вставшая за записью
в полёте той же единицы (`PENDING`), не отправлялась никем. Вытеснение старых версий не хранило причину.
Воспроизведение на PostgreSQL (`packages/pricing-store-pg/test/write-queue.pg.test.ts`): 40 единиц по 6 решений,
канал отвечает за 20–80 мс. В пяти прогонах шага 10 у 19–35 единиц из 40 последняя решённая цена не дошла до канала (числа из журнала прогонов, а не утверждение теста; с шага 15 контрольный тест утверждает, что потери есть, — ретроспективное ревью, A2/B2),
141–160 вытеснений не имели причины. Порядок при этом не нарушался: базу старая версия не проходит.
Это самый опасный класс дефекта в продукте — тихая потеря изменения цены.

## Решение

### 1. Три слоя порядка по `write_scope_id`

| Слой | Что гарантирует | Где |
|---|---|---|
| База данных | Одна запись в полёте на единицу (`write_scope_sync_state.in_flight_write_id`); отправляется только последняя созданная версия; захват — под блокировкой строки единицы; пол, потолок и остановка перепроверяются при отправке | 0008, 0030, 0032, 0036 |
| Брокер | События `scope.write.v1` с ключом `write_scope_id` — одна партиция, один потребитель группы | `@repracer/broker`, ADR-0005 |
| Процесс | Вызовы `dispatchScope` по одной единице выстраиваются в цепочку | `@repracer/write-dispatcher` |

Каждый слой сам по себе не пускает старое значение после нового. Брокер нужен для параллелизма без гонок,
а не для корректности.

### 2. Диспетчер опирается на состояние, а не на событие

Событие — только сигнал «проверь единицу». Диспетчер делает `claimNext` под блокировкой единицы и получает один из итогов:
- в полёте другая запись;
- срок повтора ещё не наступил;
- запись завершена с причиной;
- захвачена последняя версия.

Отсюда:
- дубль и повторная доставка события безвредны;
- порядок событий в пределах единицы не влияет на результат;
- потерянное событие подбирает обход `maintenance.due_write_scopes`. Обход видит только идентификаторы и сроки, суммы и цены ему недоступны.

### 3. Запись не остаётся PENDING бесследно

| Итог | Статус | Причина (`end_reason`) |
|---|---|---|
| Новая версия создана, пока старая ждала | `SUPERSEDED` (из `FAILED` — `DISCARDED_STALE`) | `WRITE_SUPERSEDED_BY_NEWER_VERSION` + ссылка на новую запись |
| При отправке цена вне границ | `DISCARDED_STALE` | `WRITE_BLOCKED_BY_BOUND_RECHECK` |
| Канал остановлен, цена из данных конкурентов | `DISCARDED_STALE` | `CHANNEL_HALTED` |
| Режим цены сменился | `DISCARDED_STALE` | `WRITE_PRICING_MODE_CHANGED` |
| Постоянная ошибка канала | `DISCARDED_STALE` | `WRITE_NOT_ACCEPTED_BY_CHANNEL` |
| Временные ошибки сверх лимита попыток | `DISCARDED_STALE` | `WRITE_RETRIES_EXHAUSTED` |
| Бюджет правок исчерпан | `BUDGET_EXHAUSTED` | `WRITE_EDIT_BUDGET_EXHAUSTED` |
| Ошибка требует человека | `FAILED` без срока, единица `BLOCKED` | алерт `PRICE_WRITE_SCOPE_BLOCKED` |

Дополнительно:
- **Закреплено в базе.** Причина обязательна (`channel_write_end_explained`) и копируется в историю и в ClickHouse.
- **Неизвестный итог** (`OUTCOME_UNKNOWN`): запись остаётся в полёте. Через `reconcileAfterMs` её сверяет обратное чтение: значение совпало — `APPLIED`, не совпало — повтор той же версии. Слепой повтор запрещён.
- **Процесс упал между захватом и итогом:** обход находит запись в полёте старше `inFlightTimeoutMs`.

### 4. Событие в той же транзакции

Отложенный constraint-триггер `zz_channel_write_announce_dispatch` срабатывает при COMMIT, в том числе для строки, удалённой завершением. Если единица свободна и у неё есть `PENDING`, он ставит в outbox `scope.write.v1` / `WRITE_DISPATCH_DUE`.

Почему гонки нет:
- «запись встала в очередь» и «запись в полёте завершилась» обе берут блокировку строки `write_scope_sync_state`;
- завершающая транзакция видит закоммиченную ждущую запись;
- ждущая запись, закоммиченная после освобождения единицы, захватывается самой транзакцией решения.

### 5. Передача в процессе и Р-59

`recordDispatch` в той же транзакции сообщает, освободилась ли единица и ждёт ли запись (`queuedWaiting`). Только тогда путь решения вызывает диспетчер в своём процессе. Итог по транзакциям:
- у оценки остаётся не больше трёх транзакций;
- у отправленной из очереди записи свои две — захват и итог.

Со стороны вставшей в очередь записи передача не нужна: см. п. 4.

### 6. За брокером

`services/pricing-worker` — экземпляр пути решения. Экземпляров — сколько угодно.
- **Снимки:** слушает `raw.competitor-snapshot.v1` (ключ — товар канала) и ведёт оценку.
- **Записи:** слушает `scope.write.v1` (ключ — `write_scope_id`) и вызывает диспетчер.
- **Обход-страховка:** раз в `sweepIntervalMs`.
- **Ретранслятор outbox** запущен во всех экземплярах, активен держатель advisory lock (Р-34).
  - Внутри единицы он публикует по `scope_seq`, а не по `created_at`: транзакция, начатая раньше, может закоммитить событие позже.
  - При пропуске номера ждёт `gapTimeoutMs`. Откат транзакции тоже оставляет пропуск, поэтому затем публикация продолжается с алертом.
- **Продюсер:** идемпотентный, `acks=all`, одна пачка в полёте.
- **Потребитель:** последовательно по партиции, смещение фиксируется после обработки.
- **Топики:** автосоздание выключено, число партиций проверяется при старте.

## Последствия

- **Доставка и порядок.** Событие доставляется at-least-once. Корректность порядка обеспечивает БД, производительность — брокер.
- **Роли без бизнес-данных.** Появились `repracer_dispatcher` (обход: идентификаторы и сроки) и `repracer_relay` (outbox и своё состояние) — проверка схемы 0039.
- **Клиент Kafka** — `@confluentinc/kafka-javascript` 1.10.1, слой совместимости с KafkaJS [Р-66]. Заменил kafkajs 2.2.4 (OQ-110). На брокере не прогонялся (OQ-114).
- **Задержка из очереди.** Запись из очереди уходит после итога предыдущей. Для синхронного канала — сразу после ответа, для асинхронного — после подтверждения применения; ожидание ограничено `confirmationTimeoutMs`.
- **Параметры повторов** (5 попыток, пауза от 2 с до 5 мин, сверка через 30 с, запись в полёте — 2 мин) — допущение до замеров задержек каналов (Р-8).

## Отклонённые варианты

- **Отправка только диспетчером (без быстрого пути в оценке).** Лишний переход через брокер на каждую запись удлиняет задержку Р-8. Корректность от быстрого пути не страдает (п. 1).
- **Retry-топик для записей.** Переупорядочивает события единицы (ADR-0005, обязательство 5).
- **Очередь в таблице PostgreSQL вместо брокера.** Противоречит Р-20 и не распределяет работу между экземплярами без внешнего планировщика. Обход по таблице оставлен только как страховка.
- **Хранить в событии значение записи.** Устаревшее событие несло бы устаревшее значение. Диспетчер читает последнюю версию из БД.
