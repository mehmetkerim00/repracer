# ADR-0017: Мутационная проверка защит, список разрешённого пути решения, административные операции только от человека

Статус: принято (шаг 17). Заменяет часть ADR-0016 (раздел 2 и «Что база НЕ обещает»).

## Контекст

Ревью шага 16 показало три вещи.

1. **Тесты защит не проверяли причину отказа.** Ревьюер удалил триггер журнала снятия остановки — три набора тестов
   остались зелёными: отказ давала другая защита. Таблица соответствия Р-93 (какое поведение заменяет какое правило имени)
   ничего не доказывала: она перечисляла тесты, которые не падают при снятии заявленной защиты.
2. **Разделение ролей было списком запретов.** Путь решения не мог писать аудит, членства, тенантов и остановки человеком —
   но мог создать `migration_consent` (согласие на **необратимую** миграцию листингов eBay), включить Smart Pricing тенанта,
   изменить границы, себестоимость и стратегии. Перечень запретов был неполон ровно наполовину.
3. **ADR-0016 преуменьшал компрометацию административного сервиса** и не описывал, что у него нет следа: фоновая запись
   без пользователя сессии была возможна, признак второго фактора любого пользователя менялся одним UPDATE.

## Решение

### 1. Причина отказа обязательна [Р-94]

`pg_temp.expect_fail(метка, запрос, причина)` в смоук-тестах сверяет SQLSTATE или текст сообщения и различает три исхода:
отказа не было; отказ по другой причине; отказ по заявленной причине. Тесты TypeScript сверяют текст отказа.

Правило, которое нельзя довести до собственной причины (раньше срабатывает другая защита), не пишется вовсе: в смоук-тесте
остаётся комментарий, почему проверка недостижима. Так в `smoke_app.sql` исчезла проверка «автоматическое снятие в сессии
пользователя»: без записи проверки снятие отклоняет Р-52, а запись автоматической проверки в сессии человека невозможна.

### 2. Мутационная проверка схемы [Р-95]

`scripts/db/mutation-check.mjs` + каталог `tests/db/mutations.mjs`. Для каждой строки каталога: создать базу из шаблона,
снять ОДНУ защиту (DROP TRIGGER, DROP CONSTRAINT, REVOKE, подмена условия в теле функции), прогнать заявленные проверки
и убедиться, что падает ожидаемая. Контрольный прогон без мутаций обязан быть зелёным — иначе проверка ничего не значит.

Что измерено до исправлений — `docs/evidence/step17-mutation-before.md`; после — `docs/evidence/step17-mutation-after.md`.

### 3. Список разрешённого [Р-96]

`security.decision_path_allowed_privileges()` перечисляет права `repracer_app` (таблица, привилегия, столбец). Миграция 0062
отзывает у роли пути решения все права в прикладных схемах и выдаёт ровно список; всё, что нужно приложению сверх данных
решения, перенесено административной роли. Проверка схемы 0067 сверяет права в обе стороны: право есть тогда и только тогда,
когда оно в списке; столбцовые права — тоже; исполняемые путём решения функции SECURITY DEFINER — по отдельному короткому списку.

Две вещи пути решения выражены функциями базы, а не правами:

- блокировка товара при фиксации решения (`tenant_data.lock_decision_products`, 0065): `FOR SHARE` требует права UPDATE на
  товар, которого у пути решения быть не должно;
- автоматическая проверка остановки по выборке (`channel_data.review_halt_by_sample`, 0063): путь решения записывает только
  наблюдения (`channel_data.pricing_halt_sample`, без времени записи — его ставит база), а итог и снятие вычисляет база.
  Подделать автоматическое снятие путь решения не может: ни записи проверки, ни изменения срока проверки у него нет.

### 4. Административные операции — только по действию человека, всё в аудите [Р-97]

Компрометация административного сервиса — полная компрометация тенантов, к которым у него есть доступ. Это не смягчается:
он заявляет пользователя сессии и второй фактор сам. База добавляет не доверие, а след и границы:

- таблица, запись в которую есть у административной роли и нет в списке разрешённого пути решения, получает триггер
  `security.require_person_for_admin_write()`: без пользователя сессии и без действующего членства в тенанте строки — отказ;
- и триггер `security.audit_admin_write()`: состоявшаяся запись даёт событие `admin_change.<операция>` с автором, списком
  изменённых столбцов и признаком второго фактора. Значения столбцов в событие не пишутся (среди них ссылки на секреты);
- право менять `platform.app_user` (включая `mfa_enabled`) у административной роли отозвано.

Следствие: фоновых административных задач нет. Синхронизация остатка, которой понадобится писать `stock_pool` без человека,
получит собственную роль подключения — это открытый вопрос, а не исключение из Р-97.

### 5. Перепривязка входа [Р-98]

Автоматической перепривязки нет. Владелец тенанта со вторым фактором выпускает приглашение перепривязки
(`security.invite_relink`); приём приглашения новым входом того же поставщика отзывает прежнюю привязку
(`platform.external_identity_revocation` — неизменяемая; удалить отзыв значило бы вернуть старый вход). Отозванный вход
никого не сопоставляет и приглашений не принимает. Выпуск и приём — в журнале аудита. Закрывает OQ-148.

### 6. Создание тенанта и существующие пользователи (находка 5)

`security.provision_tenant` присоединяет существующего пользователя только владельцем, только его собственным адресом и
только если он уже входил через поставщика. Остальные участники входят в тенант приглашением владельца — как в работе;
посев стенда делает то же самое (`joinMember`).

### 7. Содержимое слепка (находка 6)

`security.eternal_param_kinds()` — реестр видов значений параметров причин, сгенерированный из `reasons.ts`. Слепок
проверяется не только по именам ключей: сумма — целое, валюта — код ISO, перечисление — из объявленных значений, момент —
ISO 8601, `null` — только у объявленных nullable; формат слепка — ровно `r80.1`; имена в `withheld` — идентификаторы.

## Последствия

- Все смоук-тесты и тесты защит проверяют причину; мутационная проверка — часть сборки и CI.
- Административный сервис обязан вести пользователя сессии во ВСЕХ операциях, включая посев стенда и тесты.
- Стенд и тесты приглашают участников, а не присоединяют их созданием тенанта.
- Открыто: OQ-149 (доверие административному сервису — записан прямо), роль синхронизации остатка без человека,
  первый прогон CI в GitHub (OQ-146: у токена нет права `workflow`).
