# ADR-0019: Честный раннер мутаций без исключений, закрытие находок ревью шага 18, остаток в канал только полем QUANTITY

Статус: принято (шаг 19). Уточняет ADR-0018 (разделы 1, 5). Последний шаг линии безопасности [Р-106]: незакрытое — в
[accepted-risks.md](../accepted-risks.md).

## Контекст

Ревью шага 18 показало, что итог «не поймано 5 из 124» — нижняя граница:

- исход смоук-проверки «отказ по другой причине» раннер засчитывал своей поимкой;
- метки смоук-проверок сверялись подстрокой (`append-only channel_data.price_decision` — префикс `…_snapshot_ref`);
- причина теста сверялась с текстом, в который `assert.match` включает ожидаемый шаблон, — совпадение при любом отказе.

Плюс семь находок в защитах (статус единицы записи мимо стража, обход Р-101 через элементы и отзыв согласия, «ручная цена
владельца» от пути решения, системная остановка от человека, удаление привязок ролью хранения, гонка привязок в REPEATABLE READ,
скаляры в массивах слепка) и два пробела проверки схемы (столбцовые права роли остатков, триггеры с `WHEN (false)`).

## Решение

### 1. Честный раннер (A)

- Смоук: поимка — только «EXPECTED FAILURE DID NOT HAPPEN» своей метки; «HAD ANOTHER REASON» и «HAS NO DECLARED REASON» —
  провал проверки, но не поимка. Метка и строка успеха сверяются целиком.
- Тест (в редакции после ревью шага 19, находка 1): у проверки — точная метка утверждения и результат «без защиты». Сообщение
  утверждения попадает в поле `error` при любом провале, в том числе при отказе по другой причине, — поэтому само по себе оно ничего
  не доказывает. Поимка: для `assert.rejects` — `Missing expected rejection: <метка>` (отказа не было вовсе); для остальных — поле
  `actual` совпадает с объявленным результатом без защиты (`STOPPED` вместо `FORBIDDEN`, `accepted`, `true` и т. п.). Первая редакция
  шага (сверка сообщения утверждения) была нечестной для 51 проверки теста.
- Первый прогон честным раннером — до любых исправлений: 124 мутации, **22 не пойманы своей проверкой** (все 22 — «упала только
  соседняя»), [step19-mutation-honest-first.md](../evidence/step19-mutation-honest-first.md).

### 2. Без исключений [Р-104]

Каждая из 22 получила одно из двух:

- собственную проверку: сценарий, в котором соседняя защита не срабатывает раньше (свежий intent на каждую проверку решения,
  второй фактор в проверке журнала Р-52, второй владелец для проверки «от своего имени», уже входивший пользователь для проверок
  создания тенанта, подтесты вместо цепочки утверждений, захват отказа фиксации в тесте блокировки, сообщения утверждений);
- удаление защиты как дубля с названием защиты, которая её держит: `channel_write_end_explained` (держит ограничение истории),
  проверка владельца в стражах согласия (держит общий страж роли), отдельная проверка платформенного тенанта (у него нет участников —
  держит `audit_event_check1`, см. ниже), «не административный сервис» в страже ручного intent (у пути решения нет пользователя сессии — держит
  проверка «от своего имени»), вид элемента массива слепка (держит рекурсивная проверка скаляра), `price_decision_explanation_keys_declared`
  (тот же слепок в той же вставке проверяет ограничение вечного ядра), проверка владельца в страже отзыва согласия (держит общий страж
  роли), проверка «пользователь — действующий участник» в страже административной записи (держит `audit_event_check1`: событие USER без
  членства не записывается, а административная запись без события не фиксируется).

Две защиты, держащие одно и то же, не проверяются мутацией ни одна: без любой из них отказ даёт другая. Поэтому дубль удаляется, а в
каталоге остаётся оставшаяся защита со своими проверками. Исключение из «удалить» одно и записано как риск: «без пользователя сессии» на
таблицах с общим аудитом держат и страж, и `audit_event_check`; страж остаётся, потому что он же — единственная защита таблиц без общего
аудита (там у его мутации своя проверка), а мутация, возвращающая в страж пропуск рабочих столбцов (находка 1), в каталог не входит —
она добавляет код, а не снимает защиту ([accepted-risks.md](../accepted-risks.md), п. 9).

Сценарии, в которых своя проверка доходит до своей защиты, строились по результатам промежуточного прогона
([step19-mutation-intermediate.md](../evidence/step19-mutation-intermediate.md): 147 мутаций, 14 непойманных — все в новых строках
шага 19: элемент согласия от не-владельца отклонял страж роли, остановка витрины отклонялась индексом действующей остановки, ручной
intent — стражем режима движка и т. п.).

### 3. Находки ревью шага 18 (0072)

| № | Защита | Собственная проверка |
|---|---|---|
| 1 | на таблицах административной записи (`security.admin_write_action`) любое изменение строки в сессии административного сервиса — страж человека и аудит (статус единицы записи больше не пропускается). Таблицы пути решения административный сервис пишет и без человека — принятый риск | смоук: без человека, наблюдатель, событие аудита |
| 2 | элемент согласия — владелец, давший согласие, второй фактор, та же транзакция, существующая предполётная проверка листинга; отзыв — от своего имени, второй фактор; «только владелец» — общий страж роли | смоук: по одной на каждую ветку |
| 3 | ручной intent — только пользователь сессии административного сервиса, от своего имени, с `ENABLE_REPRICING` [Р-107] | смоук: путь решения от имени владельца, от чужого имени, наблюдатель |
| 4 | системную остановку и наблюдения её выборки не создаёт сессия административного сервиса (наблюдения — по ревью шага 19, находка 3) | смоук |
| 5 | привязки и отзывы удаляет только `repracer_identity_purger` функцией удаления отключённого пользователя; у роли хранения прав нет | смоук: `SET ROLE repracer_retention` и DELETE — отказ в правах; проверка схемы |
| 6 | привязка входа — только в READ COMMITTED (блокировка сериализует проверку только там) | тест в REPEATABLE READ |
| 7 | скаляр на месте узла слепка (корень, элемент массива причин или проверок) — отказ | подтесты |

### 4. Роль остатков пишет в канал только QUANTITY [Р-105]

Список разрешённого роли остатков расширен записью в канал и тем, что читают и пишут её триггеры; политики строк роли
ограничивают `channel_write`, `channel_write_history`, `write_scope` и `write_scope_sync_state` полем QUANTITY. Блокировка
единицы записи `FOR SHARE` в триггере записи требует права UPDATE хотя бы на один столбец — роль получила `UPDATE (status)` и
политику UPDATE только на единицах остатка; сменить статус она может только как путь решения (ACTIVE → BLOCKED, страж 0068).
Завершение записи (в том числе вытеснение ждущей новой версией) удаляет строку и её отправки правами вызывающего — роль получила
DELETE записи (незавершённую не пропускает страж удаления) и отправок с политикой по полю (ревью шага 19, находка 6). «Без цен» не
выполнено полностью: бюджет правок и состояние синхронизации роль меняет в обход «только из триггера» временным триггером —
принятый риск. Цену в запись канала роль не пишет: первой отказывает проверка пола (у роли нет чтения границ) — это не собственная проверка
политики, поэтому политика проверяется видимостью строк и вставкой в историю записей.

### 5. Проверка схемы 0073

- права роли остатков по столбцам — в обе стороны; политики роли на записях — с условием поля QUANTITY;
- условие WHEN — только у пяти перечисленных триггеров с точным текстом условия;
- функция, принадлежащая служебной роли, — SECURITY DEFINER. Правило появилось из дефекта: `CREATE OR REPLACE FUNCTION` сбрасывает
  SECURITY DEFINER и search_path, и 0069 (шаг 18) так незаметно лишила атрибутов `platform.external_identity_one_active()`;
  0072 восстанавливает атрибуты всех заменённых функций;
- DELETE привязок входа — только у роли удаления привязок; у неизменяемой платформенной таблицы без срока хранения должно быть
  удаление этой ролью.

## Последствия

- Прогоны шага: первый честный — 22 из 124; промежуточный — 14 из 147; «0 из 146» до ревью шага 19 — с нечестной сверкой проверок
  тестов ([step19-mutation-before-review.md](../evidence/step19-mutation-before-review.md)); после исправления раннера — 2 из 148
  (ветка NOT_DUE оказалась кодом ответа, а не защитой; [step19-mutation-runner-fixed.md](../evidence/step19-mutation-runner-fixed.md));
  итог — **148 мутаций, не поймано своей проверкой — 0**, контроль — 176 проверок ([step19-mutation-final.md](../evidence/step19-mutation-final.md)).
  Число относится к каталогу. Вне каталога по имени — 82 триггера, 53 именованных и 434 автоматически названных CHECK-ограничения
  ([step19-uncatalogued-protections.txt](../evidence/step19-uncatalogued-protections.txt)); что их проверки падают без своей защиты,
  не проверено ([accepted-risks.md](../accepted-risks.md), п. 13).
- Ручной intent проверяется функцией с правами роли аудита (`SECURITY DEFINER`): у пути решения нет чтения членств, и без этого отказ
  давал бы отсутствие права, а не страж. Право исполнения функции триггера — у владельца схемы: секции `price_intent` копируют триггеры.
- CI не запускался: у токена gh по-прежнему нет права `workflow` (OQ-146) — все проверки держатся на ручных запусках.
- Незакрытое — [accepted-risks.md](../accepted-risks.md), без смягчений.
