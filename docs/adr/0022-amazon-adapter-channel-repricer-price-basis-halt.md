# ADR-0022: Адаптер Amazon по снимку спецификации, чужой репрайсер, сверка базы цены, отчёт об удержаниях полом

Статус: принято (шаг 22). Решения владельца — Р-114…Р-117.

## Контекст

Снимок SP-API сохранён на шаге 20 (`vendor/amazon/sp-api-models/2026-09-16`, SOURCE.md). Адаптера Amazon не было: симулятор шага 21
моделировал Amazon портом, а не HTTP. Решение Р-32 выбрало `patchListingsItem` для цены и остатка. Доступа к живому аккаунту нет:
нет регистрации разработчика и учётных данных LWA.

Р-111 запретил писать `minimum_seller_allowed_price`, считая его включателем репрайсера Amazon. Р-114 исправил причину. Принятый
риск 19 (нетто `listing_price` у Kaufland не обнаруживается) показал класс тихих отказов на выходе, против которого у ядра проверки
нет. Отчёт шага 21 «границы остановили N опасных изменений» считал отклонения Gate, а их в норме ноль: стратегию у границы держит сам
движок.

## Решение

### 1. Два пакета: клиент и адаптер

- **`packages/amazon-client`** — транспорт без знания о ценах:
  - токен LWA по `refresh_token` с кэшем до `expires_in − 60 с`;
  - заголовки `x-amz-access-token`, `x-amz-date`, `user-agent`;
  - регионы NA/EU/FE;
  - повтор 429 — всегда; повтор 5xx и сетевых ошибок — только у идемпотентных запросов (GET);
  - таймаут записи — «итог неизвестен», без повтора;
  - тело ошибки LWA не логируется.
- **`packages/amazon-adapter`** — порт `ChannelAdapter` шага 5:
  - **цена** — `purchasable_offer.our_price[].schedule[].value_with_tax`, `op: merge`, селекторы `marketplace_id`, `currency`,
    `audience: ALL`;
  - **остаток** — `fulfillment_availability` с кодом `DEFAULT`. Единица записи — аккаунт + регион + SKU (A-01 подтверждён
    документацией: у атрибута нет селектора витрины);
  - **цены нескольких витрин одного SKU** уходят одним PATCH, но только внутри региона. В Release 1.0 одна витрина ЕС, поэтому
    ветка не достигается (AMZ_C06);
  - **Amazon подтверждает запись асинхронно:** `ACCEPTED` означает «принято», применение подтверждает обратное чтение
    `getListingsItem`. Окно подтверждения — 30 минут (проверить, A-06);
  - **конкуренты** — уведомление `ANY_OFFER_CHANGED` (снимок TOP_N). Опроса нет: `getCompetitiveSummary` — 0.033 rps, порт
    отвечает UNSUPPORTED (AMZ_C07);
  - **заказы** — UNSUPPORTED: Orders API не в снимке, и это PII [Р-4].
- Всё, что документация не подтверждает, — консервативные правила **AMZ_C01…C10** с вопросами A-nn, каждое пишет лог при
  срабатывании. Стенд проверяет, что каждое правило достижимо; C06 недостижим в Release 1.0, и это записано в тесте.

### 2. Ограничитель на двух уровнях

`TwoLevelBudget` — корзины токенов на пару «продавец–приложение» и на приложение по операциям (`patchListingsItem` 5/500,
`getListingsItem` 5/100, `searchListingsItems` 5/100 rps, burst 5).

- Запрос забирает токен из обеих корзин атомарно. Отказ называет уровень: PAIR или APPLICATION.
- Нагрузка других продавцов на приложение уменьшает burst приложения, но пока свободная скорость есть, burst не меньше 1 (ревью шага 22,
  находка 3). Это параметр стенда: у адаптера нет данных чужих тенантов, есть
  только общий счётчик приложения.
- Заголовок `x-amzn-RateLimit-Limit` уточняет лимит пары (AMZ_C10).

### 3. Запрещённые атрибуты [Р-114]

`NEVER_WRITTEN_CHANNEL_ATTRIBUTES` несёт причину.

| Причина | Атрибуты |
|---|---|
| `CHANNEL_REPRICER` | Kaufland `minimum_price`; Amazon `automated_pricing_merchandising_rule_plan` |
| `SECOND_BOUNDS` | Amazon `minimum_seller_allowed_price`, `maximum_seller_allowed_price` |

- Адаптер строит тело только из `our_price` и `fulfillment_availability`.
- Контрактный стенд отклоняет запрос, в теле которого есть любой запрещённый атрибут канала — ключом значения или путём операции PATCH
  (ревью шага 22, находка 8). Это закрывает находку 6 ревью шага 21:
  база видит поле порта, а не тело запроса.

### 4. Чужой репрайсер и границы канала [Р-115]

**Перед каждой записью цены адаптер читает оффер** (AMZ_C03). Если есть привязка к правилу автоматического ценообразования, PATCH не
отправляется: отказ `CHANNEL_REPRICER_ACTIVE` класса REQUIRES_HUMAN. Если у оффера есть границы канала, отказ —
`CHANNEL_BOUNDS_PRESENT`.

**Изменения правил асинхронны,** поэтому обратное чтение проверяет то же и отказывает тем же кодом.

**Ядро:**
- **отказ записи** блокирует единицу, как и раньше;
- **отказ сверки** с кодом `CHANNEL_REPRICER_ACTIVE` или `CHANNEL_BOUNDS_PRESENT` теперь тоже блокирует единицу сразу. Раньше сверка
  повторялась бы час до OUTCOME_UNRESOLVED. Принятая запись остаётся принятой. Прочие отказы «нужен человек» (например, отказ сервера
  токенов) сразу не блокируют: они не про оффер (ревью шага 22, находка 2);
- **алерт:** CRITICAL `PRICE_WRITE_SCOPE_BLOCKED` несёт код;
- **причина HELD** несёт действие продавца: «выключить репрайсер канала» или «убрать границы канала» (DE/EN).

### 5. Сверка базы цены [Р-116]

**Проверка.** `priceBasisMismatch(отправлено, применено, ставка НДС)` — расхождение ровно на ставку в любую сторону, с допуском 1 цент
на округление (проверить). Если ставка по сумме неотличима от округления или ставки нет, проверка не выполняется. Ставки нет в режиме
sales tax (США).

**Где сравнивается.** Цену покупателя берут три места: диспетчер после сверки с итогом APPLIED, диспетчер после синхронного применения
повтора и путь решения после синхронного применения первой отправки (ревью шага 22, находка 1). Цена покупателя — `effectivePrice`
адаптера (у Amazon — цена оффера B2C, у Kaufland — поле `price` unit). Если она не совпала с отправленной, вызывается
`checkPriceBasis` хранилища. В остановке хранятся только наши значения, прочитанная цена — нет [Р-3].
Сверка с итогом NOT_APPLIED (канал сохранил сумму другой базы) базу не проверяет — риск 19. Хранилище
берёт ставку товара и налоговый режим единицы — ту же ставку, что у пола маржи.

**Что происходит.** При расхождении на ставку ставится **системная остановка витрины `CHANNEL_PRICE_BASIS_MISMATCH`** и поднимается
CRITICAL-алерт `PRICING_PRICE_BASIS_MISMATCH` (коды и ставка, без сумм).

**Чем эта остановка отличается от остановки по массовому сдвигу:**
- **Блокирует любую цену.** Канал применяет каждую нашу сумму с той же ошибкой — фиксированную и маржинальную тоже. База: 0080,
  `ac_price_decision_basis_halt_guard` и `bc_channel_write_basis_halt_guard`. Gate и двойник в памяти ведут себя так же. Когда у
  витрины две остановки, решение видит эту первой.
- **Не снимается выборкой.** `review_halt_by_sample` проверяет только CHANNEL_MASS_SHIFT: свежие цены конкурентов не доказывают, что
  канал понимает базу цены. Снимает человек с заметкой и вторым фактором.
- **Не мешает остановке по массовому сдвигу:** одна действующая остановка — на витрину и причину, а не на витрину.

**Почему системная остановка, а не остановка человеком.** Её ставит система по данным канала. Расширение Р-51/Р-69 («системная
остановка — только цены из данных конкурентов») записано вопросом владельцу (OQ-162).

**Покрытие Kaufland.** Проверка общая для каналов. У Kaufland `effectivePrice` — поле `price` unit. Симулятор шага 21 с нетто
`listing_price` (K-12) теперь заканчивается остановкой и алертом, а не молчанием. Включает ли `price` доставку или Smart Pricing, не
известно (K-12): тогда возможна ложная остановка (риск 20). Обнаружение по снимку Buy Box — OQ-158.

### 6. Отчёт об удержаниях полом [Р-117]

**Главное число** — сколько раз пол удержал стратегию:
- `CAPPED_AT_MIN_PRICE` — цена поставлена на пол;
- `TARGET_OUTSIDE_BOUNDS_HOLD` с целью ниже пола — цена оставлена без изменения.

**Удержание — эпизод:** подряд идущие оценки одной единицы, в которых пол держит цену, считаются одним удержанием. Иначе цена на полу
давала удержание на каждой оценке (ревью шага 22, находка 4).

**Сумма X** — по эпизодам: наибольшая за эпизод разница «удержанная цена − цель стратегии», по валютам. Удержанная цена — пол или
текущая цена, оставленная без изменения.

**Ограничение данных.** Цель выведена из цены конкурента и живёт только в горячем intent 3 дня [Р-85, Р-28]. Старше видны только
удержания, сдвинувшие цену на пол (решение со слепком), — без суммы. Удержания без изменения цены (NO_OP) старше 3 дней не видны
вовсе. Это пробел экрана, а не ноль.

**Второй раздел** — отклонения Gate больше 10 % за границей [Р-73].

### 7. Контрактный стенд Amazon

Тот же формат сценария и тот же раннер, что у Kaufland.

**Проверки раннера:**
- обмен LWA — поля формы;
- заголовки SP-API — токен и момент виртуальных часов;
- ни одного секрета в URL, теле и заголовках;
- ни одного запрещённого атрибута в теле.

**Сценарии:**
- обязательные сценарии Kaufland в смысле Amazon;
- асинхронное применение и «принято, но не применено»;
- чужой репрайсер при записи и при сверке, границы канала;
- оба уровня ограничителя, остаток на регион;
- сверка базы цены;
- 16 сценариев пути решения, преобразованных из Kaufland генератором фикстур.

**Хранилища.** Сценарии пути решения идут на памяти и на PostgreSQL (`amazon.pipeline.pg.test.ts`). Посев PostgreSQL научился
аккаунту мира Amazon.

## Найдено при построении

1. **Р-52 на Amazon недостижим.** Автоматическое снятие остановки витрины требует свежей независимой выборки, а выборка — это опрос
   конкурентов, которого у Amazon нет. Остановка по массовому сдвигу снимается только вручную (OQ-164).
2. **Дефект ядра, не только Amazon.** Когда сверка останавливалась у принятой записи (D1, теперь и Р-115), код ошибки не попадал в
   причину HELD: продавец видел «проверьте статус оффера» вместо своего действия. Хранилища искали код только у FAILED; исправлено в
   обоих. Код прежней временной ошибки теперь очищается при приёме записи, чтобы не попасть в причину HELD (ревью, находка 13).
3. **Идентичность оффера расходится между путями.** Путь решения передаёт `externalUnitId = SKU`, очередь записей — `externalSku` и
   регион. Адаптер принимает оба варианта (OQ-165).

## Последствия

- Адаптер Amazon готов к живому аккаунту, но ни один запрос не отправлялся в Amazon. Все фикстуры синтетические по документации.
- Остановка по базе цены — новая защита в базе. У неё смоук-проверки и строка каталога мутаций «Р-116» (4 мутации). Проверка схемы
  перенесена в 0081.
- Периодической проверки чужого репрайсера у офферов без записей нет (OQ-163). Правило, привязанное в кабинете к офферу, цену которого
  мы не меняем, обнаружится при следующей записи.

## Отклонённые варианты

- **Писать `maximum_seller_allowed_price` = наш `max_price`, чтобы Amazon сам держал потолок.** Это второй набор границ [Р-114]: при
  рассинхронизации версий Amazon отклонит нашу цену.
- **Остановка человеком (`price_stop`) при неверной базе цены.** Автор остановки — человек [Р-76]; система не может её создать от
  чужого имени.
- **Снимать остановку по базе цены выборкой.** Выборка проверяет рынок, а не понимание базы цены каналом.
