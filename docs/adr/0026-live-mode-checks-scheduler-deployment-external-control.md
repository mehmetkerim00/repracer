# ADR-0026. Проверка в живом режиме, развёртывание планировщика и внешний контроль

Дата: 2026-09-18. Статус: принято. Решения владельца: Р-127, Р-128, Р-129.

## Контекст

Ярусный опрос [Р-47] не работал с шага 17 до шага 25: условие «движения цены» было `move_bp <> 0`, а коэффициент «цена не изменилась»
равен 10 000. Дефект пережил девять шагов, потому что ярусы проверялись вызовом функции планирования, а не наблюдением за сутки работы.
Это третий случай одного типа: главный инвариант границ (шаг 15) и проверка валюты сумм (шаг 16) тоже были написаны, покрыты тестами и не
исполнялись. Одновременно у планировщика [Р-126] не было ни развёртывания в репозитории, ни внешнего контроля: об остановке процесса
никто не узнаёт, пока он не вернётся (риск 29).

## Решение

### 1. Живой режим как способ проверки [Р-128]

Периодическая работа проверяется прогоном процесса, а не вызовом её функции. Проверка утверждает наблюдаемое за период: запросы, дошедшие
до канала, и строки, появившиеся в базе. Мир прогона — настоящая PostgreSQL (отдельная база), симулятор канала с состоянием [Р-113] и
модель порта Amazon, приёмник уведомлений и диспетчер записей между тактами, виртуальные часы. Виртуальные сутки заканчиваются «сейчас»:
часы базы всегда позже виртуальных, иначе проверки базы отклоняют моменты из будущего.

Каждая работа каталога обязана иметь утверждение о наблюдаемом поведении: работа без него — красная сборка. Это правило того же вида,
что «тест вне сборки не существует» [Р-89] и «мутация ловится своей проверкой» [Р-99].

### 2. Что нашёл первый прогон

Семь дефектов, из них четыре — в работах, которые «работали» по своим тестам (подробности и числа — docs/evidence/step26-live-mode.md).
Главные: новый товар и товар, где Buy Box держим мы, застревали в холодном ярусе; половина офферов Amazon не сверялась ни разу;
остановка витрины без ENGINE-товаров не снималась никогда.

### 3. Развёртывание [Р-129]

`deploy/scheduler/compose.yaml`: закреплённые версии образов, один экземпляр, `restart: unless-stopped`, конфигурация переменными
окружения, секреты — файлами (в переменных окружения их видит `docker inspect`), проверка работоспособности по `/healthz` процесса,
ограничение журнала. Точка входа `services/scheduler/src/main.ts` собирает процесс: каталог аккаунтов — база [Р-31], учётные данные —
файл на `credentials_ref`, журнал и алерты — строки JSON в stdout, метрики — Prometheus без идентификаторов тенантов.

### 4. Внешний контроль [Р-127]

Процесс отмечается во внешнем сервисе после каждого такта. Проверка `/healthz` и перезапуск контейнера ловят зависший процесс, но не
видят остановленный контейнер и выключенный хост — их видит только тот, кто ждёт отметку снаружи. Отсутствие отметки дольше периода и
допуска сервис превращает в письмо владельцу.

Протокол выбран по документации Healthchecks.io (снимок страниц — `vendor/healthchecks/`): `GET <адрес>` — «жив», `GET <адрес>/fail` —
«сбой». Адрес содержит идентификатор проверки, поэтому это секрет развёртывания. Ответ 200 не подтверждает запись отметки («not found» и
«rate limited» — тоже 200): подтверждение — только письмо при пропуске, которое проверяется при подключении аккаунта.

### 5. Часы сроков — часы базы [риск 31]

Срок работы сравнивается с `now()` базы, а не процесса: разошедшиеся часы процесса не запускают работу раньше срока. Уровень отставания,
по смене которого поднимается алерт, хранится в строке работы: перезапуск и второй процесс алерт не повторяют.

## Последствия

- Проверка суток занимает около трёх минут машинного времени на прогон — это цена за наблюдаемое поведение; она входит в сборку.
- Модель внешнего сервиса — наша: реальный сервис не подключён (нет аккаунта), письмо при пропуске проверяется по документации, а не
  ответом сервиса (docs/evidence/step26-external-control.md).
- Живой режим проверяет то, что умеет модель канала: ошибки модели становятся ошибками проверки. Два дефекта модели Amazon шаг нашёл и
  исправил (пакет getCompetitiveSummary, источник снимка сверки).
