# ADR-0042: промышленная проводка под прогоном пилота, кэш миров по членствам, вход панели у поставщика

Статус: принято (шаг 45). Решения: [Р-181…Р-183](../decisions.md). Закрыты OQ-236 и OQ-238.

## Контекст

Шаг 44 прошёл путь пилота одним прогоном, но консоль в нём была собрана тестом из тех же служб — `createStandServer`,
`createChannelConnectService`, `createTenantWorlds`, — а не функцией, которую запускает контейнер. Класс находки шага 43
как раз такой: подмена в прогоне скрывает ровно тот стык, который подменяет. Ревью шага 44 оставило ещё два пробела:
мир тенанта строился на каждый запрос для ВСЕХ тенантов пользователя (агентство из 50 тенантов — сотни обращений к базе
на клик), а страница панели оператора входить у поставщика не умела. И вопрос OQ-238 — где у ZITADEL адрес и методы
входа — был отложен как «(проверить) по документации».

## Решение

1. **Прогон пилота — через `startConsole(env)` и сервис `bulk-worker` в режиме окружения** [Р-181]. Всё, чем прогон
   отличается от работы, — значения, принимаемые только режимом стенда: адрес обнаружения модели поставщика на петле
   и адрес токенов LWA на петле. Планировщик и диспетчер остаются собранными тестом: канал в них — модель порта, а не
   HTTP; это сказано в доказательстве.
2. **Указатель миров с кэшем по отпечатку членств** [Р-182]. Principal читается из базы при каждом запросе, значит
   отпечаток его членств — точный ключ: изменение членства видно следующим запросом без общей шины инвалидации между
   репликами. Счётчики списка — одним обращением (пары «контекст тенанта; счётчики» в одной транзакции), мир — только
   запрошенный.
3. **Снимок документации ZITADEL** ([vendor/zitadel/SOURCE.md](../../vendor/zitadel/SOURCE.md)): в токене доступа нет ни
   `email`, ни `email_verified`, ни `amr`. Адрес для приёма приглашения — из userinfo, второй фактор — из ID-токена,
   который страница передаёт заголовком `x-repracer-id-token`; сервер проверяет его подпись, аудиторию (клиент
   страницы) и совпадение `sub`. Токен доступа приложения — JWT: сервер проверяет его ключами. Модель поставщика
   прогонов повторяет эту матрицу — и, после находки 1 ревью, аудиторию ID-токена «клиент + проект» и `auth_time`; ID-токен
   как Bearer не принимается, а второй фактор из него привязан к тому же обмену кода по `iat`.
4. **Панель входит сама** [Р-183]: тот же модуль входа (панель отдаёт его по `/oidc.js`), свой клиент, второй фактор из
   ID-токена; промышленный профиль панели отказывает режиму стенда и локальному издателю при старте.

## Последствия

- Прогон пилота: 4,2 с настоящего времени против 5,0 с на шаге 44; самый долгий экран — 0,038 с против 0,156 с
  ([доказательство](../evidence/step45-pilot-live.md)).
- Клик агентства из 50 тенантов: список миров 452 → 2 обращения к базе, экран пути 164 → 16, товары 171 → 23
  ([замер](../evidence/step45-agency-click.md)).
- Снимок нашёл второй, незамеченный дефект: с настоящим ZITADEL второй фактор не доходил бы до базы вовсе — каждая
  операция, требующая его (массовые правки, смена ролей, перевод в бой), отказывала бы владельцу пилота.
- Название настройки «тип токена доступа JWT» в консоли ZITADEL страницы снимка не называют — (проверить) при заведении
  приложения; без неё вход откажет всем, а не пропустит.
