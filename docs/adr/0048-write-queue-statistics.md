# ADR-0048: статистику очереди записей обновляет большая транзакция

Статус: принято (шаг 66, Р-203, OQ-247).

## Контекст

`tenant_data.channel_write` — очередь: запись живёт в ней, пока не дошла до канала, затем уходит в историю. Очередь в работе то и дело
пустеет. Статистика, снятая в этот момент, говорит «0 строк на N страниц». Это бывает, когда:
- автоанализ застал опустевшую очередь;
- очистка не смогла обрезать файл — например, в его конце живая строка или блокировку не дали.

При такой статистике каждый путь к таблице стоит для планировщика одну строку. На воспроизведении все кандидаты — индексы с
`tenant_id`, частичные индексы ждущих — имели стоимость 4,13. Выбор между ними решают мелочи: высота деревьев, порядок индексов. Поиск
«прежние версии этой единицы», «ждущая запись этой единицы», даже поиск записи по полному ключу шли индексом тенанта. Транзакция,
ставящая в очередь десятки тысяч записей, проходила на каждой строке все предыдущие: пересчёт остатков 50 000 единиц — около 10 минут
вместо 17 с (шаг 65). Выборка кандидатов работы заказов — больше 7,8 минуты вместо 2,8 с.

## Что проверено и не держит план

На воспроизведении — строки вставлены и удалены, затем очистка или анализ, затем всплеск записей в транзакции:

| Вариант | Итог |
|---|---|
| `vacuum_truncate = off` | Хуже: очистка оставляет «0 строк на N страниц» — ровно ловушку. Спасает как раз обрезка файла до нуля страниц: тогда планировщик оценивает строки по текущему размеру файла |
| Анализ только при большой очереди, автоанализ выключен | Очистка всё равно записывает живые строки — ноль; выключенный автоанализ замораживает статистику столбцов (ревью) |
| Барьеры `MATERIALIZED`, `OFFSET 0` | Выбор индекса внутри барьера тот же |
| `ORDER BY version` (порядок даёт только индекс единицы) | Держит в одних состояниях и не держит в других: битовая карта с сортировкой у плана дешевле |
| Перестановка столбцов уникальных ключей | PostgreSQL берёт индекс и по неведущему столбцу |
| Партиции с ротацией | Не понадобились |

## Решение

1. **Большая транзакция обновляет статистику сама.**
   - Строчный триггер `aa_channel_write_queue_stats` идёт первым по алфавиту среди AFTER INSERT — раньше поиска прежних версий. Число
     вставленных транзакцией записей — счётчик в настройке транзакции, помеченный её номером: чужой номер — счёт с нуля.
   - Счётчик PostgreSQL (`pg_stat_get_xact_tuples_inserted`, первая редакция по ревью) не годится: он несёт и вставки прежних
     транзакций сеанса, пока статистика сеанса не сброшена (до 10 с). Маленькая транзакция сразу после большой в том же соединении
     пула делала ANALYZE — нашёл тест «меньше порога — без анализа». Подделать настройку может сам сеанс — и получит ANALYZE в своей
     транзакции: держать эту блокировку роль с правом изменения очереди может и `LOCK TABLE`, нового он не получает.
   - На сотой записи — `ANALYZE` очереди. Внутри транзакции он считает её незафиксированные строки живыми, и следующие поиски той же
     транзакции идут индексом единицы. AFTER ROW срабатывает после всей многострочной вставки, поэтому к сотой строке в таблице уже вся
     вставка.
   - Функция триггера — от владельца очереди. Права исполнения нет ни у одной роли: триггер срабатывает от события таблицы. У роли
     остатков по-прежнему нет функций с правами владельца (Р-102), это держит проверка схемы.
   - Блокировку ANALYZE ждать 2 с — дольше `deadlock_timeout` (1 с). Автоочистку, держащую её, база снимает ради ждущего сеанса
     только через `deadlock_timeout`; при 100 мс ожидания попытки на всех порогах проигрывали автоанализу за доли секунды, и боевой
     пересчёт 50 000 шёл 767 с вместо 27. Занято дольше — другая большая транзакция держит блокировку до своей фиксации — повтор на
     вдвое большем числе записей, в том числе внутри одной многострочной вставки. Ожидание дольше `deadlock_timeout` может
     быть выбрано жертвой взаимоблокировки — это тоже повтор, а не отказ транзакции.
   - Обычные транзакции — одна-две записи — до порога не доходят.
2. **Автоанализ очереди остаётся включённым.** Первая редакция шага его выключала. Ревью показало, что тогда статистика столбцов
   замерзает на выборке последней большой транзакции: тенант, которого в ней не было, снова попадает в ничью путей, а его очередь,
   накопленную мелкими транзакциями, не анализирует никто. Пустую очередь с мёртвыми строками автоанализ не застаёт: при большом числе
   мёртвых строк автоочистка сначала очищает таблицу, потом анализирует.
3. **«Уже объявлено в транзакции»** (отложенный триггер объявления диспетчеру) — множество по хешу единицы, 1024 корзины. Одна строка
   на всю транзакцию была квадратичной: 50 000 записей — около 55 с. Корзинами — 0,16 с. Квадрат остался в каждой корзине, деление на 1024
   делает его заметным только на сотнях тысяч записей в одной транзакции.

## Последствия

- Ловушку держат:
  - `write-queue-stats.pg.test.ts` — портит статистику, проводит настоящий пересчёт через настоящие триггеры. Утверждает:
    - большая транзакция проанализировала очередь (время ручного анализа, автоанализ его не трогает) — строка каталога мутаций
      «шаг 66 (Р-203)»;
    - после этого поиск идёт индексом единицы;
    - транзакция меньше порога не анализирует;
    - пока блокировку держит другой сеанс, транзакция ждёт не дольше 2 с на попытку и не падает, а следующая после освобождения
      анализирует;
  - замер масштаба — портит статистику перед каждой операцией, пределы те же. Для чтений ловушка безвредна, когда очередь пуста, и
    снята очисткой, когда в ней живые строки: держатся этим замером операции записи.
- Остаток:
  - ручной `ANALYZE` пустой очереди до её очистки возвращает ловушку для чтений — README профиля §4а;
  - транзакция, вставляющая записи ПО ОДНОЙ строке в тени, к порогу успевает убрать свои строки в историю — анализ сосчитает мало. Пересчёт
    остатков и включение вставляют многострочно;
  - ожидание дольше `deadlock_timeout` делает взаимоблокировку возможной в принципе: транзакция, уже держащая блокировку анализа, ждёт
    строку или блокировку другой большой транзакции, а та ждёт анализа. Жертвой становится тот, чья проверка сработала первой: наше
    ожидание — повтор позже, чужая транзакция — отказ `40P01`. Шаг 67 разобрал, достижим ли цикл, — **сейчас нет**:
    - в очередь вставляют ровно два места кода: путь решения (одна запись на транзакцию, порога анализа не достигает) и пересчёт
      остатков, а функции базы в очередь не вставляют;
    - пересчёт берёт блокировку пересчётов тенанта ДО вставки (шаг 57): второй пересчёт того же тенанта ждёт её и до анализа не доходит;
    - после вставки пересчёт ждёт только маленькие транзакции (захват диспетчера, отзыв подтверждения), а те анализа не ждут никогда.
  - Дешёвой защиты в коде нет: ждать только автоочистку функция не может — `backend_type` чужих сеансов роли без `pg_read_all_stats`
    не видна, а это право читать тексты запросов всех сеансов. Поэтому условие держит правило репозитория: «в очередь вставляют ровно два
    места кода, и вставка пересчёта — после блокировки пересчётов тенанта». Третий массовый писатель очереди красит сборку и требует
    разобрать цикл заново.
  - Распознать по журналу, если случится: `ERROR: deadlock detected` с `DETAIL: Process … waits for ShareUpdateExclusiveLock on relation …
    (channel_write)` — ожидание анализа очереди в цикле;
  - транзакция из одних обновлений (отзыв, перевод в тень) статистику не обновляет: её строки к фиксации уходят в историю, и анализ
    сосчитал бы ноль. Поиски в ней идут по строкам, которые были в очереди до неё, — статистика их видела.
