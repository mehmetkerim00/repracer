# ADR-0066: две полосы CI и ночной полный прогон main

Статус: принято (шаг 110, Р-236). Уточняет Р-137 (быстрый и полный прогон). Опирается на Р-95 и Р-108 (мутационная проверка — в полном
прогоне), Р-84 и Р-89 (тест не пропускается и не выпадает из сборки), Р-146 (находка закрывается правилом).

## Контекст

1. С шага 29 каждый шаг сливается в main только после двух зелёных прогонов одного коммита: быстрого от push (типы, юнит-тесты, PostgreSQL,
   критичные мутации) и полного по запросу (весь каталог мутаций, брокер, ClickHouse, развёртывания, сутки демо и тени, хаос, масштаб).
   Полный идёт 60–100 минут. Шаг, меняющий только текст экрана, ждёт его так же, как шаг с миграцией.
2. Полный прогон шёл и на каждый push в main. Для шага, уже проверенного полным прогоном на ветке, это был повтор того же коммита.
3. На последних 30 шагах (история до 109.1) семь касались только консоли, текстов и документов: 95, 96.2, 97.4, 98.1, 99.1, 99.2, 100.
   Что ловит только полный прогон, у таких шагов почти не меняется: каталог мутаций ссылается на тесты хранилища, а хаос, масштаб и
   развёртывания проверяют процессы и базу.

## Решение

1. **Полоса — по диффу, скриптом** (`scripts/ci-lane.mjs`). Лёгкие места — явный список:
   - `apps/console/src/`;
   - `packages/console-model/src/`;
   - `apps/console/test/`;
   - `docs/`;
   - `CLAUDE.md`, `README.md`.

   Путь вне списка — тяжёлая полоса: «спорное = тяжёлая». Сюда попадают и сервер консоли, и конфигурация её сборки, и зависимости,
   и процесс CI, и сами правила. Тест в лёгком месте тоже тяжёлый, если быстрый прогон его не гоняет (`scripts/test-scopes.mjs`) или на
   него ссылается каталог мутаций (`tests/db/mutations.mjs`): его правку видит только полный прогон. Одного тяжёлого пути хватает, чтобы
   весь шаг шёл тяжёлой полосой. Пустой дифф — тяжёлая.
2. **Слияние — скриптом с одним решением** (`scripts/merge-when-green.mjs`, функция `mergeDecision`):
   - лёгкая полоса — по зелёному быстрому прогону ветки этого коммита; затронутые тесты называются в отчёте шага;
   - тяжёлая — по зелёным быстрому и полному прогону ветки того же коммита;
   - красный прогон — стоп с причиной;
   - красная последняя ночь — стоп для любого шага;
   - **только fast-forward проверенного SHA** (уточнение владельца): ворота читают прогоны по точному SHA и отправляют в main ровно его,
     без force; перед слиянием `origin/main` обязан быть его предком (`isFastForward`), иначе стоп `NOT_FAST_FORWARD`. Merge-коммит,
     rebase, push другого SHA — новый коммит без прогонов: его отправляют веткой, и ворота ждут его прогоны по его полосе (у тяжёлой —
     полный обязательно);
   - сбой чтения GitHub или `git fetch` — ожидание до следующего опроса (`READ_FAILED`), а не конец ворот; неудачный пуш повторяется
     следующим опросом после новой проверки fast-forward.
3. **Ночной полный прогон main** (`on.schedule`, 02:17 UTC). Ночь — последний завершённый прогон main по расписанию или повтор по
   запросу на main. Не зелёная, в том числе снятая, — разбор первым делом; слияния стоят до зелёной ночи. **Сторож ночи** (довесок
   владельца) — задание `night-watch` после всех заданий ночи при любом их исходе (`scripts/night-watch.mjs`): красная ночь — Issue
   «Красная ночь YYYY-MM-DD» с меткой `night-red`, ссылкой на прогон и упавшими заданиями; повторная — комментарий в открытый; зелёная —
   комментарий и закрытие. Уведомление не зависит от настроек почты аккаунта; ворота держат и красная ночь, и открытый Issue — вместе.
4. **Полные задания** — `full`, `demo-day`, `shadow-day`, `chaos`, `scale` — идут только по расписанию и по запросу, на push больше нет.
   Быстрые задания — `fast` (два шарда), `guards`, `clickhouse-compression` — на каждый push, как прежде.
5. Правило репозитория `scripts/test/ci-lanes.test.ts` держит три вещи, у каждой положительный контроль [Р-94]:
   - классификатор: лёгкое, тяжёлое, спорное, тесты полного прогона и каталога;
   - таблицу решения слияния, fast-forward на настоящих репозиториях git и цикл ворот при сбоях чтения и пуша;
   - сторожа ночи: план Issue (создать, дописать, закрыть) и команды `gh`;
   - форму `ci.yml`: расписание раз в сутки не в начале часа, полные задания — только ночью и по запросу, быстрые — без условия,
     сторож — после всех заданий при любом исходе, только на main, с правом на Issues.

## Последствия

- Шаг лёгкой полосы сливается после быстрого прогона, около 25–40 минут, а не 60–100. Что ловит только полный прогон, у такого шага
  увидит ночь: до 24 часов позже. Красная ночь останавливает слияния, поэтому дефект не копится под новыми шагами.
- Повтор полного прогона на push в main исчезает. Это верно, пока слияние — fast-forward того же проверенного SHA: тогда main получает
  ровно коммит, прошедший оба прогона (тяжёлая полоса) или быстрый (лёгкая — её ловит ночь). Ворота сливают только так. Push в main
  мимо ворот запрещён правилом, но технически не закрыт (защиты ветки на стороне GitHub нет): такой коммит не проверен, и первой его
  увидит ночь.
- Расписание GitHub Actions работает только на ветке по умолчанию и только когда файл workflow лежит в main. Время — UTC. Запуск может
  сдвинуться или быть снят при пиковой нагрузке (сильнее всего — в начале часа). В публичном репозитории расписание отключается после
  60 дней без активности. Уведомление о ночи получает пользователь, последним менявший строку cron. Источник —
  [docs.github.com, Events that trigger workflows, schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- Список лёгких мест расширяется только решением владельца: правило держит его дословно.

## Красная ночь и её исправление (шаг 110.3, решения владельца после ночи 2026-10-31)

Первая красная ночь (2026-10-31, Issue #19) показала два пробела правила. Подробно — [docs/evidence/step110.3-repair-mode.md](../evidence/step110.3-repair-mode.md).

**1. Тупик исправления.** Ворота останавливали любой шаг при красной ночи или открытом Issue — и сам шаг, который ночь чинит. Решение
владельца — **режим исправления**: `merge-when-green.mjs <ветка> <sha> --repair <Issue>`.
- Действует, только пока есть что чинить: ночь красная или Issue красной ночи открыт. Чинить нечего — обычные правила полосы.
- Исправляет ровно открытый Issue этой ночи: другой номер или Issue нет — стоп `REPAIR_ISSUE_NOT_OPEN`. Issue — ручка исправления.
- Сливает только по ОБОИМ зелёным прогонам своего SHA — полный обязателен и лёгкой полосе (`REPAIR_BOTH_GREEN`); fast-forward — как всегда.
- После слияния ворота запускают полный прогон main и пишут комментарий в Issue; зелёный прогон закрывает Issue сторожем ночи (повтор по
  запросу на main считается ночью). До его итога остальные шаги стоят — ночь всё ещё красная.
- Тупика нет: ворота — локальный скрипт. Шаг, вводящий режим исправления, сливается им же; затем — само исправление ночи, затем — шаги,
  ждавшие зелёной ночи, перебазированными.

**2. Пограничный замер и погода раннеров.** Замер «полное состояние каталога на 50 000» (медиана трёх прогонов, предел 10 с — шаг 107)
на одном и том же коммите `dfc98e8`:

| Прогон | Медиана | Три прогона |
|---|---|---|
| полный на ветке, 2026-10-29 | 6,95 с | 7,18 / 6,95 / 6,92 |
| ночь 2026-10-30 | 9,97 с — зелёная | 9,97 / 9,84 / 10,10 |
| ночь 2026-10-31 | 10,23 с — красная | 10,24 / 10,05 / 10,23 |

Код не менялся: разброс раннеров GitHub — почти 50 %. Пока ночь не была воротами, пограничный замер красил одно задание; теперь он
останавливает слияния всех. Решение владельца: **предел временно 15 с** (квадратичный рост он по-прежнему ловит — вдвое больше каталога,
вчетверо дольше) **и оптимизация отдельным шагом** — массовые маршруты записи перестают читать полное состояние каталога; **после
оптимизации предел ВЕРНУТЬ к 10 с**. Это не сдача принципа, а признание погоды: послабление временное, обратный билет — строка
[docs/deferred.md](../deferred.md), и пока предел выше цели, без неё сборка красная (`tests/contract/src/scale-median.test.ts`).
