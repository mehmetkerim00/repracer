# ADR-0066: две полосы CI и ночной полный прогон main

Статус: принято (шаг 110, Р-236). Уточняет Р-137 (быстрый и полный прогон). Опирается на Р-95 и Р-108 (мутационная проверка — в полном
прогоне), Р-84 и Р-89 (тест не пропускается и не выпадает из сборки), Р-146 (находка закрывается правилом).

## Контекст

1. С шага 29 каждый шаг сливается в main только после двух зелёных прогонов одного коммита: быстрого от push (типы, юнит-тесты, PostgreSQL,
   критичные мутации) и полного по запросу (весь каталог мутаций, брокер, ClickHouse, развёртывания, сутки демо и тени, хаос, масштаб).
   Полный идёт 60–100 минут. Шаг, меняющий только текст экрана, ждёт его так же, как шаг с миграцией.
2. Полный прогон шёл и на каждый push в main. Для шага, уже проверенного полным прогоном на ветке, это был повтор того же коммита.
3. На последних 30 шагах (история до 109.1) семь касались только консоли, текстов и документов: 95, 96.2, 97.4, 98.1, 99.1, 99.2, 100.
   Что ловит только полный прогон, у таких шагов почти не меняется: каталог мутаций ссылается на тесты хранилища, а хаос, масштаб и
   развёртывания проверяют процессы и базу.

## Решение

1. **Полоса — по диффу, скриптом** (`scripts/ci-lane.mjs`). Лёгкие места — явный список:
   - `apps/console/src/`;
   - `packages/console-model/src/`;
   - `apps/console/test/`;
   - `docs/`;
   - `CLAUDE.md`, `README.md`.

   Путь вне списка — тяжёлая полоса: «спорное = тяжёлая». Сюда попадают и сервер консоли, и конфигурация её сборки, и зависимости,
   и процесс CI, и сами правила. Тест в лёгком месте тоже тяжёлый, если быстрый прогон его не гоняет (`scripts/test-scopes.mjs`) или на
   него ссылается каталог мутаций (`tests/db/mutations.mjs`): его правку видит только полный прогон. Одного тяжёлого пути хватает, чтобы
   весь шаг шёл тяжёлой полосой. Пустой дифф — тяжёлая.
2. **Слияние — скриптом с одним решением** (`scripts/merge-when-green.mjs`, функция `mergeDecision`):
   - лёгкая полоса — по зелёному быстрому прогону ветки этого коммита; затронутые тесты называются в отчёте шага;
   - тяжёлая — по зелёным быстрому и полному прогону ветки того же коммита;
   - красный прогон — стоп с причиной;
   - красная последняя ночь — стоп для любого шага.
3. **Ночной полный прогон main** (`on.schedule`, 02:17 UTC). Ночь — последний завершённый прогон main по расписанию или повтор по
   запросу на main. Не зелёная, в том числе снятая, — разбор первым делом; слияния стоят до зелёной ночи.
4. **Полные задания** — `full`, `demo-day`, `shadow-day`, `chaos`, `scale` — идут только по расписанию и по запросу, на push больше нет.
   Быстрые задания — `fast` (два шарда), `guards`, `clickhouse-compression` — на каждый push, как прежде.
5. Правило репозитория `scripts/test/ci-lanes.test.ts` держит три вещи, у каждой положительный контроль [Р-94]:
   - классификатор: лёгкое, тяжёлое, спорное, тесты полного прогона и каталога;
   - таблицу решения слияния;
   - форму `ci.yml`: расписание раз в сутки не в начале часа, полные задания — только ночью и по запросу, быстрые — без условия.

## Последствия

- Шаг лёгкой полосы сливается после быстрого прогона, около 25–40 минут, а не 60–100. Что ловит только полный прогон, у такого шага
  увидит ночь: до 24 часов позже. Красная ночь останавливает слияния, поэтому дефект не копится под новыми шагами.
- Повтор полного прогона на push в main исчезает. Тяжёлая полоса проверяет тот же коммит до слияния, лёгкую ловит ночь.
- Расписание GitHub Actions работает только на ветке по умолчанию и только когда файл workflow лежит в main. Время — UTC. Запуск может
  сдвинуться или быть снят при пиковой нагрузке (сильнее всего — в начале часа). В публичном репозитории расписание отключается после
  60 дней без активности. Уведомление о ночи получает пользователь, последним менявший строку cron. Источник —
  [docs.github.com, Events that trigger workflows, schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
- Список лёгких мест расширяется только решением владельца: правило держит его дословно.
