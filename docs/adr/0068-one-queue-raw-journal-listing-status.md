# ADR-0068: одна очередь уведомлений, журнал сырья и статус листинга из трёх источников

Статус: принято (шаг 114, Р-239). Строит приёмник шага 23 ([ADR-0023](0023-channel-distrust-notification-receiver-console.md)) и
журнал обработанных OQ-171 (шаг 24); часть A-30 (деактивация листинга); опирается на Р-3 (данные канала ≤ 18 месяцев), Р-20 (PostgreSQL —
только нужное текущему решению), Р-31 (тенант сверяется с аккаунтом), Р-121 (сверка опросом).

## Контекст

1. Уведомления листингов SP-API (LISTINGS_ITEM_STATUS_CHANGE, LISTINGS_ITEM_ISSUES_CHANGE) идут только через EventBridge,
   ANY_OFFER_CHANGED и PRICING_HEALTH — только через SQS (notification-type-values, столбец Workflow). Задание шага называло все
   уведомления «только через EventBridge» — снимок с этим расходится.
2. Правило EventBridge кладёт в очередь событие EventBridge, а не уведомление SP-API. Что SP-API кладёт в `detail`, страницы не говорят.
3. Приёмник шага 23 писал только журнал обработанных — идентификатор и тип, без тела. Повтор доставки отсекал журнал обработанных в
   транзакции снимка.
4. Статус листинга адаптер Amazon уже читал (обратное чтение — `liveness`, обнаружение — `isLive`), но не хранил: продавец не видел, что
   Amazon перестал продавать включённое предложение.

## Решение

1. **Одна очередь — два конверта.** Адресат SQS SP-API и цель правила EventBridge — одна очередь, одна очередь недоставленных, в
   политике два разрешения. Приёмник отличает событие EventBridge по его полям (`detail-type`, `source`, `detail`) и принимает его, только
   если `source` — источник партнёра SP-API, `detail` — уведомление SP-API, `detail-type` равен его типу. Иначе — отказ CRITICAL с
   именами ключей `detail`: по нему разбирается форма на живой очереди (A-33). Путь решения получает уведомление SP-API без конверта.
2. **Журнал сырья до пути решения** (`channel_data.notification_journal`, 0213). Тело сообщения, как пришло, и конверт; одна строка на
   уведомление тенанта (`notification_journal_once`). Повтор — `REPEAT`, а не ошибка. Обработку по-прежнему решает журнал обработанных;
   сообщение удаляется из очереди только после обработки. Смерть процесса в любой момент: до записи сырья — сообщение придёт снова; после
   записи и до обработки — придёт снова и обработается; после обработки и до удаления — придёт снова и будет повтором. Срок — 16 суток:
   дольше хранения сообщения в очереди (14 суток) с запасом; тела ANY_OFFER_CHANGED — данные конкурентов, им не место в PostgreSQL
   дольше, чем нужно повтору [Р-20].
3. **Статус листинга — одно наблюдение из трёх источников** (`channel_data.listing_status`, 0213): уведомление, обратное чтение после
   записи, обнаружение каталога. Одно правило (`listingStatusStep`) у хранилища в памяти и на PostgreSQL: уведомление пишется всегда
   (повтор отсекают журнал обработанных и `listing_status_once_per_notification`), опрос — только изменение; «перестало продаваться» —
   новое и самое позднее наблюдение говорит «не покупается», а прежнее известное — «покупается» или его не было; только у предложения
   с единицей цены ENGINE; CRITICAL `LISTING_NOT_BUYABLE` один раз на переход. В решение о цене статус не входит.
4. **Видимость.** Offers — пилюля «Not buyable on Amazon» с причиной словами (принудительные действия Amazon) и источником; Channels —
   откуда данные аккаунта Amazon: уведомления за сутки по видам или «только опрос». Считается по журналу сырья — по тому, что дошло.
5. **Проверка без живого AWS.** Очередь — модель стандартной SQS на стенде (`FakeSqs`), а не localstack: образы Docker Hub на машине
   разработчика не скачиваются (OQ-114), а модель уже держит повторную доставку после смерти получателя — то, от чего зависит свойство.
   Хаос — смерть на каждой границе ввода-вывода пачки по очереди, с настоящими приёмником, адаптером, путём решения и базой.

## Последствия

- Подписки (`createSubscription`) продукт пока не создаёт — часть Б заводит их руками; решить, делает ли это «Connect Amazon».
- `createDestination` требует скоупа grantless `sellingpartnerapi::notifications`; у приложения его нет (`invalid_scope`) — часть Б ждёт
  ответа поддержки.
- Уведомление о новом листинге не создаёт предложения в каталоге: каталог по-прежнему строит обнаружение [Р-179]; уведомление пишет
  только статус.
- LISTINGS_ITEM_MFN_QUANTITY_CHANGE и прочие типы EventBridge приёмник не принимает: запись в журнал процесса и удаление из очереди, в журнал сырья они не попадают — на них не подписываемся.
