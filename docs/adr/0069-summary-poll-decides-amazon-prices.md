# ADR-0069: опрос сводки решает цену на Amazon, бюджет — на пару продавец-приложение

Статус: принято (шаг 115, Р-240). Решение владельца по аудиту 2026-11-06: вариант (b), P0-01 закрыт, тикет о скоупе уведомлений идёт параллельно. Отменяет правило AMZ_C07
(шаг 22), уточняет Р-121, Р-221, Р-235 и основание Р-119. Опирается на Р-39 (доступность стратегии по источникам), Р-128 (живой прогон), Р-226 (исполнение).

## Контекст

1. Конкуренты для решения на Amazon шли только из `ANY_OFFER_CHANGED`. Для него нужен адресат, для адресата — grantless-скоуп `sellingpartnerapi::notifications`, а LWA отвечает
   `400 invalid_scope`. Без скоупа конкурентные стратегии на Amazon не получали входа вовсе. Это нашёл аудит: FDD обещал «работает на опросе», код этого не делал.
2. `getCompetitiveSummary` уже читался кругом для сверки потерь и для долей Buy Box. Лимит [док]: 0.033 запроса в секунду, burst 1, пакет до 20 товаров, то есть ≈ 57 000 товаров в сутки
   на пару. Каталог поиска не больше 1000 SKU (A-31): круг около 26 минут.
3. Лимит приложения не документирован (A-15). Код принимал его равным лимиту пары, то есть делил один запрос в 30 секунд на всех продавцов приложения.
4. Сверка потерь у Amazon была включена безусловно: у аккаунта без подписки каждое движение рынка становилось «потерей». Живой прогон шага на старом коде: 160 ложных проверок за
   час и CRITICAL `NOTIFICATION_LOSS_SUSPECTED`. В пилоте без уведомлений это был бы шум на весь срок пилота.

## Решение

1. **Источник `AMAZON_COMPETITIVE_SUMMARY` — основной** (0215, описание канала): снимки идут настоящим путём решения — проверка входов, стратегия, Gate, запись. Уведомления остаются
   основным источником тоже: у них свой снимок, порядок решает момент наблюдения.
2. **Опрос по кругу — своей работой** `amazon-summary-poll`, а не ярусным `competitor-poll`: у того единица бюджета — запрос на товар, у сводки — запрос на 20 товаров раз в 31 с.
   Признак источника `rotation`. Окно — самые давние первыми (`stalestFirst`, как с шага 55).
3. **Бюджет — пара продавец-приложение** (задание владельца): 31 с на аккаунт, сколько бы аккаунтов ни было; у операции `application: null`, как у `searchOrders` (ревью шага 51,
   находка 4). 429 не повторяется внутри вызова: при квоте раз в 30 секунд повтор через полсекунды только расходует следующее окно.
4. **Лимит приложения виден, а не предположен.** 429 при темпе пары — провал работы кодом RATE_LIMITED, растущая пауза и CRITICAL `SCHEDULER_JOB_FAILING`. На этом основании
   владельцу идёт стоп-доклад. Вариант модели канала `summaryApplicationRps` (A-15) показывает это тестом.
5. **Окно и товар падают по-разному.** Окно, отклонённое каналом целиком и временно, не отмечается и повторяется первым, иначе 20 предложений ждали бы весь круг. Отказ по одному товару
   отмечается и не роняет запуск: постоянный отказ не занимает окно и не тормозит каталог.
6. **Цена и держатель Buy Box снимка — большинством просмотров.** Единого победителя канал не называет. Держатель — продавец с суммой долей > 50 % [Р-235], цена и доставка — его предложения;
   его строка помечена `holdsBuyBox` и добавляется в предложения, если не попала в наименьшие. Большинства нет — цена самой большой группы и `isSelf: null`: тот же случай, что цена Buy Box
   без продавца у уведомления, отрезка доли нет, стратегии с держателем цену не двигают. Предложений в Buy Box нет вовсе — Buy Box в снимке нет.
7. **«Win the Buy Box» на Amazon доступна** (ответ на вопрос владельца, Q11): этот путь называет держателя. Фильтр FBA/FBM тоже: `fulfillmentType` — обязательное поле модели. Неизвестное
   значение исполнения остаётся неизвестным, а не становится MFN.
8. **Сверка потерь — там, где уведомления приходят.** Опрос страхует их, только если `ANY_OFFER_CHANGED` дошло до журнала сырья за семь суток (не уведомления листингов: у них свой
   путь через EventBridge). Подписка замолчала — неделю CRITICAL о потере, затем аккаунт считается опрашиваемым. Сравнивается наименьшая цена конкурента: цена Buy Box сводки — другое число,
   чем `Summary.BuyBoxPrices`.
9. **Экран говорит правду.** Channels называет источник и возраст самого давнего чтения; сноска Competition больше не обещает «цены не двигает».

## Последствия

- Конкурентные стратегии на Amazon работают без скоупа уведомлений, реакция — в пределах круга: около 26 минут на 1 000 предложений. Быстрее будет с уведомлениями.
- Купон конкурента теперь попадает в снимок решения, и квитанция Amazon его показывает [Р-234]; расчёт по базовой цене прежний.
- Правило большинства и форма ответа подтверждены моделью снимка и настоящим ответом песочницы, но песочница статична. Главная проверка первого живого дня — чек-лист A4.
- Снятие остановки выборкой на Amazon осталось ручным [Р-119]: весь бюджет занят кругом.
- Строки «115» в [отложенном](../deferred.md): приоритет опроса по стратегиям, второй продавец, держатель без строки решения, уведомление поверх опроса, предложения без доставки.
