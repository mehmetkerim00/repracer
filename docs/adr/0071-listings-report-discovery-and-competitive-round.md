# ADR-0071: каталог Amazon — отчётом листингов, круг опроса — по конкурентной части

**Статус:** принято, шаг 117 (P0-16 аудита, A-31). Решения владельца 2026-11-07: обнаружение отчётом — безусловно (размер каталога пилота неизвестен,
ответа не будет); приоритет опроса по стратегиям, две цифры круга и порог `AMAZON_SUMMARY_ROUND_SLOW` на конкурентной части — в составе шага.

## Контекст

1. Обнаружение каталога Amazon шло только `searchListingsItems`, а поиск «is limited to 1000 listings total across all pages» (A-31 [док]). У продавца
   больше 1 000 листингов каталог был неполон молча.
2. Конкуренты Amazon — опрос `getCompetitiveSummary` по кругу (Р-240, ADR-0069): окно до 20 предложений раз в 31 с на пару продавец-приложение. Круг шёл
   ровно по всему каталогу, и с каталогом больше 1 000 реакция на рынок росла вместе с выключенными и фиксированными предложениями, которым данные конкурента
   не нужны.

## Решения

1. **Отчёт — основной путь.** По каждой витрине региона — `createReport` `GET_MERCHANT_LISTINGS_ALL_DATA` (у отчёта принимается только первая витрина
   запроса, заголовки — `en_US`), `getReport` до `DONE`, `getReportDocument`, документ по подписанному адресу. Документ даёт список SKU, подробности — тот же
   `searchListingsItems`, но по 20 SKU (`identifiers`, тип SKU) и тем же разбором, что у поиска по витрине. Записи обнаружения поэтому одинаковы на обоих
   путях: правило ценообразования канала (Р-120), рамки канала (Р-233), статус листинга (Р-239), FBA. Отчёт сам этих полей не несёт.
2. **Фазы — курсором адаптера**, как две фазы обнаружения eBay. Курсор `amz2:` несёт фазу (запрос, ожидание, документ, поиск), витрину и место в документе.
   Где ждать нечего, адаптер проходит фазы в одном вызове. Пока отчёт готовится, он отдаёт пустую страницу с `notBefore`: путь решения ждёт в пределах
   срока захода или кончает заход с курсором, и следующий заход продолжит. Порт получил `DiscoveryPage` (`notBefore`, `catalogs`). Неиспользуемый интерфейс
   `SupportsAsyncReports` не взят: обнаружение — контракт страниц, отчёт — подробность курсора одного адаптера.
3. **Поиск по витрине — резерв.** Отказ `createReport` (роль, витрина), ответ не по модели, `CANCELLED`, `FATAL`, неготовность за 2 ч, недоступный документ,
   кодировка не UTF-8, заголовок без `seller-sku` — круг идёт поиском. Поиск называет, сколько нашёл; «найдено не меньше 1 000» или «не назвал» — каталог
   может быть виден не полностью. Это WARNING `AMAZON_CATALOG_MAY_BE_INCOMPLETE` и строка на экране Channels, а не молчание.
4. **Источник каталога — в базе** (0220): `tenant_data.discovery_catalog_source`, строка на аккаунт и витрину. Пишет только функция узкой роли обнаружения,
   экран читает функцией. Форму держат ограничения: у отчёта нет причины и неполноты и есть число, у поиска — причина из списка.
5. **Строгий разбор документа.** BOM снимается; колонка `seller-sku` обязательна; строка с лишними полями и строка с пустым или непечатным SKU пропускаются
   поштучно и считаются; повтор SKU — один раз. Короче заголовка строка допустима: хвостовые колонки не читаются. GZIP распаковывается с пределом 256 МиБ.
6. **Подписанный адрес — без токена.** Адрес живёт вне нас, токен в журнале хранилища был бы утечкой; стенд это проверяет. Документ не пишется на диск
   (страница: «Unencrypted report content must never be stored on disk»): адаптер держит в памяти процесса только список SKU, после перезапуска скачивает
   документ заново.
7. **Лимиты — бюджетом пары**, тем же `TwoLevelBudget`, что у остальных операций: `createReport` и `getReportDocument` — 0.0167 запроса в секунду, burst 15;
   `getReport` — 2, burst 15 (модель снимка 2026-09-16). Лимит приложения не предполагается, как у `searchOrders` (A-23).
8. **Приоритет опроса — доля мест окна.** Конкурентное предложение — движок включён и стратегия из данных конкурентов (признак выборки снятия остановки,
   шаг 26). В каждом окне из 20 мест остальным отведено `r = max(1, round(20·R / (24·C + R)))`, но не больше 19; остальное — конкурентным; свободные места
   одной группы отдаются другой; внутри группы — самые давние первыми. Отсюда две верхние границы: конкурентный круг — ⌈C / (20 − r)⌉ окон, полный —
   ⌈R / r⌉ окон (`summaryRounds`). Первая редакция ставила давность с весом 24. Живой прогон показал, что после старта она собирает остальные предложения в
   одну волну, и в первом цикле 360 из 1 000 ждали дольше обещанного полного круга. Доля мест даёт ту же долю без волны с первого окна.
9. **Порог и абзац — по конкурентной части.** `AMAZON_SUMMARY_ROUND_SLOW` — когда круг конкурентной части дольше часа, в событии обе цифры. Абзац о разрыве
   с Р-8 и билет считают обе цифры по формуле окна. Часы допустимы только предложениям, которым данные конкурента не нужны; цель пилота — конкурентная часть
   в пределах часа, сильно больше — стоп-доклад.

## Последствия

- Новый листинг появляется не позже следующего круга и возраста отчёта (кэш 1–6 ч). Поиск видел его сразу.
- Обход шагает вместе с отчётом: на витрину — один `createReport`, один документ и ⌈SKU / 20⌉ запросов поиска. 10 000 SKU — 500 запросов, около 100 с бюджета пары.
- Записанные фикстуры стенда начинают обнаружение с отчёта; проверка тел по модели знает Reports из снимка 2026-09-16; путь к документу — не операция SP-API.
- Что снимок не закрывает — A-35…A-40 и чеклист первого живого дня.
