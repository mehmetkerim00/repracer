# ADR-0074: профиль QA-A — демо-стенд за Cloudflare Tunnel, видимая версия сборки, сброс только закрытой базы

**Статус:** принято, шаг 121 (план запуска, фаза 1). Задание владельца: подготовить QA-A до сервера.

## Контекст

Тестировщику нужен свой адрес, где работает демо с настоящим путём решения: без машины разработчика и без ключей каналов. В отчёте об ошибке
он должен назвать версию, а данные сбрасывать одной командой. Репетиция QA-A (план исполнения, §2.4) нашла три вещи:

- `demo-prepare.sh` не запускает исполнитель заданий;
- `vite preview` отвечает 403 на чужой заголовок Host;
- без `REPRACER_DEMO_ONLY=on` стенд не стартует на базе региона US.

## Решения

1. **Состав — стенд, а не развёртываемая консоль.** Консоль production входит у настоящего поставщика (ZITADEL, это QA-B), а QA-A нужен вход
   имитатором и демо. Стенд, PostgreSQL, исполнитель заданий и `cloudflared` — одним compose (`deploy/qa`). Код смонтирован только на чтение,
   как у остальных развёртываний.
2. **Интерфейс отдаёт сам стенд** (`STAND_STATIC_DIR`) тем же HTTP-слоем, что у консоли. Одна точка для туннеля, без `vite preview`.
   Стенд слушает сеть compose (`STAND_HOST`); на хост — только loopback, наружу — ничего.
3. **Вход закрывает Cloudflare Access** (cookie): имитатор стенда пускает любого, кто дошёл до страницы. Basic Auth у прокси не годится —
   консоль занимает `Authorization` своим Bearer.
4. **Версия сборки — свойство развёртывания.** `REPRACER_BUILD_SHA` и `REPRACER_BUILD_AT` задаёт выкладка. Процесс называет их в
   `/healthz`, консоль — человеку в подвале. Источник один — процесс, страница берёт его из сессии. Правки в рабочей копии видны как `-dirty`.
5. **Каждая выкладка пересоздаёт базу QA.** Миграции идут на чистую базу так же, как в CI, демо всегда свежее, около 3 минут.
   Данные QA-A синтетические, хранить в них нечего.
6. **Сброс — только закрытой базы.** `scripts/qa-reset.sh` отказывает базе без стража P0-09 (шаг 119). Боевая база этим стражем не закрыта
   никогда, значит, сброс на ней физически не запускается. Пересоздание теряет настройки уровня базы, поэтому страж ставится снова до
   подключения стенда. Новую базу создаёт только явный `--first-time`.
   Шаг 121.3 (решение владельца по докладу 121.1): база QA не бывает без стража ни в какой момент. Сборка идёт под именем `<база>_next`,
   страж ставится на неё до замены, затем переименование. Сброс идёт в фоне под журналом, один за раз (`deploy/qa/detach.sh`): обрыв
   SSH прерывает только показ журнала, повтор во время работы показывает её же, а повтор после обрыва посреди замены доводит её.
7. **Р-127:** стенд, доступный не только с этой машины, отмечается во внешнем сервисе или выключает отметку явно. Аккаунта нет (OQ-188) —
   в профиле выключено явно.

## Последствия

- QA-A — не QA-B. Нет настоящего входа и второго фактора, планировщика, брокера, ClickHouse, почты и копий. QA-B выращивает этот хост в
  профиль production.
- Перезапуск стенда на той же базе сеет новых демо-тенантов, прежние остаются мусором (OQ-225). Чистое состояние — `reset.sh`.
- Образы, туннель, Access и Linux проверяются первой выкладкой: Docker Hub на машине разработчика образы не отдаёт (OQ-114).
