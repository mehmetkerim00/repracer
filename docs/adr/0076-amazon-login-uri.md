# ADR-0076: log-in URI Amazon — шаги 5–8 потока с сайта

**Статус:** принято, шаг 125 (П6 аудита авторизации Amazon 2026-11-14). Решение владельца: «П6 — отдельным шагом и раньше П1», красное сначала —
тест, воспроизводящий приход продавца со стороны Amazon на log-in URI.

## Контекст

Подключение Amazon шага 43 ([ADR-0040](0040-seller-oauth-connect-and-channel-tokens.md)) строит адрес согласия и ждёт код сразу на redirect URI
(`/connect/callback`). Страница website-authorization-workflow (снимок [2026-11-14](../../vendor/amazon/lwa-authorization/2026-11-14/SOURCE.md),
архивные копии 2025-06-16 и 2026-01-04) описывает поток из 16 шагов, и между согласием и кодом стоят шаги 5–8:

5. Amazon вызывает **log-in URI** приложения с `amazon_callback_uri`, `amazon_state`, `selling_partner_id` и, у черновика, `version=beta`.
6. Продавец входит на сайте приложения.
7. Приложение проверяет запрос и создаёт `state`.
8. Приложение отправляет продавца на `amazon_callback_uri` с `amazon_state`, `state`, необязательным `redirect_uri` и, у черновика, `version=beta`.

Только после этого Amazon отправляет на redirect URI `state`, `selling_partner_id` и `spapi_oauth_code`. В консоли log-in URI не было, и модель
поставщика LWA в прогонах шаги 5–8 пропускала. Значит, все прогоны подключения зеленели на потоке, которого у Amazon нет: с настоящим Amazon
авторизация, скорее всего, до кода не дошла бы.

## Решение

1. **Log-in URI консоли — `/connect/amazon/login`.** Его регистрирует владелец у приложения (`deploy/pilot/README.md`, §1). Страница
   сохраняет параметры Amazon в хранилище вкладки до входа и сразу стирает адрес, как адрес возврата шага 43. После входа она пересылает их
   серверу (`POST …/connections/amazon-login`) вместе со `state`, который вкладка запомнила при «Connect» (он же — в адресе согласия), и уходит
   на адрес, который назвал сервер.
2. **Сервер продолжает только ждущий запрос Amazon этого тенанта.** `state` сверяется по отпечатку: запрос не отменён, не истёк, обмен кода не
   начат, канал — Amazon. Иначе — отказ своей причиной (`UNKNOWN_STATE`, `EXPIRED`, `ALREADY_DONE`), и продавец не уходит к Amazon со
   `state`, который консоль потом не примет. Право — то же, что у «Connect» (`MANAGE_TENANT`). В базе шаг ничего не меняет.
3. **Адрес продолжения — только confirm-адрес своего приложения на хосте Amazon** (`continueFromLogin` поставщика LWA): https, хост
   `amazon.com` или его поддомен (пример страницы — `amazon.com`, Seller Central наших витрин — поддомены), без логина, порта и фрагмента, путь
   ровно `/apps/authorize/confirm/<application_id>`. Иначе — отказ `LOGIN_CALLBACK_NOT_AMAZON` / `LOGIN_CALLBACK_OTHER_APP`, а не
   переадресация: иначе log-in URI — открытый редирект, уносящий наш `state`.
4. **`version=beta` от Amazon должен совпасть с флагом черновика** (`REPRACER_AMAZON_APP_DRAFT`). Расхождение — ошибка настройки,
   `LOGIN_VERSION_MISMATCH`, а не догадка.
5. **`redirect_uri` в продолжении — явный**, тот же, с которым меняется код (без него Amazon берёт первый зарегистрированный).
6. **`state` шага 7 — тот же, что у адреса согласия.** Страница говорит, что приложение создаёт `state` на шаге 7, и что redirect URI вернёт
   `state` приложения; один `state` на попытку делает обе фразы верными и не требует новой строки в базе.
7. **Модель поставщика LWA ведёт поток по странице:** согласие → log-in URI → `confirm` (одноразовый `amazon_state`, не старше десяти минут,
   путь и `application_id` выданного визита, тот же `version`, зарегистрированный `redirect_uri`) → redirect URI с кодом. Без log-in URI модель
   Amazon не создаётся.

## Последствия

- Прогоны подключения (`connect-live`, `pilot-live`) и браузерный смоук идут документированным потоком; прямой поток «согласие → код» модель
  больше не даёт.
- Поток, начатый в Selling Partner Appstore, приходит без нашего `state`: консоль говорит «начните с Channels» и ничего не подключает. До
  публикации приложения такого прихода нет — строка «125» в [docs/deferred.md](../deferred.md).
- Какой хост и путь `amazon_callback_uri` пришлёт настоящий Amazon и какую форму `application_id` (A-34), проверяет первое живое подключение —
  [чеклист первого аккаунта](../live-first-account-checklist.md), A1; отказ виден в журнале консоли (`channel_connect_login_refused`: причина и
  хост, без `amazon_state` и `state`).
