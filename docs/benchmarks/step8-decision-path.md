# Замер пути решения на реальной PostgreSQL (шаг 8)

Статус: 2026-09-14. Скрипт — [packages/pricing-store-pg/bench/decision-path.bench.ts](../../packages/pricing-store-pg/bench/decision-path.bench.ts);
сырые результаты — [step8-run1-commit.json](step8-run1-commit.json) (фиксация, кривая задержки, процессы, партиции, границы),
[step8-run2-path-variants.json](step8-run2-path-variants.json) (полный путь, триггеры и RLS). Данные синтетические.

## Условия и оговорки

| | |
|---|---|
| Машина | Apple M1, 8 ядер, 8 ГБ; **генератор нагрузки и PostgreSQL на одной машине**, TCP через loopback |
| PostgreSQL | 16.13, настройки по умолчанию `initdb`: `shared_buffers` 128 МБ, `work_mem` 4 МБ, `synchronous_commit` on, `fsync` on |
| Приложение | Node 22, один процесс = один экземпляр, пул `pg` |
| Мир | 10 000 SKU × 2 витрины = **20 000 единиц записи** в ENGINE (+500 выключенных); история конкурентов 20 дней; себестоимость на товар |
| Второй канал | Смоделирован второй витриной Kaufland: справочника возможностей записи цены Amazon/eBay/Otto ещё нет, схема пути та же |
| Интенсивность | **База 18,5 оценки/с** по ярусам Р-47 (допущение долей: 10 % горячих — раз в 2 мин, 30 % — раз в час, 60 % — раз в сутки); **пик ×10 = 185/с**; 10 % оценок меняют цену |

Цифры — порядок величины для одного ноутбука, не ёмкость production. Абсолютные значения на сервере будут выше; соотношения
(доля триггеров, место узкого места) переносятся лучше.

## 1. Фиксация intent и решения (`commitDecision`)

Операция: блокировка единицы записи и товара, чтение версии границ, `price_intent` + `price_decision` (+ `channel_write` в 10 % случаев), COMMIT.

**Замкнутый цикл, один процесс:**

| Параллельно | Фиксаций/с | p50, мс | p95, мс | p99, мс | Цикл событий Node |
|---|---|---|---|---|---|
| 1 | 473 | 1,85 | 3,22 | 4,25 | 0,16 |
| 4 | 1 801 | 1,88 | 3,66 | 5,50 | 0,55 |
| **8** | **1 996** | 3,67 | 6,47 | 8,55 | **0,95** |
| 16 | 1 902 | 7,84 | 12,48 | 17,02 | 0,99 |
| 32 | 1 610 | 17,26 | 32,35 | 92,75 | 0,98 |

**Один экземпляр выдерживает ≈ 2 000 фиксаций intent и решения в секунду.** Дальше рост параллельности только удлиняет очередь:
цикл событий Node загружен на 95–99 %, сессии PostgreSQL в основном ждут клиента (`Client:ClientRead`).

**Открытый цикл (поступления по расписанию, пул 32):**

| Темп, /с | Выдержано, /с | p50, мс | p95, мс | p99, мс |
|---|---|---|---|---|
| 18,5 (база) | 18,6 | 8,06 | 13,41 | 17,65 |
| 185 (пик) | 185 | 2,43 | 10,28 | 114,24 |
| 400 | 400 | 1,70 | 4,90 | 84,20 |
| 800 | 800 | 1,61 | 87,49 | 183,52 |
| 1 200 | 1 200 | 1,52 | 51,22 | 126,78 |
| 1 600 | 1 571 | **204,51** | 304,75 | 317,68 |
| 2 400 | 1 688 | 2 082,89 | 4 031,91 | 4 186,59 |

**Задержка начинает расти:** хвост (p95) — с ≈ 800/с, медиана — между 1 200 и 1 600/с; насыщение ≈ 1 700/с. На базовом темпе медиана
выше, чем на пиковом (8 против 2,4 мс): между редкими запросами соединения и процессор простаивают (вероятно; нагрузкой это не объясняется).

**Несколько процессов-генераторов на той же машине:** 2 × 8 — 1 728/с, 4 × 8 — 1 294/с (p95 144 мс). PostgreSQL занимает 5,2 → 7,1 из 8 ядер,
появляются `LWLock:LockManager` (0,56), `LWLock:WALInsert`, `Lock:extend`. Предел этой машины — общий процессор, а не отдельный ресурс БД.
`LWLock:LockManager` — вероятно, исчерпание быстрых слотов блокировок: транзакция касается многих секций и их индексов (проверить на сервере).

**Число секций `price_decision`:** 5 против 35 (установившиеся 30 дней, Р-28, пустые) — 1 437 против 1 635/с; разница в пределах разброса между
прогонами, влияния не выявлено. Оговорка: секции пустые.

## 2. Отложенная проверка границ

| Операция | Время | Разница |
|---|---|---|
| Изменение `min_price` уровня единицы, отдельная транзакция, единица **ENGINE** | 1,04 мс (p95 1,21) | **+0,51 мс** |
| То же, единица OFF (проверки нет) | 0,53 мс (p95 0,61) | — |
| `min_price` уровня товара (проверяются обе витрины) | 1,06 мс | — |
| 2 000 изменений одной транзакцией, ENGINE: вставка / COMMIT | 196 / 75 мс | **COMMIT 0,04 мс на строку** |
| 500 изменений одной транзакцией, OFF: вставка / COMMIT | 51 / 3,4 мс | COMMIT 0,007 мс на строку |
| Включение ENGINE для 20 000 единиц: UPDATE / COMMIT с отложенными проверками | 1,3–4,2 с / 0,71–0,76 с | **0,04 мс на единицу** |

**Отложенная проверка стоит ≈ 0,5 мс на одиночное изменение границы (вдвое дороже вставки без неё) и ≈ 0,04 мс на строку при массовом
изменении.** В пути решения её нет: она срабатывает при изменении границ и при включении репрайсинга. Одиночное изменение берёт
`FOR UPDATE` на товар — фиксации решений по этому товару ждут его COMMIT (так Р-54 и упорядочен).

## 3. Цена триггеров и RLS

Та же операция фиксации с явной версией записи, пользовательские триггеры `price_intent`, `price_decision`, `channel_write` выключены
(`DISABLE TRIGGER USER`) и/или RLS снят со всех таблиц. Внешние ключи остаются. Схема восстановлена и проверена после замера.

| Вариант | 1 поток, /с | p50, мс | 8 потоков, /с |
|---|---|---|---|
| Триггеры и RLS включены (среднее двух прогонов) | 559 | 1,62 | 2 150 |
| Без триггеров | 922 | 1,05 | 3 515 |
| Без RLS | 609 | 1,48 | 2 302 |
| Без триггеров и RLS | 995 | 0,97 | 3 899 |

| | Доля времени транзакции (1 поток, p50) | Потеря пропускной способности (1 поток / 8 потоков) |
|---|---|---|
| **Триггеры** | **≈ 35 %** (+0,57 мс) | 39 % / 39 % |
| **RLS** | **≈ 9 %** (+0,14 мс) | 8 % / 7 % |
| Вместе | ≈ 40 % | 44 % / 45 % |

При 8 потоках варианты без триггеров упираются в цикл событий Node (0,95): их реальный потолок выше, доля триггеров — не меньше указанной.
Триггеры здесь — не «накладные расходы», а протокол записи: версия и идемпотентность, проверка обеих границ и остановки, копия ядра intent.
Без них вариант выполним только потому, что замер сам задаёт версию и ключ.

## 4. Полный путь: снимок → проверка входов → стратегия → Gate → запись

Одна оценка — **10 транзакций** хранилища (12 при изменении цены), каждая — BEGIN с контекстом тенанта, запрос, COMMIT.
Адаптер канала — заглушка, отвечающая сразу.

| Нагрузка | Оценок/с | p50, мс | p95, мс | Самые дорогие вызовы, мс на оценку |
|---|---|---|---|---|
| **База 18,5/с**, открытый цикл | 18,5 — **выдерживается** | 33,95 | 41,10 | `findPriceScopes` 15,2 · `loadSanityContext` 10,6 · `loadCost` 2,6 · `commitDecision` 2,4 |
| Замкнутый цикл 16, окно движений базы | 162,9 | 95,45 | 145,22 | `findPriceScopes` 40,6 · `loadSanityContext` 21,3 · `commitDecision` 9,8 |
| **Пик 185/с** | **не выдерживается**: замкнутый цикл даёт 58,5/с | 271,20 | 327,01 | `loadSanityContext` **240,6** · `findPriceScopes` 9,9 · `commitDecision` 8,2 |

**Окно массового сдвига до и после исправления шага 8** (одна витрина, окно пика — 305 тыс. движений за час):

| | Строк наружу | Размер | Время запроса |
|---|---|---|---|
| Было: все движения за час, JSON | 304 838 | **41 МБ** на каждый снимок | 585 мс, сортировка на диск 16 МБ |
| Стало: последнее движение товара за 15 мин, наружу — число товаров и большие движения | 28 движений + счётчик | < 1 КБ | 52 мс, сортировка на диск 2 МБ |

С исходным запросом путь на 10 000 SKU падал уже в окне **базовой** интенсивности: при 16 параллельных оценках сервер не смог отправить
результат («could not send data to client: No buffer space available»), соединение разорвано, процесс приложения упал.

## Первое узкое место

1. **Экземпляр приложения, а не PostgreSQL** — для фиксации решений. Один процесс Node упирается в ≈ 2 000 фиксаций/с при загрузке
   цикла событий 95–99 %; сервер в это время занят на 4–5 ядер из 8 и ждёт клиента.
2. **Для полного пути — чтения контекста, а не вставки intent и решения.** Фиксация — 2–10 мс из 34–270 мс оценки. На базе дороже всего
   `findPriceScopes` (**планирование 24 мс при исполнении 0,4 мс**: подзапрос последних цен по `price_history`, секции месяц × hash 8,
   план строится на каждый запрос) и чтение окна сдвига; на пике — окно сдвига (сортировка последних движений каждого товара уходит на
   диск). Затем — 10–12 транзакций на оценку ([OQ-92](../open-questions.md), [OQ-93](../open-questions.md)).
3. Триггеры — ≈ 35 % времени фиксации, RLS — ≈ 9 %: заметно, но не первое.

## Найдено замером и исправлено в шаге 8

- Окно сдвига пересылалось целиком (1 ч вместо 15 мин конфигурации, все движения вместо последних больших) — исправлено; `SanityContext.channel.windowProducts`.
- Две одновременные фиксации по одной единице вычисляли одну версию записи — вторая падала; фиксация сериализуется блокировкой строки `write_scope`.
- Два одновременных снимка одного товара: старший, записанный позже, нарушал монотонность `competitor_state` — старший снимок проекцию больше не перезаписывает.
- Потеря простаивающего соединения роняла процесс (необработанное событие `error` пула) — обработчик в `createPool`.
- Двойной ROLLBACK в транзакции тенанта (предупреждения сервера) — исправлен.

## Воспроизвести

```sh
# одноразовая база: все миграции, затем суперпользователем
psql -f packages/pricing-store-pg/test/setup.sql
REPRACER_PG_URL=postgres://svc_app@127.0.0.1:55432/repracer_eu \
REPRACER_PG_ADMIN_URL=postgres://postgres@127.0.0.1:55432/repracer_eu \
npm run bench -w @repracer/pricing-store-pg -- --out=result.json --tmp=/tmp --allow-schema-toggles
```

`--allow-schema-toggles` выключает триггеры и RLS и создаёт секции — только на одноразовой базе; фаза `variants` — последней, потому что
записи без триггеров не обновляют watermark версий.
