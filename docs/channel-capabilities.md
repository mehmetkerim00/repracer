## 3. Следствия для Dispatcher и модели

### Amazon
- **QUANTITY:** все офферы SKU в маркетплейсах EU — один `WriteScope`; значение считается и пишется один раз.
  Даже при работе только с DE запись меняет остаток SKU на .fr/.it/.es и других маркетплейсах, где SKU активен.
  Перед включением синхронизации это показывается продавцу и подтверждается (INV-11).
- **Гонка с заказом:** Amazon уменьшает остаток сам. Запись, посчитанная до получения `ORDER_CHANGE`, перезапишет
  уменьшение. Смягчение: буфер канала, приоритет обработки заказов перед пересчётом остатка, обнаружение через наблюдение.
- **p95 < 60 с** достижим только до точки `ACCEPTED`; время применения внутри Amazon мы не контролируем (OQ-48).
- **Шаг 20, по снимку SP-API:** лимит `patchListingsItem` — 5 rps на продавца и **500 rps на приложение, общий для всех тенантов**:
  при 100 одновременно активных продавцах пиковая сумма их лимитов (500) упирается в лимит приложения — ограничитель запросов
  адаптера нужен на двух уровнях (продавец и приложение), а распределение по тенантам — честное, без агрегирования их данных
  (AUP). Фид `JSON_LISTINGS_FEED` сообщения не упорядочивает — цена и остаток пишутся только `patchListingsItem` (Р-24, OQ-32).
  Суммы Amazon — десятичные в основных единицах: адаптер переводит целые центы (инвариант 7) без потери точности.
- **Не пишутся никогда [Р-111, Р-114]:**
  - `automated_pricing_merchandising_rule_plan` — привязка оффера к правилу автоматического ценообразования, включает чужой репрайсер;
  - `minimum_seller_allowed_price` и `maximum_seller_allowed_price` — второй набор границ на стороне канала: базовая цена обязана
    лежать между ними, иначе Amazon отклоняет запись. Наши границы должны быть единственными.

  Причина Р-111 («включатель репрайсера») исправлена Р-114 решением владельца. Страница manage-purchasable-offer называет атрибут
  правила только «Automated pricing rule configuration» и не описывает ни включение репрайсера, ни ошибку вне границ. База отклоняет
  поле порта CHANNEL_MIN_PRICE у Amazon (0077). Порт перечисляет атрибуты с причиной в `NEVER_WRITTEN_CHANNEL_ATTRIBUTES`. Контрактный
  стенд Amazon отклоняет запрос, в теле которого есть любой из них.
- **Шаг 22, адаптер** (`packages/amazon-adapter`, ADR-0022):
  - **чужой репрайсер [Р-115].** Перед записью цены адаптер читает оффер. Привязка к правилу или границы канала — PATCH не
    отправляется, единица требует человека. Обратное чтение проверяет то же;
  - **база цены [Р-116].** Цена покупателя (оффер B2C) против отправленной; расхождение ровно на ставку НДС — остановка витрины;
  - **ограничитель запросов** — на двух уровнях (пара и приложение), отказ называет уровень;
  - **неподтверждённое** — правила AMZ_C01…C10 (§11).

### eBay
- **250 правок/день на листинг [Р-2]** при целевой задержке < 5 мин: непрерывный репрайсинг раз в 5 минут даёт
  288 правок в сутки — **больше лимита** даже без записей остатка. Поэтому:
  - резерв `quantity_reserve` в `EditBudget` недоступен для цены;
  - минимальный интервал между записями цены на листинг — параметр, выводимый из остатка бюджета и времени до конца дня;
  - при исчерпании — только уменьшения остатка из резерва; цена ждёт нового дня;
  - `unaccounted_margin` на правки продавца в Seller Hub, которых мы не видим.
- Мульти-вариационный листинг делит один бюджет на все вариации (проверить) — частота репрайсинга на вариацию ниже.
- `quantity = 0` без включённого out-of-stock control может завершить листинг (проверить) → предполётная проверка C11.

### Kaufland (первый канал)
- **Запись:** `PATCH /v2/units/{id_unit}` для одной единицы, `POST /v2/units/bulk` — до 150 unit **одной витрины**; поля `listing_price`,
  `amount`, у Smart Pricing — `minimum_price`. Каждый запрос требует `listing_price` > 0 (формулировка документации — проверить,
  допускается ли `bulk` только с `amount`, K-13). Частичный успех пакета — 207 с результатом по каждому unit.
- **Лимит:** 111 rps на продавца, общий на все эндпоинты. Дневной лимит правок объекта не документирован.
- **Единица записи остатка — аккаунт + `id_offer` [Р-35]:** связанные одинаковым `id_offer` unit разных витрин делят `amount`
  и склад, поэтому единица записи QUANTITY одна на `id_offer`, а PRICE — по витрине и unit. Шаблоны справочника и CHECK — миграция 0027;
  общее правило «область записи остатка шире области записи цены» — [ADR-0002, Р-37](adr/0002-write-scope-per-field.md#дополнение-р-37-область-записи-остатка-шире-области-записи-цены).
- **Подтверждение применения:** синхронный ответ с объектом unit + событие `item_unit_changed` с полным объектом unit + обратное
  чтение. Для Smart Pricing фактическая цена покупателя — поле `price`, а не `listing_price`.
- **Вебхуки:** подписка на событие и витрину; в теле уведомления нет идентификатора продавца, поэтому адрес вебхука должен
  однозначно указывать аккаунт: один адрес на аккаунт с непрозрачным ротируемым токеном в пути; подпись проверяется всегда,
  токен аутентификацией не считается [Р-40, Р-31]. Ответ 2xx за 5 секунд, иначе повтор (от 1 до 60 минут, ~12 ч),
  затем подписка отключается и события теряются — нужна сверка.
- **Конкуренты [Р-36]:** основной источник — `buy_box_changed` и `GET /v2/buybox` (топ-10 по рангу); `competitors-comparer` — только
  сверка. `buy_box_changed` приходит с задержкой и под нагрузкой теряется, поэтому `GET /buybox` — запасной опрос; допустимая частота
  опроса — K-10. Что это значит для стратегий — [ADR-0007](adr/0007-competitor-data-completeness.md) [Р-39].
- **Ранний доступ и опрос [Р-45, Р-47]:** `buy_box_changed` выдаётся аккаунт-менеджером; до выдачи адаптер не пробует подписку, а основной
  источник — опрос `GET /v2/buybox` по ярусам волатильности: горячий ярус — с интервалом целевой задержки (Р-8), длинный хвост — раз в сутки.
  Сколько товаров помещается в горячий ярус, определяет бюджет запросов (K-04, K-10).
- **Уведомления с данными и без [Р-46]:** выбор по факту доставки. Без payload адаптер отдаёт `RESOURCE_CHANGED` с запросом из `resource`
  (`/buybox?id_product=…&condition=…` → опрос конкурентов, `/units/{id}` → обратное чтение), правило KFL_C19.
- **Потеря подписки [Р-48]:** после ~12 ч недоступности Kaufland отключает подписку и пишет на `fallback_email` — это ящик платформы с
  мониторингом. Восстановление — PATCH `is_active = true`, затем обязательный догон: заказы с момента потери, наши unit, конкуренты по ярусам,
  отчёт сверки. События за время отключения канал не повторяет.
- **Проверка входов [Р-42]:** снимки из `buy_box_changed` и `/buybox` проходят проверку правдоподобия до стратегии; ошибка единиц
  (K-17) ловится правилом «ровно ×100 / ×0.01» ([ADR-0008](adr/0008-price-decision-path.md)).
- **Комиссии:** в API есть `POST /v2/info/commission-rates/lookup` (до 50 EAN), но по Р-32 комиссии берутся из тарифных таблиц.
- **Технологический партнёр:** SaaS обязан зарегистрироваться как партнёр и подписывать запросы двумя парами ключей.
- **Адаптер (шаг 6):** [packages/kaufland-adapter](../packages/kaufland-adapter/). Всё, что документация не подтверждает, адаптер делает
  консервативно и пишет в журнал код правила — раздел 8. Контрактные тесты без сети — [tests/contract](../tests/contract/).

### Otto
- ~10 req/s **[ТЗ]**; если лимит на приложение, а не на партнёра — делится между тенантами (OQ-36).
- Централизованное обновление токенов (60 мин).

## 4. Консервативная политика для неподтверждённых значений

Применяется к каждому атрибуту со статусом `TO_VERIFY` или `UNKNOWN`:

| Атрибут | Поведение до проверки |
|---|---|
| `rate_limit` | Один параллельный запрос на `(channel_account, operation)`; экспоненциальный backoff с джиттером на 429/5xx; учёт заголовков лимита, если канал их отдаёт |
| `batch_max_items` | 1 |
| `object_edit_limit` | Если лимит может существовать — считаем все попытки, включая неуспешные |

| `apply_grace_period` | Расхождение не объявляется до наблюдения после grace; `ASK_HUMAN` вместо `REASSERT` |
| `reversible` | Считаем необратимой: требуется подтверждение человека |
| `webhooks` | Считаем отсутствующими: сверка по расписанию |

## 6. Готовность канала к Release 1.0 [Р-11, Р-56]

Продукт не выпускается, пока не готовы три канала Release 1.0: **Kaufland** (витрины `de`, `at` [Р-26]), **Amazon** и **eBay** —
каждый на витринах ЕС и США [Р-56]. Otto и Walmart добавляются после первых клиентов, по факту спроса; их строки в матрице
остаются для плана. Канал готов, когда одновременно:

| Критерий | Как подтверждается |
|---|---|
| Витрины канала описаны | Строки `platform.marketplace` (идентификатор, страна, валюта, база цены, налоговый режим [Р-57, Р-58], часовой пояс суток [Р-62]) подтверждены документацией со ссылкой; сейчас у Amazon и eBay — (проверить) |
| Закрыты все «(проверить)» по каналу в этом документе | Каждый атрибут строк канала в `platform.channel_capability.verification` имеет статус `VERIFIED` или `DECIDED` с источником и датой |
| Работает запись | Запись PRICE и QUANTITY на тестовом аккаунте проходит путь `PENDING → DISPATCHED → ACCEPTED` |
| Работает обратное чтение | Для каждого поля есть рабочий способ `READBACK` или `REPORT` |
| Есть подтверждение применения | Запись переходит в `APPLIED` по наблюдению; измерено распределение задержки применения |
| Соблюдены бюджеты правок | Для каналов с лимитом правок на объект: попытки учитываются до отправки, превышение отклоняется БД (`edit_budget`); для каналов без документированного лимита — подтверждено, что лимита нет |

## 13. Сверка потерь уведомлений опросом (шаг 24) [Р-121]

Ярусный опрос [Р-47] — обязательный дублирующий контур уведомлений: ни `buy_box_changed`, ни `ANY_OFFER_CHANGED` не несут номеров
последовательности, пропуск обнаруживает только опрос.

| | Kaufland | Amazon |
|---|---|---|
| Уведомление | `buy_box_changed` (ранний доступ, Р-45) | `ANY_OFFER_CHANGED` (очередь SQS) |
| Опрос сверки | ярусный `GET /buybox` — тот же опрос, что даёт снимки решению | `getCompetitiveSummary` по кругу: до 20 ASIN за вызов, 0.033 rps, burst 1 **[док]**; снимок только для сверки, в решение не идёт (AMZ_C07, AMZ_C11) |
| Что сверяется | цена Buy Box (её дают и уведомление, и опрос) | наименьшая цена конкурента (`lowestPricedOffers` New/Consumer; победителя Buy Box ответ не даёт — сегменты) |
| Срок уведомления | 15 минут — допущение (K-10, OQ-175) | 15 минут — допущение (A-08, OQ-175) |
| Открытые вопросы | K-19 (уведомление о смене цены того же победителя) | A-15 (совпадение наборов предложений, лимит приложения) |

Правило: опрос сверяется с последним принятым состоянием товара до обработки; расхождение — проверка со сроком; база ставит «задержка»,
если до срока пришёл снимок уведомления этого товара новее прежнего состояния, иначе «подозрение на потерю» — CRITICAL-алерт
`NOTIFICATION_LOSS_SUSPECTED` (0088). Сверка включается, когда подписка на уведомления активна: без неё каждое изменение рынка было бы
«потерей». Замер на модели Kaufland — docs/evidence/step24-notification-loss.md.
