# Шаг 106: предел поиска Amazon в моделях, быстрая область двумя заданиями, dev-зависимости — доказательство

Технический шаг по решениям владельца после шага 105 (п. 4–6 разбора A-30/A-31 и CI).

## 1. Предел `searchListingsItems` в моделях Amazon (A-31)

Поиск листингов отдаёт не больше 1000 SKU на все страницы — страница «Understanding Amazon listing status» и **модель снимка**
`2026-09-29` (описание `numberOfResults`: «The maximum number of items (SKUs) that can be returned and paged through is 1000»; сам
`numberOfResults` — сколько найдено). Решение владельца: при боевом подключении каталог обнаруживается отчётом
`GET_MERCHANT_LISTINGS_ALL_DATA`, поиск — только точечные чтения (в отложенном); модели должны знать предел, чтобы прогон, опирающийся на
поиск, честно показывал неполноту.

- HTTP-модель SP-API (`tests/contract/src/simulator/amazon-channel.ts`): страницы — только внутри первых 1000 SKU, токена дальше нет,
  `numberOfResults` — полное число найденного. Что отвечает канал за пределом (нет токена или ошибка) — не сказано: поведение модели —
  консервативное допущение (проверить на живом аккаунте).
- Модель порта (`SimulatedAmazonPort.discoverOffers`): обнаружение отдаёт не больше 1000 листингов.
- Прогонов, обнаруживающих больше 1000 листингов Amazon поиском, сейчас нет (масштаб — Kaufland, kill-test заводит каталог посевом,
  пилоты и демо — десятки предложений), поэтому предел ничего не роняет: он ловит того, кто опрётся на поиск позже.

**Поправка.** Шаг 105.1 записал в `vendor/amazon/listing-status/2026-10-21/SOURCE.md` и A-31, что предела «нет ни в модели снимка» —
неверно: предел искался по словам «1000 listings» и «1,000», а в модели он сформулирован «items (SKUs) … is 1000». Исправлено в обоих
местах с пометкой.

## 2. Быстрая область — двумя заданиями CI

Push-прогон шага 105 снят пределом 40 минут на задании `fast` (упавших тестов нет): тот же код в соседнем прогоне прошёл за 36 мин 19 с,
а по одинаковым строкам журнала push-прогон отставал равномерно — раннер был на четверть медленнее. Задание `fast` уже несколько шагов
шло 30–37 минут. Решение владельца — разделить, а не поднимать предел (подъём лишь отсрочил бы снятие: быстрая область растёт с каждым
шагом).

- `scripts/test-scopes.mjs`: `FAST_SHARDS = 2` и `fastShards` — единица деления — общий прогон рабочего пространства или файл-замер (они
  идут по одному); вес — минуты из журнала зелёного быстрого прогона шага 105 по запросу (39600159918); деление жадное. Шарды: 87 и 87
  файлов, ~18,2 и ~18,1 минуты весов.
- `scripts/test-all.mjs --shard=K/N`: только у быстрой области; журнал выполненных файлов сверяется с файлами своего шарда; неверный
  шард — `BUILD RED` до запуска тестов (проверено: `3/2`, `1/3`, шард у полной области).
- `.github/workflows/ci.yml`: задание `fast` — матрица `shard: [1, 2]`, у каждого прежние 40 минут; проверка типов, покрытие каталога и
  отчёт `npm audit` по dev-зависимостям — во втором шарде (тестам не нужно дважды).
- Правило репозитория [Р-146] «шаг 106»: каждый файл быстрой области — ровно в одном шарде, ни один шард не пуст, матрица CI — шарды
  1…`FAST_SHARDS`, и задание передаёт свой шард `test-all`; зубы — потерянный и повторённый файл правило видит.
