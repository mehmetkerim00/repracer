# Шаг 108: разведка живой песочницы SP-API — настоящие ответы против порта и фикстур

2026-10-29. Песочница NA (`sandbox.sellingpartnerapi-na.amazon.com`), приложение Sandbox шага 70. Учётные данные — файл секретов вне
репозитория; в журнал и в этот отчёт попали только имена ключей (`AMAZON_SANDBOX_LWA_CLIENT_ID`, `AMAZON_SANDBOX_LWA_CLIENT_SECRET`,
`AMAZON_SANDBOX_REFRESH_TOKEN`). Код продукта не менялся: расхождения ниже — список для отдельных решений.

- Скрипт — [tools/sp-api-recon.mjs](../../tools/sp-api-recon.mjs): вне продукта и вне CI (не рабочее пространство, не входит в `test-all`).
- Журнал — [step108-sp-api-recon-exchanges.json](step108-sp-api-recon-exchanges.json): 32 обмена с запросами и ответами. Перед записью скрипт
  проверяет журнал на каждое значение секрета, на оба токена доступа и на форму токена Amazon [Р-177], и при находке отказывается писать.
- Сверка повторяется без сети: `--offline` по журналу дал байт в байт те же находки.

## Как сделано

1. **LWA.** `grant_type=refresh_token` (Client ID, Client Secret и refresh-токен со страницы Sandbox Testing) → 200, `bearer`, 3600 с,
   токен доступа `Atza|…` 353 знака, в ответе тот же refresh-токен (как на шаге 70). В задании сказано «client credentials»: обмен
   `grant_type=client_credentials` (scope `sellingpartnerapi::notifications`) у этого приложения → **400 `invalid_scope`**. Токен без
   продавца по документации годится только для операций без продавца (адресаты и подписки уведомлений). Листинги, цены и FBA Inventory
   требуют токен продавца — его и берёт адаптер.
2. **Параметры** — ровно образцы `x-amzn-api-sandbox.static` из моделей снимка `vendor/amazon/sp-api-models/2026-09-29`: статическая
   песочница отвечает только на них. Обязательный параметр, которого образец не задаёт, — синтетика проекта: продавец `A1SYNSELLER0001`,
   SKU `SYN-SKU-108`, amazon.com, тело PATCH формы нашего адаптера. FBA Inventory — динамическая песочница: запрос ровно формы адаптера
   по `SYN-FBA-70` (7 шт., созданы шагом 70) и по SKU без запаса.
3. **Сверка каждого ответа** в четыре слоя:
   - (а) байт в байт с образцом модели;
   - (б) со схемой ответа модели — строже модели в одном, как проверка уведомлений шага 97: поле, которого модель не описывает, — находка;
   - (в) разбором НАСТОЯЩЕГО адаптера `packages/amazon-adapter`. Настоящий ответ подаётся адаптеру заглушкой `fetch`: проверяется
     разбор ответа, а не форма нашего запроса (её песочница не принимает — шаг 70, расхождение 6);
   - (г) с телами ответов той же операции в фикстурах стенда `tests/contract/fixtures/amazon`.

   У сверки со схемой есть положительный контроль: в образец подсаживаются лишнее поле, неверный вид суммы и снятое обязательное
   поле — скрипт без всех трёх находок не работает.
4. **Не вызывалось:** заказы (у образцов `searchOrders` и `getOrder` наборы `BUYER` и `RECIPIENT` — не запрашиваем и в песочнице [Р-4],
   шаг 70, находка 13), `putListingsItem` и `deleteListingsItem` (порт их не зовёт), уведомления.

Итог по статусам: 200 — 20, 400 — 9, 403 — 3. Время ответа 0,2–1,2 с. `x-amzn-RateLimit-Limit` — 5.0 у всех операций: это лимит песочницы,
а не Usage Plan (шаг 70).

## Расхождения — правки отдельным решением

1. **Фикстуры ответов листингов без обязательных полей модели.** У `ItemSummaryByMarketplace` модель требует `createdDate` и
   `lastUpdatedDate`, настоящий ответ их несёт. В фикстурах их нет у 57 из 61 сводки (24 файла `getListingsItem` и
   `searchListingsItems`). Есть только у `sandbox-response-mismatch.json`: он записан с песочницы на шаге 70. Разбору это не мешает —
   адаптер полей не читает. Но это тот же класс, что 34 тела уведомлений шага 97, теперь у ответов API: проверка шага 97 смотрела только
   уведомления.
   Предложение: распространить `strictErrors` шага 97 на тела ответов API в фикстурах (правило Р-146) и дополнить построитель
   `tests/contract/src/amazon-fixtures/build.ts`.
2. **Стенд не подаёт полей, которые адаптер читает.** `conditionType` (из него состояние предложения) и `itemName` (название, OQ-249)
   есть только в той же записанной с песочницы фикстуре. Разбор на настоящем ответе верен (`new_new` → `new`, название взято). HTTP-модель
   SP-API (`tests/contract/src/simulator/amazon-channel.ts`) эти поля и обязательные даты отдаёт — расходятся только фикстуры построителя.
3. **`attributes` песочница не отдаёт никогда.** Нет ни у одного образца `getListingsItem` и `searchListingsItems`, хотя адаптер их
   просит. На форме `attributes.purchasable_offer` держится многое:
   - записанная цена (`our_price`) — обратное чтение и подтверждение;
   - правило автоматического ценообразования (Р-115, Р-120);
   - рамки `minimum/maximum_seller_allowed_price` (Р-114, Р-233).

   Эта форма взята только со страниц документации (`manage-purchasable-offer`). Настоящим ответом статическая песочница её не проверит;
   в разборе адаптером цена так и даёт `no our_price` (как на шаге 70). Закрыть может только первый живой аккаунт — вместе с уже
   отложенным живым чтением рамок канала (A-30).
4. **Снимок моделей Listings Items устарел.** После 2026-09-29 официальная модель (`amzn/selling-partner-api-models`, ветка `main`,
   последний коммит `df7c62985ae6` от 2026-10-28) добавила:
   - `ItemOfferByMarketplace.replenishmentDiscount` — скидка Subscribe & Save;
   - `ItemOfferByMarketplace.quantityDiscountPlan` — скидки за количество, «returned only when the offer has an active quantity
     discount schedule»;
   - определения `ReplenishmentDiscount`, `QuantityDiscountPlan`, `QuantityDiscountLevel`.

   SHA-256 файла — `d60eed71…` против `117617f4…` у снимка. Песочница отдаёт новые образцы байт в байт. Адаптер поля не читает, разбор
   не страдает. Цену покупателя адаптер берёт из `offers[].price`, а скидки — отдельные поля.
   Предложения:
   - новый снимок моделей с датой (отдельным шагом, с суммами);
   - вопрос: учитывать ли эти скидки в сверке базы цены [Р-116]. Скидка за количество меняет цену при покупке нескольких штук, а не
     цену одной.
5. **Динамическая песочница FBA отдаёт поле вне модели:** `inventoryDetails.futureSupplyQuantity`. Модель FBA Inventory с 2026-09-29 не
   менялась (SHA-256 совпал) и поля не знает. Адаптер читает только `fulfillableQuantity` — разбор не страдает. Отдаёт ли поле бой —
   неизвестно.
6. **Купоны конкурентов.** Настоящие предложения `getCompetitiveSummary` несут `promotions[].promotionSavings.discountedPrice`: у
   `A2ZWOLFOFDPJL1` цена $17.15, а с купоном — $16.29. Снимок сверки берёт `listingPrice`, то есть цену без купона. На решение о цене это
   не влияет: снимок — только сверка потерь уведомлений [AMZ_C11, Р-121]. Но цена в нём — не та, что видит покупатель с купоном.
   Вопрос владельцу: считать ли цену с акцией ценой конкурента.
7. **Держатель Buy Box — по сегментам, а не один.** Образец `getCompetitiveSummary` с `featuredBuyingOptions` называет продавца
   предложения в Buy Box по сегменту покупателя, с долей просмотров:
   - `A3DJR8M9Y3OUPG` — NON_PRIME 72 % и PRIME 10 %;
   - `A2ZWOLFOFDPJL1` — NON_PRIME 18 %.

   Это второй возможный источник держателя для A-29 [Р-221]: лимит тот же 0.033 rps, адаптер этот набор не просит. Образец
   `getItemOffers`, на котором стоит план A-29, `IsBuyBoxWinner` не несёт вовсе — песочницей путь не проверить. Вопрос владельцу:
   «доля Buy Box» [Р-220] считает одного держателя, а канал называет держателей по сегментам.
8. **Задокументированный 400 отвечает 403.** Образец 400 `searchListingsItems` (`marketplaceIds=invalid`) и оба образца
   `getFeaturedOfferExpectedPriceBatch` (`marketplaceId: "MARKETPLACE_ID"`) → 403 `Unauthorized` «Access to requested resource is
   denied.», `details` пустое, `x-amzn-ErrorType: AccessDeniedException`. Наш клиент принял бы `Unauthorized` за протухший токен: обмен и
   один повтор. Адаптер затем назвал бы это `FORBIDDEN` уровня аккаунта.
   Из порта такой запрос не уйдёт: витрины отфильтрованы по таблице адаптера до вызова. Но это ещё одно свидетельство к A-26: по ответу
   403 не отличить неверную витрину от неверного пути и от недействительного токена (шаг 70: неизвестный путь — тоже 403 с пустым
   `details`).
9. **Тела ошибок: `details: ""`** там, где у образцов `details` нет. Клиент пустое `details` отбрасывает — совпадает, правка не нужна.
10. **Токен без продавца не выдан** (`invalid_scope` на `sellingpartnerapi::notifications`). Листингам, ценам и остаткам он и не нужен. Но
    адресаты уведомлений (`createDestination`) — операция без продавца (модель снимка `notifications.json`: «The `createDestination`
    operation is grantless»). Подписку `ANY_OFFER_CHANGED` и `PRICING_HEALTH` на очередь SQS
    этим приложением не завести, пока у него нет этого scope. Отдельно стоит проверить на боевом приложении до пилота
    ([pilot-readiness](../pilot-readiness.md)).

## Чего разведка не проверяет

- Данных и наших собственных форм запросов `searchListingsItems` и `getCompetitiveSummary`: статическая песочница принимает только
  параметры образцов (шаг 70).
- Боевых лимитов и боевых ответов на чужую витрину (A-26, A-27, A-28).
- Заказов, уведомлений, отзыва авторизации (A-17).

## Повторить

```
node --experimental-strip-types --disable-warning=ExperimentalWarning tools/sp-api-recon.mjs --secrets <файл секретов> --out <каталог>
node --experimental-strip-types --disable-warning=ExperimentalWarning tools/sp-api-recon.mjs --offline docs/evidence/step108-sp-api-recon-exchanges.json
```

Без `--secrets` скрипт читает переменную `REPRACER_AMAZON_SANDBOX_ENV`, иначе файл `amazon-sandbox.env` в каталоге
`.config/repracer/secrets` домашнего каталога. Снятие типов нужно ради разбора адаптером: исходники пакета — TypeScript.
