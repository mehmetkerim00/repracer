# Шаг 110: две полосы CI и ночной полный прогон main [Р-236]

Решение владельца после шага 109.1 — четыре пункта: тяжёлая полоса, лёгкая полоса, ночь, запись и доклад. ADR —
[0066](../adr/0066-two-ci-lanes-and-nightly-full-run.md).

## Что сделано

**Полоса по диффу** — `scripts/ci-lane.mjs` (`laneOf`, `changedPaths`; `node scripts/ci-lane.mjs [база] [вершина]` печатает JSON).
- **Лёгкие места — явный список:**
  - `apps/console/src/`;
  - `packages/console-model/src/`;
  - `apps/console/test/`;
  - `docs/`;
  - `CLAUDE.md`, `README.md`.
- **Всё остальное — тяжёлая полоса** с причиной «вне списка лёгких мест». Спорное — тяжёлое: сервер консоли
  (`apps/console/server/`) пишет в базу; тяжёлые также конфигурация сборки консоли, зависимости, процесс CI, сами правила, снимки каналов
  и лендинг.
- **Тест в лёгком месте всё равно тяжёлый**, если:
  - быстрый прогон его не гоняет (`INFRASTRUCTURE_FILES` из `scripts/test-scopes.mjs`: сутки демо, сутки тени и прочие);
  - на него ссылается каталог мутаций (`tests/db/mutations.mjs`, по полному пути или по имени файла).
- **Переименование** проверяется по обоим именам. Пустой дифф — тяжёлая полоса.

**Ворота слияния** — `scripts/merge-when-green.mjs <ветка> <sha>`. Полоса считается по диффу против `origin/main`, затем раз в минуту
опрашиваются прогоны и принимается одно решение (`mergeDecision`):

| Состояние | Решение |
|---|---|
| Последняя ночь не зелёная (в том числе снятая) | STOP `NIGHT_RED` — слияний нет до зелёной ночи |
| Быстрый прогон ветки красный | STOP `FAST_RED` |
| Тяжёлая полоса, полный прогон ветки красный | STOP `FULL_RED` |
| Быстрый ещё не начат или идёт | WAIT |
| Тяжёлая полоса, полного нет или он идёт | WAIT `FULL_NOT_STARTED` / `FULL_RUNNING` |
| Лёгкая полоса, быстрый зелёный | MERGE `LIGHT_FAST_GREEN` |
| Тяжёлая полоса, оба зелёные | MERGE `HEAVY_BOTH_GREEN` |
| Открыт Issue красной ночи | STOP `NIGHT_ISSUE_OPEN` |
| `origin/main` не предок проверенного SHA | STOP `NOT_FAST_FORWARD` |
| Не прочиталось (GitHub, `git fetch`) | WAIT `READ_FAILED` — следующий опрос через минуту |

Ночь — последний ЗАВЕРШЁННЫЙ прогон main по расписанию или по запросу на main. Ночей ещё не было — лёгкая сливается. Слияние —
`git push <sha>:refs/heads/main` без force; не прошёл — следующий опрос проверяет всё заново, включая fast-forward.

**Только fast-forward проверенного SHA** (уточнение владельца): отмена полного прогона на push в main верна, пока main получает ровно
коммит, чьи прогоны прочитали ворота. Ворота ищут прогоны по точному SHA и отправляют его же; перед слиянием `origin/main` обязан быть его
предком (`isFastForward`: свежий `git fetch`, `git merge-base --is-ancestor`), иначе стоп. Merge-коммит, rebase, push другого SHA — новый
коммит без прогонов: его отправляют веткой, и ворота ждут его прогоны по полосе (у тяжёлой — полный обязательно). Push в main мимо ворот
запрещён правилом, но технически не закрыт — защиты ветки на стороне GitHub нет; такой коммит первой увидит ночь.

**Сторож ночи** (довесок владельца) — задание `night-watch` в `ci.yml`, `scripts/night-watch.mjs`:
- ждёт все задания (`needs`) и идёт при любом их исходе — `always()`, а не `failure()`: иначе зелёная ночь не закрыла бы Issue;
- только на main, по расписанию или по запросу; право `issues: write` — только у него;
- красная ночь — Issue «Красная ночь YYYY-MM-DD» с меткой `night-red`: ссылка на прогон, коммит, задания не в success (снятое и
  пропущенное — тоже: ночь прошла не целиком), `cc @<владелец репозитория>`;
- повторная красная — комментарий в открытый (самый ранний), нового Issue нет;
- зелёная — комментарий «Зелёная ночь …» и закрытие всех открытых с меткой;
- ворота слияния держат и красная ночь (прогон), и открытый Issue — вместе: Issue, закрытый руками при красной ночи, слияний не откроет,
  а Issue, открытый при зелёном прогоне, их держит, пока его не закроют.

Сторож сам — задание ночного прогона: если упадёт он, прогон не зелёный, и ворота стоят (`NIGHT_RED`) — сторона fail-closed. Живьём он
впервые сработает первой ночью после слияния: на ветке он пропущен по условию, а создавать пробные Issue в публичном репозитории до
этого не стоит.

**Первый настоящий запуск ворот.** Шаг 109.1 слили ворота: тяжёлая полоса (`tests/contract/src/console/stand.ts`), оба прогона того же
коммита, `MERGED HEAVY 23abfe7`. Ворота шага 110 упали через 4 минуты: `gh run list` — «net/http: TLS handshake timeout», исключение
дошло до верха, и процесс завершился, а прогоны шли дальше без того, кто их сольёт. Исправлено: цикл ворот — функция `gate` с внедрённым
чтением; сбой чтения — `READ_FAILED` и ожидание, неудачный пуш — повтор следующим опросом; у вызовов `gh` и `git` — сроки.

**Ночь** — `.github/workflows/ci.yml`:
- `on.schedule`, `cron: '17 2 * * *'` — 02:17 UTC, не в начале часа;
- задания полного прогона (`full`, `demo-day`, `shadow-day`, `chaos`, `scale`) — только `schedule` и `workflow_dispatch`, на push больше не идут;
- быстрые задания (`fast` 1/2 и 2/2, `guards`, `clickhouse-compression`) — на каждый push, без условий.

**Правило репозитория** — `scripts/test/ci-lanes.test.ts`, 8 тестов:
- лёгкая полоса и дословный список лёгких мест;
- тяжёлая полоса и спорные пути;
- тесты полного прогона и каталога в лёгком месте — тяжёлые;
- таблица решения слияния, включая fast-forward и открытый Issue;
- fast-forward на настоящих репозиториях git (временные, голый удалённый и рабочий): ветка поверх main, main ушёл вперёд, перебазированный
  шаг — новый SHA без прогонов;
- цикл ворот при сбоях: чтение падает и возвращается, не возвращается, `git fetch` падает, пуш падает, main ушёл, Issue открыт, Issue
  не прочитался;
- сторож ночи: план (создать, дописать, закрыть, ничего) и команды `gh`;
- форма `ci.yml`, включая сторожа.

## Красное сначала

| Что | Как показано |
|---|---|
| Форма `ci.yml` | на прежнем `ci.yml` из main правило красное семью находками: «нет ночного расписания on.schedule», «не только ночью и по запросу» у `full`, `demo-day`, `shadow-day`, `chaos`, `scale`, «нет задания night-watch» |
| Зубы правила `ci.yml` | положительные контроли внутри теста: прежнее условие `github.ref == 'refs/heads/main'` и пропавшее расписание — шесть находок; расписание в начале часа (`0 2 * * *`); у сторожа — забытое задание в `needs`, `if: failure()` вместо `always()`, нет `issues: write` |
| Сбой чтения | цикл ворот без перехвата — тест красный той же ошибкой, что настоящий запуск: `net/http: TLS handshake timeout` |
| Fast-forward | решение без строки проверки — тест красный: MERGE вместо STOP `NOT_FAST_FORWARD` |
| Открытый Issue | решение и цикл без проверки Issue — оба теста красные: MERGE вместо STOP `NIGHT_ISSUE_OPEN` |
| Классификатор, ворота, `isFastForward`, сторож | новый код — исключение, названное явно: на старом коде их нет. Зубы — контроли с настоящими путями (тесты полного прогона `demo-day-live` и `shadow-live`, имя и путь из каталога), снятая ночь, настоящий git (main ушёл вперёд — `false`), сторож: повторная красная ночь — комментарий, а не новый Issue; зелёная — закрытие |

## Что нужно для ночного расписания

Настраивать в GitHub ничего не нужно: расписание — строка `on.schedule` в `ci.yml`. Условия из документации
([Events that trigger workflows, schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)):
1. **Файл с расписанием должен лежать в main.** Расписание работает только на ветке по умолчанию и по её последнему коммиту. Первая
   ночь — ближайшие 02:17 UTC после слияния шага 110.
2. **Время — UTC; пик нагрузки — начало часа.** Запуск может сдвинуться или быть снят — поэтому 02:17. Снятая ночь — не зелёная: ворота
   слияния её не пропустят, её повторяют.
3. **60 дней без активности** в публичном репозитории — расписание отключается само. Пока идут шаги, это не грозит. После долгой паузы —
   включить workflow заново во вкладке Actions.
4. **Уведомление о провале ночи.** Письмо GitHub о проваленном прогоне уходит пользователю, последним менявшему строку cron, и зависит
   от настроек почты аккаунта. Поэтому главное уведомление — Issue «Красная ночь YYYY-MM-DD» от сторожа ночи: он виден в репозитории и
   держит ворота слияния сам; упоминание владельца в нём приходит в уведомления GitHub.
5. **Стоимость:** репозиторий публичный, минуты Actions бесплатны. Ночь — около 1,5 часа параллельных заданий раз в сутки.
6. **Красная ночь — разбор первым делом.** В начале каждого шага смотрится последняя ночь
   (`gh run list --branch main --event schedule --limit 1`), ворота слияния проверяют её сами. Повтор после исправления —
   `gh workflow run ci --ref main` (повтор по запросу на main считается ночью) или `gh run rerun <id>`.

Защита слияния — ворота-скрипт, а не правило ветки на стороне GitHub. Шаги в main отправляет тот же `git push`, и обойти ворота может
только человек, который пушит руками.
