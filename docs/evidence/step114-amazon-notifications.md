# Шаг 114: приёмник уведомлений Amazon, часть А — наша сторона без живого AWS

Задание владельца «приёмник уведомлений Amazon — часть А»: обработчик очереди с журналом сырья, реакция на уведомления листингов и
место под ANY_OFFER_CHANGED / PRICING_HEALTH, честная деградация, стенд с эмуляцией очереди и хаосом, конфиг и чек-лист части Б.
Решения — [Р-239](../decisions.md), [ADR-0068](../adr/0068-one-queue-raw-journal-listing-status.md).

## Противоречие задания и снимка — доложено до кода

Задание: «уведомления SP-API приходят только через EventBridge». Снимок (notification-type-values, столбец Workflow): только через
EventBridge приходят уведомления **листингов**; ANY_OFFER_CHANGED и PRICING_HEALTH — только через SQS. Стоп-вопросы владельцу и ответы:

- **очереди** — «Одна очередь»: адресат SQS SP-API и цель правила EventBridge — одна очередь и одна очередь недоставленных, в политике
  два разрешения, приёмник различает конверт;
- **реакция на листинги** — «Состояние листинга»: одно наблюдение «статус и проблемы листинга» из трёх источников (уведомление, чтение
  после записи, обнаружение), данные канала 18 месяцев, пилюля Offers «Not buyable on Amazon», CRITICAL, когда включённое предложение
  теряет BUYABLE.

## Что сделано

| Пункт задания | Как |

Обработчик очереди, журнал сырья, дедупликация | `packages/amazon-notifications`: конверт SP-API и событие EventBridge (`envelope.ts`), сырьё — в `channel_data.notification_journal` (0213) **до** пути решения, одна строка на уведомление; повтор — `REPEAT`, не ошибка; удаление из очереди — только после обработки |
| 2. Реакция на LISTINGS_ITEM_*; место под ANY_OFFER_CHANGED / PRICING_HEALTH | адаптер Amazon разбирает LISTINGS_ITEM_STATUS_CHANGE 1.0 и LISTINGS_ITEM_ISSUES_CHANGE 2023-12-13 в событие `LISTING_STATUS`; чтение после записи и обнаружение дают то же наблюдение; одна запись — `recordListingStatus`, одно правило — `listingStatusStep`; ANY_OFFER_CHANGED и PRICING_HEALTH — прежним путём; путь решения о цене не тронут |
| 3. Честная деградация | без очереди опрос работает как прежде (обнаружение пишет статус настоящим адаптером); отказ очереди — не потеря; ждавшее в очереди доходит, когда приёмник вернулся; экран Channels говорит, откуда данные: уведомления за сутки по видам или «только опрос» |
| 4. Стенд: эмуляция SQS, хаос | модель стандартной SQS на стенде (`FakeSqs`), тела — формы примеров снимка; хаос — смерть обработчика на каждой границе пачки |
| 5. Конфиг части Б | шаблон `deploy/notification-receiver/part-b.env.example` (заглушки), файл секретов вне репозитория с теми же заглушками (права 600), проверка «да/нет» без значений — `services/notification-receiver/src/part-b.ts` |
| 6. Чек-лист части Б | [amazon-notifications-part-b.md](../amazon-notifications-part-b.md): очереди, политика с двумя разрешениями, ключи приёмника, адресаты SP-API, EventBridge, подписки, проверка, критерии успеха, «если что-то не так» |

**Эмуляция очереди — модель на стенде, а не localstack:** образы Docker Hub на машине разработчика не скачиваются (OQ-114), а модель
уже держит то, от чего зависит свойство «ни потери, ни дубля», — повторную доставку после смерти получателя (скрытие на
VisibilityTimeout, удаление по ReceiptHandle последнего получения); живой AWS — часть Б.

## Хаос — смерть посреди пачки

`tests/contract/src/notification-chaos.pg.test.ts`. Настоящие приёмник, адаптер Amazon, путь решения и база; очередь — модель.

- **Пачка:** два статуса листинга событием EventBridge, ANY_OFFER_CHANGED сообщением SP-API и повтор первого статуса — 4 сообщения.
- **Сколько границ:** пачка без смерти пересекает **28 границ** ввода-вывода: обращения к очереди, к журналу сырья, к журналу
  обработанных, каждая транзакция хранилища пути решения — до вызова и после.
- **Как умирает процесс:** раунд за раундом процесс умирает на каждой границе по очереди. Умерший больше ничего не делает: его следующие
  вызовы не возвращаются никогда. Транзакция неделима, поэтому смерть посреди неё — это откат.
- **Перезапуск:** новый экземпляр приёмника на той же очереди и базе, часы — за VisibilityTimeout.
- **Свойство на каждой из 28 границ:**
  - очередь пуста;
  - у каждого уведомления ровно одна строка журнала сырья и одна — журнала обработанных;
  - у каждого уведомления ровно одно следствие: статус листинга — одна строка, ANY_OFFER_CHANGED — один снимок в журнале снимков.
- **Зубы:** мутация «удалить сообщения из очереди сразу после получения» (доставка «не больше раза») — красный на границе 4 из 30,
  уведомление потеряно.

**Деградация — тот же файл, второй тест:**
- приёмник выключен, уведомлений за сутки нет — Channels: «polling only»;
- обнаружение настоящим адаптером (модель ответа `searchListingsItems`) записывает статус «не покупается» без очереди;
- очередь отвечает 503 — 0 получено, сообщение осталось;
- следующий круг доставил ждавшее уведомление — Channels: «Amazon notifications … 1 offer status change»;
- пустая очередь — не ошибка.

## Расхождения снимка — записаны

- **LISTINGS_ITEM_STATUS_CHANGE, имя типа:** схема модели 2026-10-29 перечисляет тип как `LISTINGS_ITEM_STATUS_CHANGED`, а страница,
  пример схемы и `createSubscription` — `LISTINGS_ITEM_STATUS_CHANGE`. Приёмник принимает оба написания одного типа.
- **SellerId:** таблица страницы пишет поле продавца «SellerID», схема и пример — «SellerId». Разбор читает оба.
- **Форма `detail` события EventBridge** у SP-API не задокументирована — вопрос **A-33**. Разбор строгий; непонятое событие — CRITICAL с
  именами ключей `detail`.
- **Use case guide уведомлений:** страница, скачанная 2026-11-05, оказалась «Page Not Found». Факты взяты из страниц EventBridge,
  notification-type-values, notifications-api и модели снимка ([vendor/aws/SOURCE.md](../../vendor/aws/SOURCE.md), раздел «Шаг 114»).

## Что ждёт часть Б

- **Скоуп grantless.** `createDestination` требует скоупа `sellingpartnerapi::notifications`; проверка ключей 2026-11-05 — LWA ответил
  `400 invalid_scope`. Ждём ответа поддержки.
- **Подписки** продукт не создаёт; шифрование очереди и роли подписок — на звонке. Строки «114» в [отложенном](../deferred.md).
