# Шаг 114.1: P1-03 — проверка части Б принимает идентификатор боевого приложения

Находка аудита 2026-11-06 (`TMPRICE_MVP_READINESS.md`, раздел 13.3; задача P1-03) и задание владельца «отдельным шагом, красный тест сначала».

## Дефект

`services/notification-receiver/src/part-b.ts` (шаг 114) требовал, чтобы приложение и источник партнёра были вида `amzn1.sellerapps.app.…`.
У боевого приложения идентификатор начинается с `amzn1.sp.solution.` (проверка ключей 2026-11-05, значения не печатались). На верном файле
проверка сказала бы «нет» четырьмя пунктами.

## Красное сначала

Тест шага в `services/notification-receiver/test/part-b.test.ts` на прежней проверке — красный, фактический результат:

```
'приложение — вида amzn1.sellerapps.app.…'
'всё в одном аккаунте AWS'
'источник партнёра — наше приложение'
'шина — шина источника партнёра, правило — на этой шине'
```

Контроли того же теста: LWA client id вместо приложения (частая ошибка заполнения) по-прежнему «нет», источник с другим приложением — своей
причиной.

## Исправление

- Проверка принимает обе формы и сверяет равенство строк: приложение = приложение в имени источника партнёра.
- Шаблон `part-b.env.example` и `receiver.env.example` — новой формой.
- Какую форму Amazon подставит в имя источника партнёра и в `NotificationMetadata.ApplicationId`, снимок не говорит: все его примеры — старой
  формы. Это вопрос **A-34** ([channel-capabilities.md](../channel-capabilities.md)); проверяется на звонке части Б
  ([amazon-notifications-part-b.md](../amazon-notifications-part-b.md), раздел 8). Настоящий риск: приёмник сравнивает `ApplicationId` равенством,
  и другая форма дала бы `NOTIFICATION_FOREIGN_APPLICATION` на каждом уведомлении — строка добавлена в таблицу «если что-то не так».

## Решения владельца, записанные вместе с шагом

[Р-240](../decisions.md): конкуренты Amazon для пилота — опрос `getCompetitiveSummary` решает цену, тикет о скоупе — параллельно; Q11: без
«Win the Buy Box» на Amazon MVP приемлем. Строится шагом 115.
