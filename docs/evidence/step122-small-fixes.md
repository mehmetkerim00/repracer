# Шаг 122: малые правки по аудиту авторизации Amazon — П2, П7; П6 — стоп-доклад

Решения владельца по стоп-докладу аудита 2026-11-14: одним шагом малых правок — П6 (передавать `redirect_uri` явно), П2 (повтор обнаружения каталога не через
час, а по лестнице), П7 (пропущенные отчётом SKU показать, а не только в журнале процесса); П3, П4, П5, П8 — в [deferred.md](../deferred.md).

## П2: незакрытый круг обнаружения продолжается по лестнице

Было: заход обнаружения — раз в час (`discoveryEverySeconds`). Если отчёт листингов Amazon не готов за заход (~23 минуты ожидания внутри срока захода, A-38),
следующая попытка — через час, и каталог нового продавца появлялся позже часа.

Стало:

- планировщик принимает от запуска `continueAfterSeconds`: следующий срок — конец запуска плюс пауза, но не позже обычного срока; только у LATEST-работы и только
  после успеха (`services/scheduler/src/scheduler.ts`);
- работа `offer-discovery` просит продолжение, когда заход остановил срок или предел страниц: круг открыт меньше 30 минут — 5 минут, меньше часа — 10, меньше
  двух — 20, меньше четырёх — 40, дальше — обычный час (`DISCOVERY_CONTINUE_LADDER`, `services/scheduler/src/jobs.ts`); суточная квота приложения раньше не
  восполнится — там час, как было;
- `discoverOffers` называет начало своего круга (`circleStartedAt`): у продолжения — момент из хранилища круга, у нового круга — этот заход.

Миграций у П2 нет: возраст круга уже хранит `tenant_data.channel_discovery_circle` (0148).

## П7: SKU отчёта, которых поиск не вернул, — на экране Channels

Было: SKU, которые назвал отчёт, а поиск подробностей по SKU не вернул (A-39: листинг снят между отчётом и поиском), — только число в журнале процесса
(AMZ_C16 `SKU_NOT_FOUND`).

Стало:

- адаптер возвращает их со страницей (`DiscoveryPage.reportSkusNotFound`), ядро записывает у источника витрины функцией узкой роли обнаружения
  `tenant_data.record_discovery_not_found` (0227): число за круг и первые 20 SKU; новый круг начинает счёт заново; у поиска по витрине — ноль;
- форму держит база — ограничение `discovery_catalog_source_not_found`: число не отрицательное, названо не больше 20 и не больше числа, у поиска — ноль;
- Channels: «Not found when we asked Amazon for details, so not in the catalog this circle: 23 — SKU-…, … and 3 more.» и пилюля «may be incomplete»;
  EN/DE/ES/FR.

Оператору пропуски видны тем же экраном продавца; панель оператора не менялась (её экраны — операционное состояние, а не каталог тенанта).

## П6: стоп-доклад — `redirect_uri` в адресе согласия не передаётся по документации, а шага log-in URI в нашем потоке нет

Задание: «передавать `redirect_uri` явно» в адресе согласия. Сверка со страницей website-authorization-workflow (загружена 2026-11-14,
[vendor/amazon/lwa-authorization/2026-11-14](../../vendor/amazon/lwa-authorization/2026-11-14/SOURCE.md)):

- у адреса согласия параметров три — `application_id`, `state`, `version=beta`; `redirect_uri` среди них нет;
- `redirect_uri` — параметр перехода на `amazon_callback_uri` в шаге 8, а этот шаг — часть шагов 5–8 через **log-in URI** приложения: после согласия Amazon
  вызывает log-in URI с `amazon_callback_uri`, `amazon_state`, `selling_partner_id`; приложение отправляет продавца на `amazon_callback_uri` с `amazon_state`,
  своим `state`, `redirect_uri` и `version=beta`; только потом приходит код на redirect URI;
- тот же поток из 16 шагов — в архивных копиях страницы 2025-06-16 и 2026-01-04. Снимок шага 43 (2026-09-26) шаги 5–8 не записал, и поток шага 43 их не
  делает: адрес согласия — и сразу ожидание кода на `/connect/callback`; модель поставщика LWA в прогонах делает так же.

Вывод: с настоящим Amazon авторизация, скорее всего, не дойдёт до кода — продавец после согласия попадёт на log-in URI, которого консоль не обслуживает.
Это не правка S, а построение шагов 5–8 (страница log-in URI консоли, проверка `amazon_callback_uri` по списку адресов Amazon, новый `state`, `redirect_uri`
явно, модель поставщика LWA в прогонах — с этими шагами, живой прогон подключения). П6 в этом шаге не делался — решение владельца.
