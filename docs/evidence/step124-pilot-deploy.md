Б2 и Б5 — чек-листом в README.

## Что сделано

- **`deploy/pilot/compose.yaml`.** Состав:
  - PostgreSQL с паролями ролей (не trust, как у QA-A);
  - ClickHouse тем же образом и digest, что CI;
  - консоль, планировщик и панель — через `extends` своих развёртываний;
  - исполнитель заданий, `cloudflared`;
  - `tools` для разовых работ выкладки.

  Свойства:
  - консоль — промышленный профиль без публичного демо;
  - панель — `REPRACER_INVITE_LINK_REVEAL=on` [Р-245];
  - планировщик — роль адаптеров для токенов продавца;
  - наружу ничего: базы без портов, процессы только на loopback, страница — туннелем.

  Брокера и диспетчера нет.
- **`secrets.sh`** — на машине владельца, в `$HOME/.config/repracer/secrets/pilot` (700/600). Делает:
  - пароли ролей подключения и суперпользователя;
  - строки подключения процессов;
  - администратора и логины ClickHouse;
  - кольцо ключей токенов каналов;
  - секрет клиента LWA и идентификаторы приложения — из файла ключей боевого приложения.

  Ни одно значение не печатается, повторный запуск ничего не меняет. **`push-secrets.sh <user@server>`** копирует каталог одним потоком
  tar по SSH.
- **`db.sh`** — база пилота.
  - Первая сборка: журнал миграций с регионом, роли входа и строки возможностей каналов, пароли ролей, страж.
  - Выкладка: только новые миграции, роли и пароли (идемпотентно), проверка стража.
  - Снятый по процедуре (`allowed`) страж остаётся снятым. Снятый без значения — отказ выкладки: не отличить решение от ошибки.
- **`scripts/db/migrate.sh`** — журнал миграций живой базы в настройке базы `repracer.migrations = '<номер>:<сумма>'`.
  - Применяет только файлы после номера.
  - Миграцию, изменённую после применения, отказывается накатывать дальше.
  - База без журнала — отказ.
- **`deploy.sh` / `smoke.sh` / `compose.sh` / `clickhouse-users.mjs`** — выкладка одной командой и её проверка:
  - версия сборки каждого процесса, страж, ClickHouse;
  - панель только на loopback, брокера нет;
  - снаружи — `https://<имя>/healthz` через туннель.
- **README** — внешние шаги (ZITADEL, кабинет разработчика Amazon, Cloudflare), сервер, туннель, секреты, выкладка, страж и процедура
  его снятия, путь пилота, чего нет.

## Две находки по дороге

1. **Поэтапного применения миграций в репозитории не было.** Один путь схемы — `scripts/db/prepare.sh`: он пересоздаёт базу и сеет
   смоук-мир. README промышленного профиля советовал его «при каждом обновлении миграций». На пилоте каждая выкладка стёрла бы подключённый
   аккаунт продавца, каталог и неделю тени (Р-204 требует 7 суток подряд).
   - Исправлено журналом `scripts/db/migrate.sh`.
   - README промышленного профиля переписан на него.
2. **`infra/local/apply-clickhouse.mjs` перечислял файлы DDL списком.** С шагов 97 и 109 он пропускал `097_step97.sql` и
   `098_step109.sql`. Выгрузка пишет их столбцы (`offers.holds_buybox`, `offers.coupon_minor`, `buybox_segments.*`), а ClickHouse, поднятый
   этим скриптом (CI и любой сервер), их не знал.
   - Теперь список берётся из каталога.
   - Правило `scripts/test/clickhouse-ddl-files.test.ts`: каждый файл, кроме проверки 099, применяется по порядку.
   - Первый push-прогон шага это подтвердил: `clickhouse-compression` упал на строке замера сжатия, собранной руками ещё на шаге 20 —
     `Elements 'offers.seller_ref' and 'offers.holds_buybox' … have different array sizes`. Столбцы 097 появились, а строка их не знала.
     Сам выгрузчик пишет все вложенные столбцы согласованно (`competitor-history.ts`). Строка замера дополнена; на ClickHouse, поднятом
     прежним скриптом, `offers.holds_buybox`, `offers.coupon_minor` и `buybox_segments.*` в базу не попадали.
