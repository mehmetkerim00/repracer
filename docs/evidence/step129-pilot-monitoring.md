# Шаг 129: внешний контроль пилота — отметки процессов, копий и выноса, проверка `/healthz` снаружи [Р-127]

Решение владельца 2026-11-15 (п. 3.1 прод-готовности): «Отметки процессов во внешний сервис + отметка после каждой копии и каждого pull +
внешняя проверка /healthz через туннель. Аккаунты (healthchecks.io и внешняя проверка) заведём бесплатные… любые платные уровни — только через
Мердана». Там же (п. 2): перевод тень→бой — вариант (а), не строить сейчас, оценить и поставить в очередь с пометкой «обязательно до первого
перевода аккаунта в бой».

## Что сделано

- **Процессы пилота** — планировщик, консоль, панель, исполнитель заданий — отмечаются в healthchecks.io. Отметки умели все четыре с шагов 26–40,
  но в пилоте были выключены (OQ-188). Теперь в `compose.yaml` пилота умолчание — «включено», у каждого процесса свой файл адреса
  (`scheduler_heartbeat_url`, `console_heartbeat_url`, `operator_heartbeat_url`, `bulk_heartbeat_url`).
- **Отметка после каждой копии.** В образе копии (postgres 16 bookworm) нет ни curl, ни wget. По Dockerfile docker-library/postgres, wget
  ставится на время загрузки gosu и удаляется. Поэтому отметку шлёт новый сервис `backup-heartbeat` (`deploy/pilot/backup-heartbeat.ts`).
  Он только читает каталог копий:
  - новая готовая копия (файл сумм) — «жив», одна отметка на копию;
  - `BACKUP_FAILED` — «сбой», новая строка провала — снова «сбой»;
  - копия, готовая раньше его старта больше чем на 10 минут, не отмечается: повторная отметка сдвинула бы срок проверки и спрятала бы
    остановившуюся копию.
- **Отметка после каждого выноса.** `pull-backups.sh` на машине оператора шлёт «жив» после зелёного прохода и «сбой» после красного.
  - Адрес — не аргументом curl (аргументы видны в `ps`), а его конфигурацией со стандартного ввода.
  - Без адреса копии всё равно забираются: копии важнее.
  - `OFFSITE_PULLED` записывает `"monitored":true|false`. `backup-state.sh` без контроля красный: «вынос копий не под внешним контролем».
- **Отказ без контроля.** `deploy/pilot/heartbeat-state.sh` спрашивают `deploy.sh` (до сборки) и `smoke.sh`. Красный, если:
  - стоит строка `REPRACER_*_HEARTBEAT=off`;
  - нет одного из пяти файлов адресов;
  - адрес не https.

  Смоук вдобавок требует работающий `backup-heartbeat`.
- **Заведение проверок** — `scripts/setup-heartbeats.mjs --stand <имя>`. Скрипт заводит шесть проверок:
  - процессы — период 2 мин, допуск 3 мин;
  - копия и вынос — период сутки, допуск 2 ч, то есть письмо после 26 часов молчания, тот же предел, что у смоука.

  Пять адресов он пишет файлами 600 в каталог секретов стенда (на сервер их копирует `push-secrets.sh`). Адрес выноса — в
  `$HOME/.config/repracer/secrets/<имя>-pull-heartbeat-url`: серверу он не нужен. Адреса в вывод не попадают. Стенд — параметр: у QA-B
  (п. 3.4) будут свои проверки.
- **Проверка `/healthz` снаружи** — монитор UptimeRobot по ключевому слову на `https://app.<домен>/healthz`, раз в 5 минут, тревога
  «Keyword not exists» на `"status":"ok"`. healthchecks.io сам ничего не опрашивает, поэтому нужен второй сервис. Монитор заводится руками в
  кабинете (одна строка), кода API в репозитории нет.
- **Бесплатные уровни проверены по страницам** (снимки — адрес, дата, SHA-256): [vendor/healthchecks](../../vendor/healthchecks/2026-09-17/SOURCE.md),
  [vendor/uptimerobot](../../vendor/uptimerobot/2026-11-14/SOURCE.md).
  - healthchecks.io Hobbyist: $0, 20 проверок; условия коммерческого использования не ограничивают.
  - UptimeRobot Free: 50 мониторов, 5 минут, keyword; «Good for personal and commercial projects», в условиях — «available for any use,
    including commercial and business use».
- **README пилота, §9** — таблица проверок (кто отмечается, период, что значит письмо), шаги для Керима и чего этот контроль не видит:
  алерты из базы без почты (OQ-224), ClickHouse — только через планировщик, проверка восстановления — только смоуком.
- **Перевод тень→бой (п. 2)** — строка [deferred.md](../deferred.md) «128 (тень → бой с рамками)»: решение (а), размер 0,5–1 дня, пометка
  «ОБЯЗАТЕЛЬНО до первого перевода аккаунта в бой». Условие стоит и в чеклисте «День перевода в бой» ([live-first-account-checklist.md](../live-first-account-checklist.md)).

## Найдено

**Проверки, заведённые `setup-heartbeats.mjs` шага 33, не прислали бы ни одного письма.** Страница API healthchecks.io: «By default, this API
call assigns no integrations to the newly created check», значение `"*"` назначает все. Скрипт `channels` не передавал. Теперь передаёт в
обоих режимах, и тест держит это на модели API.

## Красное сначала

На коде шага 128 (`f0b26d3`) — 7 из 7 красные, каждый своей причиной:

| Тест | Причина на старом коде |
|---|---|
| `pilot-deploy` — состав сервисов | нет `backup-heartbeat` |
| `pilot-deploy` — отметки процессов | «scheduler: the heartbeat is not turned off in the pilot» |
| `pilot-monitoring` — backup-heartbeat | модуля нет |
| `pilot-monitoring` — сервис в compose | «the pilot has the backup-heartbeat service» |
| `pilot-monitoring` — отказ без контроля | `heartbeat-state.sh` нет |
| `pilot-monitoring` — pull | нет строки «отметки выноса нет» |
| `pilot-monitoring` — заведение проверок | старый скрипт не знал `HC_API_URL` и `--stand`: ушёл в настоящий API с синтетическим ключом и получил 401 — ничего не заведено |

Первая редакция последнего теста висела: `spawnSync` останавливал цикл событий процесса, в котором жила модель API. Тест перешёл на `spawn`.
