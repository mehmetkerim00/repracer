# Шаг 131: откат выкладки пилота — план миграций до переключения, копия перед миграциями, восстановление на место, учение

Решение владельца 2026-11-15 (п. 3.3 прод-готовности, ~3 дня): «процедура в README; свежая копия перед миграциями в deploy.sh; проверка журнала
миграций ДО переключения рабочей копии с понятным отказом вместо «applied migrations changed»; учение «N → N+1 с миграцией → откат» тестом,
красным сначала».

## Что было (стоп-доклад)

`deploy.sh <прежний SHA>` после выкладки с миграцией шёл так:
1. переключал рабочую копию, ставил зависимости и собирал интерфейс;
2. `migrate.sh` отказывал «applied migrations changed». Это сообщение о правке миграции задним числом, а случилось другое: база новее кода;
3. к этому моменту работающие процессы читали с диска (рабочая копия смонтирована) файлы и `node_modules` другой версии.

Копии перед выкладкой не было: откат через миграцию означал суточную копию и до суток потерь. Процедуры отката в репозитории не было, и она
ни разу не проверялась.

## Что сделано

- **`scripts/db/migrate.sh --check`** — план без применения: `MIGRATIONS PLAN: <база> at <номер>; pending <K>[: <первая>…<последняя>]`.
  У базы новее кода свой отказ, код 3: «database … is at migration N, this code knows migrations only through M: the database is newer than the
  code — going back past migrations is a restore of the copy taken before them». Эта проверка идёт раньше сверки сумм. Правка задним
  числом — по-прежнему код 1.
- **`deploy.sh`** читает настройки, готовность копий и внешнего контроля, затем план миграций выкладываемой версии. Миграции версии берутся
  из git (`git archive <SHA> migrations`), не с диска. Всё это — до `git checkout`.
  - Версия старше базы — «DEPLOY RED: … выкладка остановлена ДО переключения рабочей копии, ничего не менялось», со ссылкой на README «Откат».
  - Есть миграции к применению — после подъёма базы и до `db.sh` снимается копия (`pre-release-copy.sh`). Провал копии — стоп до миграций.
  - Каждая выкладка оставляет строку в `deploy/pilot/state/releases.log`.
- **`pre-release-copy.sh`** — одна копия тем же сервисом `backup` (`REPRACER_BACKUP_ONCE=1`) и отметка `repracer-<время>.pre-release`:
  `before`, `release`, `migrationsBefore`, `at`.
- **`rollback.sh [<SHA>]`** (без SHA — версия, с которой ушла последняя выкладка):
  - миграций между версиями нет — просто `deploy.sh <SHA>`, база не трогается;
  - база новее — журналы по сей момент, остановка процессов кроме базы, восстановление копии перед выкладкой на место живой базы, выкладка
    прежней версии.
- **`rollback-inner.sh`** — в одноразовом контейнере сервиса `backup`, суперпользователем, закрытый ключ со стандартного ввода:
  - находит копию: по SHA — по отметке `.pre-release`, либо копию по имени;
  - ДО того как тронуть живую базу — суммы копии и ключ (расшифровка ролей);
  - живую базу переименовывает в `<база>_rb_<время копии>`, а не удаляет;
  - восстанавливает тем же `deploy/production/restore.sh`, что при беде;
  - проверяет регион, страж боевых записей [Р-247] и журнал (миграция из отметки);
  - провал после переименования — частичная база удаляется, живая возвращается на место.
- **README пилота, §11 «Откат»** — два пути, что теряется, где лежит записанное после копии, как убрать отложенную базу, что проверено. §5 —
  выкладка по шагам с планом и копией.

## Найдено

- **Опасное место в первой редакции `rollback-inner.sh`.** Флаг «идёт восстановление» ставился до переименования живой базы. Если бы
  переименование упало (к базе подключены), уборка выполнила бы `DROP DATABASE <база>`, то есть удалила бы живую базу. Флаг теперь ставится
  только после удачного переименования, комментарий говорит почему.
- **`set -e` и подстановка в присваивании.** `list=": …$([ … ] && echo …)"` получал код подстановки, и `--check` при одной миграции к применению
  молча завершался с кодом 1. Переписано без подстановки.

## Красное сначала

На коде шага 130 красные 3 из 3 первых тестов, каждый своей причиной:
- `db-migrate` — «unknown arguments: --check»;
- `pilot-rollback` — `pre-release-copy.sh` нет;
- `pilot-rollback` — в `deploy.sh` нет плана миграций до переключения.

Тест порядка шагов `rollback.sh` и учение написаны вместе с файлами, которых на старом коде нет. Учение держится утверждениями на каждом шаге и
тремя контролями:
- чужой ключ — отказ, живая база не тронута;
- копия не той версии — отказ, живая база не тронута;
- провал ПОСЛЕ того, как живая база отложена (копия другого региона), — живая база вернулась на своё имя с записанным после выкладки,
  отложенных баз не осталось.

Третий контроль добавлен после первого зелёного прогона: оба прежних отказывают раньше переименования, и путь «как было» не проходился ни разу.

**Мутация** — уборка без возврата отложенной базы на её имя. Учение красное своим утверждением: вместо `ROLLBACK_UNDONE` пришло
`ROLLBACK_UNDONE_FAILED` («rename … back by hand»). Без мутации — 5 из 5. Отложенную базу, которую мутационный прогон оставил на локальном
PostgreSQL, я удалил. Уборка теста теперь удаляет `<база>_rb_*` сама.
