# Шаг 134: заведение проверок внешнего контроля — без получателя не бывает «готово»

Решение владельца 2026-11-15: «setup-heartbeats.mjs отказывает, если в проекте нет ни одной интеграции, и после заведения проверяет, что у
каждой проверки есть получатель; README §9 говорит прямо, что интеграцию Email в проект добавляют руками. Тест красным сначала».

## Что было

Первое настоящее заведение проверок пилота (2026-11-15, `setup-heartbeats.mjs --stand pilot`) напечатало «готова» у всех семи проверок и
записало адреса. Сверка через API сразу после этого показала:
- у проекта healthchecks.io ни одной интеграции (`GET /api/v3/channels/` — пустой список);
- у каждой проверки пустое `channels`.

Скрипт передаёт `channels: "*"` (находка шага 129), но страница API говорит: «*» назначает все **существующие** интеграции. В проекте без
интеграций это никто. Пропуск отметки не дал бы ни одного письма, а заведение выглядело успешным. README §9 обещал, что письма уйдут на
адрес аккаунта. Для этого проекта это неверно.

## Что сделано

- **До заведения** скрипт спрашивает интеграции проекта (`GET /api/v3/channels/`), в пробном запуске тоже: это только чтение. Нет ни одной —
  отказ и что сделать (Integrations → Email), ни одна проверка не заводится.
- **После заведения** скрипт сверяет получателя у каждой проверки по тому, что хранит сервис (`channels` в `GET /api/v3/checks/`), а не по
  тому, что он просил. Проверка без получателя — отказ с её именем, адреса не записываются. Повторный запуск обновляет те же проверки:
  upsert по `slug`, «updates the existing check», снимок [vendor/healthchecks](../../vendor/healthchecks/2026-09-17/SOURCE.md), раздел
  шага 134.
- **README пилота, §9, п. 1:** интеграцию Email добавляют в проект руками; второй получатель — ещё одна интеграция и повторный запуск.
- Модель API в тесте знает интеграции проекта и назначает по «*» только существующие, как сервис.

## Красное сначала

`pilot-monitoring.test.ts`, тест «step 134», на прежнем скрипте красный: в проекте без интеграций заведение выходит с кодом 0
(`expected: 1, actual: 0`). Остальные пять тестов файла в том же прогоне зелёные. После правки — 6 из 6.

## Попутно (решение владельца, п. 3)

Поиск `source` / `.` файлов секретов в скриптах выкладки нашёл одно место: `deploy/pilot/secrets.sh` исполняет файл ключей боевого
приложения Amazon. `pilot.env` и `qa.env` — настройки, а не секреты. Замена чтением строк `KEY=` — при следующем касании скриптов выкладки
([docs/deferred.md](../deferred.md), строка «134»).

## Живьём после слияния

Когда в проекте пилота появится интеграция Email, повторный запуск заведения обновит те же семь проверок. Сверка через API должна показать
получателя у каждой. Этот запуск — на машине владельца, ключ — из файла, значения не печатаются.

Миграций нет.
