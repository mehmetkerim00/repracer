# Шаг 138: к публикации — с расчётом (INV-01)

Отчёт Мердана «QA-A Bug & Findings Report 1.0», INV-01. Наблюдение: строка остатков «on-hand 60, reserved 1, available 59, к публикации 57»,
а форма Synchronization показывала «Buffer per channel = 0». Разница 2 на экране не объяснена.

## Разбор на QA-A (`b249573`)

Через API стенда, Demo store, строка Bike light · amazon.com: on-hand 60, reserved 0, available 60, к публикации 58.
- **Арифметика верна.** Демо включает синхронизацию amazon.com с буфером 2 (`apps/console/server/demo-world.ts`: `enableStockSync(…,
  { bufferUnits: 2, … })`). Правило одно в коде и в SQL хранилища: `max(0, доступное − буфер)`, потолок, порог выставления. 60 − 2 = 58,
  59 − 2 = 57 — ровно случай Мердана.
- **Неверно было показанное:**
  - поле формы Synchronization — значение по умолчанию для следующего включения (`useState('0')`), а не сохранённый буфер;
  - строка остатков сохранённых настроек не называла вовсе — модель экрана их не получала.

  Критического дефекта арифметики нет.

## Что сделано

- **Строка канала несёт сохранённые настройки аккаунта** (`StockChannelRow.allocation`: буфер, потолок, порог) — в PostgreSQL (та же
  выборка, по которой считается число) и в модели памяти.
- **Строка называет расчёт** — EN/DE/ES/FR:
  - «57 to publish = 59 available − buffer 2»;
  - с потолком: «5 to publish = 21 available − buffer 7, capped at the maximum published 5»;
  - ниже порога: «0 to publish = 9 available − buffer 7 = 2, below the minimum to list 3».
- **Подпись поля буфера:** значение формы относится к аккаунту, который включают кнопкой ниже; буфер в силе показан в каждой строке.

## Красное сначала

- Модель экрана (`connections.test.ts`, «step 138») на прежнем коде — «57 to publish» без расчёта.
- PostgreSQL (`stock.pg.test.ts`): строка несёт буфер 7, потолок 5 и порог 3 — до шага поля не было.
