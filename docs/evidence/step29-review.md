# Ревью шага 29

Дата: 2026-09-19. Ветка `step29`, изменения не закоммичены (`git diff HEAD`).
Проверенная редакция `apps/console/test/console-live.pg.test.ts` — SHA-256 `8b45639…493d32` (файл правился по ходу ревью:
первая прочитанная редакция прятала утверждения под `if (batch.status === 200)`, в проверенной редакции этого уже нет).

**Что запускалось:** `npm test -w packages/cost-import` (10 из 10), `npm test -w packages/console-model` (9 из 9),
`npm run typecheck` (все рабочие пространства зелёные), точечная проверка `pageOf` / `parseListQuery` / размеров тела запроса
отдельным скриптом на чистых функциях.

`docs/evidence/step29-console-live.md` мной не перепроверено** — выводы о нём сделаны чтением кода прогона и посева.

## Как воспроизвести

**Находка 1 (тело запроса мимо предела).** Предел живёт только в `main()`:

```
$ grep -rn "bodyLimitFor\|MAX_BODY_BYTES" apps packages tests services scripts | grep -v node_modules

apps/console/server/stand-server.ts:621:const bodyLimitFor = ...
apps/console/server/stand-server.ts:667:    const limit = bodyLimitFor(req.url ?? '');
```

Ни одного вызова из тестов. Размер тела, которое прогон считает успешным:

```js
const ids = Array.from({length: 10000}, () => '11111111-2222-4333-8444-555555555555');
Buffer.byteLength(JSON.stringify({request:{writeScopeIds: ids, min:{kind:'PERCENT',bp:500}}}))
// 390065  против  MAX_BODY_BYTES = 65536
```

Уже 2000 идентификаторов (78 065 байт) не проходят. Проверка была бы честной, если бы прогон поднимал `createServer`
(или выносил обвязку `createServer` из `main()` в экспортируемую функцию) и ходил в неё настоящим `fetch`.

**Находка 3 (листание назначает невидимое).** Открыть экран стратегий на каталоге больше 50 предложений → нажать «дальше» →
список сменился, галочки нарисованы по новой странице → нажать «предпросмотр». В теле запроса уедут `writeScopeIds` первой
страницы: `selected` инициализирован `assignable` первого рендера (`Strategies.tsx:115, 120`) и не пересчитывается, потому что
`StrategiesScreenView` не получает `key` (`:269`). На экране комплаенса такой `key` есть (`Compliance.tsx:174`) — значит форма
проблемы автору знакома.

**Находка 8 (пол по «большей» оценке).** На одной области записи завести две действующие оценки:
`FEE_SCHEDULE {feeRateBp: 0, fixedFeeMinor: 500}` и `SELLER_DECLARED {feeRateBp: 1000, fixedFeeMinor: 0}`, затем
`SELECT * FROM tenant_data.effective_price_floor(:t, :ws)`. Будет выбрана вторая (ставка выше), хотя на цене 10,00 € она даёт
комиссию 1,00 € против 5,00 € у первой, то есть пол ниже. Существующий тест Р-138 сравнивает 1500bp/0 и 500bp/0 — случай, в
котором порядок по ставке и порядок по величине комиссии совпадают, поэтому дефект не виден. Проверка станет содержательной,
если одна из двух оценок будет «низкая ставка + большая фиксированная часть».
