## Что ревьюер проверил и нашёл верным

- **Риск 22 закрыт по-настоящему:** `insertNotification` — первый вызов в транзакции `commitEvaluation`, на конфликте
  откат с `DUPLICATE_NOTIFICATION`; уникальность `(tenant_id, channel, notification_id)` есть в 0083. Правило «один
  процесс на очередь» для рабочего пути действительно перестало быть несущим.
- **Риски 29 и 31 закрыты по коду** — с оговорками, которые шаг называет сам: живым сервисом отметка не проверена.
- **Задача A не выдаётся за сделанную:** формулировка «проверено, что процесс ОТПРАВЛЯЕТ отметку, а не что её отсутствие
  кем-то замечается» признана точной.
- **Порядок развилки верен:** `windowRefused` проверяется до `secondFactorRefused`, хотя обе маски ловят 42501; ранние
  возвраты `MFA_REQUIRED` без обращения к базе новый флаг не ломают.
- **`jobOf` ничего не сломал:** просмотрены все восемь мест вызова, ни одно не ожидает отсутствия работы; три из них
  раньше зеленели на заглушке.
- **Чистка логов — только пути:** численно сверено на `step18-mutation-after.log` (231 строка, все различия путевые).
- **Проxy не путает метки** при `await` внутри тела и сбрасывает их в `finally`; мета-тест выполняется последним.

## Оставлено сознательно

**История git сохраняет прежние пути**, и на публичном GitHub они видны в просмотре коммита. Вычистить их можно только
перезаписью всех 101 коммита — это меняет SHA всех веток и требует отдельного решения владельца. Секретов там нет
(проверено перед переводом репозитория в публичные), поэтому шаг 33 на перезапись не пошёл, но сказал об этом прямо в
тексте Р-148.

**Утверждения через `strictAssert` не считаются** мета-проверками (это `jobOf`). Сейчас блоков, у которых единственная
проверка внутри `jobOf`, нет; на будущее это ловушка, и она названа.
