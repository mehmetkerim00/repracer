# Шаг 40: панель оператора платформы — живой прогон через HTTP

Прогон: `apps/operator/test/operator-live.pg.test.ts` (`npm test -w apps/operator`). Поднимается ТОТ ЖЕ процесс,
который поднимает промышленный профиль (`startOperatorPanel`), и прогон ходит по нему по HTTP как браузер [Р-136, Р-142].
Под панелью работает демо-мир на симуляторе Kaufland [Р-151] — 200 предложений, три конкурента у каждого; данные
синтетические. Все числа ниже — из вывода прогона, а не пересказ.

## Что поднято

| Часть | Как |
|---|---|
| Процесс панели | `apps/operator/server/operator-service.ts`, порт выдаёт система (`REPRACER_OPERATOR_PORT=0`) |
| Роль подключения | `svc_operator` (член `repracer_operator`) — прав на таблицы нет ни одного |
| Вход | токен издателя стенда; в работе — поставщик identity по JWKS, ключ стенда в работе не принимается вовсе |
| Почта | перехватчик `FakeMail`: письмо приглашения ЧИТАЕТСЯ прогоном |
| Мир под панелью | демо-мир, 2 виртуальных часа, время настоящее |

## Семь экранов чтения [Р-168]

Предел ответа экрана — 10 с (шаг 29). Строки — то, что реально лежит в базе демо-мира на момент обхода.

| Экран | Строк | Секунд |
|---|---|---|
| tenants | 1 | 0,009 |
| jobs | 8 | 0,004 |
| alerts | 0 | 0,003 |
| write-queue | 1 | 0,278 |
| notifications | 0 | 0,005 |
| snapshot-skips | 0 | 0,003 |
| actions | 0 | 0,014 |

Экран очереди диспетчера — единственный, чей объём растёт со ВСЕМИ тенантами платформы, и здесь он измерен на демо-мире
в 200 предложений (находка 5 ревью шага 40). После ревью его запрос разделён на две ветки ровно по предикатам
существующих частичных индексов очереди (`PENDING` и «в полёте»): с тройкой статусов в одном условии частичный индекс
неприменим, и запрос шёл полным проходом. Замера на каталоге целевого клиента у него нет — это названо в отчёте шага.

Пустые экраны — это ответ, а не ошибка: за два виртуальных часа демо-мира ни одного алерта не поднято, уведомлений
Amazon в нём нет вовсе (канал — Kaufland), пропусков выгрузки не случилось. Непустые утверждаются числами: у демо-тенанта
видны предложения, у работ планировщика — выполненные запуски, в очереди диспетчера — записи.

## Остановленный планировщик виден числом, а не уровнем прошлого такта

Уровень отставания `lag_level` ставит САМ планировщик в такте (0094). У остановленного процесса он остаётся тем, каким
был, — и экран, показывающий только его, скажет «всё в порядке» ровно в том случае, ради которого панель и нужна.
Поэтому `platform.operator_jobs()` считает просрочку по часам БАЗЫ при каждом запросе:

```
работа snapshot-export-check: overdue_seconds = 300, lag_level = OK   (планировщик остановлен)
через 3 секунды:              overdue_seconds = 303
```

Самая просроченная работа стоит первой — оператор видит её, не листая.

## Путь «завести пилота» [Р-167] — по шагам и секундам

| Шаг | Запрос | Ответ | Секунд |
|---|---|---|---|
| открыть панель | `GET /` | 200 | 0,028 |
| кто я | `GET /api/operator/session` | 200 | 0,008 |
| создать тенанта пилота (язык `en`) | `POST /api/operator/tenants` | 201 | 0,009 |
| пригласить владельца | `POST /api/operator/tenants/{id}/invite` | 201 | 0,004 |
| письмо перехвачено, ссылка и отпечаток сверены | — | — | — |
| владелец принял приглашение (у поставщика) | `security.accept_identity_invitation` | 200 | 0,005 |
| пригласить его же второй раз | `POST /api/operator/tenants/{id}/invite` | **403** | 0,006 |
| журнал действий оператора | `GET /api/operator/actions` | 200 | 0,002 |

Весь путь от пустого места до владельца с привязанным входом — **меньше 0,1 с** запросов панели; ожидание человека в
нём — только заполнение формы и чтение письма. Проверено буквально:

- письмо адресовано владельцу, тема на АНГЛИЙСКОМ — это язык, который оператор назвал при создании пилота [Р-161];
  немецкого умолчания в теме нет, и это утверждается отдельно (до ревью язык тенанта не задавался вовсе, и утверждение
  прошло бы у кода, читающего константу, — находка 6);
- второе приглашение тому же владельцу отклонено: вход уже привязан, а это перепривязка, дело владельца тенанта [Р-98]
  (находка 7);
- в базе лежит ОТПЕЧАТОК токена из письма, а не токен;
- после приёма у владельца активное членство с привязкой `(издатель, субъект)`;
- `tenant_data.onboarding_status` отдаёт шаги пилота, и незавершённые среди них есть: дальше продавец идёт сам [Р-149].

## Две оставшиеся операции [Р-166]

```
POST /api/operator/alerts/{id}/acknowledge          → 200
POST /api/operator/alerts/{id}/acknowledge (второй) → 409  «is unknown or already acknowledged»
POST /api/operator/snapshot-skips/{id}/resolve      → 200  разбор и заметка видны на экране пропусков
```

Оба действия попали в `audit_event` с идентификатором учётной записи оператора (OQ-191 закрыт).

## Чего панель не может

| Попытка | Ответ | Кто отказал |
|---|---|---|
| запрос без токена | 401 | панель |
| настоящий вход без учётной записи оператора | 403 `NOT_AN_OPERATOR` | база (`resolve_platform_operator`) |
| действие входом без второго фактора | 403 «needs a second factor» | база (`security.operator_acting`) |
| `POST /api/operator/price-stops` | 404 | маршрута нет |
| `POST /api/operator/bounds` | 404 | маршрута нет |
| `POST /api/operator/strategies` | 404 | маршрута нет |

Страница панели умеет все четыре действия формами (после ревью — находка 3: до него действия существовали только как
адреса, и человек мог выполнить их лишь `curl`). Прогон утверждает это по САМОЙ странице: в ней есть путь каждого
действия и `method: 'POST'`.

После отказа по второму фактору тенанта в базе нет — отказ это отказ, а не предупреждение.

Права проверяются отдельно, в `tests/db/smoke_operator.sql`: себестоимость, границы, решения о цене, таблица тенантов и
остановка цен отвечают роли панели `permission denied for table …`. Мутационная проверка возвращает каждое из этих прав
по одному и требует падения именно этой строки смоука (`STEP40_ROWS`).
