# Шаг 43: ревью — 21 находка (4 критичные, 9 существенных, 8 мелких)

Ревьюер работал только на чтение, со своей базой, которую удалил. По правилу скорости исправлены критичные и
существенные; мелкие вынесены ниже для следующего шага.

## Критичные — 4, исправлены все

1. **Консоль могла прочитать и расшифровать токены всех тенантов.** `security.grant_retention` выдаёт роли удаления по
   сроку SELECT на все столбцы, а в ней состоят планировщик и пул консоли; у консоли есть кольцо ключей. Утверждение
   Р-177 «читает одна роль» было ложным, и смоук этого не видел — он проверял три роли поимённо. **Исправлено (0132):**
   роли удаления — SELECT только по столбцам ключа; проверка смоука — «ни один вход, кроме роли адаптеров, не читает
   шифротекст» перебором ВСЕХ ролей входа с учётом членства; мутация «выдать роли удаления SELECT» ловится ею.
2. **Аккаунт, подключённый по OAuth, в бою не писал:** диспетчер (`services/pricing-worker`) читал только файлы, ссылка
   `db:` давала `CREDENTIALS_UNREADABLE` на каждую отправку. Живой прогон подменял адаптер моделью с пустыми учётными
   данными — «зелено в прогоне, сломано в работе». **Исправлено:** общий поставщик `channelCredentialsProvider`
   (service-runtime) в диспетчере и планировщике — файлы, токены из базы ролью адаптеров, ключи приложения; живой прогон
   получает токен ТЕМ ЖЕ путём, что адаптер.
3. **Недельный дайджест покрывал начало недели, а неотправленное письмо терялось.** **Исправлено:** период — целая ISO-неделя
   (по умолчанию прошлая, закрытая) с верхней границей во всех счётчиках; работа ежедневная — недоставленное письмо
   повторяется каждые сутки до конца следующей недели, доставленное второй раз не уходит (уникальность периода). Письмо
   прямо говорит, что экран считает скользящие семь дней и числа расходятся.
4. **Ссылка `db:` разрешалась мимо проверенного аккаунта:** строка аккаунта тенанта A со ссылкой на аккаунт тенанта B
   дала бы адаптеру A токен продавца B. **Исправлено:** ограничение `channel_account_db_credentials_own` (ссылка `db:` —
   только на свой аккаунт) со своей проверкой и мутацией; поставщик ищет владельца по аккаунту И его собственной ссылке.

## Существенные — 9, исправлены все

5. `selling_partner_id` приходит от браузера и каналом не проверен: чужой ID занимал продавца платформы (500), а внутри
   тенанта ADMIN без второго фактора перепривязывал боевой аккаунт. **Исправлено:** конфликт уникальности — названный
   исход `SELLER_TAKEN` (409), перепривязка существующего аккаунта — только со вторым фактором. Проверка ID каналом —
   вопрос A-19.
6. eBay: `pending-identity` уникален на запрос, «Connect again» создавал второй аккаунт того же продавца. **Исправлено:**
   второй аккаунт eBay в тенанте не начинается (`IDENTITY_UNKNOWN`), кнопки повторного подключения у eBay нет, аккаунт
   без названного продавца в бой не переводится (`channel_account_pending_identity_not_live`, проверка и мутация).
7. Массовый `invalid_grant` по нашей вине отозвал бы всех продавцов с письмами. **Исправлено:** отзыв записывается после
   прохода; три и больше отзывов и больше половины проверенных — `SUSPICIOUS_MASS_INVALID_GRANT`, аккаунты не тронуты,
   CRITICAL `CHANNEL_REVOCATIONS_SUSPICIOUS` оператору; текст письма смягчён до «вероятно, авторизацию отозвали».
8. «We have been notified» при провале обмена — ложь. **Исправлено:** текст говорит «это на нашей стороне, попробуйте позже».
9. Код обменивался до захвата запроса; параллельный провал перетирал успех. **Исправлено:** `exchange_started_at` —
   захват одним оператором до обращения к каналу; повторный захват и захват после срока отклоняет база (проверки и
   мутации); эффект страницы возврата защищён от двойного запуска строгого режима React.
10. Код согласия и `state` в журнале Caddy. **Исправлено:** фильтр журнала маскирует `spapi_oauth_code`, `code`, `state`.
    Проверяется подъёмом профиля production в полном прогоне CI (локально образ Caddy недоступен).
11. Страж срока запроса — перезапись `requested_at` — без своей проверки. **Исправлено:** «запрос из будущего» отклоняется
    ограничением срока, мутация снимает перезапись. Сбросы полей в триггере токена удалены как дубли прав по столбцам.
12. Путь решения мог вставлять удержания пола и подделывать сумму «деньгами». **Исправлено:** триггер — SECURITY DEFINER
    узкой роли `repracer_floor_hold`; у пути решения и консоли права вставки нет (проверка и мутация).
13. Два источника ключей приложения Amazon. **Исправлено:** при настроенном приложении адаптер получает ключи из той же
    конфигурации по своей ссылке; файл по ссылке — только запасной путь.

Попутно: находка 19 (провайдер выбирался по виду параметров возврата) закрыта вместе с №9 — канал берётся из захваченного
запроса.

## Мелкие — 8, вынесены в шаг 44

    боевого приложения; настройки дублируются в двух env-файлах.
15. Ошибка кольца ключей выдаётся за отказ ключей приложения и повторяется каждый час.
16. Постоянно падающие проверки стоят первыми в `ORDER BY verified_at NULLS FIRST LIMIT 500` и могут вытеснить остальные;
    `fetch` без тайм-аута держит аренду.
17. Живой запрос согласия нельзя отменить — продавец ждёт до десяти минут.
18. Экран: провал показывается сутки даже после более нового успеха; состояние канала — по первому аккаунту; у отозванного
    — «доступ подтверждён тогда-то».
20. Смоук «аудит без токена» утверждает только наличие события; журнал прогона — собственный журнал теста, а поиск по
    дампу не видит токен, попавший в bytea другой таблицы.
21. Вытесненные токены хранятся до закрытия тенанта; перевод в REVOKED не в аудите; роль адаптеров может поставить любой
    `auth_status` и вставить любой алерт напрямую — сузить до EXECUTE функции.
