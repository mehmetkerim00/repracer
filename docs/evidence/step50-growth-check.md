# Шаг 50: требования eBay Application Growth Check и наше положение (задача D шага 49)

Источник — раздел «Request an application growth check» руководства «Get started with eBay APIs»
(`vendor/ebay/2026-09-28/get-started-with-ebay-apis.html`, сохранён владельцем 2026-09-28).

## Зачем нужна проверка

«Requesting an application growth check is required if you want to: Increase the API call limits for your application; Use
restricted APIs in production».

- Суточных квот по умолчанию (Inventory 2 млн, Trading 5 000) нам на пилот хватит.
- Без проверки нельзя расти по числу продавцов: у Trading 5 000 вызовов в сутки на приложение, общие для всех тенантов.
- Нельзя и использовать restricted API в бою. Какие из наших API к ним относятся, снимок не говорит — (проверить).

## Требования и наше положение

| Требование | Как у нас | Что сделать |
|---|---|---|
| Рабочее приложение, которое eBay может проверить | Боевого развёртывания нет (шаг 38, ч. 2: сервер) | Сервер и боевой ключ; приёмник Account Deletion зарегистрирован [Р-192] |
| Лицензия API: не собирать статистику о пользователях и группах пользователей eBay, о самом eBay; не выводить средние цены и GMV категорий; не выводить конверсии и темпы продаж, кроме данных вошедшего пользователя и только для него; не показывать резервные цены чужих аукционов и чужие профили | Логики и отчётов, объединяющих тенантов, нет по правилу репозитория; конкурентов на eBay не читаем вовсе [Р-39]; отчёты — только по своим предложениям продавца | Ничего; сослаться на правило в анкете |
| eBay site policies, User Agreement, User Privacy Notice, законы о защите потребителей и данных | Данные покупателей не храним (белый список EBAY_C17, Р-4); удаление по Marketplace Account Deletion [Р-192] | — |
| OWASP secure coding, «Top Ten» | **Самопроверка по OWASP Top 10 (2021), шаг 52** — [step52-owasp.md](step52-owasp.md). По категориям: 4 соответствуют, 5 частично, 1 слабое место (A06). Мелкие слабые места исправлены в шаге 52: аудит зависимостей в CI (`npm audit --audit-level=high`) и Dependabot, заголовки безопасности консоли и HSTS у прокси, `permissions: contents: read` в CI | Крупные — в план: внешняя отметка и почта (после аккаунтов), настоящий ZITADEL, шифрование резервной копии, изоляция панели оператора, ограничение частоты, хранение журналов 12 месяцев. Документ — приложение к анкете |
| Кодировка UTF-8 | JSON REST; тела Trading — `<?xml version="1.0" encoding="utf-8"?>` | — |
| Последние версии API; версию каждого API назвать в анкете | **Соответствуем (шаг 53), живьём проверить в следующей сессии песочницы.** Inventory 1.18.5, Account 1.9.3, Identity 2.0.0 — совпадают с опубликованными контрактами. **Trading — уровень совместимости поднят 1349 → 1477** (текущий, 2026-08-24), изменения для наших вызовов разобраны по заметкам к выпускам ([step53-ebay-trading.md](step53-ebay-trading.md)); модель стенда и сценарии идут с 1477. Устаревших вызовов (`GeteBayDetails`, `UploadSiteHostedPictures`, Finding, Shopping, VeRO) не зовём | В анкете: Trading 1477, Inventory 1.18.5, Account 1.9.3, Identity 2.0.0, Fulfillment v1, Browse v1 (в бою не вызывается [Р-190]) |
| «Handles errors gracefully and implements retries correctly … retries for a maximum of two times for infrastructure errors» | **Соответствуем (шаг 51).** Чтения адаптера eBay — не больше двух повторов (`DEFAULT_READ_RETRY.maxAttempts = 3`, только 429 и обрыв у идемпотентных запросов). Записи — правило канала `EBAY_DESCRIPTOR.writeRetry` ([packages/ebay-adapter/src/descriptor.ts](../../packages/ebay-adapter/src/descriptor.ts)): не больше трёх попыток одной версии (два повтора) и только после сбоя инфраструктуры — 5xx или недоступный сервер токенов (`CHANNEL_UNAVAILABLE`), таймаут, обрыв соединения. Ответ eBay 4xx на значение не повторяется никогда, включая 429. Повторяется отказ нашего клиентского бюджета или режима пакетов до отправки: в eBay запроса не было. Ядро применяет правило в диспетчере и во встроенной отправке пути решения (`retryPolicyFor`, [packages/write-dispatcher/src/transitions.ts](../../packages/write-dispatcher/src/transitions.ts)). Тесты: [tests/contract/src/ebay-write-retry.test.ts](../../tests/contract/src/ebay-write-retry.test.ts) — правило из описания адаптера; `dispatcher.test.ts` «step 51» — диспетчер берёт правило адаптера аккаунта (падает, если вернуть общую политику); `simulator-ebay.test.ts` «Р-189 end to end» — отказанная проба не повторяется, следующие записи уходят по одной. Неизвестный итог (запрос мог дойти) не повторяется вслепую: сначала сверка обратным чтением, повтор после неё — тоже попытка из трёх. Отказ формы пакета EBAY_C18 (400, значение не оценено) переотправляется по одному SKU в пределах тех же трёх попыток. После 401 вызов повторяется с новым токеном — это второй POST той же записи, один на попытку, и он считается в бюджет правок (ревью шага 39, находка 14). Худший случай — 6 POST на версию, если каждая из трёх попыток получит 401. Чтения повторяют 429 и обрыв не больше двух раз (ревью шага 51) | В анкете назвать честно: 2 повтора после сбоя инфраструктуры; 4xx на значение не повторяется; 401 — один повтор с новым токеном; отказ формы пакета — переотправка по одному SKU |
| Повтор после отказа формы пакета (Р-189, EBAY_C18) — не повтор в смысле проверки | Решение владельца, шаг 52: переотправка отвергнутого по форме пакета одиночными вызовами — смена формы запроса, а не повтор. Значение eBay не оценивал (400 без ответов по элементам и без кодов значений). Происходит один раз на аккаунт — при первой боевой пробе пакета из 2 SKU; дальше аккаунт пишет по одному SKU. Худший случай по записи — до 6 запросов на версию (3 попытки × повтор с новым токеном после 401) — описан в строке выше и остаётся как есть | Формулировка для анкеты: «a batch rejected for request shape is split and re-submitted once as single-SKU calls, within the same overall attempt budget» |
| Ошибки с полезными подробностями для людей и приложений | Коды причин и тексты DE/EN [Р-72], алерты с первым действием [Р-156] | — |
| Не запрашивать больше данных и не звать чаще нужного; eBay может ограничить частоту опроса | Конкурентов на eBay не опрашиваем; пересчёт по расписанию — единица без решения за сутки [шаг 47]; ключи и токены кэшируются | Оценить пиковые объёмы (ниже) |
| Не собирать логины и пароли eBay — только токены пользователя | OAuth, согласие продавца [Р-175]; паролей нет | — |
| Не ломаться, если eBay изменит число элементов на странице | **Соответствуем (шаг 52).** Страницы limit/offset: следующее смещение — из `next` или по числу пришедших записей, а не `offset + limit`; прежний расчёт перепрыгивал записи при странице короче запрошенной (`nextOffsetOf`, [packages/ebay-adapter/src/listing.ts](../../packages/ebay-adapter/src/listing.ts)). Пустая страница без `next` — конец; тот же курсор второй раз — ошибка обхода, а не вечный цикл (обнаружение и чтение заказов). Модель стенда урезает страницу (`pageSizeCap`); тесты — обнаружение и заказы eBay и Amazon | — |
| Не показывать страницы eBay во iFrame; полный адрес во встроенном браузере; поиск — только через Buy/Finding API | Страниц eBay не встраиваем, поиска нет | — |

## Анкета

eBay просит заранее подготовить ответы, «including your estimated call peak, both hourly and daily volume, for each of the API
calls in your application». С шага 54 они есть РАСЧЁТОМ ([step54-peak-volumes.md](step54-peak-volumes.md)): вызовы по операциям в
пиковую минуту, в час и в сутки на продавца трёх профилей; ответ анкеты — эти числа, умноженные на ожидаемое число продавцов. Замер
пилота заменит допущения измерением. Затем — вкладка «App Growth Check» в MyAccount; перед этим нужно
включить developer account support.
