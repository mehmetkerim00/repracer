# Шаг 66: план очереди записей, экраны без полного каталога, объявление множеством

## 1. OQ-247: что держит план очереди

**Ловушка.** Очередь `tenant_data.channel_write` в работе то и дело пустеет. Статистика, снятая в этот момент, — «0 строк на N страниц».
Её оставляют:
- автоанализ, заставший опустевшую очередь;
- очистка, которой не дали обрезать файл: живая строка в конце, занятая блокировка.

Тогда каждый путь к таблице стоит одну строку. На воспроизведении стоимость была 4,13 у всех путей — индексов с `tenant_id` и частичных
индексов ждущих. Выбор решают мелочи: при удалённом индексе идемпотентности поиск записи по полному первичному ключу ушёл на индекс
единицы с условием только по тенанту.

**Воспроизведение.** База из шаблона. В очередь вставлено 20 000 строк тенанта без стражей (режим репликации) и удалено, затем очистка
или анализ. Затем в транзакции — всплеск в 5 000 строк и планы запросов от имени роли (общий план).

| Состояние | Поиск прежних версий | Ждущая запись | Запись по ключу |
|---|---|---|---|
| Таблица ни разу не анализирована | индекс единицы | индекс единицы | первичный ключ |
| Автоанализ застал пустой | **индекс идемпотентности** (тенант) | **частичный индекс всех ждущих** | **индекс идемпотентности** |
| Очистка обрезала до нуля страниц | индекс единицы | индекс единицы | первичный ключ |
| (а) `vacuum_truncate = off`, очистка | **тенант** | **все ждущие** | **тенант** |
| (а)+(б) анализ «большой», затем очистка пустой | **тенант** | **все ждущие** | **тенант** |
| Очистке не дали обрезать (живая строка в конце) | **тенант** | **все ждущие** | **тенант** |

Варианты из задания и то, что показало воспроизведение:

| Вариант | Итог |
|---|---|
| (а) `vacuum_truncate = off` | **Хуже.** Очистка оставляет «0 строк на 385 страниц» — ровно ловушку. Спасает как раз обрезка до нуля страниц: у такой таблицы планировщик оценивает строки по текущему размеру файла |
| (б) анализ только обслуживающим заданием при большой очереди | **Не держит.** Очистка после опустения всё равно пишет «живых строк ноль» |
| (в) барьеры `MATERIALIZED`, `OFFSET 0` | **Не держат.** Выбор индекса внутри барьера тот же — индекс идемпотентности и частичный индекс ждущих |
| (в) порядок, который даёт только индекс единицы (`ORDER BY version`) | **Держит не всегда.** При одних состояниях — индекс единицы, при других — битовая карта по индексу тенанта с сортировкой: она дешевле |
| перестановка столбцов уникальных ключей | **Не держит.** PostgreSQL берёт индекс и по неведущему столбцу |
| (г) партиции очереди с ротацией | **Не понадобились** |
| **ANALYZE внутри большой транзакции** | **Держит.** Транзакция считает свои незафиксированные строки живыми (`reltuples = 5000`), и все три поиска уходят на индекс единицы и первичный ключ. ANALYZE — 44–98 мс |

**Почему держит именно он.** При «пустой» статистике ничья путей полная: стоимость 4,13 у всех. Никакая форма запроса не даёт
индексу единицы преимущества, которое переживёт мелочи вроде высоты деревьев. Преимущество появляется только из правды о числе строк. В
большой транзакции эта правда — её собственные строки, а ANALYZE внутри транзакции их видит.

**Решение (Р-203, 0171, ADR-0048).**
- Строчный триггер `aa_channel_write_queue_stats` на сотой записи транзакции делает ANALYZE очереди:
  - счёт — в настройке транзакции, помеченной её номером (счётчик PostgreSQL несёт вставки прежних транзакций сеанса до 10 с);
  - функция — от владельца очереди, права исполнения ни у кого;
  - блокировку ждать 2 с — дольше `deadlock_timeout`: автоочистку, держащую её, база снимает ради ждущего только через `deadlock_timeout`
    (при 100 мс первый замер 50 000 проиграл автоанализу — боевой пересчёт 767 с); занято дольше — повтор на вдвое большем числе записей.
- Автоанализ оставлен. Выключенный, он замораживал статистику столбцов (ревью, находка 5).
- Пересчёт остатков считает источник вставки целиком до первой строки (`ORDER BY` в `INSERT … SELECT`). Иначе подзапросы цели по
  очереди шли вперемешку со вставкой этого же оператора, и обновление статистики после первой сотни строк его плану уже не помогало.
- Отдельно (не OQ-247, но в том же замере): запрос импорта, сопоставляющий ключи файла с товарами, — хеш-соединение при любой
  статистике. Вложенный цикл по только что загруженным таблицам шёл 246 с на 50 000.

**Тесты ловушки.**
- [write-queue-stats.pg.test.ts](../../packages/pricing-store-pg/test/write-queue-stats.pg.test.ts) портит статистику и проводит
  настоящий пересчёт через настоящие триггеры. Утверждает:
  - большая транзакция проанализировала очередь;
  - поиск идёт индексом единицы;
  - транзакция меньше порога не анализирует;
  - занятая блокировка — транзакция ждёт не дольше 2 с на попытку и не падает, следующая анализирует;
  - маленькая транзакция сразу после большой в том же пуле не анализирует (счёт — по транзакции).

  Строка каталога мутаций «шаг 66 (Р-203)»: снятый триггер ловится своей проверкой.
- Замер масштаба портит статистику («0 строк на N страниц») перед каждой операцией — пределы те же. Таблица ниже.

## 2. OQ-248: экраны без полного каталога

| Экран | До шага 66 | После |
|---|---|---|
| Товары, индекс границ | состояние каталога целиком (50 000 — 41,5 МБ, 6,4 с на запрос), страница в памяти | страница и итоги по всему каталогу — базой (`consoleCatalogPage`), мир только из единиц страницы |
| Остатки, тень | состояние каталога целиком до разбора экрана (не нужно им вовсе) | мир без каталога |
| Онбординг | без мира (с шага 34) | без изменений |
| Стратегии, поиск предложения, комплаенс, остановка, карточка границ, решения | состояние каталога целиком | без изменений — остаток OQ-248 |

- **Равенство итогов** (SQL против `enabledCell` и `applyingCell` экрана) держит
  [console-catalog-page.pg.test.ts](../../apps/console/test/console-catalog-page.pg.test.ts):
  - все 26 миров стенда на PostgreSQL;
  - страницы в середине, на конце и за концом каталога;
  - экран из страницы равен экрану из всего каталога;
  - каждое состояние встретилось хотя бы раз: включено, остановлено, выключено, применяется — в том числе запись, ждущая повтора, и
    заблокированная.
- **Предел ответа экрана** — 2 МиБ (`SCREEN_RESPONSE_MAX_BYTES`). Экран мира больше предела отвечает 500 `RESPONSE_TOO_LARGE`, журнал
  называет маршрут и размер. Ответ записи и Inbound API под предел не попадает: он приходит после фиксации. Тест — через настоящий
  HTTP-слой.

## 3. «Уже объявлено в транзакции» — множество

Отложенный триггер объявления диспетчеру хранил «уже объявлено» одной строкой. Каждая запись искала себя в ней и дописывала её копией.
Теперь это 1024 корзины по хешу единицы. Замер — тот же цикл, что у триггера:

| Записей в транзакции | Строка (шаг 65) | Множество |
|---|---|---|
| 10 000 | 1,9 с | 0,13 с |
| 20 000 | 8,6 с | 0,05 с |
| 50 000 | ~55 с (оценка) | 0,16 с |

## 4. Масштаб 10 000 → 50 000 при испорченной статистике

Замер — [scale.pg.test.ts](../../tests/contract/src/scale.pg.test.ts), локально, по одному прогону на размер. **Перед каждой операцией
замер портит статистику очереди:** вставляет в очередь столько строк, сколько предложений, удаляет их и чистит без обрезки файла.
Столбец «очередь» — что статистика говорила планировщику в начале операции.
- Пока очередь пуста, это ровно ловушка: «0 строк на N страниц».
- Когда в очереди живые записи (после боевого пересчёта — десятки тысяч ждущих), очистка записывает их число. Ловушки тогда нет: её
  порождает только опустевшая очередь.

**Что показывает таблица.**
- Все операции в своих пределах при испорченной статистике. Операции записи, ради которых OQ-247 был открыт, идут быстрее, чем шаг 65
  мерил при ПРАВИЛЬНОМ плане. Пересчёт «изменилось всё» на 50 000 — 16,1 с против 46,4: шаг 65 считал его ×12 на ×5 каталога, теперь
  ×5,6. Импорт — 19,1 с против 40,9; на CI шага 65 он шёл 79,7 с, и задание `scale` было красным.
- Экран товаров на 50 000 — 0,7 с и 50 КБ на любой странице против 3,6 с и 41,5 МБ состояния, собиравшегося на каждый запрос.
- Посев 50 000 — 426 с против 952: включение синхронизации и пересчёт посева — те же большие транзакции очереди.
- **Круг обнаружения на 50 000 стал медленнее: 148 и 102 с против 78 и 71.** В пределе 600 с, причина не разобрана. В шаге 66 круг
  идёт после боевого пересчёта, и в очереди ждут 63 тыс. записей; в шаге 65 их не было. Остальные операции после боевого пересчёта
  не замедлились. Остаётся в замере как есть.

**Первый замер 50 000 после переделки провалился** — он и нашёл, что обновление статистики проигрывает автоанализу:

| Операция | Предел, с | Первый замер | Итог |
|---|---|---|---|
| посев | — | 2574 | 426 |
| импорт | 60 | 97,67 | 19,12 |
| пересчёт, изменилось всё | 60 | 43,5 | 16,08 |
| выборка кандидатов | 60 | 9,18 | 2,67 |
| боевой пересчёт | 60 | **767** | 15,63 |
| круг обнаружения, первый и следующий | 600 | 71,95 и 100,39 | 147,86 и 101,87 |

- Всплеск записей будит автоанализ очереди, и тот держит ту же блокировку, что нужна ANALYZE транзакции. Ждущему сеансу база
  снимает автоочистку только через `deadlock_timeout` (1 с), а функция ждала 100 мс.
- Многострочная вставка делала ОДНУ попытку: счётчик PostgreSQL внутри оператора не растёт.
- Прямой замер на сохранённой базе того прогона, без новой порчи: импорт 22,6 с, боевой пересчёт 23,5 и 27,1 с. Время ANALYZE
  транзакции сдвинулось — обновление работает, когда ему не мешают.
- Исправление (0171): ждать 2 с; ожидание, выбранное жертвой взаимоблокировки, — тоже повтор; счёт записей — по транзакции, с повторами
  внутри одного оператора.

**Размеры ответов экранов** — столбец «Ответ». Самые большие:
- товары — 50 КБ на страницу при любом каталоге;
- остатки — 33 КБ;
- тень — 21 КБ.

Предел ответа экрана — 2 МиБ. Ответ больше предела — 500 `RESPONSE_TOO_LARGE`. Состояние каталога целиком (41,5 МБ на 50 000) экраном
больше не отдаётся. Его собирает сервер для экранов из остатка OQ-248: стратегии, поиск предложения, комплаенс, остановка, карточка
границ, решения. Их ответы — страницы, но сборка — весь каталог.
