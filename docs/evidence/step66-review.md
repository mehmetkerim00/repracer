# Ревью шага 66 — план очереди записей, экраны без полного каталога, объявление множеством

Ревьюер читал изменения шага, запускал проверку типов, юнит-тесты без базы и правила репозитория. Найдено **13 находок: 3 критичные,
4 существенные, 6 мелких**. По правилу скорости критичные и существенные исправлены в шаге. Из мелких исправлено то, что стоило
минуты; остальное — в отложенный список.

Ревьюер проверил и дефектов не нашёл:
- **0171:**
  - порядок триггеров по имени (`aa_` < `c_` < `ea_`, отложенный `zz_` — при фиксации);
  - AFTER ROW после всей многострочной вставки;
  - `set_config(…, true)` внутри SECURITY DEFINER переживает выход из функции;
  - откат к точке сохранения откатывает и счётчик;
  - блокировка из подтранзакции переходит родителю;
  - `search_path` зафиксирован, права исполнения нет ни у кого.
- **Корзины «уже объявлено»** — поведение равно прежней строке: ключ фиксированного формата `uuid:uuid,` не совпадёт через границу ключей.
- **Итоги `consoleCatalogPage`** равны `enabledCell` и `applyingCell` экрана; порядок страницы и подтягивание смещения — как у каталога.
- **Изоляция:** `$1` и политика строк; список единиц формирует сервер.
- **Маршруты записи не затронуты;** экраны, которым нужен весь каталог, получают его.

## Критичные — исправлены

1. **Заголовок проверки схемы называл чужой номер** (`0172_…` с первой строкой `0170_…`). Правило Р-146 краснело. Исправлено.
2. **Мир, проигнорировавший список единиц, превращал страницу товаров в весь каталог.**
   - Живые прогоны консоли строят мир сами, и их `view` параметр не брали. Экран товаров на 10 000 отдал бы весь каталог — больше
     предела, 500.
   - Исправление:
     - строки страницы — ровно единицы, выбранные базой, в её порядке (`catalogRows`), а не всё состояние мира;
     - все семь самодельных `view` прогонов передают список.
3. **Импорт остатков складывал строки разных ключей одного товара.**
   - Ключи товара — артикул, EAN, ссылка канала. Две строки про один товар считали дельту от одного прочитанного остатка: 5 и 7 давали
     12, а две нулевые строки при остатке 10 давали −10 и роняли весь импорт.
   - Исправление: товар — один раз, значение — последней строки (как прежде, когда строки шли по одной). Тест «два ключа одного товара».

## Существенные — исправлены

4. **ANALYZE делался ровно один раз.** Если блокировка занята — соседом или очисткой, — транзакция шла O(n²) целиком.
   - Исправление: занято — повтор на вдвое большем числе записей.
   - Тест двумя сеансами: пока блокировку держит другой сеанс, транзакция ждёт только срок попытки и не падает; после освобождения следующая
     анализирует.
5. **Выключенный автоанализ замораживал статистику столбцов** на выборке последней большой транзакции. Тенант, которого в ней не было,
   снова попадал в ничью путей, а его очередь, накопленную мелкими транзакциями, не анализировал никто.
   - Исправление: автоанализ очереди оставлен включённым (первая редакция шага его выключала).
   - Пустую очередь с мёртвыми строками он не застаёт: при большом числе мёртвых строк автоочистка сначала чистит, потом анализирует.
6. **Тест равенства страниц выбирал тенанта без порядка и глотал отказ уборки.** Соседние файлы строят миры стенда в той же базе
   параллельно.
   - Исправление:
     - тенант — только из своих миров (`identityTenantId`), с порядком;
     - уборка — в режиме репликации, без проглатывания ошибки.
7. **Предел ответа превращал «медленные» экраны и ответы записи в 500.**
   - Экран стратегий перечислял все предложения с ценообразованием канала — у мигрирующего продавца Amazon их тысячи.
   - Ответ Inbound API приходит после фиксации, и отказ сказал бы «не применено» о применённом.
   - Исправление:
     - предел — только у экранов (GET `/api/worlds/…`);
     - список стратегий — 200 и общее число;
     - тест проводки через настоящий HTTP: экран больше предела — 500, ответ записи проходит.

## Мелкие

Исправлены:
- **настройка-счётчик записей транзакции помечена номером транзакции** (находка 9). Первая редакция исправления взяла счётчик
  PostgreSQL (`pg_stat_get_xact_tuples_inserted`), и это оказалось дефектом — см. «сверх ревью». Подделка настройки даёт сеансу только
  ANALYZE в его же транзакции: держать эту блокировку роль с правом изменения очереди может и `LOCK TABLE`;
- **`enable_nestloop = off` — только для каталога целиком;** для страницы из 50 единиц хеш-соединения прошли бы все предложения тенанта
  (часть находки 8);
- **ADR и README:**
  - построчные вставки в тени;
  - корзины — квадрат делится на 1024;
  - честный охват тестов;
  - после `pg_upgrade` — `VACUUM` очереди (находки 10–13).

Отложены:
- `readConsoleState` со списком единиц по-прежнему читает весь тенант в `offerChannelPricing` и `pricingHealth`. У Amazon это строка на
  предложение. Замер масштаба — Kaufland, там их нет (часть находки 8);
- корзины «уже объявлено» — 1024 заглушки настроек живут в сеансе пула; квадрат внутри корзины заметен на сотнях тысяч записей одной
  транзакции (находка 11).
- сверх ревью, из замера: круг обнаружения на 50 000 при 63 тыс. ждущих записей в очереди — 148 и 102 с против 78 и 71 с шага 65 с
  пустой очередью. В пределе 600 с, причина не разобрана.

## Найдено сверх ревью

- **Пересчёт остатков был квадратичным внутри одного оператора.** Замер 50 000 после исправлений ревью: пересчёт шёл минуты.
  - Стек процесса базы: `INSERT … SELECT` записей пересчёта считал подзапросы цели по очереди на каждой строке ВПЕРЕМЕШКУ со вставкой.
  - При «пустой» статистике каждый подзапрос проходил индекс тенанта со всеми строками, уже вставленными этим же оператором.
  - Обновление статистики триггером этому оператору не помогает: его план выбран до первой строки.
  - Исправление: сортировка в источнике вставки забирает и считает весь источник до первой вставки.
- **Импорт остатков:** запрос, сопоставляющий ключи файла с товарами, шёл вложенным циклом по только что загруженным таблицам — 246 с
  на 50 000 (журнал медленных запросов прогона). Теперь хеш-соединение при любой статистике, как у каталога консоли (шаг 35).
- **Тест сеансов завис на себе самом:** держатель блокировки взял единственное соединение пула суперпользователя теста. У держателя
  теперь свой пул.
- **Прогоны на машине разработчика упёрлись в диск.** В кластере лежали 39 одноразовых баз упавших и снятых прогонов. Удалены, место
  освободилось с 1,6 до 6,9 ГБ; базы не проекта не тронуты.
- **Счётчик PostgreSQL «вставлено в транзакции» несёт прежние транзакции сеанса.** `pg_stat_get_xact_tuples_inserted` складывает
  текущую транзакцию с несброшенными счётчиками прежних: сеанс сбрасывает их не чаще раза в секунду и в простое — до 10 с. Маленькая
  транзакция сразу после большой в том же соединении пула делала ANALYZE и держала его блокировку до фиксации. Нашёл тест «меньше
  порога — без анализа». Счёт — снова в настройке транзакции, теперь с её номером.
- **Первый замер 50 000 при испорченной статистике провалился: обновление проигрывало автоанализу.**
  - Боевой пересчёт шёл 767 с, импорт — 98 с, обнаружение — 72 и 100 с.
  - Причина: всплеск записей будит автоанализ, а он держит ту же блокировку. Ждущему сеансу база снимает автоочистку только через
    `deadlock_timeout` (1 с), а функция ждала 100 мс. Многострочная вставка делала ОДНУ попытку: счётчик PostgreSQL внутри оператора
    не растёт.
  - На той же базе без автоочистки — пересчёт 27 с, импорт 23 с: обновление работает, когда ему не мешают.
  - Исправление: ждать 2 с; ожидание, выбранное жертвой взаимоблокировки, — тоже повтор; повторы и внутри одного оператора.
