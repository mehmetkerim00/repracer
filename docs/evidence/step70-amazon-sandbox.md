# Шаг 70: первая живая сессия песочницы Amazon SP-API

2026-10-05. Приложение repracer в Solution Provider Portal, тип Sandbox, регион NA. Учётные данные — Client ID, Client Secret и
refresh-токен со страницы **Sandbox Testing** (кнопка **Create Token**) — лежат в файле секретов вне репозитория. В репозитории их
нет, в журнал обменов они не попали: прогон вычищал их из записи и падал бы, найдя хоть один. Данные запросов синтетические: SKU
`SYN-SKU-70`, продавец `A1SYNSELLER0001`.

- Документация песочницы — снимок [vendor/amazon/sandbox/2026-10-05/SOURCE.md](../../vendor/amazon/sandbox/2026-10-05/SOURCE.md).
- Все 20 обменов с заголовками и телами ответов — [step70-amazon-sandbox-exchanges.json](step70-amazon-sandbox-exchanges.json).

Одноразовый прогон: голый клиент `createSpApiClient` и НАСТОЯЩИЙ адаптер `createAmazonAdapter`, у которого адрес региона NA заменён
адресом песочницы. Так проверяются наши заголовки и формы запросов, а не написанные руками. Скрипты прогона в репозиторий не идут: они
читают файл секретов; повторить — тем же путём с теми же вызовами, перечисленными ниже.

## Что песочница проверяет, а что нет

Песочница SP-API статическая: на запрос, совпавший с образцом из модели операции (`x-amzn-api-sandbox.static`), она отдаёт ответ
этого образца. Данных в ней нет. FBA Inventory — динамическая: ответ зависит от запроса, состояние создают операции только для
песочницы.

| Проверяет | Не проверяет |
|---|---|
| Настоящий обмен LWA: `api.amazon.com` — боевой сервер токенов, у песочницы только приложение. Коды и статусы его отказов | Данные: листинги, цены, заказы, конкурентов. Образец один и тот же для любого SKU |
| Аутентификацию SP-API: без токена и с недействительным токеном — 403 | Наши формы запросов `searchListingsItems`, `searchOrders`, `getCompetitiveSummary`: совпасть могут только параметры образца, наши — нет (400 «Could not match input arguments») |
| Маршрут: операция существует, путь верен | Тело записи: `patchListingsItem` принимает любое тело, отвечает образцом ACCEPTED и ничего не применяет. «Принято ≠ применено» [AMZ_C05] здесь не проверить |
| Соответствие витрины региону адреса (403) | Боевые лимиты: заголовок `x-amzn-RateLimit-Limit` — 5.0 у любой операции. Это лимит песочницы (5 в секунду, burst 15), а не Usage Plan операции |
| Заголовки ответа: `x-amzn-RequestId`, `x-amzn-RateLimit-Limit`, `x-amzn-ErrorType` у отказов | Уведомления `ANY_OFFER_CHANGED` и `PRICING_HEALTH` из SQS |
| Форму тела ошибки: `{"errors":[{"code","message","details"}]}` | Отзыв авторизации продавцом (A-17): токен выдан страницей Sandbox Testing, продавца и согласия нет |
| Динамический FBA Inventory: можно наполнить операциями только для песочницы (`createInventoryItem`, `addInventory`) — в этом прогоне не делалось | Кто продавец по токену (A-19): `getMarketplaceParticipations` отдаёт образец без идентификатора продавца |

Строгость заголовков песочница не показывает. Запросы без `x-amz-date` прошли. Без нашего `user-agent` тоже, но `fetch` в этом
случае подставляет свой заголовок, так что проверка без заголовка вовсе не получилась. Стенд строже: требует оба заголовка по
документации.

## Вопросы

- **A-17** (ответ LWA после отзыва): дополнен. На недействительный refresh-токен LWA отвечает `invalid_grant` и сам называет отзыв
  среди причин. Обмена после НАСТОЯЩЕГО отзыва не было — вопрос открыт.
- **A-26** (новый): что значит боевой 403 SP-API — роль, токен или путь, и всегда ли есть `details`.
- **A-27** (новый): привязан ли токен доступа к региону в бою.
- **A-28** (новый, после решения Р-205): ограничивает ли бой сводки и офферы ответа витринами запроса. Пока ответа нет, витрина вне
  запроса считается несовпадением (AMZ_C15).

Тексты — в [channel-capabilities.md §9](../channel-capabilities.md).

## Сверка ответа с запросом [Р-205]

Решение владельца после первой части шага: ответ о чужом товаре — отказ с кодом, а не тихое принятие. Ревью шага 70 сузило правило
витрин (находки 2 и 3 — [step70-review.md](step70-review.md)).

- **Код.** Новый код ошибки канала `RESPONSE_MISMATCH` в порту (`packages/channel-port`): класс «нужен человек». Тексты — в словарях
  EN и DE; действие продавца — `TELL_PLATFORM_TEAM` («скажите нам»: поддержка канала тут не поможет). Код и действие — в реестре видов
  параметров базы (0175: прежний реестр плюс значения — пять перечислений кодов записи и два перечисления действий; новых защит нет).
  Консервативное правило AMZ_C15, вопрос A-28.
- **Что сверяется.** `sku` ответа чтения и ответа на запись равен запрошенному (обязателен по модели снимка). Чужой SKU в текст ошибки
  не попадает — только вид несовпадения.
- **Чужие витрины — не отказ.** Сводки и офферы витрин вне `marketplaceIds` не используются и называются в журнале. Данные адаптер и
  так берёт по своей витрине, а отказ при «да» на A-28 (pan-EU продавец с одной витриной в аккаунте) блокировал бы и единицы количества —
  уменьшение остатка перестало бы уходить. Запасной ход `productTypeOf` к первой сводке снят: тип товара — только своей витрины.

| Где | Итог при SKU не о том |
|---|---|
| Обратное чтение и подтверждение | Отказ без наблюдения; диспетчер сразу блокирует единицу кодом RESPONSE_MISMATCH (алерт блокировки — CRITICAL) |
| Чтение перед записью | Запись не уходит (PATCH не отправляется), единица блокируется |
| Ответ на ушедшую запись | Исход неизвестен: запись могла примениться, но принятие не о ней. Алерт адаптера `AMAZON_RESPONSE_MISMATCH` (WARNING) сразу; ядро сверяет обратным чтением |
| Страница обнаружения | Предмет без `sku` и сводки чужих витрин пропускаются поштучно, с журналом; остальное страницы — в каталоге (отказ страницы целиком остановил бы обход навсегда) |
| Сводки FBA | Ответ другой витрины или о чужом SKU — ни одно количество из него не берётся (на экране остаётся прежнее значение со своим временем, Р-196); сводка без `sellerSku` — пропуск поштучно |

- **Проверено:**
  - сценарий стенда `amazon/sandbox/response-mismatch` из НАСТОЯЩИХ ответов песочницы (вид происхождения
    `RECONSTRUCTED_FROM_SANDBOX` теперь разрешён и Amazon; у Kaufland песочницы нет — для него запрет остался);
  - юнит-тесты на каждое место сверки с положительными контролями, тест перехода диспетчера;
  - 17 мутаций — пойманы своими тестами ([step70-mutation.md](step70-mutation.md)).

## Количество FBA живьём (динамическая песочница)

Журнал — [step70-amazon-sandbox-fba-exchanges.json](step70-amazon-sandbox-fba-exchanges.json), 11 обменов. SKU `SYN-FBA-70`, amazon.com.

`fulfillableQuantity`, проверка витрины и SKU ответа прошла. Прогон шёл до правок по ревью (сводка без `sellerSku` — пропуск поштучно):
в ответе песочницы `sellerSku` был у каждой сводки, итог тот же. Не проверено — уменьшение запаса: нужен виртуальный заказ в динамической
песочнице Fulfillment Outbound. Товар `SYN-FBA-70` (7 шт.) остался в песочнице приложения — удалить его, не обнулив запас, нельзя.
