# Шаг 73: лестница к полу [Р-208], переоценка после отказа по курсу [Р-209], подъём по росту себестоимости [Р-210]

Решения владельца по OQ-251…OQ-253, устройство — [ADR-0051](../adr/0051-floor-ladder-and-reevaluation-requests.md).

## Что сделано

| Где | Что |
|---|---|
| `packages/strategy-engine` | ступень лестницы: подъём к полу больше предела шага — `нынешняя + ⌊нынешняя · предел / 10 000⌋`, причина `RAISED_TOWARD_FLOOR` с `stepsLeft`; подъём без снимка конкурентов после запроса базы (`raiseAfter`) — правило `FLOOR_RAISE` |
| `packages/price-gate` | ступень ниже пола одобряется только как ступень (причина, предел шага задан, цена строго между нынешней и полом); решение несёт `ladderFromMinor` |
| `packages/pricing-model`, словари DE/EN | `RAISED_TOWARD_FLOOR` («… raised one step, as far as the step limit of 10% allows; about 4 more steps to the floor»); у `RAISED_TO_FLOOR` повод `after` — «after cost update», «after the floor was recomputed before sending (current cost, fees, exchange rate and VAT)»; «почему эта цена» показывает проверку пола у ступени непройденной |
| `packages/pricing-pipeline` | `recomputeScheduled` сначала переоценивает единицы с запросом базы и продолжает лестницы, потом — должные; запрос снимается после переоценки; зеркало в памяти — то же правило ступени и те же запросы |
| `packages/pricing-store-pg` | вставка `ladder_from_minor`; выборка запросов и продолжений лестницы; оценка комиссии для контекста — с наибольшим полом (шаг 72) |
| 0180 | `ladder_from_minor` у решения, ядра и журнала цен; CHECK `price_decision_ladder_step`; страж ступени `tenant_data.price_ladder_step_allowed` (роль `repracer_price_ladder`) в перепроверке пола перед созданием записи и перед каждой отправкой [Р-83]; таблица `tenant_data.floor_raise_request` и четыре триггера запроса (роль `repracer_floor_raise`) |
| 0180, после ревью | суточная свёртка и системная поправка закрытых суток считают ступени (`ladder_steps`), «цена суток не ниже пола суток» допускает сутки со ступенями; при расхождении витрины ступень выше и цены на витрине; удержание пола у ступени — сама ступень; время запроса — часы исполнения |
| ClickHouse | `schemas/clickhouse/095_step73.sql`: `ladder_from_minor` в решении, `floor_respected` пропускает ступень; экспортёр несёт столбец |
| 0181 | проверка схемы v48 — две новые функции пути решения в списке разрешённого |
| kill-test | `--step-pct N`: первая ступень и «about N more steps» в разделе «Products priced below your margin floor», пункт «Step limit» в допущениях |

## Проверки

- движок (`engine.test.ts`, 16 из 16): лестница 10,00 → 11,00 → 12,10 → 13,31 → 14,64 → 15,24 (пол) с `stepsLeft` 4…1, затем
  `RAISED_TO_FLOOR`; тень глушит повтор ступени; без предела шага — сразу пол (отрицательный контроль); подъём без снимка после
  `COST_UPDATE` — правило `FLOOR_RAISE`; ступень после `FLOOR_RECHECK`; цена не ниже пола без снимка не оценивается, как прежде;
- Gate (`gate.test.ts`, 16 из 16): ступень ниже пола одобрена с `ladderFromMinor`; без предела шага, с другой причиной стратегии и
  ниже нынешней цены — `BELOW_MARGIN_FLOOR`; ступень больше предела — `STEP_LIMIT`; обычное решение ступенью не помечено;
- словари (`console-model.test.ts`, 18 из 18) — тексты ступени и повода;
- **PostgreSQL** (`floor-raise.pg.test.ts`, 4 из 4, своя база):
  - лестница через путь решения и пересчёт по расписанию: четыре ступени и подъём на пол, `ladder_from_minor` у каждого решения,
    на полу лестница кончается;
  - база отклоняет ложную ступень («a step below the current price») и обычное решение ниже пола («a plain decision below the floor»);
  - **Р-210**: новая версия себестоимости — запрос базы; пересчёт по расписанию без снимка конкурентов поднимает цену на пол с поводом
    COST_UPDATE, запрос снят; не ниже пола — без подъёма; изменение модели комиссии и новая оценка комиссии `SELLER_DECLARED` — тоже
    запросы;
  - **Р-209, весь цикл**: решение на полу по старому курсу, курс ЕЦБ меняется, диспетчер получает отказ перепроверки пола, база ставит
    запрос FLOOR_RECHECK, пересчёт поднимает цену по новому курсу, запись уходит; состояние синхронизации — записи в полёте нет,
    последняя отправленная равна новому полу, открытых записей 0, запрос снят — версия не застревает;
- после ревью ([docs/evidence/step73-review.md](step73-review.md)): ступень ниже цены на витрине после правки продавца — отказ, выше —
  проходит; сутки с лестницей закрываются (строка 11,00 € при поле 15,24 € с четырьмя ступенями), строка ниже пола без ступеней — отказ;
  запрос снимается только суждением (правило на всех исходах), единица под недоверием каналу переоценку не получает, пока оно действует;
  `floor-raise.pg.test.ts` — 6 из 6; Omnibus, граница суток, перепроверка записи, реестры параметров, ядро — 62 из 62 вместе с ним;
  выгрузка ступени в ClickHouse — тестом выгрузки на настоящем ClickHouse (локально его нет — полный прогон CI);
- смоук схемы: три новые проверки CHECK ступени, ступень в смоуке удержаний пола;
- мутации строк шага — 9 из 9 своей проверкой ([docs/evidence/step73-mutation.md](step73-mutation.md));
- kill-test (`killtest.pg.test.ts`, 11 из 11): с `--step-pct 5` товар с полом +6,7 % получает первую ступень +5 % и «about 1 more step».

## Чего нет

- Запрос не ставят: новый курс ЕЦБ без записи в полёте, смена НДС товара, `min_price` и гардрейла минимальной маржи — вопрос владельцу
  OQ-254; скорость лестницы — одна ступень на оценку, а не по времени — OQ-255.
- Ручная поправка закрытых суток человеком (`price_daily_correction`) ступеней не знает: её «цена не ниже пола» осталась прежней.
- В тени лестница стоит на первой ступени — цена на витрине не меняется; «осталось ~N шагов» — счёт по нынешней цене и пределу.
