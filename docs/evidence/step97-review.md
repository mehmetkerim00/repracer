# Шаг 97: независимое ревью и чистый замер (поручения владельца по шагу 97)

Ревью вёл свежий агент, не видевший кода шага: коммит `e705017` против `125bc89` (main до шага), две одноразовые базы — схема шага 97 из
шаблона и чистая база с миграциями 0001–0186 для сравнения «до/после», `pg_depend`, `pg_dump -s`, счёт объектов на каждую секцию, 28 входов
проверки формы, свой сценарий движка. Базы удалены. Исправления — коммит шага 97.1 на той же ветке; по правилу скорости исправлены
существенные находки, мелкие — в [deferred.md](../deferred.md), строки «97 (ревью …)».

## Найдено при правке (сверх ревью)

**Таймер подъёма почти инертен.** Снимок для стратегии устаревает через 15 минут (`STRATEGY_STALENESS_SECONDS`), а таймер подходит к единице,
когда решения не было 15 минут, — к этому моменту снимок обычно уже устарел, и движок не оценивает. Полезен таймер только на самой границе
(I3 шага 97 сделал ступень на t+20 ровно на ней). Подъём на деле идёт по снимкам: Kaufland — ярусный опрос и уведомления, Walmart — опрос.
Это расхождение одобренного механизма (решение владельца 4б: «плановый пересчёт включает “Win the Buy Box” с подъёмом») с правилом свежести —
вопрос владельцу: разрешить ступени подъёма более старый снимок при нашем Buy Box (например, два периода) или оставить подъём на снимках.
До решения таймер берёт единицу только со свежим снимком — без пустой работы.

## Чистый замер

Машина не была спокойной: чужое приложение (VPN Happ, процесс Tunnel) держало ~165 % CPU во всех прогонах; оба прогона — подряд, загрузка
записывалась каждые 5 с (средняя 5,8 и 5,4 — одинаковые условия).

| | main (125bc89) | шаг 97 (e705017) | шаг 97.1 |
|---|---|---|---|
| подготовка демо | 102 с | 143 с (+40 %) | **110 с (+8 %)** |
| неделя США | 53,7 с | 85,1 с (+58 %) | **59,9 с (+12 %)** |
| лёгкие продавцы (без walmart.com) | 27,0 с | 36,7 с (+36 %) | **30,1 с (+11 %)** |

Средняя загрузка в прогоне шага 97.1 — 5,3 при Happ ~150 % (в прогонах main и шага 97 — 5,8 и 5,4).

**Профиль** (обёртка `pg.Client.query` в процессе стенда, время по тексту запроса; на сами замеры не повлияла — 106 и 144 с): запросов +5 %,
их суммарное время +48 % (82,2 → 121,5 с); +34,9 с из +39 — один запрос, контекст единицы на снимке: 14,5 → 22,7 мс на вызов. Сравнение
текстов main и шага 97 на одной базе и одной единице: **исполнение < 1 мс у обоих, планирование 10,4 → 19,8 мс**. Добавила колонка `creep`
(состояние подъёма — три коррелированных подзапроса с `jsonb_array_elements`) в общем списке колонок единицы: планировщик разбирает её на
каждом вызове, даже где `CASE` её не исполнит; без неё — 12,8 мс, как у main. В CI с JIT (образ `postgres:16` с LLVM; локальная сборка без
него — `pg_jit_available() = false`) то же раздутое выражение компилируется на каждое чтение каталога: тест равенства экранов шёл 968 с против
53 с у main, чтение каталога без статистики — 3,6 с при пределе 3 — это и есть отмена `fast` по пределу 40 минут.

**Сделано (шаг 97.1):**
1. Состояние подъёма вынесено из общего списка колонок единицы: запрос контекста — 12,8 мс против 13,6 у main (планирование 10,7 против 10,6).
2. Второй профиль показал, что вынесенный запрос с теми же тремя подзапросами стоит ~11 мс на каждую оценку единицы «Win the Buy Box» (1021 вызов,
   +11,3 с). Теперь это один простой проход по одобренным решениям за сутки (`CREEP_SQL`), последнее каждого вида выбирается в коде, и только у
   стратегии с включённым подъёмом.
3. Часовой таймер подъёма walmart.com в прожатой неделе демо убран: аккаунт в тени, а таймер тень не берёт (в1) — выборка планового пересчёта
   там была чистой тратой (+5,9 с). **Предложение на будущее (не сделано):** у main запрос контекста и так тратит
~10 мс на планирование при < 1 мс исполнения — подготовленный запрос сократил бы оба; и `jit = off` для ролей приложения — JIT в коротких
запросах пути решения только мешает. Оба — отдельным решением с замером, у обоих есть риски (общий план после пяти исполнений уже ломал
права в PL/pgSQL, шаг 35).
