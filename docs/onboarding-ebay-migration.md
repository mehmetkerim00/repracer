# Онбординг eBay: предполётная проверка и миграция листингов

Статус: сценарий v0.1 · 2026-09-14 · основан на решении [Р-2](decisions.md).

## 0. Принципы

1. **Миграция необратима.** После `bulkMigrateListing` Trading API Revise/Relist/Verify для листинга не работают,
   а продавец **навсегда** теряет управление настройками Best Offer, требованиями к покупателям,
   благотворительностью и шаблоном оформления [Р-2].
2. **Автомиграция запрещена.** В системе нет пути, который мигрирует листинг без согласия человека (INV-12).
3. **Согласие — на конкретный листинг и конкретный результат проверки**, а не «на аккаунт вообще».
4. **Проверка устаревает.** Непосредственно перед миграцией листинг проверяется заново; изменился — согласие недействительно.
5. **Сомнение — не в пользу миграции.** Непроверяемое условие = листинг не предлагается к миграции.
6. **Миграция ≠ включение репрайсинга.** Синхронизация цены и остатка включается отдельно после миграции.

Сущности: `SyncJob(EBAY_MIGRATION_PREFLIGHT)`, `ListingMigrationCheck`, `MigrationConsent`,
`SyncJob(EBAY_LISTING_MIGRATION)` — см. [domain-model.md §3.30–3.31](domain-model.md).

---

## 1. Когда запускается

- После подключения `ChannelAccount` eBay (`EBAY_DE`) — автоматически запускается **только проверка** (read-only).
- Повторно — по кнопке «Перепроверить» или по расписанию для листингов со статусом `FIXABLE`/`UNKNOWN`.
- Проверка не меняет ничего на eBay и не расходует бюджет правок листинга (проверить, что чтения не считаются правками).

---

## 2. Шаг 1 — инвентаризация (read-only)

1. Получить все активные листинги продавца на `EBAY_DE` (операции Trading API для чтения — проверить выбор и лимиты
   постраничного чтения).
2. Для каждого листинга — детальные атрибуты, нужные проверкам (формат, Best Offer, требования к покупателям,
   благотворительность, шаблон оформления, SKU листинга и вариаций, бизнес-политики, out-of-stock control).
3. Определить, какие листинги уже под Inventory API (способ определения — проверить).
4. Чтения планируются с учётом дневных лимитов приложения, общих для всех тенантов: у крупного продавца проверка
   может занять больше одного дня. Прогресс виден продавцу.

---

## 3. Шаг 2 — проверки

Серьёзность: **BLOCKER** — мигрировать нельзя; **LOSS** — можно, но продавец теряет возможность навсегда;
**WARNING** — можно, есть риск; **INFO** — к сведению.

| Код | Проверка | Как определяем | Серьёзность | Основание |
|---|---|---|---|---|
| C01 | Формат — аукцион | Формат листинга | BLOCKER → `INELIGIBLE` | Р-2 |
| C02 | Уже под Inventory API | Способ — проверить | → `ALREADY_MANAGED` | Р-2 |
| C03 | Включён Best Offer | Атрибуты листинга | **LOSS** | Р-2 |
| C04 | Заданы требования к покупателям | Атрибуты листинга / аккаунта (уровень — проверить) | **LOSS** | Р-2 |
| C05 | Благотворительность | Атрибуты листинга | **LOSS** | Р-2 |
| C06 | Шаблон оформления | Атрибуты листинга (как отличить шаблон от обычного описания — проверить) | **LOSS** | Р-2 |
| C07 | Нет SKU у листинга или вариаций, дубли SKU | Атрибуты листинга | BLOCKER → `FIXABLE` (требование — проверить) | проверить |
| C08 | Не используются бизнес-политики (оплата, доставка, возврат) | Атрибуты листинга | BLOCKER → `FIXABLE` (проверить) | проверить |
| C09 | Прочие условия `bulkMigrateListing` (категория, местоположение товара, статус листинга) | По полному списку требований | BLOCKER → `FIXABLE` / `INELIGIBLE` (проверить) | проверить |
| C10 | Листинг правит другой инструмент через Trading API (ERP, листер, другой репрайсер) | **Автоматически не определяется.** Обязательная декларация продавца | **WARNING (критично):** после миграции эти инструменты перестанут изменять листинг | Р-2 |
| C11 | Out-of-stock control выключен | Настройка аккаунта (проверить) | WARNING → рекомендуем включить до миграции: при `quantity = 0` листинг может завершиться (проверить) | проверить |
| C12 | Мульти-вариационный листинг | Наличие вариаций | INFO: бюджет 250 правок/день общий на все вариации (проверить) | Р-2 |
| C13 | Высокая частота текущих правок | Если доступно из истории (проверить) | WARNING: бюджет 250/день будет делиться с этими правками | Р-2 |
| C14 | Листинг участвует в акции/распродаже | Атрибуты / Marketing API (проверить) | WARNING (влияние на запись цены — проверить) | проверить |

Если проверку выполнить не удалось (ошибка API, нет данных) — результат `UNKNOWN`, листинг не предлагается.

## 4. Шаг 3 — вердикт по листингу

| Вердикт | Условие | Предлагаем миграцию |
|---|---|---|
| `ALREADY_MANAGED` | C02 | Не требуется, можно подключать сразу |
| `READY` | Нет BLOCKER и LOSS | Да |
| `READY_WITH_LOSSES` | Нет BLOCKER, есть LOSS | Да, с поимённым перечнем потерь |
| `FIXABLE` | Есть BLOCKER, который продавец может устранить на eBay | Нет; показываем, что исправить |
| `INELIGIBLE` | Аукцион или неустранимое условие | Нет, никогда |
| `UNKNOWN` | Проверка не завершена | Нет, до перепроверки |

WARNING не меняет вердикт, но обязательно показывается и подтверждается в согласии.

## 5. Шаг 4 — что показываем продавцу

### 5.1 Сводка
- Сколько листингов в каждом вердикте; сколько товаров (Product) затронуто.
- Сколько листингов останется **вне управления** и что это значит для остатка (5.4).
- Оценка времени миграции: пакеты по 1–5 листингов за вызов [Р-2] с учётом лимитов приложения.

### 5.2 Блок необратимости (показывается перед любым выбором, не сворачивается)

> Миграция листинга в Inventory API **необратима**. Отменить её нельзя ни нам, ни вам, ни поддержке eBay (проверить формулировку относительно поддержки eBay).
>
> После миграции:
> - перестанут работать изменение, повторное выставление и проверка листинга через Trading API (Revise / Relist / Verify) — **в том числе в других программах**, которые вы используете;
> - вы **навсегда** потеряете возможность управлять: настройками Best Offer, требованиями к покупателям, благотворительностью, шаблоном оформления.
>
> Можно ли будет править эти листинги в Seller Hub — (проверить; текст зависит от результата).

### 5.3 По каждому листингу
- Название, ItemID, SKU, формат, вердикт.
- Для `READY_WITH_LOSSES`: **конкретные** потери именно этого листинга (например, «Best Offer включён: вы потеряете управление его настройками»).
- WARNING с объяснением последствий.
- Для `FIXABLE`: что именно исправить на eBay и кнопка «Перепроверить».
- Для `INELIGIBLE`: причина и последствия (5.4).

### 5.4 Что останется вне управления
- Цена и остаток таких листингов **не синхронизируются** системой.
- Заказы из них всё равно импортируются и уменьшают доступный остаток общего пула (`Reservation`), но **опубликованное количество на самих этих листингах мы не меняем** — риск перепродажи, если товар общий с управляемыми офферами. Товары с таким риском перечисляются явно.

### 5.5 Декларация об иных инструментах (C10)
Обязательный вопрос: «Изменяют ли эти листинги другие программы или сервисы?» — `Нет` / `Да, перечислите`.
При `Да` — повторное предупреждение, что после миграции они перестанут работать с этими листингами.

## 6. Шаг 5 — согласие

| Требование | Как выполняется |
|---|---|
| Кто | Человек с ролью `OWNER` в этом тенанте, прошедший MFA не ранее чем за N минут (N — OQ-56) |
| Не может дать | Система, сотрудник поддержки, API-токен, роль ниже `OWNER` |
| На что | Явно выбранные листинги с вердиктом `READY` / `READY_WITH_LOSSES`; «выбрать все» допустимо только внутри одного вердикта и с отдельным подтверждением |
| Информированность | Для каждого `READY_WITH_LOSSES` — отметка «понимаю потери» по перечню этого листинга |
| Подтверждение | Ввод фразы подтверждения (текст — продуктовое решение) |
| Что фиксируем | `MigrationConsent`: пользователь, membership, время MFA, листинги со ссылкой на `check_id` и `listing_snapshot_hash`, принятые потери, версия и хэш показанного текста, декларация C10, фраза, время, срок действия |
| Срок действия | Ограничен (значение — OQ-56) |
| Отзыв | До начала миграции листинга — да; после — ничего не откатывает |
| Аудит | `AuditEvent(migration.consent_given)` |

## 7. Шаг 6 — выполнение

1. `SyncJob(EBAY_LISTING_MIGRATION)` берёт только листинги из действующего согласия.
2. **Повторная проверка** каждого листинга (C01–C09, C11) непосредственно перед вызовом:
   - хэш и находки совпадают — продолжаем;
   - изменились или появились новые LOSS/BLOCKER — листинг пропускается со статусом `CONSENT_INVALIDATED`, продавец получает запрос на новое согласие.
3. **Пилот:** первый листинг тенанта мигрируется отдельно; после него — readback (оффер и товар инвентаря
   видны в Inventory API, ItemID сохранился — проверить) и только затем остальные.
4. Пакеты по 1–5 листингов за вызов [Р-2], в пределах лимитов приложения и справедливой квоты тенанта.
5. Результат по листингу: `MIGRATED` / `FAILED(причина)` / `OUTCOME_UNKNOWN`.
   - `OUTCOME_UNKNOWN` (таймаут, обрыв) — **не повторять вслепую**; сначала readback, чтобы понять, произошла ли миграция (поведение повторного вызова на уже мигрированном листинге — проверить).
   - `FAILED` — повтор только без изменения параметров и только если причина временная.
6. После `MIGRATED`:
   - обновить `OfferMapping.identity` (`inventory_sku`, `offer_id`, `inventory_api_managed = true`), вывести `WriteScope`;
   - получить **базовое наблюдение** цены и остатка (`ChannelObservation`) до первой записи;
   - `pricing_enabled` / `stock_sync_enabled` остаются выключенными до явного включения пользователем.
7. `AuditEvent(migration.listing_migrated)` по каждому листингу.

## 8. Шаг 7 — непригодные и немигрированные листинги

| Категория | Что делаем | Чего не делаем |
|---|---|---|
| `INELIGIBLE` (аукционы и пр.) | Статус `OfferMapping = INELIGIBLE`; заказы импортируются в `Reservation`; предупреждение о риске перепродажи по общим товарам | Не пишем цену и остаток; не предлагаем миграцию |
| `FIXABLE` | Показываем причину и инструкцию; перепроверка по кнопке или расписанию | Не исправляем листинг за продавца |
| `UNKNOWN` | Автоматическая перепроверка с backoff; уведомление, если не удаётся | Не предлагаем миграцию |
| Продавец отказался (не дал согласие на `READY*`) | Статус `MIGRATION_REQUIRED`, листинг вне управления; можно вернуться позже | Не напоминаем навязчиво; не мигрируем |
| `CONSENT_INVALIDATED` | Новая проверка и новый запрос согласия | Не мигрируем по старому согласию |

Пересоздание листинга «с нуля» через Inventory API (с потерей истории продаж) — решение продавца вне системы;
мы только описываем такую возможность. Создание листингов вне скоупа.

## 9. Откат

**Отката нет.** Обратимо только одно — не мигрировать. Это формулируется в интерфейсе, в договоре и в тексте согласия.

## 11. Требует проверки

- Полный список условий `bulkMigrateListing` (SKU, бизнес-политики, категории, местоположение).
- Как определить, что листинг уже под Inventory API.
- Сохраняется ли ItemID после миграции.
- Можно ли редактировать мигрированный листинг в Seller Hub и что именно.
- Поведение повторного вызова миграции для уже мигрированного листинга.
- Считаются ли миграция и чтения в лимит 250 правок/день; часовой пояс «календарного дня».
- Out-of-stock control: где настраивается и что происходит при `quantity = 0`.
- Уровень требований к покупателям (листинг или аккаунт) и видимость шаблона оформления через API.
- Лимиты операций чтения Trading API для инвентаризации крупных продавцов.
