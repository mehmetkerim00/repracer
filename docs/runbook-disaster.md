# Runbook: потеря базы — восстановление из копии

Для того, кто поднимает repracer после потери сервера или базы. Команды — точные; скрипт восстановления и все его шаги
проверяет учение в сборке ([packages/pricing-store-pg/test/disaster-recovery.pg.test.ts](../packages/pricing-store-pg/test/disaster-recovery.pg.test.ts)):
копия → гибель базы → восстановление → консоль отвечает.

## Что теряется — сказать сразу

- **Всё, что случилось после последней копии.** Копия снимается раз в сутки (`REPRACER_BACKUP_EVERY_SECONDS=86400`). Худший случай —
  сутки работы плюс время до восстановления. **Восстановления на момент времени нет**: журналы WAL не архивируются, база
  возвращается ровно к моменту копии.
- **История наших цен за потерянный промежуток.** Цены, применённые в каналах после копии, в нашем журнале не останутся. Доказательство
  Omnibus за эти сутки неполное, и экран соответствия покажет это сам: история известна не за все дни. Цены в каналах остаются такими,
  какими их оставили; после подъёма путь решения прочитает канал заново и продолжит.
- **Удаления аккаунтов eBay после копии откатываются** (принятый риск 36). Скрипт восстановления находит их в месячных архивах журналов
  и печатает. Повторить их — вручную, по [deploy/production/README.md §4](../deploy/production/README.md) «eBay: восстановление из копии».
  Горячие сутки журналов с сервера не выносятся: если сервер погиб, удаления за окно «копия → авария», ещё не попавшие в месячный архив,
  найти нечем.
- **Что в копии есть:** база целиком — каталог, решения, записи, резервации, аудит, роли кластера без паролей.
- **Чего в копии нет:**
  - секретов — строк подключения, кольца ключей токенов каналов, открытого ключа копий;
  - закрытого ключа копий;
  - ClickHouse — это слой хостинга.

## Где что лежит

| Что | Где | Кто держит |
|---|---|---|
| Копии (`repracer-<время>.dump.gpg`, `.globals.sql.gpg`, `.sha256`) | на сервере — `/srv/repracer/backups` (`REPRACER_BACKUP_DIR`), не старше 7 суток; вне сервера — то, что забрала вторая машина (README §3в) | сервер и внешнее хранилище |
| Месячные архивы журналов (`<проект>/<ГГГГ-ММ>.log.gz` + `.sha256`) | `/srv/repracer/archive/platform=logs` (`REPRACER_ARCHIVE_DIR`) и вне сервера | сервер и внешнее хранилище |
| Закрытый ключ копий | только у владельца — машина владельца и сейф (README §3в: пара создаётся на машине владельца) | владелец |
| Секреты: строки подключения ролей, `channel_keyring.json`, `backup_public_key.asc`, ключи каналов | `/srv/repracer/secrets` (`REPRACER_SECRETS_DIR`); копия — в хранилище секретов владельца | владелец |

**Без кольца ключей (`channel_keyring.json`) токены каналов в восстановленной базе не расшифровываются.** Каналы тогда придётся
подключить заново кнопкой «Connect» (Р-175).

## Порядок

### 0. Сервер и база

- PostgreSQL той же главной версии, что в копии (16).
- Ни одной базы и роли проекта: восстановление ставит их само.
- Каталоги `/srv/repracer/{secrets,backups,archive}`, секреты — из хранилища владельца.
- **Нужен суперпользователь кластера.** Через него идут:
  - копия ролей — она ставит атрибуты ролей;
  - восстановление без `--no-owner` — объекты отдаются ролям схемы;
  - `ALTER ROLE … PASSWORD`;
  - `SET ROLE svc_scheduler`.

  На управляемом хостинге без настоящего суперпользователя строки вроде `ALTER ROLE postgres WITH SUPERUSER` откажут, и скрипт
  остановится на шаге ролей. Что хостинг допускает, проверяется до пилота на выбранном хостинге (OQ-246).
- Параметры строки подключения (`?sslmode=require`) скрипт сохраняет: `REPRACER_RESTORE_ADMIN_URL=postgres://…/postgres?sslmode=require`.

### 1. Файлы копии на сервер

Последняя копия — три файла с одним временем:

```bash
ls -1 /srv/repracer/backups | sort | tail -3
# repracer-20261001T030000Z.dump.gpg  repracer-20261001T030000Z.globals.sql.gpg  repracer-20261001T030000Z.sha256
```

Месячные архивы журналов — в `/srv/repracer/archive/platform=logs` как есть.

### 2. Восстановление — одна команда

Нужен закрытый ключ владельца в `GNUPGHOME`. Лучше запускать скрипт с машины владельца, указав сетевой адрес базы. Если ключ всё же
привезён на сервер — удалить его сразу после восстановления (`gpg --delete-secret-keys`, затем каталог `GNUPGHOME`): закрытый ключ на
сервере обесценивает шифрование всех копий.

```bash
GNUPGHOME=~/.gnupg-repracer \
REPRACER_RESTORE_ADMIN_URL=postgres://postgres@127.0.0.1:5432/postgres \
REPRACER_RESTORE_SECRETS_DIR=/srv/repracer/secrets \
REPRACER_RESTORE_LOGS_DIR=/srv/repracer/archive/platform=logs \
deploy/production/restore.sh /srv/repracer/backups repracer-20261001T030000Z
```

Что делает [restore.sh](../deploy/production/restore.sh), по шагам:
1. сверяет SHA-256 копии с файлом сумм;
2. расшифровывает во временный каталог (права 700, удаляется при выходе);
3. ставит роли кластера;
4. восстанавливает базу через `pg_restore --create`: с именем, владельцем и **настройками базы** — регион `repracer.region`, без него
   база не заводит ни одного тенанта;
5. ставит пароли ролей из строк подключения в секретах;
6. создаёт секции на ближайшие сутки;
7. проверяет регион;
8. сверяет суммы и целостность архивов журналов и печатает удаления eBay для повтора.

Успех — последняя строка `RESTORE_DONE`:

```json
{"event":"RESTORE_DONE","database":"repracer_eu","region":"EU","rolesWithPassword":14,"logArchives":12,"ebayDeletionsToRedo":0,"stepsMs":{…}}
```

Любой отказ — строка `RESTORE_FAILED` с шагом и причиной (или строкой скрипта), код выхода 1.

`"warning"` в `RESTORE_DONE` говорит, что пароль не поставлен ни одной роли: копия ролей паролей не несёт, их источник — строки
подключения в секретах.

**Повторный запуск после частичного отказа.** Если шаг `restore` или следующий упал, база уже создана, и `pg_restore --create` второй раз
откажет («already exists»). Удалить недовосстановленную базу и запустить скрипт снова:

```bash
psql "$REPRACER_RESTORE_ADMIN_URL" -c 'DROP DATABASE repracer_eu WITH (FORCE)'
```

**Не использовать `scripts/db/prepare.sh`:** он удаляет базу и гоняет смоук-проверки. **Не восстанавливать через `createdb` +
`pg_restore` без `--create`:** так теряется регион базы (этой ошибкой страдал README до шага 65).

### 3. Удаления eBay — повторить

Если `ebayDeletionsToRedo` больше нуля: строки `EBAY_DELETION_APPLIED` скрипт напечатал в stderr. Для каждого `accountIds` —
действия README §4.

### 4. Процессы

```bash
docker compose -f deploy/production/compose.yaml --env-file deploy/production/production.env up -d
# планировщик, путь решения и приёмник — своими профилями (deploy/scheduler, deploy/worker, deploy/notification-receiver)
curl -sf http://127.0.0.1:9467/healthz        # консоль
```

### 5. Проверка после подъёма

- **Консоль:** вход владельца, список товаров, экран тени.
- **Панель оператора:** работы планировщика без просрочки. Первый круг — чтение заказов, обнаружение, сверка — догоняет промежуток
  с момента копии.
- **Каналы:** экран подключений. Если кольца ключей нет — «Connect again».

## Сколько это длится

Время считается от «есть файлы копии» до «консоль отвечает». Учение ниже — та же последовательность.

| Где | База (копия) | Скрипт восстановления | Консоль до `/healthz` | Итого |
|---|---|---|---|---|
| Учение в сборке, малая база, машина разработчика | мир стенда | — | — | 2,4 с |
| Машина разработчика, каталог 50 000 предложений | 1027 МБ (копия 73 МБ) | 28,4 с, из них `pg_restore` 27,6 с | 0,4 с | **29,0 с** |

Учение в сборке печатает строку `recoveryDrill` с разбивкой по шагам (`stepsMs`); число CI — в журнале задания.

**Оговорка про gpg.** На машине разработчика нет GnuPG (macOS 13, шаг 54). Поэтому локальные числа сняты с заменой gpg, которая копирует
байты, не расшифровывая. Настоящая расшифровка копии в 73 МБ добавит секунды. Учение с настоящим gpg идёт только в CI, на малой базе.

Копия той же базы 50 000 снималась 30,4 с (`backup-loop.sh`, одна итерация).

Время восстановления растёт с размером базы: его почти целиком занимает `pg_restore`. Подъём процессов и первый круг работ сюда не
входят. Догон каналов после подъёма — это первые круги работ: чтение заказов от позиции копии, обнаружение и сверка.
