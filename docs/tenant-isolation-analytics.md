# Изоляция тенантов в ClickHouse, архиве и брокере

Статус: 2026-09-14 · шаг 4 · решение [Р-23]. Для PostgreSQL — [ADR-0003](adr/0003-tenant-isolation.md).

## 1. Принципы

1. **Доступ к данным тенанта вне PostgreSQL — только через слой, который сам подставляет `tenant_id`**
   из аутентифицированного контекста. Ни люди, ни тенанты, ни BI-инструменты не подключаются к ClickHouse или архиву напрямую.
2. **Никаких общих выгрузок.** Экспорт для клиента — только его данные, только через шлюз. Выгрузок «по всем тенантам» нет.
3. **Внутренние конвейеры** (приёмник брокера, экспортёр партиций PostgreSQL) пишут данные многих тенантов,
   но **не читают** их и не выдают наружу.
4. **Данные каналов** живут не дольше 18 месяцев **в любом слое**. В архив попадают только данные тенанта (наши цены и записи).
5. **AUP и Р-10:** никаких межтенантных агрегатов, моделей и автоподбора параметров на данных SP-API — ни в ClickHouse, ни на архиве.

## 2. ClickHouse

### 2.1 Роли

| Роль | Кто использует | Права | Видимость строк |
|---|---|---|---|
| `repracer_ingest` | Потребитель брокера, экспортёр партиций | `INSERT` | Не читает |
| `repracer_tenant_reader` | **Шлюз аналитики** (симулятор, бэктест, отчёты) | `SELECT`; без DDL, временных таблиц и источников (S3, URL, FILE, REMOTE) | Только строки `tenant_id = SQL_tenant_id` |
| `repracer_retention` | Задание закрытия тенанта | `SELECT`, `ALTER DELETE` | Все строки |
| `repracer_analytics_admin` | Миграции схемы | DDL | Бизнес-данные не читает |

DDL: [schemas/clickhouse/](../schemas/clickhouse/).

### 2.2 Контракт шлюза аналитики

| Требование | Как |
|---|---|
| Тенант запроса | Берётся из сессии пользователя (тот же контекст, что `app.tenant_id` в PostgreSQL) и передаётся как настройка `SQL_tenant_id` **каждого** запроса |
| Запросы | Только параметризованные шаблоны шлюза; сырой SQL от пользователя не принимается |
| Политика строк | `tenant_id = toUUID(getSetting('SQL_tenant_id'))` на каждой таблице. Настройка пуста или не UUID — ошибка запроса (fail-closed) |
| Второй рубеж | Шаблоны шлюза всё равно содержат `WHERE tenant_id = {tenant}`; ключ сортировки начинается с `tenant_id` |
| Ограничения | `readonly = 2`, `max_execution_time`, `max_result_rows`; результат возвращается шлюзу, не в файл или хранилище |
| Бэктест и симулятор | Одно задание — один тенант. Задание, которому нужны данные нескольких тенантов, не существует по построению |
| Р-10 | Бэктест оценивает параметры, заданные человеком. Перебор параметров по данным SP-API запрещён |

### 2.3 Запись

- Приёмник проверяет, что `tenant_id` события совпадает с владельцем `write_scope_id` или `channel_account_id` в PostgreSQL
  (кэш резолва). Несовпадение — событие в карантин, алерт.
- CHECK-ограничения таблиц отвергают платформенного тенанта и некорректные классы данных.

### 2.4 Удаление тенанта

1. `DELETE FROM repracer_analytics.<table> WHERE tenant_id = :tenant` для каждой таблицы (роль `repracer_retention`).
2. Проверка: `SELECT count() FROM <table> WHERE tenant_id = :tenant` = 0 для всех таблиц (после применения мутаций).
3. `maintenance.tenant_purge_status.clickhouse_purged_at = now()` в PostgreSQL.

Независимо от закрытия все данные слоя удаляются по TTL — не позже 18 месяцев.

### 2.5 Доступ сотрудников

Только через шлюз с явным тенантом (разбор обращения) или через `repracer_retention` в процедуре закрытия. Прямой
интерактивный доступ к данным — процедура break-glass с аудитом (описание — вне этого шага).

### 2.6 Проверка

[schemas/clickhouse/099_verify.sql](../schemas/clickhouse/099_verify.sql): таблица без политики изоляции, ключ сортировки не с
`tenant_id`, таблица без TTL, лишние права у ролей чтения и записи — развёртывание неуспешно.

## 3. Архив (Parquet в объектном хранилище)

### 3.1 Раскладка

```
s3://repracer-archive-<region>/
  tenant=<tenant_id>/
    dataset=price_history/year=YYYY/month=MM/part-<uuid>.parquet
    dataset=channel_write/year=YYYY/month=MM/part-<uuid>.parquet
    _manifests/<dataset>/<partition>.json      -- число строк, контрольные суммы файлов, схема, время выгрузки
```

- **Бакет на регион** (EU, US).
- **Только данные тенанта:** сырьё `price_history` старше 90 дней, завершённые `channel_write`
  (идентификатор, единица записи, версия, значение, статус, время — без ответов канала, Р-17).
- Каждая строка Parquet содержит `tenant_id`; читатель сверяет его с префиксом.

### 3.2 Шифрование и удаление

- **Отдельный ключ шифрования на тенанта** (конвертное шифрование через KMS).
- **Удаление тенанта = удаление префикса `tenant=<id>/` + уничтожение ключа тенанта** (криптографическое стирание):
  данные нечитаемы даже в не удалённых ещё копиях.
- Версионирование бакета выключено или непостоянные версии истекают ≤ 7 дней; Object Lock не используется —
  иначе удаление префикса не удаляет данные.
- Факты фиксируются в `maintenance.tenant_purge_status` (`archive_prefix_deleted_at`, `archive_key_destroyed_at`).

### 3.3 Доступ

| Кто | Как |
|---|---|
| Экспортёр | Запись в префикс тенанта; перечисление и чтение других префиксов запрещены политикой |
| Сервис архива (восстановление, выдача клиенту, запрос регулятора) | Получает временные учётные данные, **ограниченные префиксом одного тенанта** на одну операцию (session policy) |
| Люди, BI | Нет доступа |
| Общие выгрузки | Не существуют: у бакета нет роли, которой разрешено читать все префиксы, кроме удаления при закрытии тенанта |

### 3.4 Целостность вместо append-only

Архив не имеет триггеров. Замена гарантий PostgreSQL:
- манифест партиции с числом строк и контрольными суммами пишется до подтверждения экспорта;
- `maintenance.partition_export` хранит число строк; PostgreSQL удаляет партицию, только если оно совпадает с партицией
  (миграция 0022);
- перезапись объектов запрещена политикой бакета для экспортёра (только создание новых ключей).

## 4. Брокер

Общие топики, `tenant_id` в конверте и заголовке, доступ по ACL только сервисам, retention ≤ 7 дней, отдельный кластер
на регион. Подробно — [ADR-0005](adr/0005-message-broker.md).

## 5. Что слабее, чем в PostgreSQL

| Гарантия в PostgreSQL | Вне PostgreSQL | Компенсация |
|---|---|---|
| RLS `FORCE`, нет обходных ролей | Политика строк ClickHouse зависит от настройки сессии; администратор кластера видит всё | Шлюз — единственный читатель; админ без чтения бизнес-данных; проверка 099 |
| Append-only триггерами | ClickHouse и архив изменяемы тем, у кого есть права | Нет прав на изменение у ролей записи и чтения; манифесты и контрольные суммы |
| Составные FK по тенанту | Нет FK | Сверка `tenant_id` при записи с владельцем в PostgreSQL |
| Удаление строк транзакцией | Мутации ClickHouse асинхронны; удаление в хранилище объектов — не транзакция | Проверка нуля строк; статус по слоям в `tenant_purge_status`; уничтожение ключа |
