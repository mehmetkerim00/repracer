# migrations/

DDL-миграции горячего слоя — PostgreSQL. Только схема и служебные функции; ни прикладного кода, ни seed-данных.
Аналитический слой — [schemas/clickhouse/](../schemas/clickhouse/). Слои — [ADR-0004](../docs/adr/0004-storage-tiering.md).

## Требования

- PostgreSQL **16+** (набор проверен на 16 во временном кластере, см. отчёты шагов 3 и 4).
- Расширения не требуются.
- Отдельная база на регион: `repracer_eu`, `repracer_us` [Р-16]. Для каждой задаётся регион:
  `ALTER DATABASE repracer_eu SET repracer.region = 'EU';` — без него тенанта создать нельзя.

## Роли

| Роль | LOGIN | Назначение |
|---|---|---|
| `repracer_owner` | нет | Владелец объектов; DDL, создание и удаление партиций |
| `repracer_app` | нет | Рантайм приложения; видит только строки текущего тенанта |
| `repracer_resolver` | нет | Функции резолва тенанта для входящих событий, ключей Inbound API и входа |
| `repracer_retention` | нет | Удаление по сроку, закрытие тенанта, истечение резерваций; единственная роль с DELETE в append-only таблицах |
| `repracer_exporter` | нет | Чтение транзитных партиций всех тенантов для выгрузки в ClickHouse, архив и брокер; отметки в `maintenance.partition_export` |
| `repracer_dispatcher` | нет | Обход ждущих записей всех тенантов: только идентификаторы, статусы и сроки (`maintenance.due_write_scopes`), без сумм [Р-64] |
| `repracer_relay` | нет | Ретранслятор outbox → брокер: чтение `outbox_event` всех тенантов и свой водяной знак, без бизнес-таблиц [Р-34] |
| `repracer_fx_loader` | нет | Загрузка дневных курсов ЕЦБ в `platform.fx_rate`; курс дня неизменяем [Р-61] |
| мигратор (создаёт ops) | да | Член всех ролей; запускает миграции |

`BYPASSRLS` не используется ни одной ролью.

## Контекст тенанта

```sql
SET LOCAL app.tenant_id = '<uuid>';
SET LOCAL app.user_id   = '<uuid>';   -- если действие пользовательское
```

Без `app.tenant_id` политики не пропускают ни одной строки. Транзакции, меняющие режим цены и `min_price`, — READ COMMITTED
или SERIALIZABLE (см. `0006`).

Миграции шага 4 (0015–0023) предполагают **отсутствие production-данных**: переносимые таблицы проверяются на пустоту,
и миграция падает, если в них есть строки. До первого production-развёртывания набор можно схлопнуть.
`0016` выполняется несколькими транзакциями (удаление таблиц с сотнями партиций); её шаги идемпотентны.

## Правила для новых миграций

1. Каждая таблица: `tenant_id uuid NOT NULL`, `security.register_table(...)`, строка в `maintenance.retention_policy`,
   `security.grant_retention(...)`; для транзитных таблиц — `security.grant_export(...)`.
2. Ссылки между тенантными таблицами — составные FK `(tenant_id, …_id)`.
3. Нет FK из `tenant_data` в `channel_data`, `audit`, `legal`.
4. Партиционированная таблица ⇔ политика `DROP_PARTITION`. Данные тенанта удаляются по времени только с `requires_export`.
5. Таблицы аналитического слоя (`channel_observation`, `competitor_snapshot`, `channel_write_response`, `fee_actual`)
   в PostgreSQL не возвращаются — проверка схемы (`0023`, `0029`, `0031`, `0033`, `0035`, `0039`, `0041`, `0043`, `0047`, `0050`, `0056`).
6. Индекс — только вместе с запросом, который его использует (комментарий над индексом).
7. Последняя миграция набора — проверка схемы; при добавлении таблиц копия проверки переносится в конец.
8. Представление — только `WITH (security_invoker = true)`: RLS применяется от имени читающего (проверка `0029`).
