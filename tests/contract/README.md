# tests/contract/

Стенд контрактных тестов адаптеров каналов. Адаптер работает против **записанных обменов с каналом из файлов**, без сети.
Тот же формат — основа будущего симулятора канала.

```sh
npm test                       # из корня репозитория или из tests/contract
npm run typecheck -w @repracer/contract-tests
```

Node ≥ 22, TypeScript исполняется через `--experimental-strip-types` (без сборки).

## Что гарантирует зелёный прогон — и чего не гарантирует

- ✅ Адаптер отправляет **ровно** ожидаемые запросы в ожидаемом порядке: метод, путь, параметры и тело совпадают точно
  (лишнее поле в теле — провал; например, `listing_price` в записи остатка).
- ✅ Каждый запрос подписан синтетическим секретом продавца и партнёра на момент виртуальных часов; секреты не попадают в URL и тело.
- ✅ Результаты порта, журнал (коды консервативных правил) и алерты соответствуют сценарию.
- ✅ Секреты, синтетические PII и токен адреса вебхука не появляются в результатах, журнале и алертах.
- ✅ Каждое консервативное правило адаптера срабатывает хотя бы в одном сценарии.
- ❌ **Не гарантирует, что Kaufland ведёт себя так же.** Все фикстуры сейчас `SYNTHETIC_FROM_DOCS`: собраны по спецификации 2.44.0
  и страницам документации. Реальные ответы появятся после регистрации технологического партнёра (OQ-75).

## Формат сценария `repracer.contract-scenario/v1`

```jsonc
{
  "format": "repracer.contract-scenario/v1",
  "id": "kaufland/dispatch/bulk-207-partial",      // kebab-case, / — группы
  "channel": "KAUFLAND",
  "apiVersion": "2.44.0",                          // версия спецификации, по которой собран сценарий
  "title": "...", "description": "...",
  "tags": ["mandatory:bulk-207-partial", "conservative:KFL_C09"],
  "provenance": { "kind": "SYNTHETIC_FROM_DOCS", "sources": ["openapi.json#POST /units/bulk"] },
  "world": { ... },        // начальное состояние: часы, тенант, аккаунт, синтетические ключи, бюджет, окна
  "steps": [ ... ],        // что делает ядро: вызовы порта, входящие уведомления, сдвиг часов
  "exchanges": [ ... ],    // что отвечает канал, в порядке ожидания
  "expect": { ... }        // ожидания по журналу, алертам, использованию обменов
}
```

### `world`

| Поле | Смысл |
|---|---|
| `clock` | Начало виртуальных часов. Время двигают только шаги `advanceClock` и паузы клиента между повторами |
| `tenantId`, `channelAccountId`, `account` | Каталог аккаунтов: вызов с другим тенантом получает `TENANT_MISMATCH` [Р-31] |
| `credentials.seller`, `credentials.partner`, `partner` | Синтетические ключи; при `partner: true` проверяются обе подписи |
| `budget` | Клиентский бюджет запросов (по умолчанию — консервативный из адаптера) |
| `client.timeoutMs`, `client.maxAttempts` | Тайм-аут транспорта (реальный, короткий) и число попыток |
| `adapter.confirmationWindowMs`, `adapter.webhookMaxAgeMs` | Окна подтверждения и приёма уведомлений |
| `pii`, `secrets` | Строки-метки: PII не должно быть нигде, секретов — в журнале и алертах |

### `steps`

| `kind` | Поля |
|---|---|
| `call` | `method` (метод порта), `args` (аргументы после контекста), `ctx` (переопределить тенант, аккаунт, срок), `repeat`, `expect` / `expectEach` / `expectThrows` |
| `inbound` | `delivery`: `method`, `url`, `headers`, `body` или `rawBody`, `claimed`; `expect` |
| `advanceClock` | `ms` |

Подстановки в аргументах, заголовках и ожиданиях:
`{"$clockIso": смещение_мс}`, `{"$clockSeconds": смещение_с}`, `{"$signWith": "seller" | "partner" | {"secretKey": "..."}}` —
подпись уведомления над методом, URL, сырым телом и `Shop-Timestamp`.

### `exchanges`

```jsonc
{ "id": "patch-3001-timeout",
  "request":  { "method": "PATCH", "path": "/v2/units/3001", "query": { "storefront": "de" }, "body": { "listing_price": 2199 } },
  "fault": "TIMEOUT" }                                     // или "response": { "status": 207, "headers": {}, "body": {...} }
```

Запрос сверяется точно. `fault`: `TIMEOUT` — канал молчит до отмены запроса клиентом (исход неизвестен), `NETWORK_ERROR` — обрыв.
По умолчанию каждый обмен должен быть использован (`expect.allExchangesUsed`).

### Ожидания и операторы

Результаты сверяются по подмножеству: проверяются только перечисленные ключи; массивы — той же длины. Операторы:
`$any`, `$absent`, `$type`, `$regex`, `$isoInstant`, `$contains`, `$unordered`, `$exact`, `$subset`.
`expect.logs` / `expect.alerts` — образец записи и `count` (без `count` — хотя бы одна); `noLogCodes`, `noAlerts`.

## Путь решения о цене (шаг 7)

Если в `world` есть раздел `pricing` (данные хранилища в памяти: единицы записи, границы, себестоимость, история, окно движений,
остановки), стенд собирает путь решения поверх того же адаптера и тех же обменов с каналом ([ADR-0008](../../docs/adr/0008-price-decision-path.md)).

| Шаг | Что делает |
|---|---|
| `pipelineInbound` | Уведомление целиком через путь: адаптер → снимок или опрос → проверка входов → стратегия → Gate → запись |
| `pipelinePoll` | Опрос конкурентов через адаптер и путь |
| `pipelineRecompute` | Пересчёт единицы без нового снимка (себестоимость, расписание) |
| `pipelineEnableRepricing` | Включение репрайсинга с проверкой обеих границ (Р-43) |
| `pricingMutation` | Изменение границы (`setBound`) или себестоимости (`setCost`) между шагами |

`expect.pipeline` — подмножество состояния хранилища после всех шагов: `scopes`, `intents`, `decisions`, `writes`,
`rejectedSnapshots`, `halts`, `haltReviews`, `divergenceCases`, `competitorState`. Хранилище в памяти повторяет инварианты БД,
важные для пути, но не заменяет их: те же сценарии прогоняются на PostgreSQL (ниже).


и обратно, поэтому ожидания одни для обоих хранилищ. Без `REPRACER_PG_URL` эти тесты пропускаются. Смоук хранения
удаляет партиции «через 19 месяцев» — после него `SELECT maintenance.ensure_partitions(now())`.

## Шаг 9: часы стенда, две валюты, два налоговых режима

**Часы стенда (OQ-95).** Перед прогоном `rebaseScenario` сдвигает все моменты сценария (ISO со `Z` или смещением) на разницу
между часами фикстуры и текущим моментом, даты без времени — на целое число дней; `provenance` не сдвигается. Сценарий
пишется с любыми часами, а суточные партиции на реальный день уже созданы миграциями. `REPRACER_STAND_CLOCK` фиксирует часы
стенда — для воспроизведения и проверки перехода суток:

```sh
REPRACER_STAND_CLOCK=2027-03-01T10:00:00Z npm test -w @repracer/contract-tests
```

| Сценарий / поле | Что проверяет |
|---|---|
| `pipeline-tax-regimes-margin-floor.json` | Один товар, себестоимость 10.00, комиссия 15 %, мин. маржа 20 %: Kaufland DE (EUR, брутто, НДС 19 %) и Amazon US (USD, нетто, sales tax). Фиксированная цена 15.00 отклонена на обеих витринах, но полы разные — 19.15 и 15.39 [Р-57, Р-58] |
| `world.pricing.accounts` | Дополнительные аккаунты других каналов тенанта; на PostgreSQL для Amazon нужна синтетическая строка справочника из `packages/pricing-store-pg/test/setup.sql` |
| `world.pricing.scopes[].taxRegime` | Налоговый режим единицы записи; по умолчанию — `VAT_INCLUDED` |
| Ожидание `decisions[].reasonParams` | Параметры причины отказа хранятся в решении (OQ-98), например `{proposedMinor, maxMinor}` для `ABOVE_MAX_PRICE` |
| Ожидание `competitorState.currency`, `suggestedMinor` | Валюта и подсказка канала сохраняются в проекции снимка (OQ-94) |

## Шаг 10: диспетчер записей и курсы ЕЦБ

Стенд создаёт диспетчер записей [Р-64] над хранилищем сценария и тем же адаптером и передаёт его пути решения: после итога
записи единица, у которой в очереди ждёт запись, передаётся диспетчеру. На PostgreSQL обход диспетчера видит только тенант
сценария (обход базы — по всем тенантам, роль `svc_dispatcher`).

| Шаг / поле | Что делает |
|---|---|
| `pipelineDispatchDue` | Обход диспетчера по часам мира: отправить ждущие записи, повторить после временной ошибки, сверить запись с неизвестным итогом обратным чтением. Результат — отчёт по единицам (`RECONCILED`, `DISPATCHED`, `ENDED`, `WAITING`, `IDLE`) |
| `world.pricing.fxRates` | Курсы ЕЦБ сценария (`rateMicros` — курс × 10⁶, `availableFrom` — когда курс загружен). На PostgreSQL загружаются ролью `svc_fx_loader`: курсы — общий справочник платформы, повторный посев того же дня — без изменений |
| Ожидание `writes[].endReason` | Причина завершения записи без отправки (`WRITE_SUPERSEDED_BY_NEWER_VERSION` и др.) |
| Ожидание `decisions[].fx` | Курс, по которому себестоимость переведена в валюту цены [Р-61]; `null` — перевода не было |
| Метка `memory-only` | Сценарий опирается на отсутствие общих справочных данных платформы (курсов), которые в общей базе засевают другие сценарии. **На PostgreSQL этот случай не проверяется** (исправлено на шаге 15: прежняя ссылка на `packages/pricing-store-pg/test` вела к тесту другой причины — устаревшего курса, а не отсутствующего; ретроспективное ревью, B3). Отдельная база теста (`test/isolated-db.ts`) позволит прогнать его — OQ-145 |

| Сценарий | Что проверяет |
|---|---|
| `pipeline-write-queue-second-not-lost.json` | Первая запись — тайм-аут (итог неизвестен, в полёте), вторая встаёт в очередь; обход сверяет первую обратным чтением и отправляет вторую [Р-64] |
| `pipeline-write-superseded-with-reason.json` | Вторая запись из очереди вытеснена третьей с причиной и в канал не уходит; уходит последняя [Р-64] |

| `pipeline-fx-cross-channel-anchor-converted.json` | Якорь «тот же EAN»: 20.50 USD → 17.75 EUR; снимок 17.80 принят, 80.00 отклонён `CROSS_CHANNEL_MISMATCH` с курсом в параметрах [Р-63] |

## Данные в фикстурах

- Только синтетические значения: `SYN-OFFER-…`, `example.invalid`, ключи `syn-…`. Реальные данные продавцов — никогда (CLAUDE.md).
- `provenance.kind`:
  - `SYNTHETIC_FROM_DOCS` — собрано по документации, `sources` — ссылки на спецификацию и страницы;
  - `RECORDED_REDACTED` — записано рекордером и обезличено; **стенд отказывается исполнять сценарий, пока `reviewedBy` не заполнен**.
- Запись с реального тестового аккаунта (после OQ-75): `recordingFetch` пишет обмены **в каталог вне репозитория**, заголовки
  не пишутся вовсе; `redactExchanges` заменяет PII покупателя, согласованно переназначает идентификаторы и EAN в путях,
  параметрах и телах, масштабирует суммы одним коэффициентом (порядок и равенства сохраняются, суммы вида «цена + доставка»
  могут разойтись на округлении). Человек проверяет результат, заполняет `reviewedBy`, дописывает шаги и ожидания — и только
  тогда файл попадает в `fixtures/`.

## От стенда к симулятору

Сценарий разделён на **мир**, **шаги** и **поведение канала** именно для этого.

| Часть сценария | В стенде сейчас | В симуляторе |
|---|---|---|
| `world` | Начальные ключи, аккаунт, часы, бюджет | Начальное состояние модели канала: unit, `id_offer`, витрины, подписки, лимиты канала |
| `steps` | Последовательность вызовов ядра | Та же; дополнительно — генераторы нагрузки и событий |
| `exchanges` | Жёсткий список ответов по порядку (`ScriptedChannel`) | Выводятся моделью (`ChannelBehaviour`): PATCH меняет unit, bulk даёт 207 по фактическим unit, 429 — от лимитера канала. Записанные обмены служат эталоном формы ответов и калибровки |
| `fault` | Сбой в конкретном обмене | Расписание сбоев: доля тайм-аутов, задержка распространения `amount` между витринами (K-06), потеря `buy_box_changed` (debounce, best-effort) |
| `expect` | Проверка результатов конкретного прогона | Те же проверки + инварианты модели (итоговое значение unit = последняя принятая версия, пол цены соблюдён) |

`runScenario(scenario, adapter, behaviour?)` уже принимает любое `ChannelBehaviour`: симулятор подключается без изменения
формата. Открытые вопросы поддержки (K-06, K-10, K-11, K-17, K-18) становятся параметрами модели — один сценарий прогоняется
при разных ответах, и видно, какие стратегии и сроки ломаются.

## Миры стенда для интерфейса [Р-67, Р-68]

`src/console/stand.ts` (`@repracer/contract-tests/stand`) прогоняет сценарии с `world.pricing` и оставляет мир живым. Хранилище по умолчанию — в памяти, `storeFactory: pgStoreFactory(...)` — PostgreSQL.

- `view(viewer)` читает состояние только через порт `PricingStore.readConsoleState`: объяснения решений — из слепков [Р-68], отчёты прогона экранам не нужны.
- `STAND_USERS` — членства стенда (`DEFAULT_MEMBERS`: владелец, администратор, оператор, менеджер цен, наблюдатель); от роли зависят действия [OQ-125, OQ-129].
- `STAND_ACCOUNTS`, `memoryStandIdentity`, `pgStandUsers` — учётные записи входа стенда [OQ-128]; `view(viewer)` получает членство из хранилища входа, `membershipAlias` переводит членство базы в псевдоним мира.
- Пайплайн и часы остаются для остановки, возобновления и включения из интерфейса.

Экраны строит [@repracer/console-model](../../packages/console-model/), сервер — [apps/console](../../apps/console/).

- `src/console.test.ts` — все миры на памяти: экраны на немецком и английском без пустых и выдуманных значений, слепок у каждого решения, объяснимость причин, опасные изменения, действующий пол до цента, kill switch и права.
- `src/console.pg.test.ts` — те же миры на PostgreSQL: у каждого решения по данным конкурентов пять шагов (снимок, проверка входов, якоря, стратегия, Gate) не «нет данных», есть ссылка на снимок, справочник слепка найден, у NO_OP — только код причины [Р-74], и путь совпадает с памятью шаг за шагом.

Шаги сценария для остановок и включения:

- `pricingStop` (`op: stop | release`, `membershipId`, `note`) — остановка человеком и её снятие [Р-69, Р-70];
- `pipelineEnableRepricing.acknowledgeWarnings` — включение после предупреждений (шаг 12, G).

Сценарии: `pipeline-kill-switch-tenant-stop` (фиксированная цена стоит, права по ролям), `pipeline-enable-margin-without-cost` (предупреждение до включения).

`runScenario(..., hooks)` принимает `onFinish` — доступ к миру после шагов и до закрытия хранилища.

## Добавить сценарий

1. Скопировать ближайший файл из `fixtures/kaufland/`, поменять `id`, `title`, `description`, `tags`.
2. Все значения — синтетические; `provenance.sources` — конкретные места в спецификации или документации.
3. Запросы в `exchanges` — ровно такие, какие должен отправить адаптер; ответы — по схеме спецификации.
4. Если сценарий проверяет консервативное правило — тег `conservative:KFL_Cnn` и ожидание в `expect.logs`.
5. `npm test`. Затем испортить одно ожидание и убедиться, что сценарий падает.
